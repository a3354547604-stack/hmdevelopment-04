> `ws63-firmware/scripts/ws63-sdk-lock.sh`（新增，锁本体）、本文件。

## 13.1 问题：一次双向失败

那天 fw-ws63-op 与 verifier-op 各自跑了一次固件构建，两边都炸，而且两边的报错**长得完全不一样**：

| 谁 | 命令 | 报错 |
|---|---|---|
| fw-ws63-op | `… node-build.sh mock hub hubmock` | `cc1: fatal error: /sdk/src/output/ws63/acore/ws63-liteos-app/mconfig.h: No such file or directory`，外加一批 `opening dependency file …/obj.d: No such file or directory` |
| verifier-op | `… node-build.sh hub hubmock` | CMake `No SOURCES given to target: samples`（`application/samples/CMakeLists.txt:72`），`BUILD_EXIT=1` |

**两侧症状合起来才是完整证据**：一边说"我要用的中间文件没了"，另一边说"我要编的源文件没了"——
两句互相对着删。**同一命令原样重跑就过**，`git status` 干净、源码一个字没改。
所以这不是代码缺陷，是**共享输出树竞争**。

为什么会互删：

- `ws63-firmware/scripts/node-build.sh` 把自研源码临时**覆盖**进
  `$SDK_DIR/src/application/samples/custom/`（SDK 用 `add_subdirectory_if_exist(custom)`
  无条件引入这个扩展点），编完再由 `trap` 还原；
- 它每次编译前会 `rm -rf` 掉 SDK 的输出目录（`output/ws63/…`），
  因为"产物存在"要被当成"这次真的编出来了"的判据；
- 两个进程各自 `rm -rf "$STASH"; cp -a "$CUSTOM/." "$STASH/"` 再清空 `$CUSTOM` ——
  于是 A 的中间文件被 B 删、B 的源文件被 A 删。

## 13.2 为什么 `tools/build-lock.sh` 的两个锁槽挡不住

`tools/build-lock.sh` 是**数量锁**：`flock -w 3600 /tmp/hm-build.lock`（槽 1）与
`HM_BUILD_LOCK=/tmp/hm-build-2.lock`（槽 2）。它解决的是另一件事 ——
本机 WSL 只有 7.4 GB 内存，最多允许两个重构建同时跑，第 3 个排队。

它**不互斥共享输出树**：两个槽各跑一份 `node-build.sh` 完全合法，
然后就一起炸。所以数量锁之外，还需要一层"**同一棵树**"的锁。

`AGENTS.md` 已按这条结论补了对应条目（"锁槽只限并发数量、不互斥共享输出树"）。

## 13.3 这层锁怎么做的

**本体**：`ws63-firmware/scripts/ws63-sdk-lock.sh`。用法：

```bash
ws63-firmware/scripts/ws63-sdk-lock.sh [--sdk DIR] [--label TEXT] [--lock PATH] [--timeout SEC] -- 命令 [参数…]
```

四个设计选择，每条都是为了少一个坑：

1. **用 `flock(2)`，不用"建个标志目录"**：进程无论怎么死（Ctrl-C、`kill -9`、OOM），
   内核都会释放锁，不存在"残留锁要人手动删"这类事故。
   `.owner` 文件只是**给人看的记录**，不参与互斥。
2. **拿到锁后 `exec` 目标命令**，而不是把命令当子进程跑：锁的持有者就是构建进程本身，
   构建一结束（任何方式）锁立刻释放。代价是这里不再有"执行结束"的日志 —— 换来的健壮性值这个价。
   实测确认 `exec 9>>lock; flock -n 9; exec 命令` 期间另一进程拿不到锁、命令结束后立刻能拿到
   （bash 的 `exec N>` 重定向不设 close-on-exec，fd 9 跨 `exec` 存活）。
3. **按锁文件路径互斥**，默认 `/tmp/hm-ws63-sdk.lock`：与 `/tmp/hm-build.lock`、
   `/tmp/hm-build-2.lock` 是**不同文件**，所以 RK2206 / `harmony-app` / 其它仓库的构建
   **永远不会**被这层锁挡住 —— 要互斥的只是"同一棵 WS63 SDK"。
   换了 SDK 路径（`SDK_DIR=…`）想各锁各的，用 `HM_WS63_SDK_LOCK` 指定不同锁文件即可。
4. **超时不无限挂起**：默认 1800 s，超时打印锁路径 + 占用者记录 + 处置建议，
   以 **75**（`EX_TEMPFAIL`，"稍后重试"的约定码）退出 —— 这样 CI/脚本能区分
   "构建失败"（1）与"没排上队"（75）。

**接入**：`node-build.sh` 在最前面（任何 `rm -rf`/`cp` 之前）把自己**重新 exec** 进锁里：

```bash
if [ "${HM_WS63_SDK_LOCK_HELD:-}" != "1" ]; then
    export HM_WS63_SDK_LOCK_HELD=1
    exec bash "$HERE/ws63-sdk-lock.sh" --sdk "$SDK_DIR" --label "node-build.sh $*" \
        -- "$HERE/$(basename "${BASH_SOURCE[0]}")" "$@"
fi
```

为什么用 re-exec 而不是"就地加个锁"：本锁要覆盖
「暂存 `custom/` → 编译 → **还原**」**整段**，而还原走的是 `trap … EXIT`。
只有让整个脚本成为一次临界区，`Ctrl-C` 之后的还原也还在锁内（否则还原本身也会踩到别人）。
`HM_WS63_SDK_LOCK_HELD=1` 是防自己锁自己的递归护栏，由脚本自己设，正常不需要手工设。

**嵌套顺序（重要）**：**数量锁在外、SDK 锁在内**。

```bash
HM_BUILD_LOCK=/tmp/hm-build-2.lock tools/build-lock.sh \
    bash -c '… ws63-firmware/scripts/node-build.sh …'      # ← 正确：先排队拿槽，再拿 SDK 锁
```

反过来（持有 SDK 锁时再去抢 `tools/build-lock.sh` 的槽）两个进程可能各持一把互等。
`node-build.sh` 已经把 SDK 锁内建在最前面，所以**照旧调用 `node-build.sh` 就行**。

## 13.4 什么命令会等待、什么不会

| 命令 | 会等 SDK 锁吗 | 说明 |
|---|---|---|
| `ws63-firmware/scripts/node-build.sh …`（任意目标，含只编一个、含 `hub`/`hubmock`） | **会** | 锁内建在脚本最前面，整个"暂存→编译→还原"是一次临界区 |
| `tools/build-lock.sh bash -c '… node-build.sh …'` | **会**（在槽之外再等） | 正确嵌套；先拿槽再拿 SDK 锁 |
| `tools/node-compile-check.py` / `tools/hub-selftest.py` / `tools/node-json-check.py` / `tools/node-radar-cache-check.py` | 不会 | 不在 SDK 树里写任何东西（编译在容器/临时目录里做） |
| `rk2206-gateway`、`harmony-app`、`server` 的构建 | 不会 | 不同的锁文件，互不阻塞 |
| `tools/spike-build.sh` | **不会**（现状） | 见 13.6 —— 它也写同一棵 SDK 树，但不在这张卡的 inScope 内 |

一个**读侧**的注意点：`tools/node-compile-check.py` 与 `tools/spike-compile-check.py` 会把
SDK 上次构建留下的 `output/ws63/acore/ws63-liteos-app/compile_commands.json` 当"官方编译参数表"读。
它只读、不写，所以**不需要**排在这层锁后面；但如果正好有构建在重写那个文件，
它可能读到半新半旧的参数表而报出莫名其妙的错。**推荐顺序：先构建完，再跑编译自检。**

## 13.5 超时与排障

| 现象 | 含义 | 怎么办 |
|---|---|---|
| `等待中：同一棵 WS63 SDK 已被占用（锁 …，等待上限 1800s）` | 有另一个构建在跑 | 等；日志会跟着打印占用者记录 |
| 退出码 **75** + `错误：等待超过 Ns 仍未拿到锁` | 排队超时，**没有**无限挂起 | 等占用者结束后重试；想等更久用 `HM_WS63_SDK_LOCK_TIMEOUT=<秒>` |
| 退出码 **2** | 用法错（没给命令、超时值不是数字） | 看 `--help` |
| 占用者记录里 `pid=… 已不存在` | 上一次留下的**残留记录**（不是残留锁） | 什么都不用做。flock 的持有关系由内核维护，进程一死锁自动释放；`.owner` 只是记录，可以直接忽略 |
| 想确认现在有没有人在编 | `HM_WS63_SDK_LOCK_TIMEOUT=0 bash ws63-firmware/scripts/ws63-sdk-lock.sh -- true; echo $?` | `0` = 空闲，`75` = 有人占着 |

环境变量一览：

| 变量 | 默认 | 作用 |
|---|---|---|
| `HM_WS63_SDK_LOCK` | `/tmp/hm-ws63-sdk.lock` | 锁文件路径（换路径即换互斥域） |
| `HM_WS63_SDK_LOCK_TIMEOUT` | `1800` | 等待上限（秒）；`0` = 不等待，拿不到立刻 75 |
| `HM_WS63_SDK_LOCK_LOG` | 空 | 可选：把"等待/获取"记录追加到该文件（事后对时序用） |
| `HM_WS63_SDK_LOCK_HELD` | 空 | 内部护栏，由 `node-build.sh` 自设，正常不要手工设 |

> **版本标记**：本节描述的是 `tools/spike-build.sh` 在 `node-build.sh` 接入本锁**之前**的形态

`tools/spike-build.sh`（星闪连通性冒烟，t16 在维护）做的是**同一件事**：

`$SDK_DIR/.spike-stash` 之外的名字（`.spike-stash`）暂存，编译同一个 `FWPKG`。
它**没有**内建这层锁，而且**不在本卡的 inScope 内**（本卡只允许改
`ws63-firmware/scripts/` 与 `doc/13`），所以我没动它。

于是现状是：**`node-build.sh` 之间的并发已经安全；`node-build.sh` 与 `spike-build.sh` 之间还不安全。**
给它的接法是**一行**，不用改它内部逻辑：

```bash

    --sdk "$SDK_DIR" --label spike-build -- tools/spike-build.sh <目标>
```

**建议 PM 决定**：由 spike 脚本的负责人（t16）把这一层套上，或明确"两者不并发"。
在那之前，跑 spike 构建前先确认 SDK 锁是空闲的（13.5 最后一行那条命令）。

## 13.7 没做 / 已知取舍

- **没有**把锁做成"按 SDK 路径自动分域"（比如把路径哈希进锁文件名）：
  这台机器上只有一棵 WS63 SDK，一个锁文件就够；
  多棵树的情况留了 `HM_WS63_SDK_LOCK` 手动分域的口子，比自动哈希更好排查（锁文件名要能一眼看懂）。
- **没有**给 `tools/` 下的自检脚本加锁：它们不写 SDK 树，加了反而会让自检排在构建后面白等半小时。
- 占用者记录靠 `pid` 判断是否还在跑；极端情况（pid 被复用）会显示成"仍在运行"，
  但那只是记录上的措辞，**不影响锁的正确性**（锁由内核维护）。

## 13.10 同一张卡里顺手修掉的三个缺陷

这一节记的三件事都不是"加锁"本身，但都在同一条构建路径上，且都是**先被实测撞到、才被发现**的。

### 13.10.1 `custom/` 的"还原"语义本来是错的（复核 finding F-01）

复核 t3 的 finding F-01 说：构建结束后 `$SDK/src/application/samples/custom/` 仍有 22 项残留，
而 SDK 不是 git 仓、pristine 参照包不在手，所以脚本自称的"已还原"**无法被第三方独立证实**。

**先查清 `custom/` 到底是不是原厂的**（这决定了"还原"该是什么语义）：

```bash
python3 - <<'PY'
import zipfile
z = zipfile.ZipFile('/home/qinyixiang/ws63/fbb_gitee.zip')
names = z.namelist()
print('归档条目总数:', len(names))
pre = 'fbb_ws63-master/src/application/samples/'
for n in sorted(names):
    if n.startswith(pre):
        rest = n[len(pre):]
        print('  ', rest.split('/')[0] if rest else '(dir)')
print('samples/custom 条目数:', sum(pre + 'custom' in n for n in names))
PY
```

实测输出：归档 **18373** 条；`samples/` 下一级只有 `CMakeLists.txt`、`Kconfig`、`bt`、`peripheral`、
`radar`、`wifi`；**`samples/custom` 条目数 = 0**。

结论：**`custom/` 不是原厂 SDK 的一部分**，它是 `src/application/samples/CMakeLists.txt` 里
`add_subdirectory_if_exist(custom)` 留给我们的**临时扩展点**（我们和 `tools/spike-build.sh` 都往它里面丢源码）。
于是**正确的"还原"语义是"清空"，而不是"把进来时看到的东西贴回去"**——
后者才是污染被固化下来的原因：暂存里存的可能已经是上一轮别人留下的文件，
还原时又原样贴回，于是"基线"越积越脏（08:51 那次碰撞时 `custom/` 有 22 项、`.node-build-stash` 有 23 项，
mtime 全是碰撞时刻）。

**清空到什么程度**（两个约束的夹缝）：

- 空目录对 SDK 是安全的：`src/build/cmake/build_function.cmake:11-15` 的
  `macro(add_subdirectory_if_exist _path)` 条件是 `if(EXISTS ${CMAKE_CURRENT_SOURCE_DIR}/${_path}/CMakeLists.txt)`，
  没有 `CMakeLists.txt` 就整段跳过，不会报 "does not contain a CMakeLists.txt"。
- 但**目录本身不能删**：`tools/spike-build.sh`（`set -euo pipefail`）会 `cp -a "$CUSTOM/." "$STASH/"`，
  目录不存在它就直接失败。

**所以清空范围 = 保留 `custom/` 目录本身、清掉其下全部内容**，退出时残留期望 **0 项**。
`node-build.sh` 现在的行为：进入时若非空，**大声告警并列出清单（只取证，不再贴回）**；
退出时 `cleanup()` 清空、追加写 `ws63-firmware/out/custom-residue.log`，
残留非 0 就打印错误并 **`exit 1`**（构建成功也不算数）。

**第三方怎么独立核对**（不依赖我们任何一句自述）：

```bash
SDK=${SDK_DIR:-$HOME/ws63/fbb_ws63-master}
ls -A "$SDK/src/application/samples/custom" | wc -l        # 期望 0
cat ws63-firmware/out/custom-residue.log                    # 每次运行一段，residue_count=0
python3 -c "import zipfile;print(sum('samples/custom' in n for n in zipfile.ZipFile('$HOME/ws63/fbb_gitee.zip').namelist()))"   # 期望 0（证明"空"才是原厂状态）
```

前两条之外还有一层保障：**`ls -A` 与归档对照这两条判据完全不依赖我们任何自述**。
`custom-residue.log` 落在 `ws63-firmware/out/` 下、被仓库 `.gitignore` 的 `*.log` 排除（和该目录里其它构建日志一样是每次现生成的），
所以真正能当"独立核对"用的是前两条命令 —— 它们要么直接看文件系统，要么直接看原厂归档。
脚本在 stdout 上也会打印同一句结论（`custom/ 已清空到原厂状态（残留 N 项…）`），配合构建日志即可复现。

**反例实测（证明这条断言有牙）**：在 `custom/` 里布下 `custom_leftover_sentinel.c` 与
`t51-protected/`（mode 500，内含 `inner.txt`，共 25 项）后跑单目标 `m2`：

```
[node-build] 注意：custom/ 进来时非空（25 项）—— 这是历史残留，本次会先清空再装源码
[node-build] m2 角色断言通过：'EC-NODE-ROLE=M2 type=fall'×1 …
[node-build] 错误：custom/ 清空后仍有 2 项残留：t51-protected t51-protected/inner.txt
RC=1
```

注意这一条的形态：**构建本身是成功的、包也编出来了**，失败的是残留断言 —— 也就是说
"编出来了"不等于"清干净了"，两者是独立的两条判据。

### 13.10.2 sha256 判据会假报失败（`--clean` 之外的真实缺陷）

`build_one()` 原来用「编译前后 FWPKG 的 sha256 必须不同」当作"这个包确实是本次编出来的"的证据：

```bash
if [ -n "$old_hash" ] && [ "$old_hash" = "$new_hash" ]; then
    die "…产物的 sha256 与编译前完全相同…这不是本次编出来的包"
fi
```

**这条判据在本项目是错的**：`.fwpkg` 实测**可复现**
（`HUB_HUB.fwpkg` 在 t3 复核 / t32 重编 / t23 重编三次逐位同哈希；
`NODE_M2.fwpkg` 在 t51 实测中连续两次也是逐位相同）。
于是"上一轮编的正好是同一个目标"时，产物哈希当然相同 —— 脚本会**假报失败**。

t51 实测撞到：并发跑 `m1 & m2` 时谁先拿到锁是随机的，一旦 `m2` 先跑而上一轮也是 `m2`：

```
BUILD_M1_RC=0 BUILD_M2_RC=1
/tmp/t51-b-m2.log: 错误：目标 m2 产物的 sha256 与编译前完全相同（8ee2a5e0…）——这不是本次编出来的包
```

**改成用文件时间戳判"新不新"**（这也是这条判据本来想表达的意思）。时间戳必须在**容器内**取，
否则 WSL/宿主时钟被 resync（AGENTS.md 环境陷阱条）时会误判：

```bash
T0=$(date +%s); <编译>; RC=$?
echo "[fresh] start=$T0 file=$(stat -c %Y <fwpkg> 2>/dev/null || echo none) rc=$RC"; exit $RC
```

宿主侧抠 `[fresh]` 行取两个数字，断言 `file >= start`；缺任一数字就 die
（"构建没按预期收尾"比"悄悄放过一个旧包"更安全）。sha256 相同不再 die，改为打印
"与编译前逐位相同 —— 可复现构建，属正常"。

顺带记一个**我自己写错的 sed**（留个教训）：第一版写成
`sed -n 's/.*\[fresh\] file=\([0-9]\{1,\}\).*/\1/p'`，而日志行是
`[fresh] start=… file=…` —— `[fresh] ` 后面紧跟的是 `start=`，**`\[fresh\] file=` 这个字面量在行里根本不存在**，
于是 `f_file` 恒空、每次构建都 die"没有可用的 [fresh] 行"。
修法是先抠整行 `fresh_line=$(grep -o '\[fresh\].*' "$log" | tail -1 || true)`，再对**这一行**做两次独立 sed。

### 13.10.3 `mock.info.txt` 的 role_marker 会冒充真 M1（复核 finding F-05）

`mock` 目标按 `-def=NODE_ROLE=1,NODE_MOCK=1` 编译，所以它的角色串与真 M1 **逐字相同**；
`ws63-firmware/out/mock.info.txt` 里 `role_marker=EC-NODE-ROLE=M1 type=gas` 单看会被误认成真 M1 包。
修法是给出处加后缀（一行）：

```bash
local marker_suffix=""
if [ "$name" = "mock" ]; then marker_suffix=" mock=1"; fi
# info.txt:
role_marker=$own_marker count=$n_own$marker_suffix
```

为什么敢改这个字段的格式：全仓只有 `tools/spike-build.sh:142` 与
`ws63-firmware/scripts/node-build.sh` **产出**它，**没有任何解析方**
（`docs/评审与验证/复核-t2-节点固件骨架-2026-10-18.md:123` 的 F-05 是给人看的阅读建议）。
