# 施工单：两块 WS63 星闪连通性冒烟（1 主 1 从）

> 目的：在写 1 主 3 从的生产组网代码之前，先用两块板证明「SLE 能广播、能连上、
> 能收到 notify」这条链路是通的。**只验连通性，不验业务**（温度计数是假的）。
>
> 预计耗时：烧录 2×3 分钟 + 观察 2 分钟。全程只需要插拔 USB 和敲几条命令。
>
> ⚠️ 本单的成功判据来自代码与 SDK 示例，**这两套固件还没有上过板**。第一次跑
> 请按第 5 节的“失败标志”逐条排除，并把串口原文回传（第 6 节）。

## 1. 两块板分别烧什么

| 板子 | 角色 | 烧这个文件 | 开机第一行（用来确认没烧反） |
|---|---|---|---|
| 板 A | 主节点（广播方/发通知） | `ws63-firmware\spike\out\SPIKE_MASTER.fwpkg` | `[SPIKE-SRV] boot: SPIKE-ROLE=MASTER svc=0x60b prop=0x1122` |
| 板 B | 从节点（扫描方/收通知） | `ws63-firmware\spike\out\SPIKE_SLAVE.fwpkg` | `[SPIKE-CLI] boot: SPIKE-ROLE=SLAVE target=0x060b/0x1122` |

两块板各自烧完，看一眼串口第一行就知道有没有烧反：
`SPIKE-ROLE=MASTER` 是主、`SPIKE-ROLE=SLAVE` 是从。**烧反了两块板都是同一个角色，
永远连不上**，而且日志一切正常，极难排查——所以先确认这一行。

固件里写死的身份（来自 `spike_common.h`，两块板不需要区分物理板子）：

- 主节点 MAC：`11:22:33:44:55:66`，广播名：`SPIKE_SRV_NODE_1`
- 从节点 MAC：`13:67:5c:07:00:51`
- 服务 UUID：`0x060B`，属性 UUID：`0x1122`（和现有 `sle_hub.c` 一致）
- 通知周期：1000ms；负载格式：`SPIKE seq=<n> t=<25.0>C`

## 2. 烧录

### 方案 A（推荐，一次插一块）

`ws63flash.exe` 的**串口号在源码里写死成 COM14**（`ws63-firmware/flasher/ws63flash.cs:455`
`string port = "COM14";`），所以一次只插一块板、让它枚举成 COM14 最省事：

```powershell
# 只插板 A，烧主节点固件
cd C:\Users\Administrator\ws63-tools\flasher
.\ws63flash.exe "C:\Users\Administrator\Desktop\HMProgram\ws63-firmware\spike\out\SPIKE_MASTER.fwpkg" app

# 拔掉板 A，只插板 B，烧从节点固件
.\ws63flash.exe "C:\Users\Administrator\Desktop\HMProgram\ws63-firmware\spike\out\SPIKE_SLAVE.fwpkg" app
```

- 第二个参数 `app` = 只烧应用镜像（boot 链走在板子上原来的），日常都用它。
- 想先看包里有什么：`.\ws63flash.exe "<路径>" list`。
- 烧完两块都插上（板 A 保持 COM14，板 B 会是 COM15 之类，不影响看串口）。
- 如果它报一串打不开串口的错、或明显在跟另一块板说话：说明 `ws63-tools` 下那个
  编译好的 exe 用的端口和仓库源码不一样，别跟它较劲，直接走方案 B 或 C。

### 方案 B（两块同时插着，不拔线）

用仓库里已有的 BurnTool 封装脚本，它可以指定端口：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File C:\Users\Administrator\Desktop\HMProgram\ws63-firmware\scripts\flash_ws63.ps1 `
  -Port COM15 -ComNum 15 -Bin "C:\Users\Administrator\Desktop\HMProgram\ws63-firmware\spike\out\SPIKE_SLAVE.fwpkg"
```

（`-Port`/`-ComNum` 换成设备管理器里那块板的实际端口；这条路径走 BurnTool 的
`-com:` 参数，比方案 A 慢，但不用来回插拔。）

### 方案 C（改一行，一次烧两块）

`ws63flash.cs` 第 455 行的 `"COM14"` 改成目标端口，然后重编（csc 已确认存在）：

```powershell
cd C:\Users\Administrator\Desktop\HMProgram\ws63-firmware\flasher
C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe /out:ws63flash.exe ws63flash.cs
```

> 这属于改 `ws63-firmware/flasher/`（本次任务范围外），只是为了让你省一次插拔；
> 改完记得把端口改回 COM14，免得下次烧错板。

## 3. 看串口

两个 PowerShell 窗口，一块板一个：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File C:\Users\Administrator\Desktop\HMProgram\ws63-firmware\scripts\watch.ps1 -Port COM14
powershell -NoProfile -ExecutionPolicy Bypass -File C:\Users\Administrator\Desktop\HMProgram\ws63-firmware\scripts\watch.ps1 -Port COM15
```

- **先关掉 MobaXterm / BurnTool**：串口一次只能被一个程序占用，否则 OPEN-FAIL。
- RTS 线接模块 EN 脚（低电平复位）：任何打开串口就拉 RTS 的软件都会把板子按在复位里，
  看起来像“固件死了”。`watch.ps1` 已经强制 DTR/RTS 为低；真遇到板子毫无输出，
  单独跑一次 `watch.ps1` 就能把 RTS 放掉、把板子救回来。
- 想原样抓文本回传：给 `watch.ps1` 加 `-Raw`。

## 4. 成功标志（照这个对着看）

### 板 A（主节点）应该出现

```
[SPIKE-SRV] boot: SPIKE-ROLE=MASTER svc=0x60b prop=0x1122
[SPIKE-SRV] my local addr=11:22:33:44:55:66
[SPIKE-SRV] service ready: server_id=.. service_handle=0x.. property_handle=0x..
[SPIKE-SRV] init OK, announcing as SPIKE_SRV_NODE_1
[SPIKE-SRV] conn state changed: conn_id=0x.. state=0x1 ...      ← 从端连上来了
[SPIKE-SRV] will notify every 1000ms from seq=0
[SPIKE-SRV] tx seq=0 t=25.0C len=.. -> conn=0x..
[SPIKE-SRV] tx seq=1 t=25.1C len=.. -> conn=0x..               ← 每秒一行，一路数下去
```

### 板 B（从节点）应该出现

```
[SPIKE-CLI] boot: SPIKE-ROLE=SLAVE target=0x060b/0x1122
[SPIKE-CLI] scanning for server 11:22:33:44:55:66 ...
[SPIKE-CLI] seek enabled status=0x0
[SPIKE-CLI] TARGET FOUND (hit #.., rssi=-..)                    ← 扫到主节点
[SPIKE-CLI] conn state changed: conn_id=0x.. state=0x1 ...
[SPIKE-CLI] auth complete status=0x0
[SPIKE-CLI] pair complete conn=0x.. status=0x0
[SPIKE-CLI] exchange MTU (req=..) -> discover service 0x60b
[SPIKE-CLI] service found: ... uuid=0x060b                      ← 服务发现到了
[SPIKE-CLI] property found: handle=0x.. uuid=0x1122 ...          ← 属性发现到了
[SPIKE-CLI] TARGET property 0x1122 at handle 0x..
[SPIKE-CLI] subscribe: write CCCD handle=0x..
[SPIKE-CLI] SUBSCRIBED ready, waiting for notify ...
[SPIKE-CLI] FIRST notify on conn=0x.., handle=0x..
[SPIKE-CLI] rx #1 seq=0 dt=..ms len=20 payload="SPIKE seq=0 t=25.0C"
[SPIKE-CLI] rx #2 seq=1 dt=1000ms len=20 payload="SPIKE seq=1 t=25.1C"
...
[SPIKE-CLI] STAT(periodic) rx=10 lost=0 dup=0 seq=0..9 interval=..ms   ← 每 10 帧一行
```

### 判据（三条全中才算通）

1. 板 B 每秒一行 `rx #N seq=.. payload="SPIKE seq=..."`，`seq` 连续递增（0,1,2,…）；
2. 板 B 出现 `lost=0`（`lost` 是序号断档累计数；`dup=0` 是重复帧）；
3. 连续观察 **≥60 秒**，`rx` 计数与秒数大致相等（60 秒 ≈ 60 帧，允许个位数波动）。

> 只收到第一帧就停、或 `lost>0`，都算**不通过**——这正是要提前发现的组网风险。

## 5. 失败标志 → 下一步

| 现象 | 大概率原因 | 下一步 |
|---|---|---|
| 板 B 一直 `scanning`，没有 `TARGET FOUND` | 主端没在广播 / 两块板离太远 / 天线没接 | 先看板 A 有没有 `announcing as SPIKE_SRV_NODE_1`；把两块板靠近到 10cm 再试 |
| `TARGET FOUND` 但一直不出现 `conn state changed ... state=0x1` | 配对/连接失败 | 回传板 B 的 `pair complete`/`auth complete` 原文 |
| 连上了但 5 秒内一帧都没收到（板 B 会自己打 `WARN: 已连接但 5s 内一帧都没收到`） | 主端没发（看板 A 有没有 `tx seq=`）/ 通知没落到这个属性上 | 对比两端的 `property_handle`：板 A 的 `property_handle=0x..` 应该等于板 B 的 `TARGET property 0x1122 at handle 0x..` |
| 板 B 出现 `!! GAP: expect seq=N got=M (lost +k)` | **真丢包**（这是要重点报告的现象） | 原样回传这一行，并说明两块板的距离和中间有没有人/金属 |
| 板 B `CCCD write failed`，但 `rx` 照常每秒来 | 这是**允许的**：本包主端连上就发，不看订阅状态 | 不用管，记一笔即可 |
| 某块板串口一个字都没有 | RTS 把板子按在复位里 / 串口被别的程序占了 | 关掉 MobaXterm/BurnTool，单独跑一次 `watch.ps1` |
| 第一行是 `SPIKE-ROLE=SLAVE` 却插在“应该是主节点”的板子上 | 两块板烧反了 | 按第 1 节重烧 |

## 6. 回传什么给我

1. 板 A、板 B 各 **≥60 秒** 的串口原文（`watch.ps1 -Raw` 抓的最省事）；
2. 特别标注：板 B 最后一行 `STAT(...)` 的原文；有没有 `!! GAP` / `WARN` 行；
3. 两块板的实际距离、板子型号（如两块都是 WS63 开发板/EVB）、有没有接天线；
4. 如果有异常，附上你当时怎么摆的、有没有插拔/复位。

回传后我会把结果、结论和遗留风险写进 `docs/技术笔记/星闪双板测试.md`。

certutil -hashfile "C:\Users\Administrator\Desktop\HMProgram\ws63-firmware\spike\out\SPIKE_MASTER.fwpkg" SHA256

两个包的关键差异只有角色定义（从端多一个 `-def=SPIKE_ROLE=2`），
编译脚本会断言「主端镜像里有 `SPIKE-ROLE=MASTER` 且没有 `SPIKE-ROLE=SLAVE`」，
反过来同理——这就是防“两块板烧成同一个角色”的那道闸。

本次构建的实际产物（已核对，正常情况直接照抄即可）：

| 包 | 字节数 | sha256 |
|---|---|---|
| SPIKE_MASTER.fwpkg | 1457768 | `c932a2ab64d4e1794d658d6cffed362ac6e5de04d7342c4134c1327552819535` |
| SPIKE_SLAVE.fwpkg | 1458664 | `a27ca845adf670f45e55f1a0daa2ecad908ed07ca625e3ee09c0aa6aeb49f4fe` |

两者字节数、哈希都不同（不是同一个镜像改了名）。镜像内字符串统计（用 python 数原始字节，
不用 grep——方括号在正则里是字符集，`[SPIKE-SRV]` 会退化成“命中任意一个字母”的假计数）：

| 包 | `[SPIKE-SRV]` | `[SPIKE-CLI]` | `SPIKE-ROLE=MASTER` | `SPIKE-ROLE=SLAVE` |
|---|---|---|---|---|
| SPIKE_MASTER.fwpkg | 38 | 0 | 1 | 0 |
| SPIKE_SLAVE.fwpkg | 1※ | 44 | 0 | 1 |

※ 从端那句「一帧都没收到」的调试提示里会合法地印出主端标签，正好一次——
这也是角色断言看 `SPIKE-ROLE=` 而不看标签的原因（拿标签当判据会误杀）。
