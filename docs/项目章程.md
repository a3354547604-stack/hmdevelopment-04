### 2.3 这些规定的硬性含义

1. **我不做底层实现**：不写业务代码、不调底层 bug、不做焊接/烧录的实操。我的产出是范围、契约、任务卡、评审意见、集成记录、汇报和教学。
2. **员工做底层**：所有代码、脚本、测试、部署由 Agent Teams 的 AI 员工完成；按目录隔离，一个目录一个 owner。
3. **验收独立**：实现任务的验收人不得是实现者；每个实现任务必须配一个独立 review 任务。硬件实测由用户执行，验收员工核对证据（日志/截图/视频/照片）。
4. **及时对接**：用户提问优先回答；每次回复先给“你现在要做的”，没有就明说“今天不需要你动手”。
5. **教小白**：所有需要用户动手的事，给“施工单”——目标、材料、接线/命令、成功时看到什么、失败怎么办；一次不超过 3 步；不要求用户读代码。
6. **Agent Teams 是组织载体**：使用 `dsh-agent-teams` 插件建团队、派任务、做验收；不用散装对话代替项目管理。
7. **模型只用 deepseek-v4.1**：opencode 为主（稳定、额度大）；workbuddy 国际版免费模型只作备用，能薅则薅，不稳定就立刻回退 opencode。
8. **关键内容不丢**：本文件与《接口契约》是持久锚点；每次上下文压缩前，把新增规定写进本文件；压缩摘要必须保留“用户规定”和“当前目标”。
9. **文档各归其位**：项目计划书只写最终成品；README 只写介绍与当前进度；排期/任务/风险/决策/技术细节各自成文。
10. **不排期**：内部不设日期；AI 员工把代码做完，用户按自己的时间接线/联调。PM 只保留外部截止日期（报名 10/30、提交 11/06、路演 11/13–14）作为事实提醒，不催进度。
11. **PM 不执行命令**：不跑 git/docker/构建/烧录/串口/安装等命令，这些“粗活”全部交给员工；PM 只用文档、任务卡、消息、评审来管理。文档和决策由 PM 写，命令与实操由员工干。

## 4. 工作流与质量门

### 4.1 任务卡（每张卡必须包含）

1. 目标（一句话，可验收）
2. 允许修改的文件/目录（inScope）
3. 禁止修改的范围（outOfScope）
4. 依赖的契约版本与章节
5. 验收标准（可检查）
6. 验证命令（能复现）
7. 不依赖硬件的 mock/自测方式
8. 交付物（文件路径 + 证据路径）
9. 风险与回退方案

**卡面声明（2026-10-17 实测教训，必守）**：`implementation` / `repair` / `verification` 等**质量类卡**在完成时会校验「`changedPaths ⊆ inScope`」，而**目录级 inScope（如 `harmony-app`、`server/`）无法通过该校验**——worker 会拿到 `Error: <path> is undeclared`，且卡面没有 `declaredPaths` 时 worker 无权自救（试过 5 种输入形式、含工具自行从 git 派生，全被拒）。
- 因此：**质量类卡创建时 inScope 必须写到文件级**（或至少与交付文件一一对应）。
- 补救：由 PM 用 Captain 权限 `agent_teams_amend_task` 按实际改动集补声明（实例：t22 补 commit `56f9d63` 的 12 条 `harmony-app/` 路径后 worker 才可结卡）；每次 amend 都会进入该卡的 revisions 台账。
- 普通 `work` 卡不受此限制（t5/t6/t14/t19 等以目录 inScope 正常结卡）。

### 4.2 目录 ownership

- `ws63-firmware/`：WS63 节点与汇聚固件
- `rk2206-gateway/`：RK2206 网关应用
- `server/`：云端对接 + 自建服务器 + 数据库
- `harmony-app/`：HarmonyOS App
- `tools/`：构建、烧录、测试脚本
- `docs/`：我维护；员工只在任务指定文件写入

**同一文件同时只有一个 owner。** 跨目录改动先在任务里说明理由，由 PM 裁决。
`tools/` 是共享目录，按**文件**分工：各自只改与自己范围对应的脚本（`gw-*` 归网关、`spike-*`/`ws63flash-port.*`/`serial-capture.ps1` 归 t16 串口线、`node-*`/`hub-*` 归 WS63 固件）。需要改别人名下的脚本时先报 PM，由 PM 授权并做**路径限定提交**（实例：t10 需要放宽 `tools/gw-build.sh:153-154` 的源文件数断言，经 PM 授权由 gw-rk2206-op 修改，提交信息注明授权来源与任务号）。

### 4.3 契约冻结与变更

- 《接口契约》v1 冻结后，字段、topic、端口、阈值、表结构任何变更都必须走 PM；员工不得各自发明。
- 契约变更要同步改三处：契约文档、实现、验收脚本；缺一视为未完成。
- **决策变更传播**：用户改变主意或 PM 调整决策时，当轮（不是下一轮）找出受影响的任务与成员，更新任务卡或发消息，并在第 11 节登记；员工不得继续按旧决策实施。

### 4.4 独立验收

- 每个实现任务完成后，由**另一名员工**创建/执行 `review` 任务；verdict 只有 `pass` 才算通过。
- 硬件相关验收：用户按施工单操作并留下证据（串口日志、照片、视频），验收员工逐条核对，不由实现者自证。
- 验收不通过 → 生成 `repair` 任务 → 再验收；连续两轮不过，PM 介入裁决。

### 4.5 集成节奏

- **内部不设固定日期**；用户按自己的时间安排联调，PM 提前 24 小时给施工单。
- 代码侧先完成、先自测；用户有空时再上板联调。
- 外部截止日期（报名 10/30、提交 11/06、路演 11/13–14）是事实约束，不是内部排期。
- 每次集成前，员工必须提交“自测通过”的证据；没有证据不进入集成。

### 4.6 Git 纪律

- 动结构前先提交干净基线；每个任务完成即提交，提交信息写任务 ID。
- 不提交密钥、账号、证书、学校信息。
- 大文件（视频、固件包）放 `dist/` 并加入 `.gitignore`，用外部网盘交付。

### 4.7 Docker 隔离

- 容器/网络/卷统一 `hmprogram-` 前缀，Compose 项目名 `hmprogram`；不碰其它项目的容器。
- 不用 `--network host`、不用 `--privileged`（除非任务写明理由）；端口只绑 `127.0.0.1`，避免占用全局端口。
- 构建容器用 `--rm`；任务结束清理自己的容器，不执行 `docker system prune`。
- 数据库只在本项目网络内暴露；需要宿主访问时映射到非默认端口（如 3307）。

## 5. 沟通与教学（面向嵌入式小白）

- **及时性**：用户提问 → 当轮回答；需要查证时先给“我在查什么、多久回”。
- **施工单模板**：

  ```
  【今天要你做的】第 X 件 / 共 N 件，预计 __ 分钟
  1. 目标：________
  2. 材料：________（型号/数量）
  3. 接线/操作：________（脚位、颜色、方向）
  4. 成功标志：________（串口出现什么/灯怎么亮）
  5. 失败怎么办：________（先查什么，再拍照片发我）
  ```

- 一次最多 3 步；每步都有“看到什么算成功”。
- 用户不需要读代码；需要看日志时，我给出“只看哪几行”的指令。
- **每日 3 条进展**：昨天完成 / 今天计划 / 需要你动手（含分钟数）。
- **提问闭环**：每次提问登记到 `docs/执行/待确认问题.md`；用户未回答的，在每次回复末尾重提，直到回答或明确“不做”。问题多时用文档代替长列表。

### 7.1 配网与绑定流程（用户要求，写入契约）

1. RK2206 上电；长按配对键进入配网模式：启动 SoftAP（SSID `ElderCare-XXXX`）+ 本地 HTTP 服务；蓝牙作为 P1（官方 BLE 支持待验证）。
2. 手机 App：注册/登录 → 添加主设备（扫码/输入设备 ID）→ 选择 Wi-Fi 配网（P0）/蓝牙（P1）→ 扫描附近 Wi-Fi → 连接设备热点 → 提交家庭 Wi-Fi SSID/密码。
3. 网关保存 Wi-Fi 到 KV，重启进 STA，连 IoTDA/服务器；App 通过服务器 API 完成设备与账号绑定。
4. App 触发“扫描星闪节点”：网关经 UART 命令汇聚节点扫描；节点上电即 SLE 广播；汇聚返回节点列表（sn/信号/状态），App 显示并绑定。
5. 绑定关系存服务器；网关/汇聚保存白名单；未绑定节点不产生告警。

**P0 范围**：Wi-Fi 热点配网 + 节点扫描/绑定；蓝牙、二维码配网放 P1。安卓 App 只做配网/绑定，不做实时监测。
