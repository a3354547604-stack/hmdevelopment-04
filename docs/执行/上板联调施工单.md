powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/serial-capture.ps1 \

## 1. 板 2：烧 M2 节点（雷达），并取它的 SN（3 步）

**烧哪个镜像**：`ws63-firmware/out/NODE_M2.fwpkg`（1468072 B，当次 sha256 `d8324b9f8bf1b4654658009ee56c0b9e5115c5163c1136546cc9736028d8a005`）

### 第 1 步：烧

用 §0 第 3 步那条命令，把 fwpkg 换成 `NODE_M2.fwpkg`、`COM15` 换成你这块板的实际口号、日志名换成 `flash-m2-<COMxx>.txt`。
**成功标志（逐字）**：日志里出现 `fwpkg magic=0xEFBEADDF`、`file transfer complete`、`handshake OK (3 ACKs)`、
最后一行 `OK: ws63-liteos-app-sign.bin`。每块约 2.5 分钟，中途别拔线。

### 第 2 步：抓 60 秒启动日志，取 SN

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/serial-capture.ps1 \
    -Port COM15 -Seconds 60 -Out 'C:\Users\<本机用户>\Desktop\HMProgram\ws63-firmware\out\m2-boot.log' -Reset -Quiet
```

**期望的逐字日志行**（这两行是「镜像角色」的唯一权威来源，`node_main.c:147-150`）：

```
[M2] EC-NODE-ROLE=M2 type=fall fw=0.1.0
[M2] node up: fw=0.1.0 type=fall mac=11:22:33:44:55:02 adv=EC-M2 proto=0x01
```

**SN 从哪一行取**：`EC-NODE-ROLE=` 后面那个两字符（这里是 `M2`）；同一行里 `adv=EC-` 后面、`mac=` 末尾那个字节也是它
（`M1=…:01`、`M2=…:02`、`M4=…:04`）。**这三处必须一致**——不一致就是烧反了或角色宏没生效。

> ⚠️ 别用 `[SLE-HUB]` 有无判断「烧的是哪套固件」：**节点镜像也会打 `[SLE-HUB]`**（那是节点侧星闪模块自己的标签），
> 判断角色只看 `EC-NODE-ROLE=`。

### 第 3 步：把 SN 写下来，别靠记忆

在纸上/记事本写一行：`板 B = COM15 = M2 = mac 11:22:33:44:55:02`。下一节要把它填进汇聚的临时镜像里，**填错就等于白跑**。

**失败对照**

| 现象 | 最可能原因 | 下一步 |
|---|---|---|
| 烧录日志停在 `waiting for handshake` / 无 `3 ACKs` | 板子没进下载模式；或 USB 线只供电不传数据 | 先按住板上的 `BOOT`（或 `RST` 后立刻按住），再点开始；换一根**能传数据**的线 |
| 烧完串口一个字都没有 | 抓的是板子的**另一个口**（USB-TTL 与板载 CH340 是两路）；或没加 `-Reset` | 用插拔对照法重新认口；先手动按一下板上的 `RST`，再抓 |
| 出现 `[M1] EC-NODE-ROLE=M1 …` | 烧成 M1 了（`-def` 没生效或拿错包） | 重烧 `NODE_M2.fwpkg`，核对 §1 第 1 步的路径 |
| 出现 `*** MOCK 模式 ***` | 烧成 `NODE_MOCK.fwpkg` 了 | 重烧真镜像 `NODE_M2.fwpkg` |
| 串口有一堆乱码 `烫烫…` | 波特率不对 | 固定 `115200 8N1`（`serial-capture.ps1` 默认就是） |

## 2. 板 1：先烧 hubmock，单板自证「烧录 + 串口 + UART 帧」（3 步）

**为什么先烧它**：`HUB_HUBMOCK.fwpkg` 内置 3 个虚拟节点，**不需要第二块板、不需要网关、不需要白名单**，
就能把「汇聚固件能跑、串口能抓、UART1 帧能发」三件事一次验掉。这一步失败就说明是烧录/接线问题，而不是星闪链路问题。

**烧哪个镜像**：`ws63-firmware/out/HUB_HUBMOCK.fwpkg`（1477672 B，当次 sha256 `e999baa7f7ec1ddd69e390a82a0b2699c10780a6f760455055da8997a3e51bae`）

### 第 1 步：烧 + 抓 60 秒

命令同 §0 第 3 步，换 fwpkg 与本板口号。

**期望的逐字日志行**：

```
[HUB] HUB-ROLE=CENTRAL sn=H1 fw=0.1.0 mock=1 (uart1 115200)
[HUB] MOCK: add virtual node M1
[HUB] MOCK: add virtual node M2
[HUB] MOCK: add virtual node M4
[HUB] MOCK: M1 online (conn=0x0, no SLE link)
[HUB] seek start ret=0x0
```

30 秒后会打一行统计（`hub_client.c` 的 `STAT`），**它必须递增**：

```
[HUB] STAT up=60s rx=… poll_ok=20 poll_miss=0 … ev_on=3 … up_sent=60 … drop(ev=0 up=0 uart=0) …
```

### 第 2 步：判读（只看两个数）

- `mock=1` —— 确认烧的是 hubmock；
- `poll_ok=` 每次 +20 左右、`poll_miss=0` —— 说明 3 秒一轮的轮询真的在跑（3 个虚拟节点 × 20 轮 = 60 s 内 20 次/节点）。

### 第 3 步：这一步过了才继续

这一步全绿 ⇒ 烧录链路、串口、汇聚固件都正常，**后面所有失败都只会是星闪/白名单问题**，不用再怀疑烧录。

**失败对照**

| 现象 | 最可能原因 | 下一步 |
|---|---|---|
| 只有 `HUB-ROLE=CENTRAL … mock=0` | 烧成生产镜像 `HUB_HUB.fwpkg` 了 | 重烧 `HUB_HUBMOCK.fwpkg` |
| 有 `mock=1` 但没有 `MOCK: add virtual node` | 烧的是旧版本的 hubmock 包 | 按 §2 的 sha256 核对包是不是当次产物 |
| `STAT` 里 `poll_ok` 一直是 0 而 `poll_miss` 涨 | 虚拟节点没进白名单/没上线 | 抓完整 60 s 日志（别只看尾部），把 `MOCK:` 与 `conn=` 行一起回传 |
| `uart1 init ret=-1` 一类错误 | 板子引脚模式不对 | 见 `ws63-firmware/doc/12` §14；先确认烧的是 `HUB_*` 而不是 `NODE_*` |

## 3. 两块板连起来：1 主 1 从（无网关，靠临时钩子镜像）（3 步）

### 为什么必须做这一步（先说清前提，别以为是我们写错）

契约 §2.7 规定：**汇聚的白名单只由网关的 `0x22 PAIR_BIND` 帧填充**。没有网关，汇聚扫到 M2 也**不会连**——
所以「1 主 1 从」只有两条路：

- **接网关**（正路，但要等 RK2206 认出来，见 §5）；
- **临时钩子镜像**：把 M2 的 SN 编进汇聚固件，开机就预置进白名单（**只替换「网关下发配对」这一次交互**，
  连接/交换信息/服务发现/写 CCCD/首帧确认/轮询全是真路径）。**这就是本节要做的。**

> 🔴 **测完必须烧回生产镜像**（`ws63-firmware/out/HUB_HUB.fwpkg`，1474152 B，
> 当次 sha256 `6abfcbe54f0008d92c8e562c16fb7c67761aa28ae0a3ec740e5084679471c02f`）。
> 钩子镜像里有硬编码的测试 SN，**绝不能当交付物**、也不能留在板子上。

### 第 1 步：编一份钩子镜像（改两行宏 → 编 → 立刻还原源码）

```bash
# ① 先把生产包备份出来（第 3 步要烧回它；编译钩子会覆盖同名文件）
cp ws63-firmware/out/HUB_HUB.fwpkg ws63-firmware/out/HUB_HUB.production-backup.fwpkg

# ② 改 ws63-firmware/src/hub_cfg.h（把列表换成你 §1 第 3 步记下的 SN，可多个）
#    #define HUB_TEST_PREBIND_ON      1
#    #define HUB_TEST_PREBIND_SN_LIST "M1,M2"

# ③ 编（需要构建窗口；编完 node-build.sh 会自己清空 SDK 的 custom/ 并断言残留 0）
bash tools/build-lock.sh bash ws63-firmware/scripts/node-build.sh hub

# ④ 立刻把钩子包另存 + 还原源码（否则源码里就留着一个测试开关）
cp ws63-firmware/out/HUB_HUB.fwpkg ws63-firmware/out/HUB_HUB.prebind-M2.fwpkg
git checkout -- ws63-firmware/src/hub_cfg.h
```

> 注意：`-def=HUB_TEST_PREBIND_ON=1` **不行**——`hub_cfg.h` 里这两个宏没有 `#ifndef` 保护，
> 命令行 `-D` 会和头文件里的 `#define` 冲突。必须改头文件（改完还原）。

### 第 2 步：把两块板的 UART1 三线接起来（只接三根）

| 汇聚 H1 | 方向 | 网关侧（现在先当「对端」用） | 说明 |
|---|---|---|---|
| 排针 **23** `U1TX` | → | 对端 **RX**（排针 24 `U1RX`） | 3.3 V 直连，不分压 |
| 排针 **24** `U1RX` | ← | 对端 **TX**（排针 23 `U1TX`） | 3.3 V 直连 |
| GND | — | GND | **必须共地**，否则收到的全是乱码 |

> 只接 UART 三线也能跑通 1 主 1 从：**汇聚会用 UART1 把 `0x01`/`0x02`/`0x24` 帧发出去**。
> 如果你没有第二个设备接这三根线，**跳过这一步也能验星闪链路**——判据全在汇聚自己的串口日志里（见第 3 步）。

### 第 3 步：烧钩子镜像到板 1 + 板 2 上电，抓 90 秒，逐条对判据

**期望的逐字日志行（按出现顺序）**：

```
[HUB] WARN: TEST HOOK prebind M2 (no gateway on this bench)
[HUB] seek hit #1 mac=11:22:33:44:55:02 sn=M2 role=1 rssi=-4x
[HUB] conn_state_changed conn=0x0 state=… pair=… reason=0x0
[HUB] slot=0 sn=M2 conn=0x0
[HUB] conn=0x0 subscribe: write CCCD handle=0x11 (prop) type=0x2 val=0x0001 try=1/3
[HUB] sub-state sn=M2 -> CONFIRMED (first 0x01 uplink; …ms after first CCCD)
[HUB] STAT … poll_ok=… poll_miss=0 … sub(conf=1 …) …
```

节点侧同时也应看到它在收轮询（`node_main.c:100`）：

```
[M2] <- poll id=…
[M2] tx … bytes: {"sn":"M2","ts":…,"type":"fall",…}
```

**判据（四条全中才算通）**：
1. 有 `TEST HOOK prebind M2` ⇒ 钩子生效、白名单已预置；
2. 有 `seek hit … sn=M2` ⇒ 汇聚真的扫到了节点（扫不到就是板子没广播/距离太远/两块板都是 server 角色烧反了）；
3. 有 `sub-state sn=M2 -> CONFIRMED` ⇒ **订阅链路通了**（这一条是整条链路最容易假绿的地方，
   「写了 CCCD」不等于「订阅成功」，必须等到首帧 `0x01` 才敢说 CONFIRMED）；
4. `STAT` 的 `poll_ok` 递增、`poll_miss=0` ⇒ 轮询在跑，节点在应答。

**失败对照**

| 现象 | 最可能原因 | 下一步 |
|---|---|---|
| 没有 `TEST HOOK prebind` | 烧的还是生产包；或宏改完没重编 | 核对包 sha256 与 §3 第 1 步；重烧 `HUB_HUB.prebind-<SN>.fwpkg` |
| 有 `TEST HOOK` 但**永不**出现 `seek hit` | 两块板都烧成 SLE server（节点角色），或都烧成客户端；或节点没上电/没广播 | 核对两块的 `EC-NODE-ROLE=` 与 `HUB-ROLE=CENTRAL`；把两块板靠近到 <1 m 再抓 |
| 有 `seek hit` 但没有 `slot=` / `conn_state_changed` | 扫到了但连不上（白名单 SN 拼错、或 `mac` 与 SN 不匹配） | 把 `seek hit` 行的 `sn=` 与 §1 记的 SN 逐字符比；SN 只可能是 `M1`/`M2`/`M4` |
| 卡在 `CCCD write rejected by local stack status=0x4` | 写的句柄不是属性句柄（照别的协议栈的习惯写成 `属性句柄+1`） | 已在 t59 修掉；若还出现，说明板上的固件不是当次产物，重烧 |
| **订阅失败**：`CCCD not confirmed in …ms -> rewrite CCCD (2/3)`，反复重试 | 节点侧没在 1.5 s 内发首帧；或 `0x1122` 属性句柄变了 | 抓节点侧日志看有没有 `tx … bytes`；两板固件都要是当次产物（`doc/11`§11、`doc/12`§14） |
| **poll 超时**：`poll sn=M2 write FAILED (stage=…)` 持续出现 | 连接断了但还没超时判离线；或节点侧写失败 | 看 `conn_state_changed … reason=` ；`stage` 值对照 `hub_client.c` 的写失败阶段表 |
| 收到全是乱码 | 三线没共地，或 TX/RX 没交叉 | 按 §3 第 2 步的表重接（**A 的 TX 必须接 B 的 RX**） |

### 第 1 步：M1（厨房，AHT20 + MQ-2）

接线按 `docs/技术/引脚与接线表.md` §4（MQ-2 模拟输出经 **1:1 分压**进排针 17 `IO09`＝ADC ch2；AHT20 走 23/24 的 MODE 2 I2C）。
**MQ-2 加热丝必须独立 5 V/2 A 供电**（≈172 mA），**不能用板子的 3.3 V**；预热要 >48 h，第一次上电读数偏高是正常的。
板子侧只有一颗 WS63：`NODE_M1.fwpkg`，命令同 §1 第 1 步。

### 第 2 步：M4（门厅，两路门磁）

接线按接线表 §6.1（两路干簧管进 `IO00`/`IO02`，另一端接 GND，模块内部上拉，不外加电阻）。
开/关门时应看到 `M4` 的心跳帧里 `open` 位跟着变；只有跳变才发事件帧（**P0 不发 `presence` 帧**，那是 P1 的开关，默认关）。

### 第 3 步：缺板时怎么顶

手上只有 2 块 WS63 时，第 3 个节点用 `NODE_MOCK.fwpkg` 顶位：它会发**格式合法、数据是伪造**的帧（串口会明确打
`*** MOCK 模式：数据为伪造，只验证链路与格式，不代表真实环境 ***`）。**汇报数据时必须写明「这一路是 mock」**，别混进实测结论。

## 5. 网关认板之后：烧网关 + 接三线（3 步）

> 现在 RK2206 只报 `未知 USB 设备(端口重置失败)`，**本节先不用做**；认板的具体分支见 `docs/执行/网关认板排查.md` §3（六个分支，每支只做 3 件事）。
> 认出来的判据是三行：`发现一个MASKROM设备` / `下载完成` / 设备管理器里出现 `Rockusb Device`。

### 第 1 步：把两个文件准备好（缺一不可）

| 用途 | 文件 | 体积 | 说明 |
|---|---|---|---|
| 镜像 | `rk2206-gateway/out/gateway-Firmware.img` | 2097152 B（分区定长，**只看体积+提交号**，sha256 每次都变，见 AGENTS.md 产物口径） | RKDevTool 里地址填 `0x00000000` |
| loader | `rk2206_db_loader.bin` | 35093 B，md5 `5f2ea974b0e1df5564a8e1ee910627bb` | SDK `out/rk2206/lockzhiner-rk2206/images/` 与原厂桌面包**三处同一份** |

> 原厂 `config.cfg` 里那一行 `C:\Users\…\u-boot.itb` **必须删掉**，否则点「执行」会报
> `u-boot.itb下载项不存在,停止执行!`——这是我们这块板子最常踩的一条。

### 第 2 步：进 MaskRom 并烧

USB 线插**板子的 USB-OTG 口（烧录口）**，不是调试串口那个 Type-C → 长按 `MaskRom` 键不松 → 点一下 `Reset` → 约 5 秒后松开 `MaskRom`
→ 工具显示 `发现一个MASKROM设备` → 两行都勾上（`LoaderToDDR` + `firmware`）→ 点「执行」→ `下载完成`。

### 第 3 步：接三线 + 抓调试串口

三线按 §3 第 2 步那张表（H1 的 23/24 ↔ 网关 `E53_UART0`，共地）。调试串口**115200 8N1**（SDK `device/rockchip/rk2206/README_zh.md` 原文：
「使用USB串口线，连接USB_UART口，打开串口工具(波特率:115200)」）。

**期望的逐字日志行**：

```
[gw] ---- RK2206 网关 M0 启动 ELDERCARE-GW-M0-v1.2 (契约 v1.2) ----
[gw] 任务已启动：UART0=115200 8N1，等待汇聚帧…
[PROV] ready: sn=… ap_ssid=… bound=0 keepalive=600s
```

> 只出 ROM/U-Boot 那几行、**没有** `RK2206 网关 M0 启动` 这一行 = 烧进去的不是我们的固件，别继续往下做。
> 串口波特率试到 `115200` 仍全 0 字节：先用插拔对照法确认「这个 COM 到底是不是网关的 UART 口」——
> **OTG 口只枚举 USB 设备、不产生 COM 口**，插错口的时候你怎么换波特率都是 0 字节。

**失败对照**

| 现象 | 最可能原因 | 下一步 |
|---|---|---|
| 工具报 `没有发现设备` | 没进 MaskRom；或线插在调试口 | 换**能传数据**的线；确认插的是 USB-OTG；按住 MaskRom→点 Reset→5 秒后松 |
| 报 `写LBA前必须完成下载Boot!` | loader 那行没勾或路径不对 | `LoaderToDDR` 指向 `rk2206_db_loader.bin`（35093 B） |
| 报 `没有勾选下载项,停止执行!` | 两行都没勾 | 两行都勾上再点执行 |
| 换了 115200/9600/921600/1500000 全 0 字节 | 打错了口（板子有两个 Type-C：OTG 与 UART） | 插拔对照法认口；OTG 口不产生 COM |

## 6. 全链路（网关能跑之后再按顺序走，3 步）

### 第 1 步：长按配网键进 AP → 手机连热点

杜邦线把 `EX_GPIO_A3`（`GPIO0_PA3`）短到 GND **长按 3 秒**（`gw_config.h` `GW_PAIRKEY_LONG_MS 3000`），松开。
**期望**：串口打 `[PROV] enter AP mode ssid=ElderCare-XXXX …`，手机 Wi-Fi 列表里出现 `ElderCare-XXXX`（XXXX 是 SN 后 4 位十六进制）。
手机连上它（默认口令见串口打印；**不给别人**）。

> 若烧的是较新的网关固件，也可以用串口命令 `gwkv` 直接写云凭据、免按键配网——以 `rk2206-gateway/施工单-凭证写入Flash-KV.md` 为准。
> 本节按「长按进 AP」这条契约 §12.2 的稳妥路径写。

### 第 2 步：浏览器打开 AP 页面，**只填家里 Wi-Fi**

浏览器访问 `http://192.168.4.1/`（**占位地址**：实际地址由板级驱动决定，**以串口首行打印的 AP 地址为准**，
这是已知偏差 CAL-12；打不开就复制串口里那行地址）。
页面里填：**家里 Wi-Fi 的 SSID/口令**——就这样，第 2 步只有这一个输入。

> **云端凭据不在页面上**（定案：华为云与服务器都由厂商侧运营，用户不建、不填）。
> 出厂时由厂商用串口写入：`gwkv set host=… port=1883 device=… secret=…`（见
> `rk2206-gateway/施工单-凭证写入Flash-KV.md` §2）；售后返修才用页面里的「厂商维护」面板
> （连点标题 5 次出现，`POST /api/config`）。
> 页面上**搜不到**「接入地址 / 设备 ID / 设备密钥」，状态卡只有一行「云端服务：已配置 / 使用出厂配置」——
> 这才是正确形态，看到了别以为是漏配。

**期望（逐段可判）**：

```
[PROV] 本地配网服务就绪 http://<实际AP地址>/（H5 单页，契约 §12.11）
[HTTP] GET / -> 200 (… B)
[gw] 取时成功(HTTP) epoch=…            ← 取时失败会打「取时失败：服务器与 NTP 都不可达，暂不连 IoTDA」
[gw] IoTDA 已连接 clientId=…            ← 这一行才是「上云成功」
```

### 第 3 步：数据落库 → App/网页读到

服务器侧（`server/`）：

```bash
cd server && docker compose up -d --build
curl -s http://127.0.0.1:3000/api/health
docker compose exec api python -m app.seed --demo    # 演示数据（会先清库再灌）
bash tools/demo-check.sh                             # 全绿 rc=0
```

**判据**：① 汇聚 `STAT` 的 `up_sent` 递增（= 帧真的发出去了）；② 网关串口有 `事件 … type=… level=…` 或节点属性上报；
③ 服务器能查到设备数据、App 首页有实时数据（App 默认 `MOCK_MODE=true`，要连真服务器请改
`harmony-app/entry/src/main/ets/common/AppConfig.ets` 的 `SERVER_BASE_URL`，并把 `MOCK_MODE` 置 false）。

**失败对照（全链路）**

| 现象 | 最可能原因 | 下一步 |
|---|---|---|
| 手机连上 `ElderCare-XXXX` 但打不开页面 | AP 地址不是 `192.168.4.1`（CAL-12） | 用串口首行打印的地址；仍不行看 `[PROV] ⚠ 取不到 AP 口地址…见 CAL-12` |
| **webhook 401** | URL 里 `?token=` 缺了或与 `server/.env` 的 `WEBHOOK_TOKEN` 不一致（契约 §9.2 只回 1502，不告诉你哪错） | 核对 IoTDA 转发 URL 与 `server/.env`；`curl -i 'http://127.0.0.1:3000/api/iotda/webhook?token=<值>'` 手工试 |
| **时间戳不同步** | 网关没取到时间就拒绝连 MQTT（`取时失败：服务器与 NTP 都不可达，暂不连 IoTDA`） | 配网页里把「时间服务器」填成你 PC/服务器的内网地址；或先用 `/api/time` 可达再试 |
| `MQTTConnect 失败 rc=4` | ClientId/HMAC 时间戳不对（`rc=2` 常见于 ClientId 错） | 核对设备 ID 与密钥；确认时间已同步 |
| 网关在线但服务器没数据 | IoTDA 的转发规则没配到我们服务器 | 见 `docs/执行/IoTDA建产品与设备指引.md` |

## 7. 收工纪律（每次动完板子都做，3 步）

### 第 1 步：板子恢复成「生产镜像」

- 板 1（汇聚）→ `ws63-firmware/out/HUB_HUB.fwpkg`（1474152 B，当次 sha256 `6abfcbe5…471c02f`）
- 板 2（节点）→ 你今天实测的那个节点镜像（`NODE_M1/M2/M4.fwpkg` 之一）
- **绝不留钩子镜像**（`HUB_HUB.prebind-*.fwpkg`）在板子上

### 第 2 步：释放串口

关掉所有 `serial-capture.ps1` / 串口工具窗口；确认没有进程占着 COM 口
（`Get-Process | Where-Object {$_.ProcessName -match 'powershell|putty|mobaxterm'}` 看有没有残留）。
源码也要干净：`git status --porcelain ws63-firmware/src/` 应为空。

### 第 3 步：收掉容器，别占内存

```bash
cd server && docker compose stop
```

**不要** `docker compose down -v`（会删库）；**不要**碰 `guanyin-*` 等别人的容器，也不要跑全局 `docker prune`。

## 8. 本单的边界（老实说在这）

1. **本单只覆盖 WS63 侧（2 块板 → 4 块板）与网关接线/配网的顺序**，不覆盖服务器与 App 的详细操作
   （那两块在 `docs/执行/演示环境搭建执行单.md` §2–§4）。
2. **没有实测过的部分**：① 4 块 WS63 同时在线（1 主 3 从）从未跑过——需要 4 块板；
   ② `LD6002C` 的**跌倒判定**本身未验证（只验证过数据链路）；③ 网关 `433` 遥控器输入（硬件几天后到）；
   ④ 网关 `SoftAP` 实际地址与 DHCP 池（CAL-12，需上板回填契约）。
3. **判据里的日志行全部取自源码字面量**（`node_main.c:147-150`、`hub_client.c` 的 `HUB_LOG` 串、`gw_main.c:1497`、`gw_prov.c:263`），
   不是手抄记忆；若你抓到的行与本文不一致，**以你抓到的为准并回传**，我来改。
4. 烧录/抓串口的两个坑（不带参数默认烧 COM14、不带 `-Reset` 抓到旧固件）各踩过一次，都写进 §0 第 3 步了；
   遇到没见过的现象，别连着试三次以上——把原始日志发回来。
