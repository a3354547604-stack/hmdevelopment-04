## 0. 一页速查：要做哪 7 件事、每件「看到什么算成」

| # | 做什么 | 在哪做 | 看到什么算成 |
|---|---|---|---|
| 1 | 建产品 | 控制台 →「产品」→「创建产品」 | 产品列表出现 `elderly-care-gateway`，协议 MQTT、数据格式 JSON |
| 2 | 建服务 + 属性 | 产品详情 →「自定义模型」→ 添加服务 →「新增属性」 | 服务 `gateway` 下有 14 个属性 |
| 3 | 建命令 | 同一个服务的「添加命令」 | 服务 `gateway` 下有 6 条命令（含 `set_threshold`） |
| 4 | 注册网关设备（**只 1 台**） | 「设备 > 所有设备」→「注册设备」 | 弹窗「设备-注册设备成功」，给出**设备ID**与**密钥**（只显示一次） |
| 5 | **厂商侧**写进网关 | 「总览」→「接入信息」取地址；串口 `gwkv set`（或页面「厂商维护」面板兜底） | 串口 `[kvcfg] OK：已写入 Flash KV 0x6FF000（256 字节，读回逐字节一致）` |
| 6 | 配数据转发 | 「规则 > 数据转发」→「创建规则」 | 规则状态「已启动」，连通性测试 200 |
| 7 | 三步验证 | 「设备 > 所有设备」→ 设备详情 | ①状态「在线」②属性/影子 60 s 刷新 ③命令下发回 `result_code:0` |

**这 7 件事全部由厂商侧完成，用户不参与、也不需要知道**。用户侧能看到的只有配网页状态卡里的
「云端服务：已配置 / 使用出厂配置」——**这是本单唯一的用户可见产出**；用户侧只看这一点，
不要把控制台截图、接入地址或设备密钥给到用户。

**关于事件（alert/sos/recover）**：控制台物模型里**不必**建事件（§3.3 解释为什么），但**转发规则能不能覆盖事件是另一回事**——见 §6.0 的红框，那是首日实测的重点。

## 0.1 术语最小集（看到不认识就回来查）

| 词 | 一句话 |
|---|---|
| IoTDA / 设备接入 | 华为云的物联网平台，本单要配的就是它 |
| 实例 | 你买的那个 IoTDA 服务实例；**必须先进实例**才能看到左侧菜单 |

| 消息跟踪 | 控制台的报文级日志页签，**排查一切问题的第一站** |
| 数据转发 / 规则 | 平台把设备数据推给我们服务器的功能（HTTP 推送） |

## 1. 进控制台、选实例、先把「消息跟踪」打开

**在哪点**
1. 浏览器打开华为云 → 搜「设备接入 IoTDA」→ 进产品页 → 点「控制台」（或直接开 `https://console.huaweicloud.com/iotdm/#/dm-portal/home`）。
2. **选择你的实例，单击实例卡片进入**。（这一步不做，左侧菜单里没有「产品 / 设备 / 规则」。）

**看到什么**：左侧出现「总览 / 产品 / 设备 / 规则 / 监控运维」等菜单。

**先做一件小事（后面全靠它）**：等 §4 注册完设备后，马上进
「设备 > 所有设备」→ 点设备 →「**消息跟踪**」页签 →「**启动消息跟踪**」，并把跟踪时长设长一点。
官方口径：**单个用户最多同时跟踪 10 台设备**；消息状态显示「失败」时可以点「**定位建议**」。

> 也可以顺手开「监控运维 > 运行日志 > 启动并配置」，它会自动建好日志组/日志流；日志在 LTS 里默认存 30 天，LTS 每月免费 500 MB。

**失败怎么办**：看不到实例卡片 → 账号没买/没进对区域（IoTDA 只在华北-北京四、华东-上海一、华南-广州等少数区域上线）。

| **协议类型** | **MQTT** | 契约 §4.1 行 560：MQTT 3.1.1 |

## 3. 建服务与物模型（字段严格对齐契约）

**入口**：左侧「产品」→ 点刚建的产品 → 产品详情「基本信息」页 → 点「**自定义模型**」。

> 官方在这两处给的命名建议（**服务ID首字母大写、属性驼峰、命令全大写下划线**）**本项目一律不采用**：
> 我们按契约用小写 `gateway` / `snake_case`。平台对大小写**敏感**，报文里的 `service_id`、属性名、命令名必须与契约逐字符一致，否则平台按「模型里没有」处理。

### 3.1 添加服务

「自定义模型」页 → 「**添加服务**」→ 填：

| 字段 | 填 |
|---|---|
| 服务ID | `gateway`（契约 §4.3 标题行 625、§4.1 行 573） |
| 服务类型 | `gateway`（官方建议与服务ID一致） |
| 服务描述 | 「网关聚合服务：属性/事件/命令」之类，随便写 |

点「确定」。**看到什么**：页面上出现一个服务卡片，标题是 `gateway`；**点它展开**，里面才会有「新增属性 / 添加命令」。

### 3.2 属性（14 项，逐项对齐契约 §4.3 行 627–642）

点开 `gateway` 服务 → 「**新增属性**」→ 弹窗里填「属性名称 / 数据类型 / 访问权限 / 取值范围 / 步长 / 单位」→ 逐条「确定」。

| # | 属性名称（必须逐字符一致） | 控制台「数据类型」选 | 取值范围 | 步长 | 单位 | 访问权限 | 契约行号 |
|---|---|---|---|---|---|---|---|
| 1 | `presence` | boolean | — | — | — | 可读 | 629 |
| 2 | `last_motion_ts` | long | 0 ~ 最大值 | 1 | Unix ms | 可读 | 630 |
| 3 | `door` | boolean | — | — | — | 可读 | 631 |
| 4 | `window` | boolean | — | — | — | 可读 | 632 |
| 5 | `temp` | decimal | −40.0 ~ 125.0 | 0.1 | °C | 可读 | 633 |
| 6 | `humi` | decimal | 0.0 ~ 100.0 | 0.1 | %RH | 可读 | 634 |
| 7 | `smoke` | int | 0 ~ 5000 | 1 | mV | 可读 | 635 |
| 8 | `lpg` | int | 0 ~ 5000 | 1 | mV | 可读 | 636 |
| 9 | `co` | int | 0 ~ 5000 | 1 | mV | 可读 | 637 |
| 10 | `nodes_online` | string | 最大长度填 256 | — | — | 可读 | 638 |
| 11 | `battery` | int | **0 ~ 255** | 1 | % | 可读 | 639 |
| 12 | `alarm_state` | int | 0 ~ 2 | 1 | — | 可读 | 640 |
| 13 | `bound_nodes` | string | 最大长度填 256 | — | — | 可读 | 641 |
| 14 | `pair_state` | string | 最大长度填 16 | — | — | 可读 | 642 |

**逐条「为什么这么填」**（这几处是最容易填错、填错就丢数据的地方）：

- **`battery` 范围必须到 255**：契约行 639 写明 `0–100，255=市电`。平台会按模型**过滤/丢弃**不符合定义的上报——范围只写到 100，网关报的 `255` 就可能没了。
- **`alarm_state` 选 `int`，不要选 `enum`**：契约行 640 的类型是 `int(enum)`、取值是**整数** `0/1/2`；控制台的 `enum` 类型要求的是**字符串枚举**（像 `OPEN,CLOSE`，上报 `"OPEN"`）。选 enum 会让「设备报 0、平台等 "0"」对不上。
- **`nodes_online` / `bound_nodes` 选 `string`，不要选 `jsonObject`**：契约行 638/641 的类型是 string、「JSON **文本**」，设备报的是**转义后的字符串**（`"{\"M1\":true}"`），不是 JSON 对象。选 jsonObject 同样会对不上。
- **`presence` / `last_motion_ts` / `lpg` / `co` 也一并建**：P0 现在不装这些传感器、报文里**直接省略这几个键**（契约行 699），省略是合法的；但先建好模型，等到 P1 装 PIR/MQ-5/MQ-7 时不用改产品。
- **访问权限统一「可读」**：属性是设备往上报。契约 §4.2 行 620 的 `properties/set`（平台改设备属性）是 **P1**，现在不用开「可写」。

> **平台会把不合模型的上报丢掉**（官方《设备数据上报》页原文：属性上报的数据「会通过定义的产品模型来校验、进行过滤，若上报的数据不符合产品模型定义，平台会丢弃该数据」）。
> 所以**属性名错一个字符 = 那条数据在平台侧直接消失**，而且设备侧看起来一切正常。

**看到什么**：`gateway` 服务下属性区列出 14 条，名称与上表逐字符一致。

**失败怎么办**：提示名称非法 → 属性名只允许字母数字下划线，且不能以数字开头；重名会被拒。

### 3.3 事件（alert / sos / recover）——**不用在物模型里建**

契约 §4.4（行 661–667）定义了三个事件：

| `event_type` | `paras` 字段 | 级别 | 契约行号 |
|---|---|---|---|
| `alert` | `type`(string)、`level`(int)、`node_sn`(string)、`ts`(int64)、`snapshot`(object, 可选)、`event_id`(string) | 1 或 2 | 663 |
| `sos` | `source`(string)、`ts`(int64)、`event_id`(string) | 2 | 664 |
| `recover` | `type`(string)、`node_sn`(string)、`ts`(int64)、`event_id`(string) | — | 665 |

`event_id` 格式 `{gateway_sn}-{type}-{ts}`（示例 `M0-3F1A2B-fall-1792243323000`，契约行 667）。**服务器按 `event_id` 幂等去重**。

**操作**：如果你的控制台在服务下有「**新增事件**」入口，就按上表建；
**如果找不到这个入口，跳过即可**——官方《在线开发产品模型》页只描述「属性」和「命令」两类（事件只在 Excel 导入模板里被提到过）。
网关是把事件发到 `$oc/devices/{device_id}/sys/events/up`（契约 §4.2 行 615），报文里自带 `event_type` + `paras`，**不依赖物模型里有没有声明事件**。

> 🚩 **但"能不能被转发"是另一回事，见 §6.0 的红框**（这是首日实测第一件事，标「待实测」）。

### 3.4 命令（6 条，逐项对齐契约 §4.5 行 673–678）

在 `gateway` 服务下点「**添加命令**」→ 填「命令名称」→ 用「**新增输入参数**」建下发参数 → 用「**新增响应参数**」建响应参数 → 「确定」。

> **命令名必须与固件里 `strcmp` 的字符串逐字符一致**（小写 + 下划线）。名字不匹配时，网关会按「未知命令」处理，回 `result_code=1`。

| 命令 | 下发参数（名称 / 类型 / 范围） | 响应参数（名称 / 类型） | 契约行号 |
|---|---|---|---|
| `set_report_interval` | `seconds` / int / 10–3600 | `result` string；`seconds` int | 673 |
| `demo_trigger` | `event` / string / 取值 `fall`、`gas`、`sos` | `result` string；`event` string | 674 |
| `mute_alarm` | `duration` / int / 1–3600 | `result` string；`duration` int | 675 |
| `pair_scan` | `duration_s` / int / 3–60（可缺省 15） | `result` string；`id` int；`duration_s` int；`estimate_s` int | 676 |
| `pair_bind` | `op` string（`add`/`del`/`clear`/`list`）；`sn` string；`mac` string | `result` string；`op` string；`bound` stringList；`slots_free` int | 677 |
| `set_threshold` | `cmd` string；`key` string；`value` int | `result` string；`key` string；`value` int | 678 |

**关于 `set_threshold` 的三点**（契约 §4.5 行 688–693，这是本单验证要用的命令）：

1. 真实报文长这样（契约行 678，**逐字抄**）：
   ```json
   {"cmd":"set_threshold","key":"gas_t1_mv","value":1500}
   ```
   响应应是 `{"result":"ok","key":"gas_t1_mv","value":1500}`。
2. `key` 的取值只有一份清单：契约 §6.9 的 `items` 键名（行 914–931），**不用口语别名**——
   口语的 `gas_l1`/`gas_l2`/`no_activity_min`/`offline_misses` 分别对应
   `gas_t1_mv`/`gas_t2_mv`/`no_motion_min`/`node_offline_timeout_s`（契约行 690）。
3. `value` 的真实类型是**逐键不同**的（契约行 691）：整数键（如 `gas_t1_mv`）、浮点键（如 `temp_high_c`）、
   还有一个**整型数组**键 `alert_repush_s`。控制台一条命令只能给 `value` 定**一种**类型，
   所以：**建模型时 `value` 选 `int`**，够跑 P0 演示（`gas_t1_mv` 就是整数）；
   要演示浮点键/数组键时不要用控制台表单，改走服务器 API 下发（`real` 模式直接构造 paras，不经过这张表单）。
   **这条标「待实测」**：控制台不同版本的表单严格程度不一样，第一次下发时留意一下报错文案。

**命令响应体**（契约行 680–686）：网关回的是
```json
{"result_code":0,"response_name":"COMMAND_RESPONSE","paras":{"result":"ok","key":"gas_t1_mv","value":1500}}
```
**失败时 `paras` 一定是空对象 `{}`**（契约行 686）——在控制台看到「`result_code` 非 0 + `paras` 是 `{}`」是**正确行为**，不是 bug。
`result_code` 含义：`0` 成功 / `1` 未知键或不支持 / `2` 参数越界 / `3` 忙 / `7` 内部错误 / `12` 三次重发无 ACK（契约行 692）。

**看到什么**：`gateway` 服务下能看到 6 条命令，点进去能看到各自的输入/输出参数。

## 4. 注册网关设备：拿 `<device_id>` + `<secret>`

**在哪点**：左侧「**设备 > 所有设备**」→ 页面右上/左上「**注册设备**」→ 填完点「**确定**」。

**填什么**

| 界面字段 | 填 | 为什么 |
|---|---|---|
| 所属资源空间 | 与产品同一个 | 不同资源空间选不到刚建的产品 |
| **所属产品** | `elderly-care-gateway` | 必须先建产品，这里才可选 |
| **设备标识码**（node_id） | `<gateway_sn>`（形如 `M0-XXXXXX`；官方要求 **4–64 个字符**，只允许字母、数字、`_`、`-`） | ⬇️ 见下面「为什么这条最关键」 |
| **设备ID** | 建议**留空**：平台按 `产品ID_设备标识码` 生成 | 留空最不容易写错；填了也合法，但要记住整串 |
| 设备名称 | 随便填，例如 `网关M0` | 只是给人看的 |
| 设备描述 | 可留空 | — |
| **设备认证类型** | **密钥** | 一机一密（X.509 证书是另一条路，P0 不用） |
| **密钥** | 留空让平台生成，或自己填 32 位 hex | ⚠️ 生成/填写后**只显示这一次** |
| 指纹 | 不出现（只有 X.509 才有） | — |

**为什么「设备标识码」这条最关键**：
我们服务器的 webhook 拿到报文后，先用 `header.device_id` 去查 `devices.iotda_device_id`；
查不到就**回落到用 `header.node_id` 按 `devices.sn` 匹配**（`server/app/services/telemetry.py:48-64`）。
P0 的 `devices.iotda_device_id` 还是 NULL，**实际走的就是这条回落路**。
所以：**设备标识码必须填成网关 SN，且和服务器的 `devices.sn` 完全一致**，否则服务器会回
`{"handled":0,...,"warnings":["device_not_found"]}`（报文进来了，但匹配不到设备）。

**看到什么**：页面弹出「**设备-注册设备成功**」，里面有**设备ID**和**密钥**；设备列表里这台设备状态是「**未激活**」。

**马上做两件事**：
1. 把**设备ID**整串复制出来（这就是 `<device_id>`），把**密钥**复制出来（这就是 `<secret>`）——**关掉弹窗就再也看不到密钥了**。
2. 回到 §1 打开「消息跟踪」。

**失败怎么办**：密钥丢了 → 只能「重置密钥」，**无法找回**；重置后必须重新烧写/写入网关凭证。

## 5. 设备侧怎么拼：ClientId / UserName / Password

> 这一节讲「网关（设备侧）拿 `<device_id>` + `<secret>` + 当前 UTC 时间，拼出什么样的登录参数」。
> **网关固件已经实现了这套拼法**；你在这里只需要核对「控制台给的三个值」和「拼出来的串对不对」。

### 5.1 接入地址从哪抄（第 4 个值，**厂商运维取**）

**在哪点**：左侧「**总览**」→ 在实例基本信息里点「**接入信息**」→ 找到 MQTT 的**接入地址**（域名）。

**看到什么**：形如 `<实例ID>.iot-mqtts.cn-north-4.myhuaweicloud.com`，端口 **1883**（明文）。

> 平台给的是**域名**；如果哪里必须用 IP，可以 `ping` 这个域名拿到 IP，但**IP 不固定**，要做成可配置项。
> 本项目里两个「填地址的地方」口径不同，别填反：
> - **MQTT 接入地址（`gwkv set host=`）填域名还是 IP：以串口实测为准**——网关 MQTT 走 paho 的
>   `NetworkConnect(&cl->net, cl->host, cl->port)`（`rk2206-gateway/src/gw_cloud.c:94`），
>   **该移植实现在 SDK 侧、不在本仓库**（全仓检索 `LWIP_DNS` / `getaddrinfo` 均 0 命中），
>   所以「能不能解析域名」从代码里确认不了；`rk2206-gateway/src/gw_config.h:84` 的默认值给的是 **IP**（占位 `117.78.16.25`）。
>   做法：**先填域名**试；串口若出现 `[gw] TCP 连接 <host>:1883 失败`（`gw_cloud.c:96` 的格式串）就改填 `ping` 出来的 IP。
> - **取时服务器地址（`gwkv set time=`）只能填 IP**——`rk2206-gateway/src/gw_timesync.c:36` / `:157` 用 `inet_addr` 解析
>   （**这条是仓库内可查的硬事实**），填域名会直接取时失败，而取时失败就不连 IoTDA（§8.3）。

### 5.2 拼法（契约 §4.1 行 568–570；网关实现 `rk2206-gateway/src/gw_iotda.c:145-177`）

| 参数 | 拼法 | 例子（用契约 §4.1 的**假值**向量，行 595–606） |
|---|---|---|
| **ClientId** | `<device_id>_0_1_<UTC YYYYMMDDHH>` | `6a1b2c3d4e5f_0_1_2025100908` |
| **UserName** | `<device_id>` | `6a1b2c3d4e5f` |
| **Password** | HMACSHA256 的 64 位小写十六进制（方向见 §5.3） | `01fd521b866bb80c2d7d662c3ccb971edd0a62a4f4f3ce04305806649808f29a` |

- **ClientId 4 段的含义**（官方《连接鉴权》原文）：设备ID / 设备身份标识类型（**固定 `0`**）/ 密码签名类型
  （`0`=不校验时间戳，`1`=校验时间戳，**本项目取 `1`**）/ 时间戳（**UTC**，格式 `YYYYMMDDHH`）。
- **时间戳只取一次**：ClientId 第 4 段与 Password 用的必须是**同一个值**（契约行 570、580；实现注释在 `gw_iotda.c:162`）。
  跨小时边界时不要各取一次。
- **`<device_id>` 就是你在 §4 拿到的整串**（可能自带下划线，如 `产品ID_设备标识码`，这是正常的，平台从右边拆最后 3 段）。

### 5.3 ⚠️ Password 的 HMAC 方向：**契约/固件与官方文档相反，必须两套都算**

这是本单最需要你留意的一处。两边说法如下（都已逐字核对）：

| 口径 | 谁 | 算法方向 | 用它算官方那个例子（secret=`12345678`、时间戳=`2025041401`） |
|---|---|---|---|
| **仓库口径** | 契约 §4.1 行 570/600（`secret` 作 HMAC **key**）；固件 `rk2206-gateway/src/gw_crypto.c:177-184`（`gw_hmac_sha256(secret, …, ts, …)`） | key=`<secret>`，消息=时间戳 | `75e7262705ff85203403e600f652133f9cac4e4d1400b44f3582e778a97f6c36` |
| **官方口径** | 华为云《连接鉴权》原文「以时间戳为密钥，对 secret 进行加密」；官方举例；官方「参数生成工具」源码 `CryptoJS.HmacSHA256(deviceSecret, timestamp)`（CryptoJS 第一个参数是 message） | key=时间戳，消息=`<secret>` | `c75150e6cb841417396819e4d2ee4358a416344a03a083e3a8567074ddec820a`（**与官方举例逐字符一致**） |

**结论**：官方三处证据**互相一致**（原文措辞 + 举例数值 + 官方工具源码），指向「key=时间戳、消息=secret」；
仓库契约与固件用的是**反方向**，两者算出的 64 位 hex **完全不同**。

**怎么用这条避免踩坑**：
1. 先按 **仓库口径**（key=secret）跑——固件就是这么实现的；
2. 如果串口出现 `[gw] MQTTConnect 失败 rc=4`（= 0x04 用户名或密码错误），
   而「取时链」和「设备ID」都已经排除（见 §8.2 的定位顺序），**第一个要试的就是把方向换过来**；
3. **换方向不用动板子**：用电脑上的 MQTT 客户端（或官方「参数生成工具」）按两种方向各算一次，
   哪个能连上，就以哪个为准（这能把「平台口径」和「固件实现」彻底分开验证）。

> 如实说明：「仓库口径 vs 官方口径」这条**尚未在真机上验证过**（P0 还没有一台设备真正连过云）。
> 首日联调必须先做这次对拍，结论回传；若确认官方方向才对，固件要改的就是 `gw_crypto.c:177-184` 那一处参数顺序（一行）。

## 6. 数据转发到我们服务器（webhook）

### 6.0 🚩 先看这个红框：转发的「数据来源」里**没有**「设备事件」

契约 §5.1（行 755）要求转发三个资源：`device.property`（属性上报）、`device.event`（事件）、`device.message`（消息）。
但官方控制台《使用 HTTP/HTTPS 转发》页（2026-10-10 版）列出的「**数据来源**」只有这 9 项：

> 设备 / 设备属性 / 设备消息 / 设备消息状态 / 设备状态 / 批量任务 / 产品 / 设备异步命令状态 / 运行日志

而规则引擎的 API 资源枚举（《创建规则触发条件》`CreateRoutingRule`，`api-iothub/iot_06_v5_01307.html`）**只有 8 项**：
`device`、`device.property`、`device.message`、`device.message.status`、`device.status`、`batchtask`、`product`、`device.command.status`
——**没有 `device.event`**。它对应的 `event` 映射也只有：
`device:create/delete/update`、`device.status:update`、`device.property:report`、`device.message:report`、
`device.message.status:update`、`batchtask:update`、`product:update`、`device.command.status:update`。

**这意味着：告警事件（§3.3）很可能没法像属性那样"选一个数据来源"就转发出去。**
这属于**首日实测必须确认的第一件事**（和仓库里既有的 CAL-04 是同一类问题），处置办法：

1. **先按能点的配**：属性 + 消息两条规则照 §6.1 配好，P0 的「属性 60 s 刷新」「命令下发」不受影响；
2. **事件单独试**：把「数据来源」选「**设备消息**」，「快速配置」里填 Topic
   `$oc/devices/{device_id}/sys/events/up`（官方允许在快速配置里指定 Topic 名称），然后看设备报事件时
   规则有没有推送、服务器 `webhook_last_at` 有没有更新。
   ⚠️ 这条有个前提：官方 API 示例里「按 topic 筛选」是**用 SQL 的 `where` 实现的，而基础版不支持 SQL 筛选**
   ——所以**基础版实例可能连这个替代办法都用不了**。先看你的实例是标准版还是基础版；
3. **如果转不出来**，把现象（截图 + 服务器日志）回传 PM 裁决——要么让汇聚把告警也塞进
   `messages/up`（走已通的 `device.message` 通道），要么由服务器改口径。**不要自己改契约**。

### 6.1 形态①：服务器有公网 IP / 域名（正式做法）

**前置（先自己确认，别到平台上报错再回头查）**：
- 服务器上 `curl -s http://<server_host>/api/health` 返回 200；
- `server/.env` 里 `WEBHOOK_TOKEN` 已换成随机值（`openssl rand -hex 32`）；
- 回调地址固定为：`http(s)://<server_host>/api/iotda/webhook?token=<WEBHOOK_TOKEN>`

（更完整的部署前置见 `server/deploy/IoTDA回调前置清单.md` §1。）

**在哪点**：左侧「**规则 > 数据转发**」→ 页面左上「**创建规则**」→ 填完点「**创建规则**」→ 再进「**设置转发目标**」页签。

**填什么（第 1 页）**

| 界面字段 | 填 | 说明 |
|---|---|---|
| 规则名称 | `eldercare-props`（另起 `eldercare-msgs` 见下） | — |
| 规则描述 | 随便 | — |
| **数据来源** | **设备属性** | 对应契约的 `device.property`（行 755） |
| 触发事件 | 选「**属性上报**」 | 与上联动 |
| 资源空间 | 选你建产品的那个 | 选「所有资源空间」时不支持快速配置 |
| **SQL语句** | **不加过滤**（首版口径，契约行 760） | 标准版/企业版才支持编辑 SQL；基础版直接用「快速配置」；配置前先点「快速配置」勾上你的**产品 + 属性** |

> 契约行 755 还要 `device.message`（节点明细，300 s 批量）。**再建一条规则**：「数据来源」=**设备消息**，
> 快速配置里选「所属产品」+ 填 Topic `$oc/devices/{device_id}/sys/messages/up`。
> （事件那条见 §6.0 红框。）

**填什么（第 2 页「设置转发目标」）**

| 界面字段 | 填 |
|---|---|
| 转发目标 | **第三方应用服务（HTTP推送）** |
| **推送URL** | `http://<server_host>/api/iotda/webhook?token=<WEBHOOK_TOKEN>` |
| **Token**（这一栏是平台的，不是我们的） | 填一个 3–32 位英文或数字的串，例如 `gatewaypush01` |
| 证书ID / 证书域名 | 留空（HTTP 不需要 CA 证书） |

**两个最容易搞混的点，必须记住**：

1. **平台弹窗里那个「Token」字段 ≠ 我们的 `?token=`**。
   平台那个是平台自己用来做签名头域（`timestamp`/`nonce`/`signature`）的密钥，**我们的服务器根本不看它**；
   我们的口令写在 **URL 的 `?token=`** 里（服务器只做这一件事的校验：`app/routers/webhook.py:25-29`）。
   所以：**URL 里的 token 必须是 `WEBHOOK_TOKEN` 的真实值**，弹窗里的 Token 随便填 3–32 位英文数字即可。
   （官方文档把「Token」写成认证签名用，很容易让人以为要两边填一样——不是。）
2. **不要配自定义 Header**。契约 §5.1 行 758 与服务器实现都只认 URL 查询串。

**最后一步**：规则详情页点「**启动规则**」。**不点这一下，规则存在但不生效。**

**看到什么**：规则列表里该规则状态是「**已启动**」。

**失败怎么办**：
- 保存报「URL 长度超限」→ 官方须知原文是「推送URL …若使用域名，请确保其长度不超过 64 位，否则将配置失败」。
  我们的 URL 里带着 64 位 token，用**长域名**时容易踩这条；先改用**公网 IP**形式试，或换短域名。
- 用 HTTPS → 需要先在「设备 > 设备证书 > CA证书」上传 CA 证书；HTTP 不需要。

### 6.2 形态②：本机联调、服务器没有公网 IP（先用这个跑通）

演示/联调阶段服务器跑在你自己电脑或内网机器上，公网访问不进来。两种做法，选一个：

**做法 A：内网穿透（要「App 端能看到数据/告警」时必须用这条）**
1. 在本机把服务起起来，确认 `curl -s http://127.0.0.1:<API端口>/api/health` 返回 200；
2. 用任意隧道工具（cpolar / ngrok / frp / natapp 之类）把该端口映射到一个公网 URL；
3. 得到形如 `https://xxxxxxxx.ngrok-free.app` 的公网地址后，
   把 §6.1 的推送 URL 换成 `https://<隧道域名>/api/iotda/webhook?token=<WEBHOOK_TOKEN>`；
4. 用浏览器从**外网/手机热点**打开 `https://<隧道域名>/api/health`，通了再回控制台保存规则。

> ⚠️ 仓库里**没有**现成的隧道脚本（全仓检索无 ngrok/frp/cpolar 相关内容），所以这条**标「待实测」**。
> 两个坑先记住：① 隧道域名普遍较长，可能触发 64 位限制（见 §6.1 失败怎么办）；
> ② 隧道给的是 HTTPS，而 HTTPS 需要在平台侧上传 CA 证书——**优先选能提供 http 地址的隧道**。

**做法 B：先不转发，只在控制台观察（推荐先用它把 §7 前两步跑通）**
不建规则（或建了不启动），设备照常上报，你在控制台里用「**设备影子**」「**消息跟踪**」「**物模型数据**」看数据。
这条不需要任何公网，能先证明「产品/设备/物模型/鉴权/上报」四件事都对。
服务器侧的实现则用 §6.4 的 `curl` 手工喂一条报文来验证（不需要平台参与）。

**什么时候必须切到 A**：要在 App 上看到实时数据、要把告警入库、要演示「事件 → 告警」全链路时。

### 6.3 在控制台哪里看「已转发 / 被拒」

| 想看什么 | 在哪点 | 看到什么 |
|---|---|---|
| 规则有没有在推数据、有没有积压 | 「规则 > 数据转发」→ 点规则「**详情**」→「**设置转发目标**」页签 → 点该转发通道的「**详情**」 | 弹窗里三个数：**消息推送速率 / 消息生产速率 / 消息积压量**；弹窗里还有「**清空积压消息**」 |
| 目标服务器能不能通（**不需要真机**） | 转发目标列表里点「**测试**」→「测试数据」页签 →（可点「模拟输入模板」）→「**连通性测试**」 | 测试结果（能连到我们的 `/api/iotda/webhook` 即说明网络与 URL 都对） |
| 单台设备的报文级「已发/被拒」 | 「设备 > 所有设备」→ 找到设备 →「详情」→「**消息跟踪**」页签 →「启动消息跟踪」 | 按「消息状态 / 业务类型 / 记录时间」过滤；状态是「失败」时点「**定位建议**」，点「详情」看原文；可「导出数据」 |
| 平台侧全量日志 | 「监控运维 > **运行日志**」→「启动并配置」 | 按日志类型（device.property / device.message / device.command / device.status…）、设备ID、时间搜索 |
| **服务器到底收到没有** | 服务器上 `curl -s http://127.0.0.1:3000/api/health` | `data.webhook_last_at` **出现**（非空）= 有回调进来**且匹配到了设备**；一直不出现 = 没进来，或进来了没匹配上设备 |

> **平台推送的成败判定**（官方原文，决定了你会不会被"静默丢数据"）：应用服务器返回 **200 OK** 才算成功；
> 无响应 / 超时 **15 s** / 返回非 200（500–504）→ 推送失败、**该条消息被丢弃**；
> **连续累计失败 10 次** → 平台把该 URL 的**主机地址加入黑名单**（黑名单期间消息积压，默认最近 24 小时或 1 GB），
> 之后**每 3 分钟**试一次，成功才解除。
> **所以我们服务器对不认识的报文一律回 200**（契约 §5.2 行 773）——避免把平台拖进黑名单。

### 6.4 服务器侧自测（不依赖平台）

**在哪做**：服务器上（或能访问它的机器上）执行；把 token 换成真实值。

```bash
curl -s -X POST "http://<server_host>/api/iotda/webhook?token=<WEBHOOK_TOKEN>" \
  -H 'Content-Type: application/json' \
  -d '{"resource":"device.property","notify_data":{"header":{"device_id":"<device_id>","node_id":"<gateway_sn>"},"body":{"services":[{"service_id":"gateway","properties":{"temp":24.5}}]}}}'
```

**看到什么（三种，含义完全不同）**：

| 返回 | 含义 | 下一步 |
|---|---|---|
| `{"code":0,...,"data":{"handled":N,"device_id":<id>,"sn":"<gateway_sn>"}}` | 报文进了、也匹配到设备了 | 正常 |
| `{"code":0,...,"data":{"handled":0,..."warnings":["device_not_found"]}}` | 报文进来了，但**没匹配到设备** | 核对注册时的**设备标识码**是否等于 `devices.sn` |
| HTTP 401 / `{"code":1502,...}` | **token 不对** | 核对 `.env` 的 `WEBHOOK_TOKEN` 与 URL 里的值（注意别带引号/空格） |

另外记住：**只接受 POST**（用 GET 打会 405）；请求体 ≤256 KB。

## 7. 三步验证（每步都有「可判定的期望原文」）

> 前置：设备已按 §5.5 写好凭证并复位；串口已挂上（115200 8-N-1）。
> 全程把「消息跟踪」开着。

### 第一步：设备在线

**在哪看**：「设备 > 所有设备」→ 找那台设备 → 看「**状态**」列。
MQTT 长连接设备只有四种状态（官方《管理设备》页原文）：`在线` / `离线` / `未激活` / `冻结`；
**刚注册完、还没连过是「未激活」**。两条容易误判的规则：
- **断线不会立刻变「离线」**：长连接断开后要**过 1 分钟**（平台数据刷新周期）才置为离线，手动刷新界面则立即显示；
- 没有「异常」这个状态（那是短连接 NB-IoT 才有），**看不到「异常」不是问题**。

**期望（可判定）**：
- 控制台：状态列显示「**在线**」；
- 设备详情 →「**设备影子**」页签 →「**上报值**」区有内容（设备上报属性后会刷新）；
- 串口出现：
  ```
  [gw] IoTDA 已连接 clientId=<device_id>_0_1_<UTC YYYYMMDDHH>
  ```

**不过怎么办**：
- 状态一直「未激活」= 设备从没连上过 → 走 §8.1/§8.2 的认证排查；
- 串口出现 `[gw] 未校时，拒绝连接 IoTDA` → 走 §8.3 的取时链；
- 串口出现 `[gw] 取时失败：服务器与 NTP 都不可达，暂不连 IoTDA` → 同上。

### 第二步：属性刷新（60 s 一条）

**在哪看**（三处任选，建议都看一眼）：
1. 「设备 > 所有设备」→ 设备「详情」→「**设备影子**」页签 →「**上报值**」（官方口径：设备上报属性时刷新）；
2. 「设备 > 所有设备」→ 设备「详情」→ **物模型数据**（官方原文：「查看最近一次设备上报到平台的数据」）；
3. 消息跟踪页签里按业务类型 `device.property` 过滤。

**期望（可判定）**：
- 每 **60 秒** 刷新一次（契约 §4.3 行 627–642 的上报列全是「60 s」；§4.8 行 735–745 的预算也是按 60 s 算的）；
- 看到的是**契约 §4.6 行 704 那条报文的字段**：
  ```json
  {"services":[{"service_id":"gateway","event_time":"20261017T120000Z","properties":{"door":false,"window":false,"temp":24.5,"humi":56.2,"smoke":320,"nodes_online":"{\"M1\":true,\"M2\":true,\"M4\":false}","battery":255,"alarm_state":0}}]}
  ```
  （`presence`/`last_motion_ts`/`lpg`/`co` **不会出现**——P0 未装，契约行 699 要求"直接省略该属性"。）

**不过怎么办**：
- **先等满 70 秒**：属性是 60 s 节拍，刚上线不会立刻有一条；
- ⚠️ **属性上报成功时串口没有专门一行日志**（设计如此，防刷屏）——串口安静不代表没上报，**以控制台为准**；
- 控制台一直空：对照 §3.2 逐字核对属性名/类型（模型对不上，平台**丢弃**该数据），并确认上报的 topic 是
  `$oc/devices/{device_id}/sys/properties/report`（契约 §4.2 行 614）。

### 第三步：命令下发（用契约 §4.5 的真实 payload：`set_threshold`）

**在哪点**：「设备 > 所有设备」→ 点设备 →「**云端下发**」页签（官方原文：控制台上可创建单个设备的**命令下发**与消息下发，
**仅 MQTT 设备支持**）→ 选「命令下发」→ 填：

| 项 | 填 |
|---|---|
| 服务 | `gateway` |
| 命令 | `set_threshold` |
| 参数（逐字抄契约行 678） | `{"cmd":"set_threshold","key":"gas_t1_mv","value":1500}` |

点「下发」。

**期望（可判定，三处同时成立）**：
1. 控制台显示**命令响应**：
   ```json
   {"result_code":0,"response_name":"COMMAND_RESPONSE","paras":{"result":"ok","key":"gas_t1_mv","value":1500}}
   ```
2. 串口出现（`gw_main.c:1441` 的格式串）：
   ```
   [gw] 命令响应 set_threshold(<request_id>) result=0
   ```
   并伴随生效日志：
   ```
   [gw] set_threshold gas_t1_mv 生效并已下发（SEQ=<n>）：{"cmd":"set_threshold","key":"gas_t1_mv","value":1500}
   ```
3. 消息跟踪里能看到 `device.command` 的下发与响应两条。

**判定的注意点**：
- MQTT 设备**只支持同步命令下发**，**平台等响应最多 20 秒**（契约 §4.5 行 695 也按 20 s 设计）；超时就算失败。
- 看到 `result_code` 非 0 且 `paras` 是 `{}` —— 这是契约要求的**正确**失败形状（行 686），
  按 `result_code` 对因：`1` 未知键/不支持、`2` 参数越界、`7` 内部错误、`12` 三次重发无 ACK（行 692）。
- 想让串口更"热闹"一点看全链路，可加一条（可选）：`demo_trigger` + `{"event":"fall"}`，
  期望串口 `[gw] 事件 M0-…-fall-… type=fall level=2`（命令 demo_trigger 契约行 674）。

**替代入口**（不占用设备、只做界面演练时用）：产品详情 →「**在线调测**」→「新增测试设备」→ 选「真实设备」→
填参数 → 确定 →「调试」→ 顶部设备状态显示「在线」→ 左侧「**应用模拟器**」的「命令下发」页签 → 选服务/命令 → 发送
→ 右侧应用模拟器展示区能看到**下发的命令与收到的命令响应**。
（注意：**仅基础版和标准版支持 MQTT 协议的在线调试**；新加的真实设备**未激活前不能调试**。）

## 8. 常见坑（按现象查）

### 8.1 认证失败 `0x02`：无效客户端标识符

**平台返回码定义**：`0x02` = **无效客户端标识符**（clientId 不符合格式 **或心跳间隔不满足平台要求**）。
`0x04` = 用户名或密码错误。

**成因（逐条对）**：
1. **ClientId 段数/内容不对**：必须是 `<device_id>_0_1_<UTC YYYYMMDDHH>`；
   `S=1` 表示平台**校验时间戳**；第 2 段固定 `0`。
2. **`<device_id>` 写错**：用了 SN（或自己拼的串）而不是平台给的**字符串设备ID**（契约 §4.2 行 623 明确"不是 SN"）。
3. **心跳不在 30–1200 s**：例如 `keepAlive=0` 或 1800，平台会按 `0x02` 拒绝——**本项目固定 120**（契约行 562）。
4. **时间戳与平台时间差太多**（S=1 会先校验时间戳再判密码）：见 §8.3。

### 8.2 认证失败 `0x04`：用户名或密码错误

**成因**：
1. **HMAC 方向反了**（§5.3 的仓库口径 vs 官方口径）；
2. **密钥抄错**：多了空格/换行、复制时少了字符、**密钥被重置过**（重置后板子里还是旧密钥）；
3. **时间戳两处不一致**：ClientId 第 4 段与 Password 用了两个不同的值（尤其跨小时边界）；
4. **时间不对**：设备时间与平台差太多。

**定位顺序（照着走，别跳步）**——**先取时链，再认证**：

1. **先看取时链有没有过**（前置条件，没过就别查密码）：
   串口有没有 `[gw] 取时成功(HTTP) epoch=…` 或 `[gw] 取时成功(NTP) epoch=…`？
   没有 → 走 §8.3。
2. **再核 ClientId 四段**：把串口打印的 `clientId=…` 抄下来，逐段对：
   第 1 段 = 控制台设备列表里那台设备的**设备ID**（整串）；第 2 段 `0`；第 3 段 `1`；第 4 段 = **当前 UTC 小时**。
   （只看 4 段格式 → 出 `0x02`；能到密码校验才谈 `0x04`。）
3. **再核密钥**：`gwkv show` 看密钥指纹与写入时的指纹是否一致；不一致就重写凭证。
4. **最后还是 `0x04`** → 换 HMAC 方向重算（§5.3）。**这一步用电脑上的 MQTT 客户端做，不要动板子**。

> 串口的 `[gw] MQTTConnect 失败 rc=4（2/4 常因 ClientId 或 HMAC 时间戳，1 是版本）` 这一行里，
> `rc` 就是平台的返回码（4 = 0x04）。

### 8.3 时间戳不同步 / 取时链（**这是前置条件，不是可选项**）

**契约的硬性顺序**（§4.1.1 行 582–593）：**网关先取到可信 UTC，再连 IoTDA**。顺序是：

| 步 | 动作 | 超时 | 失败时 |
|---|---|---|---|
| 1 | 联网后**先**调我们服务器的 `GET /api/time`（契约 §6.21 行 1082–1101，**免鉴权**、`Cache-Control: no-store`） | ≤3 s | → 步 2 |
| 2 | SNTP/NTP（`pool.ntp.org` 或局域网 NTP） | ≤5 s | → 步 3 |
| 3 | 「上次成功值 + 开机时长」（存 Flash，掉电不丢） | — | 无历史值 → 步 4 |
| 4 | 三者都不可用：**不连 IoTDA**，每 60 s 重试；`/api/health.clock_source` 必须是 `server`；**不得用自开机毫秒数拼 ClientId** | — | — |
| 5 | 取时成功：`clock_source = device`；偏差按 **±10 min** 容差，超了必须重取 | — | — |
| 6 | 同一个时刻用于 ClientId 第 4 段与 Password；**跨小时边界不要各取一次** | — | — |

**操作要点**：
- 服务器那台机器**必须与 NTP 同步**（`chrony`/`systemd-timesyncd`/`ntpd` 任一）——`/api/time` 只是把服务器时间转发给网关，不修正它。
  **服务器时钟本来就错 → 网关取到的也是错时间 → 0x02/0x04**（这类"环境坑"仓库里踩过，先排环境再判实现）。
- `gwkv set` 里的 `time=` **只能填 IP**（固件用 `inet_addr` 解析，不支持域名），填域名会直接取时失败。
- 串口判据（逐字）：
  - 成功：`[gw] 取时成功(HTTP) epoch=…` 或 `[gw] 取时成功(NTP) epoch=…`
  - 未校时被拦：`[gw] 未校时，拒绝连接 IoTDA`
  - 全失败：`[gw] 取时失败：服务器与 NTP 都不可达，暂不连 IoTDA`

### 8.4 其它高频坑（一条一句）

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 连上了、控制台也能看到设备，但收不到数据 | 用了 **QoS2** | 换 **QoS1**。平台**不支持 QoS2**（契约行 563；仓库里的 `d1_iot_mqtt` 样例就是 QoS2 + keepAlive=0 被拒） |
| 设了遗嘱/保留消息后行为诡异 | 平台**不支持 will/retain** | 一律不设（契约行 564） |
| 同时开两个客户端（MQTT.fx + 板子）后互相踢掉 | **单设备并发连接=1** | 同一设备ID 同时只留一条连接（契约行 565） |
| 属性在控制台"消失"了 | 模型没建 / 属性名大小写不一致 / 类型对不上 / 取值范围不符 | 按 §3.2 逐字核对；记住平台会**丢弃**不合模型的上报 |
| 事件（alert/sos）**转不到服务器** | 规则引擎没有 `device.event` 这个数据来源（§6.0） | 先用「消息跟踪」确认事件确实上行了（说明设备侧没问题），再按 §6.0 第 3 条回传 PM 裁决 |
| 事件（alert/sos）在控制台「消息跟踪」里也看不到 | 物模型没声明事件 / 事件 topic 拼错 | 先确认 topic 是 `$oc/devices/{device_id}/sys/events/up`（契约 §4.2 行 615） |
| 命令下发控制台报"下发失败" | MQTT 只支持**同步**命令，且要求设备 **20 s 内**回响应 | 看串口有没有 `[gw] 命令响应 …`；没回就是设备侧没收到或没订阅 `.../sys/commands/#` |
| 规则配好了但没有推送 | **没点「启动规则」** / URL 或 token 不准 / 平台已进黑名单 | 看 §6.3 的「通道详情」与「消息跟踪」；黑名单要等 3 分钟一次的重试 |
| 服务器返回非 200 | 服务器崩了或 token 校验失败 | 服务器对无法识别的报文一律回 200（契约行 773）；`1502/401` 就是 token 不对 |
