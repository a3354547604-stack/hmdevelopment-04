## 0. 通用约定

### 0.1 命名与大小写

- **设备编号 `sn`**：大写字母 + 数字，见 §0.7。JSON 里字段名一律 `snake_case`（小写+下划线）；`type` 取值小写单词；MQTT topic 全小写（IoTDA 规定的 `$oc/` 前缀除外）。
- **服务器侧主键 `device_id`**：MySQL `BIGINT` 自增；**不要**和 IoTDA 的 `device_id`（字符串，平台生成）混用。前者命名 `device_id`，后者命名 `iotda_device_id`。
- 数值字段禁止用字符串传数字（`"320"` ✗，`320` ✓）。

### 0.2 时间

- 南向 JSON 与 REST API：时间戳字段统一命名 `ts`，类型 **int64**，单位 **Unix 毫秒（UTC）**。示例 `1792243200000` = **2026-10-17T13:20:00Z**（= UTC+8 的 `2026-10-17 21:20:00`，仍是**同一个 UTC+8 日历日**，所以报表 `daily[].date` / `activity_daily.date` 都还是 `"2026-10-17"`；v1.2 起全文样例时间戳统一到 2026-10-17，见 §14）。
- MySQL：业务时间列为 `DATETIME(3)`（UTC，连接必须 `SET time_zone='+00:00'`），另有 `*_ms BIGINT` 冗余列供精确比对。
- 报表的「日/小时」一律按 **Asia/Shanghai（UTC+8）日历**切分（切分口径与表结构见 §7.9/§7.10；原始读数表见 §7.6）。
- IoTDA 报文的 `event_time` 是唯一例外，用平台格式，见 §4.6。
- 时钟来源：节点/汇聚无 RTC，开机后以「首次上电 → 汇聚轮询应答」由网关下发一次基准时间（P1，见 §3.4 `0x13`）。网关自己的取时流程见 **§4.1.1「取时与降级」**（`GET /api/time` → SNTP → 上次成功值 + 开机时长）；**降级期间允许 `ts` 为设备侧自开机毫秒数**，服务器按收到时刻纠正——该降级必须在 `/api/health.clock_source` 里暴露（取值 `device`/`server`，见 §6.20）。

### 0.3 单位与精度

| 量 | 单位 | 类型 | 精度/范围 | 示例 |
|---|---|---|---|---|
| 气体（烟雾/可燃气/CO） | mV（**已折算回传感器 AO 侧**，0–5000） | int | 1 mV | `320` |
| 温度 | °C | double | 0.1，−40.0–125.0 | `24.5` |
| 湿度 | %RH | double | 0.1，0.0–100.0 | `56.2` |
| 时间戳 | Unix ms | int64 | ≥0 | `1792243200000` |
| 持续时长 / 周期 | 秒 | int | 1–86400 | `1800` |
| 距离 | m | double | 0.1–10.0 | `2.4` |
| 电平 | 0/1 或 bool | — | — | `true` |
| 序号 | — | int | 0–65535（uint16，回绕） | `65535` |

### 0.4 布尔与空值

- JSON 布尔用 `true` / `false`，**禁止** `0`/`1`。数据库存 `TINYINT(1)` 的 0/1。
- 「无值」：JSON 字段**缺省即无值**，不要写 `null` 占位（`payload` 内必填字段除外，见各 type 表）。数据库列允许 `NULL` 时语义见列说明。

### 0.5 编码与前向兼容

- 文本一律 **UTF-8 无 BOM**；JSON 不允许注释、尾随逗号、`NaN`/`Infinity`。
- **接收方必须忽略未知字段**（前向兼容）；**新增必填字段 = 破坏性变更**，必须走 PM。
- 枚举遇到未知值：设备侧按「最保守」处理（如未知 type 丢弃并计数）；服务器侧存原值 + 记 WARN，不拒绝整条报文。

### 0.6 协议版本

每个链路都有 `ver`/版本标识：SLE JSON 用信封可选字段 `fw`；UART 帧用第 3 字节 `VER=0x01`；REST 用 URL 前缀 `/api`（v2 时改 `/api/v2`）。**本文件当前版本 v1.5**（标题、§14 与本行三者一致）。**v1.1 相对 v1 只增不改**：新增 §2.7（节点可发现性）、§3.4 的 `0x20–0x24` 五个类型与 §3.9 示例帧、§4.3 的 `bound_nodes`/`pair_state` 属性与 §4.5 的 `pair_scan`/`pair_bind` 命令、§9.2 的 1600 段业务码、**§12 本地配网 API、§13 配网与绑定端到端流程**。**v1.2 相对 v1.1 为修订**（消解独立复核 B1/B2/B3 与 M/N 项）：§3.6 重发失败改 `result=12`、新增 §4.1.1 取时与降级 + §6.21 `GET /api/time`（免鉴权）、§4.5 新增 `set_threshold`、§6.17 `compare` 拆分、§7.3 新增 `settings_json`、P0 移除 PIR、§3.7 六条样例帧补齐为完整字节等 —— 21 条逐项见 §14。v1 已冻结的字段名/帧格式/topic/表结构**一律保持原样**。**v1.3 相对 v1.2 为修订**（吸收 t10 的 10 条实现-契约偏差，并收口 t55 的 F-03）：§12.1/§12.3/§12.11/§13 的 SoftAP 地址与 DHCP 池改「由板级驱动决定，上板实测后回填，占位 `192.168.4.1`」、§12.3 客户端数上限改「建议只连 1 台」、§12.5 新增可选 `last_error`、§12.6 口令存储纪律改「不得明文落盘/落日志/回显」、§4.3 `bound_nodes`/`pair_state` 时效改「最迟一个上报周期」、§4.3.1 `mac`/`rssi` 标 P1、§4.5 `pair_scan` 表格改异步受理形状、§12.9 补汇聚拒绝码透传说明、§3.4 `0x11.target` 改可选、§2.5 阈值改「P0 只改内存、从不回 `7`」—— 10 条逐项映射见 §14.1。**v1.4 相对 v1.3 为修订（r5 拓扑收缩，用户 2026-10-20 20:30 拍板）**：拓扑固定 **1 汇聚 + 3 节点 = 4 块 WS63 全 P0**（删掉「P1 补到 5 块」与 M3/M5 两个预留编号）；节点定义 = M1 温湿度(AHT20)+燃气(MQ-2)、M2 跌倒(LD6002C 60 GHz)、M4 门窗磁×2；**删除 PIR/红外人体、MQ-5、LED 状态指示、LD6002B、BLE/蓝牙配网、WS63 本地「阈值→声光+语音」闭环、重复的「随身按钮（备选）」**；MQ-7 保留并标 **P1**；**报警不做本地声光**，出口 = IoTDA + 服务器 + App/网页；配网仍为网关 SoftAP + 手机浏览器 `http://192.168.4.1/`（**App 内配网页不做**）—— 见 §14 的 v1.4 行。**v1.5（r6）相对 v1.4 只补文档、不改协议语义**：把固件 t143 已实现、但契约漏登的 `GET /api/scan`（Wi-Fi 扫描缓存，**配网窗口内外都可用、无缓存也回 200**）正式写进 §12.4 总表与 §12.4.1 字段表，消除 App 侧字段核对脚本的例外表 —— 见 §14 的 v1.5 行。

## 1. 系统分层与地址模型

```
┌─────────────┐  SLE 星闪(0x060B/0x1122)   ┌──────────────┐   UART 115200 8N1   ┌──────────────┐
│ M1/M2/M4 等 │ ─────── JSON 上行 ───────▶ │  H1 汇聚节点 │ ──── 二进制帧(+) ──▶ │ M0 RK2206 网关│
│  WS63 节点  │ ◀────── 下行命令 ──────── │  WS63(Central)│ ◀─── 二进制帧(−) ── │  (唯一上云口) │
└─────────────┘                           └──────────────┘                     └──────┬───────┘
       ▲ 433MHz 门铃接收器（不经星闪，直进网关 GPIO 中断，唯一独立生命线）                │ MQTT 1883
       └──────────────────────────────────────────────────────────────────────────────┤
                                                                                       ▼
   ┌──────────────┐   HTTP webhook    ┌────────────────┐   规则引擎数据转发   ┌────────────────┐
   │ 鸿蒙 App     │ ◀── REST/轮询 ──▶ │ 自建服务器      │ ◀────────────────── │ 华为云 IoTDA   │
   │ (ArkTS)      │      Push Kit     │ Node.js+MySQL8 │                      │ 1 台设备=网关   │
   └──────────────┘                   └────────────────┘                      └────────────────┘
```

| 层 | 作者（ownership） | 契约章节 |
|---|---|---|
| 节点/汇聚固件 | `ws63-firmware/` | §2、§3、§8 |
| 网关固件 | `rk2206-gateway/` | §3、§4、§8 |
| 云端服务 | `server/` | §5、§6、§7、§9 |
| 手机应用 | `harmony-app/` | §6、§9 |
| 网关本地服务（配网） | `rk2206-gateway/` | §12、§13 |

**数据流四条通路**（四者互不替代，实现时都要做）：

1. **周期通路**：节点每 3 s 被轮询应答一次 → 汇聚聚合 → 网关每 60 s 上报一次 IoTDA 属性（§4.3）。
2. **事件通路**：跌倒/燃气/SOS/门磁跳变/节点离线 → 不排队，逐级立即上报（目标：传感器检出 → App 可见 ≤3 s）。
3. **兜底通路**：星闪断 → 433 仍直进网关；公网断 → 网关进入缓存模式并补传（§4.7）——**r5：不做本地声光提示**，告警出口只有 IoTDA + 服务器 + App/网页。
4. **配网通路**（**v1.1 新增**）：手机直连网关 SoftAP（`ElderCare-XXXX`）→ 本地 HTTP API 提交家庭 Wi-Fi 口令、触发星闪扫描与白名单绑定（§12、§13）。**此通路不经过服务器、不需要公网**，只在配对窗口内存在（长按配对键 3 s 进；600 s 超时或再次长按退出），窗口外一律拒绝（`1600`/窗口超时 `1601`，见 §9.2）。

### 2.3 type 取值表

### 2.5 下行：汇聚 → 节点

汇聚对节点属性句柄写一条 JSON（复用 `ssaps_write_request_cbk`，无需新 UUID）：

| 字段 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| `cmd` | string | 是 | `poll` / `set_threshold` / `demo` / `reboot` / `time_sync` | `"poll"` |
| `id` | int | 否 | 轮询序号，节点须在应答的 `req_id` 原样回显 | `7` |
| `ts` | int64 | 否 | 汇聚发令时刻（Unix ms，用于节点校时，P1） | `1792243200000` |
| `key` | string | 否 | `cmd=set_threshold` 时的参数名（**键名清单唯一来源**：§6.9 `items` 与 §8.2/§8.5/§8.7/§8.8 参数表） | `"no_motion_min"` |
| `value` | number/string/bool | 否 | `cmd=set_threshold` 时的参数值；**类型与范围逐键**见 §8.2/§8.5/§8.7/§8.8 的「范围」列 | `30` |
| `event` | string | 否 | `cmd=demo` 时：`fall`/`gas`/`sos` | `"fall"` |

**示例：**

```json
{"cmd":"poll","id":7,"ts":1792243200000}
```
```json
{"cmd":"set_threshold","key":"presence_hold_s","value":60}
```
```json
{"cmd":"demo","event":"fall"}
```

> **`cmd` 枚举口径（v1.2，消解复核 M13）**：全文唯一一份枚举就是上表（`poll` / `set_threshold` / `demo` / `reboot` / `time_sync`），§3.4 的 `GW_CMD.cmd` 与之**逐字一致**；`set` 是 `set_threshold` 的**历史别名**（节点两者都必须接受），网关侧 `reboot` 也写作 `reboot_node`（等价，且必须带 `target`）。

节点处理规则：

- `poll` → 立即回一条 `status`（+ 该节点的主数据类型，如 M1 同时回 `gas`）；
- `set_threshold` → 回 `{"cmd":"set_ack","key":"...","result":N}`。**`result` 码表**（与 §6.10 settings 写接口同一口径，业务码定义见 §9.2）：`0` = 成功；`1002` = 参数超出允许范围（带 `field`/`allowed`）；`1003` = 未知键名或不支持该键；`7` = 设备内部错误（§9.3）；
- **生效范围与持久化（v1.3 定版，PM 裁定 P0 口径）**：P0 节点**只改内存、立即生效、掉电回默认值**——阈值是演示与调试参数，P0 不写 Flash，因此**不存在「Flash 写失败」路径，节点从不回 `7`**（`7` 留给 P1 落地持久化之后）。云端/App 不得把「重启后回默认」当成下发失败（服务端 `settings_json` 只是快照，§7.3）。
- 未知 `cmd` → 回 `{"cmd":"nack","reason":1}`（§9.3 `1` = 不支持的命令/指令），不改状态。

### 2.6 汇聚侧行为（P0 必须实现）

1. 每 3 s 依次对 `M1/M2/M4` 发 `poll`，等 200 ms；收到应答即刷 `last_seen`。
2. 应答里的节点 JSON **原样**交给 §3（不解析业务字段，只做透传与聚合）——汇聚不做阈值判断，阈值判断在网关与服务器（避免三处逻辑不一致）。
3. 连续 3 次超时 → 生成 §3.4 `0x03`（节点离线事件）并在下一次`0x02`心跳里把 `online=false`。
4. 汇聚自己的心跳每 30 s 发一次 `0x02`（含所有节点在线表）。
5. 汇聚不缓存历史（只有最近一帧快照），断连期间的补传由网关的 Flash 环形缓冲负责（实施计划 §9.1 `config_task`）。

### 2.7 节点上电行为与可发现性（**v1.1 新增**）

**契约要求：节点受电即广播，不需要按键、不需要网关/汇聚在线**（配网第 ④ 条）。角色分工固定：

| 角色 | SLE 角色 | 现状 |
|---|---|---|
| `M1`/`M2`/`M4` 节点 | **服务端**（announce + 可连接 + 可扫描） | ✅ 已实现（`ws63-firmware/src/sle_hub_adv.c`：`param.announce_mode = SLE_ANNOUNCE_MODE_CONNECTABLE_SCANABLE`、`sle_hub.c:340,355,369` 调 `sle_start_announce(SLE_ADV_HANDLE_DEFAULT)`） |
| `H1` 汇聚 | **客户端**（scan → connect → 服务发现 → 写/通知） | ⚠️ **代码尚缺**（现有 `sle_hub.c` 也是服务端，属过渡实现）→ 固件任务 |

上电时序（节点侧，P0）：

```
上电 → sensor_hub_init() → sle_uuid_server_adv_init()（注册服务 0x060B + 属性 0x1122）
     → enable_sle() → sle_start_announce(SLE_ADV_HANDLE_DEFAULT)      ← 此刻起可被发现
     → 等汇聚连接；连上后按汇聚 poll 应答（§2.6）
```

**广播里必须能区分节点**——这是「扫描列表显示 `sn`」的前提。现有代码有三个必须改的点（**不改则扫描/绑定不可用**）：

| # | 现状（一手代码） | 契约要求（v1.1） |
|---|---|---|
| 1 | `own_addr` **硬编码** `{0x11,0x22,0x33,0x44,0x55,0x66}`（`sle_hub_adv.c:71,85`）→ 三块节点 MAC 完全相同，汇聚无法区分 | 按 SN 派生唯一 MAC：前 4 字节固定 `11:22:33:44`，第 5 字节固定 `0x55`，第 6 字节 = **SN 编号**（`M1`=01、`M2`=02、`M4`=04，§0.7 表）。同一硬件重烧不得让两个节点用同一 MAC |
| 2 | 广播名/扫描应答名是官方样例残留 `sle_speed_server`（`sle_hub_adv.c:57-66`） | 改为固定格式 **`EC-<SN>`**（如 `EC-M2`，≤16 字节），便于现场人工核对 |
| 3 | 广播数据只有「发现等级 + UUID 0x060B」（`sle_hub_adv.c:44-53`），**不带 SN** | 在其后**追加**一条厂商自定义 AD 结构（类型 `0xFF`、长度 `0x06`）：`'E','C'` + `sn`(2 ASCII) + `role`(`0x01`=节点/`0x02`=汇聚) + `proto_ver`(`0x01`) |

**向后兼容规则（必须实现）**：扫描到的设备若**没有** `0xFF` 结构（老固件/别家设备），汇聚照旧上报，`sn` 填 `"?"`、`bind=false`；网关/App 用 `mac` 作唯一键完成一次绑定后，由白名单记住 MAC↔SN 映射（§3.4 `0x22`），后续以白名单为准。这样新老固件可以在同一条产线上混跑，不会因为一端没升级就扫不到。

**未绑定节点不产生业务数据**：汇聚只对白名单内节点建立连接并发 `poll`；扫描到但未绑定的节点只出现在扫描结果里（不上报 `gas/fall/door/presence`、不计入 `nodes_online`），避免邻居家的同类设备混进告警。

**实现基线（v1.2 登记，供后续复核对齐）**：节点固件**已删除官方样例的 600 B 压测灌包线程**；对读请求（`poll`）返回的是**最近一帧 JSON**（读缓存，不重新采样），因此连续两次 `poll` 可能拿到相同 `ts`，属正常，不作为「节点卡死」的证据。

### 3.1 物理层与串口参数

| 共地 | 必须 | 两板 GND 直连 |

### 3.2 帧结构

```
 偏移  长度  字段        说明
  0     1     SOF1        0xAA
  1     1     SOF2        0x55
  2     1     VER         0x01（本契约版本）
  3     1     TYPE        §3.4，方向由 TYPE 决定
  4     2     SEQ         uint16 **小端**，发送方自增（0–65535 回绕）
  6     2     LEN         uint16 **小端** = PAYLOAD 字节数（0–1024）
  8     LEN   PAYLOAD     UTF-8 JSON（§3.5）
 8+LEN  2     CRC16       uint16 **小端**，CRC-16/MODBUS（§3.3），覆盖范围 = VER..PAYLOAD 末字节
```

- **整帧长度 = 10 + LEN**；`LEN > 1024` 的帧一律按非法帧丢弃（防伪造 SOF 导致的越界读）。
- 帧内多字节字段（SEQ/LEN/CRC）**统一小端**；只有 PAYLOAD 里的 JSON 是文本。**不要和雷达的 TinyFrame 混淆**（那套是帧头大端、数据小端，见 `radar_hub.c:24-29`）。

### 3.3 CRC-16/MODBUS

| 参数 | 值 |
|---|---|
| 多项式 | `0x8005`（反射实现 `0xA001`） |
| 初值 | `0xFFFF` |
| 输入/输出反射 | 是 / 是 |
| 结果异或 | `0x0000` |
| **自检向量** | `crc16("123456789") == 0x4B37` |
| 计算范围 | 帧内 `VER` 到 `PAYLOAD` 末字节（**不含** 2 字节 SOF，不含 CRC 本身） |

C 参考实现（网关与汇聚共用，放 `common/`）：

```c
uint16_t uart_frame_crc16(const uint8_t *d, uint16_t n)
{
    uint16_t crc = 0xFFFFu;
    for (uint16_t i = 0; i < n; i++) {
        crc ^= d[i];
        for (int b = 0; b < 8; b++) {
            crc = (crc & 1u) ? (uint16_t)((crc >> 1) ^ 0xA001u) : (uint16_t)(crc >> 1);
        }
    }
    return crc;
}
```

### 3.5 PAYLOAD 与 JSON

- PAYLOAD 就是一条完整 UTF-8 JSON 对象，**不允许数组或裸值作为顶层**。
- 节点 JSON 上行时由汇聚**原样透传**（§2.2），不改字段；汇聚自己产生的报文用 §3.4 定义的结构。
- JSON 内的 `ts` 等数值仍是 Unix 毫秒，与 §0.2 一致。

### 3.6 分帧与容错规则

| 情形 | 处理 |
|---|---|
| 粘包（一读多帧） | 按 LEN 循环切帧，直到剩余 < 10 字节 |
| 半包（帧不完整） | 保留残余字节，等下一批；残余 > **2068** 字节（= 2×最大帧 = 2×(10+1024)）未成帧 → 清空并计数 |
| 假 SOF | 逐字节滑动找 `0xAA 0x55`；LEN 越界或 CRC 错 → 丢弃首字节后重找，并回 `0x12 GW_NACK`（同一 SEQ 只回一次，防风暴） |
| CRC 错 | 丢帧 + `GW_NACK(reason=4)` + `err_cnt++` |
| 未知 TYPE | 丢帧 + `GW_NACK(reason=6)`，不崩溃 |
| 序号不连续 | 只记统计（`gw_rx_miss++`），**不要求重传**；下次 `0x01` 里带的 `seq` 自然揭示丢失 |
| 缓冲 | 收发各 ≥ 2048 字节环形缓冲（RK2206 侧沿用 `b6_uart0` 样例的环形缓冲） |

**重传策略（单向下行必答）**：`0x11 GW_CMD` 与 `0x13 GW_TIME` **必须**被 `0x10 GW_ACK` 确认；发送方等 500 ms 未收到对应 ACK → 重发，最多 3 次，仍失败则向上报 **`result=12`（链路超时/无应答，§9.3）** 并记 ERROR。**`1502` 只用于 webhook 校验失败（§9.2），不允许出现在设备侧 `result` 字段**（v1.2 修正复核 B2）。`0x01/0x02/0x03` **不需要**逐帧 ACK（周期通路天然自愈），网关可选择性回 ACK 用于方向自检。

**网关必须自行实现的三件事**（可行性核查把这条列为头号集成风险，失败表现是返回码 `0x04`）：

1. `HMACSHA256(secret, timestamp)` 摘要，输出 64 位十六进制小写；
2. 4 段 `ClientId` 拼装，且时间戳取 **UTC**、格式 `YYYYMMDDHH`；
3. 时间戳在 ClientId 与 Password 两处**复用同一个值**（跨小时边界时不要各取一次）。

#### 4.1.1 取时与降级（**v1.2 新增，PM 决策 D2**）

**顺序是硬性的**：网关**先取到可信 UTC，再连 IoTDA**（`S=1` 会校验时间戳，时间错会拿 `0x02`/`0x04`）：

|---|---|---|---|
| 1 | WiFi（STA）连上并拿到 DHCP 后，**先**调 `GET /api/time`（§6.21，**免鉴权**、`Cache-Control: no-store`）取 UTC | ≤3 s | → 步 2 |
| 2 | SNTP/NTP（`pool.ntp.org`，或局域网内 NTP 服务器） | ≤5 s | → 步 3 |

| 5 | 取时成功：`clock_source = device`；偏差按 **±10 min** 容差假设，超过必须重取 | — | — |
| 6 | 取到的时刻同时用于 `ClientId` 第 4 段与 `Password`，格式 `YYYYMMDDHH`（UTC），**跨小时边界不要各取一次** | — | — |

### 4.5 命令定义

| 命令 | 请求 `paras` | 响应 `paras` | 说明 |
|---|---|---|---|
| `set_report_interval` | `{"seconds":60}`（int，10–3600） | `{"result":"ok","seconds":60}` | 改属性上报周期 |
| `demo_trigger` | `{"event":"fall"}`（`fall`/`gas`/`sos`） | `{"result":"ok","event":"fall"}` | 演示注入，走**真实链路**，见 §11 D-07 |
| `mute_alarm` | `{"duration":300}`（秒，1–3600） | `{"result":"ok","duration":300}` | **不做（r5：无本地声光）**——命令仍受理并回 `ok`，但不改变任何硬件状态 |
| `pair_scan` | `{"duration_s":15}`（秒，3–60，可缺省=15） | `{"result":"accepted","id":21,"duration_s":15,"estimate_s":18}`（**v1.3：受理即回**，不等扫描结束；结果随后经 §4.3 `bound_nodes` 与 §4.6 `nodes` 明细回流） | **v1.1**：联网后远程触发节点扫描（网关 → §3.4 `0x20`）。**需要服务器侧新增一个 REST 接口来下发**，见 §12.4 的说明 |
| `pair_bind` | `{"op":"add","sn":"M2","mac":"11:22:33:44:55:02"}` | `{"result":"ok","op":"add","bound":["M1","M2"],"slots_free":6}` | **v1.1**：联网后远程绑定/解绑（网关 → §3.4 `0x22`）；`op`=`add`/`del`/`clear`/`list` |
| `set_threshold` | `{"cmd":"set_threshold","key":"gas_t1_mv","value":1500}` | `{"result":"ok","key":"gas_t1_mv","value":1500}` | **v1.2**：阈值下发（App → 云 → 网关 → 汇聚 → 节点，落到 §2.5 `cmd=set_threshold`；PM 批准） |

命令响应体（发往 `.../commands/response/request_id={request_id}`）：

```json
{"result_code":0,"response_name":"COMMAND_RESPONSE","paras":{"result":"ok","event":"fall"}}
```

`result_code`：`0` 成功；非 0 见 §9.3。**失败时 `paras` 不得回显成功语义**（v1.3 r5 / t111）：`result_code` 非 0 的命令响应里 `paras` 一律为空对象 `{}`，不回 `result`/`key`/`value`——值并未生效，回显即谎报成功，失败原因由 `result_code` 唯一表达。

`set_threshold` 的三处校验口径（**缺一不可，字段名与范围必须一致**）：

- **`key` 清单唯一来源**：§6.9 `items` 的键名（= §8.2 燃气 / §8.5 无活动 / §8.7 离线 / §8.8 抑制的参数表）。**契约不使用口语别名**——PM 邮件里出现的 `gas_l1`/`gas_l2`/`no_activity_min`/`offline_misses` 分别对应 `gas_t1_mv`/`gas_t2_mv`/`no_motion_min`/`node_offline_timeout_s`，上线字段一律用后者。
- **`value` 类型与范围**：逐键见 §8 各参数表（整数键如 `gas_t1_mv` 0–5000、`no_motion_min` 5–120；浮点键如 `temp_high_c`；`alert_repush_s` 是**整型数组**，默认 `[0,60,300]`）。
- **错误码**：App 侧（`PUT settings` §6.10）越界 `1002`、未知键 `1003`、非 owner `1104`；云端投递前设备离线 `1204`；设备侧 `result_code`：`0` 成功 / `1` 未知键或不支持 / `2` 参数越界 / `3` 忙 / `7` 内部错误（§9.3）；网关对 `0x11` 三次重发仍无 `ACK` → `result=12`（§3.6、§9.3）。
- **方向**：App → `PUT /api/devices/{id}/settings` → `POST /api/devices/{id}/config` → IoTDA 命令 → 网关 → 汇聚 `0x11` → 节点 `set_threshold`。**离线设备只投递不保证生效**（§6.11）。

> `pair_scan`/`pair_bind` 的**命令超时按 20 s**（扫描本身最长 60 s，故 `pair_scan` 用异步）。**v1.3 把表格与这段注解对齐**：上表的响应 `paras` 就是**受理形状**——`{"result":"accepted","id":N,"duration_s":N,"estimate_s":N}`（`id` = §3.4 `0x20`/`0x21` 的 `id` 回显，`estimate_s` = `duration_s` + 汇聚重扫开销 3 s），配 `result_code=0` 表示「已受理」；**扫描结果不在这条响应里**，随后通过 §4.3 `bound_nodes` 属性与 §4.6 `nodes` 明细回流。取舍理由不变：**避免 IoTDA 命令响应超时导致 App 误判失败**（实现证据：`gw_prov.c` 的受理响应）。

### 4.7 断网缓存与补传（P0 演示动作 6）

1. 网关检测到 MQTT 断开 → 进入缓存模式（**r5：不做本地声光与 LED 指示**）；`alarm_state` 保持。
2. 缓存写入板载 8 MB FLASH 环形缓冲（`b15_flash`/`b21_iot_flash` 样例），容量 **2000 条**（约 24 h 的 5 分钟明细 + 事件）。
3. 重连成功 → 先补**事件**（按 `event_id` 幂等），再把明细**按 5 分钟粒度聚合成 `node_samples`** 补传（**不逐条补**，避免超免费配额；见 §4.8）。
4. 补传完成告警全部消除；补传期间若再次断网，保留未发片段不重复写。
5. 补传进度写入 `device_online.last_heartbeat` 之外的一个属性 `sync_pending`（P1，不给 P0 增加负担）。

### 4.8 消息数预算（免费单元 10000 条/天）

| 用途 | topic | 频率 | 条/天 |
|---|---|---|---|
| 属性上报 | `properties/report` | 60 s | 1440 |
| 节点明细（M1/M2/M4） | `messages/up` | **每 300 s 发 1 条，`content` 里装全部 3 个节点的快照**（≈864 行/天入库） | 288 |
| 事件（报警/离线/恢复） | `events/up` | 按需，估 20 | 20 |
| 命令响应 | `commands/response/...` | 按需 | ≤10 |
| **合计** | | | **≈1758（17.6%）** |

结论：留出 5 倍余量。**红线**：任何新增周期上报都必须先算这张表并由 PM 批准（超过 5000 条/天即拒绝）。keepalive、订阅、命令下发不计入。

## 5. 链路四：IoTDA 规则引擎 → 自建服务器（webhook）

### 5.1 转发配置（控制台一次性配置，写进 server/README）

| 项 | 值 |
|---|---|
| 触发资源 | `device.property`（report）、`device.event`、`device.message` |
| 转发目标类型 | HTTP 推送 |
| 目标 URL | `https://{server_host}/api/iotda/webhook?token={WEBHOOK_TOKEN}` |
| 鉴权 | URL 查询串 `token` = 32 字节随机十六进制，存服务器环境变量；**不用自定义 Header**（推送头可配性不如 URL 可靠） |
| 失败行为 | 服务器返回非 200 → 平台按退避重试；服务器侧靠 `event_id` / 唯一键幂等 |
| SQL 过滤 | 首版**不加过滤**（全量转发），规则里保留 `WHERE` 注释行以备后续降噪 |

### 5.2 报文信封（服务器解析入口）

| 字段 | 类型 | 说明 |
|---|---|---|
| `resource` | string | `device.property` / `device.event` / `device.message`，用于分流 |
| `event` | string | 属性为 `report`；事件为 `event_type`（`alert`/`sos`/`recover`） |
| `event_time` | string | 平台时间，仅记日志 |
| `notify_data.header.device_id` | string | IoTDA 设备 ID → 反查 `devices.iotda_device_id` |
| `notify_data.header.node_id` | string | 网关 SN（P0 用不到，留作多网关扩展） |
| `notify_data.body.services[]` | array | **唯一业务数据源**（结构同 §4.6 的 `services[]`） |

**服务器实现约束**：只依赖 `resource` + `notify_data.header.device_id` + `notify_data.body.services[]`；**无法识别的 `resource` 一律返回 200 并记 WARN**（不阻断平台重试队列），缺 `device_id` 时用 SN 兼容匹配。这样即使平台信封字段有出入（CAL-04），业务也不受影响。

| `device.property` → `nodes_online` | `nodes` | 按 JSON 里的键更新 `nodes.online`/`last_seen` |
| `device.property` → `temp/humi/smoke/lpg/co` | `sensor_readings` | `node_sn="M0"`（网关快照）、`type="gateway"`、`payload_json=properties`、`ts=服务器接收时刻` |
| `device.event` → `paras` | `alerts` | `type/level/node_sn/ts`；`status='pending'`、`event_id` 唯一键去重 |
| `device.message` → `content` | `sensor_readings` | 展开数组，每条一行；`type` 取节点 JSON 的 `type` |
| 任意 | `activity_hourly`/`activity_daily` | 由 `sensor_readings` 定时归并（§7.9/§7.10）：**P0 = `type=door` 的跳变次数**（`payload.door` 变化即记 1 次活动）；r5 已删除 PIR，不再叠加 `type=presence` 记录 |

> `IOTDA_DISPATCH_MODE`（服务器环境变量，**验收前必须确认取值**）：`mock` = 规则引擎推来的告警/命令**只入库、不下行**（离线演示与自动验收用，真机不在场也不报错）；`real` = 真下行到 IoTDA 命令通道（联调与答辩演示用）。取 `mock` 时 App 点「下发」不会有真机反应，**不得据此判定链路故障**。

## 6. REST API

### 6.1 通用约定

| 项 | 约定 |
|---|---|
| Base URL | `http://{host}:80/api`（Nginx 反代到 `127.0.0.1:3000`） |
| 编码 | `Content-Type: application/json; charset=utf-8` |
| 鉴权 | `Authorization: Bearer <JWT>`；除 `/api/auth/*`、`/api/health`、`/api/time` 外全部必需（`/api/time` 是网关**启动取时握手**接口，此时网关还没有 JWT：定义见 §6.21、调用顺序见 §4.1.1） |
| JWT | HS256；载荷 `{sub:<user_id>, username, iat, exp}`；有效期 **7 天**；密钥来自环境变量，**不进仓库** |
| 统一响应体 | `{"code":0,"message":"ok","data":{...},"ts":1792243200000}` |
| 分页 | 查询参数 `limit`（默认 50，最大 200）、`offset`（默认 0）；响应带 `total` |
| 时间参数 | `from`/`to` 用 Unix 毫秒；服务器按 `[from, to]` 闭区间 |
| 幂等 | 写接口允许 `Idempotency-Key` 头；同一键 5 分钟内重复请求返回首次结果 |
| 错误 | HTTP 状态码表达类别，`code`/`message` 表达细节（§9） |
| CORS | 仅允许 `http://localhost`（鸿蒙 PC 预览与本地调试）；生产不放开通配 |

`code=0` 表示业务成功；HTTP 200 但 `code!=0` 的情况**不允许出现**（实现约束：错误必须同时体现在状态码上），保证 App 只判 HTTP 状态即可。

### 6.16 GET /api/reports/activity

查询参数：`device_id`（必填）、`period`（`day`/`week`/`month`，默认 `day`）、`date`（`YYYY-MM-DD`，默认今天，按 UTC+8 日历）。

响应 `data`：

```json
{"device_id":1,"period":"day","from":1792166400000,"to":1792252799999,"total":128,
 "hourly":[{"hour":0,"count":0},{"hour":1,"count":2}],
 "daily":[{"date":"2026-10-17","count":128}]}
```

`period=day` 时 `hourly` 24 项（UTC+8 小时）、`daily` 1 项；`week`/`month` 时 `hourly` 省略、`daily` 为 7/30 项。

> **`from`/`to` 口径（r4）**：`from` = 该 UTC+8 日历日 `00:00:00.000` 的 Unix ms，`to` = **当日 `23:59:59.999`**（闭区间，见 §0.4/§7.9）。上例 `date=2026-10-17` ⇒ `from=1792166400000`（= `2026-10-16T16:00:00Z`）、`to=1792252799999`（= `2026-10-17T15:59:59.999Z`），与 `daily[].date="2026-10-17"` 同一天；照抄本样例写断言即可与实现（`app/timeutil.py:cst_day_bounds_ms`）一致。

### 6.17 GET /api/reports/trend

查询参数：`device_id`（必填）、`days`（默认 7，1–90）。

响应 `data`：

```json
{"device_id":1,"days":7,"series":[{"date":"2026-10-11","count":110}],
 "compare":{"title":"今日活动频次","today":128,"yesterday":160,"delta_pct":-20,"text":"较昨日下降 20%"}}
```

**`compare` 字段位置与语义（v1.2 写死，PM 裁定）**：

| 键 | 类型 | 必现 | 说明 |
|---|---|---|---|
| `compare.title` | string | **是** | 固定文案「今日活动频次」（标题不参与趋势判断） |
| `compare.today` | int | 是 | 今日活动次数（按 §7.11/§7.9 的 P0 口径统计） |
| `compare.yesterday` | int | 否 | 昨日活动次数；**无昨日基线时该键省略** |
| `compare.delta_pct` | int | 否 | **整数百分比**（四舍五入，`-20` = 下降 20%）；无基线时省略 |
| `compare.text` | string | 否 | 趋势句，按下面规则；**无昨日基线时该键省略**（`compare.title` 仍返回） |

规则行（实施计划 §7.4）：`delta_pct = round((today−yesterday)/yesterday×100)`，**整数**；`delta_pct ≤ −10` → `text = "较昨日下降 N%"`；`delta_pct ≥ +10` → `"较昨日上升 N%"`；`−10 < delta_pct < +10` → `"与昨日基本持平"`（此情形带 `text`）。
**无昨日基线**（`yesterday` 缺省、为 `0`，或 `today = yesterday = 0`）→ **省略 `compare.text`（同时省略 `delta_pct`）**，只返回 `compare.title` 与 `compare.today`；App 显示「暂无对比数据」，文案不在契约内。

```json
 "env":{"temp_avg":23.8,"temp_min":19.2,"temp_max":26.5,"humi_avg":54.3}}
```

> **`from`/`to` 口径（r4）**：`week` = 截至 `date` 的 **7 个 UTC+8 日历日（含当日）**，`month` = 30 个；`from` = 首日 `00:00:00.000`、`to` = 末日 `23:59:59.999`（闭区间）。上例 `date=2026-10-17` ⇒ `2026-10-11`–`2026-10-17` ⇒ `from=1791648000000`（= `2026-10-10T16:00:00Z`）、`to=1792252799999`（= `2026-10-17T15:59:59.999Z`）。`activity.total`/`active_days`/`avg_daily` 都只统计这个闭区间内的 `activity_daily` 行（`avg_daily = total / 周期天数`，与 760/7=108.6 一致）。

### 6.19 POST /api/push/register

请求：`{"push_token":"<Push Kit token>","platform":"harmony"}`；响应 `data`：`{"registered":true,"user_id":1}`。同一 token 重复注册幂等（更新 `updated_at`）。写入表 `push_tokens`（§7.12）。

### 6.20 GET /api/health

响应 `data`（无需鉴权，但只暴露非敏感项）：

```json
{"ok":true,"version":"1.0.0","db":"ok","iotda_token_expire_at":1792263200000,
 "webhook_last_at":1792243200000,"clock_source":"device","server_ts":1792243201000}
```

`clock_source` 取值（v1.2 写死，**一段定义**）：`device` = 网关**已取到可信 UTC**（取时流程见 §4.1.1），设备上报的 `ts` 可信，报表按设备 `ts` 切分；`server` = 网关未校时或在校时降级中（此时设备 `ts` 其实是自开机毫秒数，见 §0.2），服务器按**收到时刻**纠正所有 `ts`，**不得用设备上报的 `ts` 做报表切分**。

### 6.21 GET /api/time

网关启动握手取时用（**v1.2 新增，PM 定稿**）：**免鉴权**（不泄露任何敏感信息）、无参数、超时 ≤3 s、响应头 `Cache-Control: no-store`。

响应 `data`：

| 字段 | 类型 | 单位 | 必现 | 说明 | 示例 |
|---|---|---|---|---|---|
| `utc_epoch` | int | 秒 | 是 | UTC 秒（**整数、秒精度**） | `1792243200` |
| `iso8601` | string | — | 是 | UTC ISO-8601，**秒精度、`Z` 结尾** | `"2026-10-17T13:20:00Z"` |

```json
{"code":0,"message":"ok","data":{"utc_epoch":1792243200,"iso8601":"2026-10-17T13:20:00Z"},"ts":1792243200000}
```

规则：

- **部署机必须与 NTP 同步**（`chrony`/`systemd-timesyncd`/`ntpd` 任一）；本接口只是把服务器时间**转发**给网关，不修正它。
- 网关取时成功后 `clock_source = device`；失败则按 §4.1.1 继续降级（SNTP → 上次值 + 开机时长），全失败时 `clock_source = server` 且**不连 IoTDA**。
- 本接口只回时间：不返回 token、不做鉴权、不接受参数；不得把它当成健康检查（健康检查是 §6.20）。

## 7. MySQL 8 表结构

### 7.1 通用约定

- 引擎 `InnoDB`，字符集 `utf8mb4` / `utf8mb4_0900_ai_ci`；主键 `id BIGINT UNSIGNED AUTO_INCREMENT`。

## 8. 阈值与状态机

### 8.1 级别定义（全系统统一）

| `level` | 名称 | 典型来源 | App/UI | 物模型 `alarm_state` |
|---|---|---|---|---|
| 0 | 正常 | — | 绿 | `0` |
| 1 | 预警 | 气体一级、无活动、节点/网关离线、门久开、温湿度越界 | 黄 | `1` |
| 2 | 报警 | 气体二级、跌倒、SOS | 红 | `2` |

`alarm_state` 取当前**未恢复**告警的最高 `level`（网关本地算，每 60 s 上报一次）。

### 8.2 燃气分级状态机（M1，网关 `algo_task` 执行）

```
         ┌──── 气体通道（P0 = MQ-2 `smoke`）≥ T1 连续 L1_HOLD(10 s) ────┐
         ▼                                                    │
    ┌─────────┐                                             ┌──────────┐
    │ 正常(0) │                                             │ 预警(1)  │
    └─────────┘ ◀── 全部 < T1−Δ(200 mV) 连续 15 次采样(30 s) ──└──────────┘
         ▲                                                        │
         │                气体 ≥ T2 连续 L2_HOLD(6 s)             │
         │                       或 预警态持续 60 s               │
         │              或（P1 多路时）≥2 路同时 ≥ T1            ▼
         │                                                   ┌──────────┐
         └──────────── 恢复条件同上（30 s 干净）──────────── │ 报警(2)  │
                                                            └──────────┘
```

| 参数 | 默认值 | 单位 | 可配 | 说明 |
|---|---|---|---|---|
| 采样周期 | 2 | 秒 | 否 | 沿用 `sensor_hub.c` `LOOP_INTERVAL_MS=2000` |
| `gas_t1_mv` | 1500 | mV（AO 侧） | 是 | 一级阈值；P0 只有 MQ-2 一路，P1 可选 MQ-7（分路阈值 P1；MQ-5 已按 r5 删除） |
| `gas_t2_mv` | 2500 | mV（AO 侧） | 是 | 二级阈值 |
| `gas_l1_hold_s` | 10 | 秒 | 是 | 一级需连续超限时长（=5 次采样） |
| `gas_l2_hold_s` | 6 | 秒 | 是 | 二级需连续超限时长（=3 次采样） |
| `gas_l1_to_l2_s` | 60 | 秒 | **算法参数**（不是 §6.9 的 settings 键，见 §6.9 说明） | 一级滞留多久升二级；P0 固定 60 s，改值走契约变更 |
| `gas_recover_mv` | 200 | mV | 是 | 恢复回差（防抖） |
| `gas_recover_hold_s` | 30 | 秒 | 是 | 恢复需连续干净时长 |

动作：进入一级 → 上报 `alert(level=1)` + App 推送；进入二级 → 上报 `alert(level=2)`；恢复 → 上报 `recover`。**r5：本地声光与语音全部不做**，告警出口只有 IoTDA + 服务器 + App/网页。

> ⏳ 阈值 1500/2500 mV 是**结构默认值，不是标定值**。必须先做 CAL-02（洁净空气静置记基线 vs 打火机放气记峰值）再定稿，否则演示时可能不报或常报。
>
> 🔴 MQ-2 的 `Vs` 最高 4.0 V（2000 ppm C₃H₈），**必须分压后进 3.3 V ADC**；加热丝必须 **5.0 V ± 0.1 V**，且**预热 >48 h / 老化 48–168 h** 是不可压缩的日历时间（详见 §2.4.1；另注意 `VH` 取 **4.9–5.0 V**：`RH` 下限 26 Ω 时 5.0 V 会到 961.5 mW > 950 mW，复核 M11）。

### 8.3 温湿度越界（M1，P1）

| 判据 | 默认值 | 级别 | 动作 |
|---|---|---|---|
| `temp` > `temp_high_c`(35.0 °C) 或 < `temp_low_c`(5.0 °C) 持续 `env_hold_min`(30 分钟) | 见左 | 1 | 上报 `alert(type=env)` |
| `humi` > `humi_high_pct`(85 %RH) 或 < `humi_low_pct`(20 %RH) 持续 30 分钟 | 见左 | 1 | 同上 |
| 恢复 | 回到区间内持续 10 分钟 | — | 上报 `recover` |

### 8.4 跌倒（M2/M3，P0，最高优先级）

跌倒判定是**三段串联**，契约只规定后两段，**不得把模块内部的 15–20 s 判定改写成「瞬时触发」**：

| 段 | 位置 | 行为 | 迟滞 / 时延 |
|---|---|---|---|
| ① 判定 | LD6002C 模块固件 | 点云离地高度持续低于阈值 | **默认灵敏度 10 下需持续跌倒 15–20 s** 才把跌倒位置 1（datasheet：Fall Sensitivity 3–30） |
| ② 上报 | 模块 → 节点 | `0x0E02` 的 `DATA[0]=1`（UART）或 TX2 电平拉高 | ≈0 ms |
| ③ 链路侧状态机 | 节点 → 汇聚 → 网关 | 见下 | **链路不额外加延时**，只做迟滞与抑制 |

链路侧状态机（迟滞型，不是「来一帧报警、下一帧恢复」）：

```
   收到 fall=1（DATA[0]=1 或 TX2 上升沿）
        │
        ▼
   ┌──────────┐                                   ┌───────────┐
   │ 正常 IDLE │                                   │ 报警 ALARM │
   └──────────┘ ◀── 连续 K 次 fall=0 且距最后一次触发 ≥ T_hold ──└───────────┘
```

| 参数 | 默认值 | 单位 | 说明 |
|---|---|---|---|
| 进入条件 | 任一通道出现 `fall=1` | — | **立即进入 ALARM，不额外延时** |
| `fall_suppress_s` | 30 | 秒 | ALARM 期内重复触发不产生新告警，不重置 `push_count` |
| 退出条件（迟滞，须**同时**满足） | `K=3` 次 `fall=0` **且** 距最后一次 `fall=1` ≥ `T_hold=30 s` | — | 两个条件缺一不可，防止「模块瞬时回落」导致告警闪断。**`fall=0` 的采样来源 = 汇聚轮询应答（3 s/次）→ K=3 即 ≈9 s，实际退出由 `T_hold=30 s` 主导**；雷达自身 1 Hz 帧率不参与计数（复核 M2） |
| 恢复事件 | `recover` | — | 回到 IDLE 时写 `recovered_at`；**不自动改 `status`**，闭环仍由人工处置结束（§6.15） |

**端到端可见时延 = 模块判定 15–20 s + 链路 ≤100 ms。** 演示与答辩必须按这个时长讲解（人在雷达下快速倒一下不会触发，不要在现场误判成「没反应」）。
厂商标称：跌倒识别 **90%**、存在识别 95%、覆盖 3×3 m 单人小区域（datasheet `:66-68`）→ 因此 P0 保留 `demo_trigger` 注入路径（§4.5、§6.12），**注入必须走真实链路**（§11 D-07）。

### 8.5 无活动与外出模式（M4/M5，P0）

| 状态 | 进入条件 | 退出条件 | 行为 |
|---|---|---|---|
| `home`（在家） | 近 30 分钟内有活动 —— **P0：`door` 跳变或节点心跳**（r5 已删除 PIR，无其它数据源） | 进入 `away` | 计时到最近一次活动，超 `no_motion_min` 报警（**P0 的活动时钟 = 最后一次 `door` 跳变/心跳**） |
| `away`（外出） | `door` 由关变开，且其后 `away_after_open_s`(600 秒) 内**无任何活动** | 检测到任意活动 —— **P0：`door` 再次跳变**（r5 已删除 PIR） | **抑制**无活动告警 |
| — | — | — | — |

| 参数 | 默认值 | 单位 | 范围 | 可配 |
|---|---|---|---|---|
| `no_motion_min` | 30 | 分钟 | 5–120 | 是（App 设置页） |
| `away_after_open_s` | 600 | 秒 | 60–3600 | 是 |
| `presence_hold_s` | 60 | 秒 | 10–600 | **不做**（r5 已删除 PIR：写入不生效，但不得报错） |

触发时上报 `alert(type=no_motion, level=1, node_sn="M4")`，文案「30 分钟未检测到活动」（分钟数按实际配置替换）。

> ⚠️ **P0 的 30 分钟无活动只看门磁**（r5 已删除 PIR，见 §0.7 与 §14）：演示与验收必须用「**开合一次门 → 之后静默 30 分钟**」来触发，不要指望真人坐在屋里不动就能报——P0 没有能测「在不在家」的传感器。P1 装 PIR 后本节的 `last_motion_ts` 才参与判定。

### 8.6 门久开（P1）

`door=true` 持续 `door_open_alarm_s`(180 秒) → `alert(type=door_left, level=1)`；关门 → `recover`。

### 8.7 离线判定（P0，两条独立规则）

| 对象 | 判定方 | 规则 | 参数 | 动作 |
|---|---|---|---|---|
| 节点 | 汇聚 | 连续 3 次轮询无应答 | 3 s × 3 = **9 s**（`node_offline_timeout_s`） | `0x03 HUB_EVENT` → 网关 → `alert(type=node_offline, level=1)`；`nodes.online=0` |
| 网关 | 服务器 | 连续 3 个上报周期无任何数据 | 60 s × 3 = **180 s**（`gateway_offline_timeout_s`） | `device_online.online=0` + `alert(type=device_offline, level=1)` |
| 恢复 | 各自 | 节点：1 次成功应答；网关：收到任意上报 | — | 上报 `recover`，`online=1` |

节点恢复时的 `recover` 事件由网关在 `0x03` 里带 `type=node_online` 触发。

### 8.8 报警抑制、去重与推送节奏（P0）

| 项 | 规则 |
|---|---|
| 去重键 | `(device_id, node_sn, type)`；`fall` 用 30 s 窗口，其余用 `alert_suppress_s`(60 s) |
| 窗口内重复 | **不新建告警**；只更新 `snapshot_json` 与 `recovered_at=NULL`；`push_count`/`next_push_at` 保持 |
| 推送节奏 | `[0, 60, 300]` 秒（`alert_repush_s`），即最多 3 次；Push 只是「叫醒」，通知里带 `alert_id` |
| 停推条件 | `status != 'pending'` **或** `recovered_at IS NOT NULL` **或** `push_count >= 3` |
| 升级 | 窗口内级别上升（1→2）→ 新建一条 `level=2` 告警，旧条置 `recovered_at=now` |
| 免打扰 | 跌倒 / SOS 不受免打扰限制；其余按用户设置（P1） |

## 12. 本地配网 API（网关 SoftAP，**v1.1 新增 / v1.2 定向**）

> **消费方（v1.2 定稿，PM 裁定 F-02）**：本节 5 个接口的**首选消费方是网关内置的 H5 页面**——手机浏览器直接打开 `http://{AP 口地址}/`（占位 `http://192.168.4.1/`；地址由驱动决定，见 §12.3/CAL-12），同源、零安装、任何手机都能开；**安卓 App 与鸿蒙 App 的配网页是 P1 消费者**（同一套 HTTP 契约，字段不变）。理由：没有鸿蒙真机、安卓 APK 是否可编取决于用户环境，浏览器路径是唯一零依赖、当场必然可用的 P0 演示路径。

### 12.1 定位与安全边界

**这是网关自己的 HTTP 服务，不是 §6 的服务器 API。** 两套 API 的域、鉴权、生命周期完全不同，App 必须分开处理：

| 项 | §6 服务器 API | §12 本地配网 API |
|---|---|---|
| Base URL | `http://{host}/api` | **`http://{AP 口地址}/api`**，占位 **`http://192.168.4.1/api`**（**地址由板级驱动决定，上板实测后回填**，CAL-12；以串口首行打印的实际地址为准） |
| 可达条件 | 手机有公网/局域网到服务器 | **手机必须连上 `ElderCare-XXXX` 这个 AP**，且配网窗口未超时 |
| 鉴权 | `Authorization: Bearer <JWT>` | **无 JWT**（此刻设备还没绑定到账号）；见下四条边界 |
| 生命周期 | 长期 | 只存在于配网窗口（默认 600 s） |
| 响应信封 | §6.1 统一信封 | **同 §6.1 统一信封**（App 可复用同一套解析代码） |
| 错误码 | §9.2 `1xxx`/`12xx`/`13xx`/`14xx`/`15xx` | §9.2 **`1600` 段** |

**安全边界（四条，缺一不可）**：

1. **物理存在**：必须先长按网关配对键 3 s 才开窗口——攻击者拿不到「按一下」这个动作。
2. **AP 口令**：SoftAP 用 WPA2-PSK，口令印在设备贴纸/串口日志首行；不知道口令就连不上（不设开放 AP）。
3. **网络隔离**：服务 bind 在 **AP 口地址**（占位 `192.168.4.1`；实际地址由驱动给出，上板实测回填，CAL-12）；**取不到该地址时退化为绑 `0.0.0.0` 并在串口打醒目告警**——这是 CAL-12 的**已知弱点**（该退化下 STA 侧也可达），此时隔离靠「只在配网窗口内开 + AP 口令 + 接口全部幂等/只读或需在窗口内」三条兜底。不暴露到公网；不需要 TLS（AP 内网链路，明文可接受，**这是有意的取舍**）。
4. **窗口期外一律拒绝**：不在配网模式 → `409 code=1600`；窗口开着但已超时 → `410 code=1601`（§9.2）。任何 `/api/provision/*`、`/api/pair/*` 都不做「先建连再校验」。

**本 API 不做的事**：不建账号、不绑定设备到账号（那是 §6.3/§6.6，必须联网走服务器）、不下发业务命令（那是 §6.11 与 §4.5）。

### 12.2 进入 / 退出配网模式

| 项 | 规则 |
|---|---|
| 进入 | **长按配对键 3 s（±0.5 s，消抖 50 ms，引脚见《引脚与接线表》§2.5）** → 串口打印 `[PROV] enter AP mode ssid=ElderCare-XXXX remain=600` |
| 退出（三种） | ① 再长按 3 s 立即退出；② 窗口超时（`provision_timeout_s` 默认 **600 s**）；③ `/api/provision/wifi` 提交成功且 STA 连接成功后 **90 s** 自动退出——这 90 s 就是 §12.6 的 `settle_s`：**期间 `remain_s` 按 `settle_s` 倒数到 0**，App 收到 200 后的自然掉线是预期（复核 N1） |
| 配网中指示 | **r5：不做本地声光指示**；串口每 30 s 打一次 `[PROV] waiting… remain_s=%u` |
| 配网成功指示 | 长鸣 1 次（≤300 ms，可被 `mute_alarm` 静音） |
| 掉电行为 | 配网状态不持久化；白名单与 Wi-Fi 口令**持久化**（见 §12.9） |

### 12.4.1 `GET /api/scan`（Wi-Fi 扫描缓存，**窗口内外都可用**）

请求：无参数、无请求体。

响应 `data`（外层信封同 §12.1：`code`/`message`/`data`/`ts`）：

| 字段 | 类型 | 单位 | 必填 | 说明 | 示例 |
|---|---|---|---|---|---|
| `cached` | bool | — | 是 | 是否有一份可用快照。**`false` 时以下字段分别为 `0`/`0`/`0`/`20`/`[]`，不是报错** | `false` |
| `scanned_at` | int | **开机毫秒** | 是 | 快照时刻，与网关内部 `gw_now_ms` 同一口径（**不是 Unix 时间戳**，不跨越掉电） | `18402` |
| `age_ms` | int | ms | 是 | 距快照的时长（H5 用来提示「扫描于 18 秒前」）；无缓存时 `0` | `18402` |
| `count` | int | 条 | 是 | `list` 的实际条数（≤ `limit`） | `3` |
| `limit` | int | 条 | 是 | 上限，固定 **`20`**（`GW_PROV_SCAN_LIST_MAX`） | `20` |
| `list` | object[] | — | 是 | 热点列表，**按扫描返回顺序**（未排序）；无缓存时 `[]` | 见下 |
| `list[].ssid` | string | — | 是 | SSID，已做 JSON 字符串转义（`"` 与 `\` 前加反斜杠） | `"Home-2.4G"` |
| `list[].rssi` | int | dBm | 是 | 信号强度（负值，越接近 0 越强）；同名 SSID 取**最强**一条 | `-52` |
| `list[].ch` | int | 信道 | 是 | 2.4 G 信道 `1–14`；取不到时 `0` | `6` |

```json
{"code":0,"message":"ok","data":{"cached":true,"scanned_at":18402,"age_ms":18402,"count":2,"limit":20,"list":[{"ssid":"Home-2.4G","rssi":-52,"ch":6},{"ssid":"CMCC-Home","rssi":-78,"ch":11}]},"ts":1792243505000}
```

规则（与固件逐条对齐）：

- **只列 2.4 GHz**：网关只能连 2.4 G，把 5 G 热点列出来只会让人选中一个连不上的 SSID。
- **同名 SSID 只留一条、取最强**：同一家庭常见多个 AP / 中继同名，列重复条目会让下拉框出现多个一样的选项。
- **隐藏 SSID（空串）不列**：选了也连不上；需要连隐藏网络时用页面上的「手动输入」。
- **最多 20 条**：`limit` 恒为 `20`，超出截断（不报错）。
- **字符串转义**：`ssid` 里的 `"` 与 `\` 由网关做 JSON 转义后再下发，App 侧按标准 JSON 解析即可，不需要自己再处理。
- **只读、无副作用、幂等**：本接口**不触发扫描**、不改任何状态，可在页面打开时轮询。
- **窗口外可用**：配网窗口关闭时其它 §12 接口回 `409 code=1600`，本接口**照样 200**——H5 页面在窗口外打开时也能立刻知道「上次扫到过什么」，不会卡在 1600 上白屏。

**为什么是「缓存」而不是现场扫（硬件硬约束）**：RK2206 是**单射频**，SoftAP 一起来驱动就**直接拒绝 `Scan()`**（`rk2206-gateway/src/gw_net.c` 里 `gw_net_scan_list()` 的注释与 `gw_net_scan_cache_refresh()` 的说明都写了这一条）。所以网关的策略是：**开窗起 AP 之前扫一次**，把结果存进内存快照供本接口读。因此：

- 快照是**「开窗那一刻」**的，不是「读接口那一刻」的（`age_ms` 就是这个时差）。
- 每次重新进配网窗口都会刷新一次快照（旧的被覆盖）。
- **掉电即失效**（只在 RAM 里），上电后第一次开窗前 `cached:false`。

**判据日志行**（串口，开窗时打一次，`N` 为热点数）：

```
[NET] 开窗前扫描完成：N 个 2.4 G 热点（页面下拉可选；没有就手输）
```

### 12.6 `POST /api/provision/wifi`

请求体：

| 字段 | 类型 | 必填 | 约束 | 示例 |
|---|---|---|---|---|
| `ssid` | string | 是 | 1–32 字节；**必须 2.4 GHz**（5 G 热点连不上） | `"HOME-2.4G"` |
| `password` | string | 是 | **8–63 字节（WPA2-PSK）**。**本阶段不支持开放网络**：既不接受空串，也不接受 `open=true` 之类的替代标志；SSID 若为开放网络 → 预检直接 `400 code=1602`、`reason=open_not_supported`（v1.2 定版，复核 M14） | `"P@ssw0rd8"` |
| `hidden` | bool | 否 | 隐藏 SSID，默认 `false` | `false` |
| `timeout_s` | int | 否 | 连接超时 10–60，默认 30 | `30` |

响应 `data`：

| 字段 | 类型 | 说明 | 示例 |
|---|---|---|---|
| `saved` | bool | 口令是否已持久化 | `true` |
| `connecting` | bool | 是否已开始连接 | `true` |
| `ssid` | string | 回显 | `"HOME-2.4G"` |
| `settle_s` | int | **SoftAP 还会保持多少秒**（给 App 收包与切网的时间），默认 90 | `90` |
| `precheck.ap_found` | bool | 预扫描是否看到该 SSID | `true` |
| `precheck.rssi` | int | 预扫描信号（dBm） | `-52` |
| `precheck.ch` | int | 预扫描信道 | `6` |

```json
{"code":0,"message":"ok","data":{"saved":true,"connecting":true,"ssid":"HOME-2.4G","settle_s":90,"precheck":{"ap_found":true,"rssi":-52,"ch":6}},"ts":1792243200000}
```

规则：

- **预检**：先扫一次 2.4 G 热点。目标 SSID 不在列表且 `hidden=false` → 直接 `400 code=1602`、`reason=not_found`，**不落盘**。
- **口令不落明文日志、不回显、不落明文盘**（**v1.3 措辞定版**）：响应与串口日志都不含 `password`；硬要求是「**不得明文落盘 / 不得进日志 / 任何响应不回显**」——口令进日志、进仓库这条不容打折。至于落盘时用**真加密还是混淆**由实现定：当前实现是「盐 + 编译期 SN 派生的 16 B」**XOR 混淆**，`gw_store.c` 注释已写明「只是混淆不是加密」；**「混淆是否算达标」待 PM 裁定**（吸收 t10 偏差 #4，不阻塞 P0 演示）。
- **成功后网关切 STA 并关闭 SoftAP**：`settle_s` 秒后 AP 消失——**App 收到 200 后的自然掉线是预期行为**，不是故障。`settle_s` 期间 `/api/provision/status` 的 `remain_s` **按 `settle_s` 倒数到 0**（不再回显原 600 s 窗口值），App 可据此显示「还有 N 秒」（复核 N1）。
- **失败自动退回 AP**：连接超时/认证失败（`reason=auth`/`timeout`）→ 网关在 30 s 内退回 AP 模式并把窗口重置为 600 s，App 重连 AP 重试（对应 §9.2 `1602`）。
- **重复提交**：`busy=connect` 期间再提交返回 `409 code=1603`。

### 12.9 `POST /api/pair/bind`

请求体：

| 字段 | 类型 | 必填 | 约束 | 示例 |
|---|---|---|---|---|
| `op` | string | 是 | `add` / `del` / `clear` / `list` | `"add"` |
| `sn` | string | `add`/`del` 必填 | §0.7 已定义的编号（`M1`/`M2`/`M4`…） | `"M2"` |
| `mac` | string | `add` 必填 | **必须来自最近一次扫描结果** | `"11:22:33:44:55:02"` |
| `alias` | string | 否 | 房间别名 ≤16 字符（仅网关与云端展示，**不进 UART 帧**） | `"卧室"` |
| `confirm` | string | `clear` 必填 | 固定 `"CLEAR"`（防误触清空） | `"CLEAR"` |

响应 `data`：

| 字段 | 类型 | 说明 | 示例 |
|---|---|---|---|
| `op` | string | 回显 | `"add"` |
| `sn` | string | 回显（`list`/`clear` 时缺省） | `"M2"` |
| `bound` | object[] | 操作后的全量白名单 | 见示例 |
| `slots_free` | int | 剩余槽位 | `6` |
| `connected` | bool | 该节点是否已建立 SLE 连接（`add` 后 3 s 内） | `true` |

```json
{"code":0,"message":"ok","data":{"op":"add","sn":"M2","bound":[{"sn":"M1","mac":"11:22:33:44:55:01","alias":"厨房"},{"sn":"M2","mac":"11:22:33:44:55:02","alias":"卧室"}],"slots_free":6,"connected":true},"ts":1792243200000}
```

规则：

- **`add` 必须「先扫后绑」**：`mac` 不在最近一次扫描结果里，或 `scanned_at` 距今 >300 s → `400 code=1604`（防止手工编 MAC 绕过）。
- `add` 成功后网关立即发 §3.4 `0x22`，等汇聚 `0x23` 再返回 200（**同步等待 ≤3 s**）；超时/汇聚离线 → `409 code=1605`（此时**网关已写白名单**，汇聚重连后按 §12.9 最后一条重建）。
- **汇聚拒绝码透传（v1.3，吸收 t10 偏差 #9）**：汇聚明确拒绝时，§3.4 `0x23` 的 `result` —— `10`（白名单满）/ `11`（MAC 已被别的 SN 占用，§9.3）—— **原样**作为 IoTDA 命令的 `result_code` 上抛；**本地 HTTP 侧仍是 `409 code=1605`**（HTTP 不新增 1600 段码，App 从 `message` 与网关串口日志区分子原因）。
- `del` 会让汇聚断开该节点并停止上报（白名单里删掉即不再轮询）。
- 白名单**持久化在网关**（掉电不丢）；**汇聚不落盘**：每次汇聚上电后，网关用 `0x22 op=list` 无参时走过一次「逐条 `add`」重建（避免两边状态不一致、也避免汇聚 Flash 写坏）。
- 上限 8（SLE 官方 8 路连接），满时 `409 code=1606`。

| 场景 | 走哪条 | 说明 |
|---|---|---|
| 现场首次配网、现场加节点 | **本地 §12** | 不依赖公网，最快；这就是 P0 演示路径 |

| 白名单状态回流云端 | 属性 `bound_nodes` + 明细 `nodes[].mac`（§4.3） | 服务器写 §7.5 `nodes`，App 从 §6.7 读 |

### 12.11 网关内置 H5 页面（**P0 主路径**，约束如下）

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **单文件** HTML（CSS/JS 内联，不引外部字体/图标库） | 网关 Flash 有限，且 AP 模式下取不到任何外部资源 |
| 2 | **无 CDN / 无外网依赖**，全离线可用 | 连 AP 时手机没有外网（系统会提示「无法访问互联网」，属正常） |
| 3 | 只调用 §12 的 5 个本地接口，**不得**调用 §6 的云端 REST（除 §6.6 绑定账号由 App/脚本负责） | 窗口期内没有公网；且本地接口不鉴权（§12.1 边界） |
| 4 | 不做账号绑定、不存口令明文、不在页面里回显 `password` | 同 §12.6 的口令纪律 |
| 5 | 每个请求自带 3 s 超时与错误码提示（`1600`–`1606` 一张文案表） | 现场演示不能只有「转圈」 |
| 6 | 页面入口 `http://{AP 口地址}/`（占位 `http://192.168.4.1/`；**HTTP 不是 HTTPS**），与 §12.1 的 API 域同源；**页面内一律用相对路径**（`/api/...`），不得把绝对地址写进 HTML | 免鉴权依赖同源；浏览器自动跳 HTTPS 会打不开（§9 排查表第 6 组）；地址由驱动决定（§12.3、CAL-12），写死会指错门 |

> 该页面是 **P0 开场演示的载体**（配网 → 绑定账号 → 扫描节点 → 绑定节点 → 看数据），实现归 `rk2206-gateway/`（t10）；契约只定「页面必须满足上面 6 条 + 只调 §12」。
> **ADR-0001 已同步（t69）**：①「SoftAP 页面承担 P0 开场演示，App 是 P1」；② A 路线的地址假设改为「**由板级驱动决定、上板实测后回填**」，并把「客户端数无法硬限」「取不到 AP 口地址时退化 `0.0.0.0`」写成已登记风险——见 ADR-0001 的「前提与风险（CAL-12）」一节。

### 13.2 步骤表（**P0 主路径 = 手机浏览器 + 网关 H5 页面**；安卓/鸿蒙 App 走同一套 HTTP 契约，均为 P1）

> 下表「谁」列里写**手机浏览器**的步骤，由网关内置 H5 页面（§12.11）完成，不需要装任何 App；写 **手机（系统 WLAN 设置）** 的步骤（**3/4/6/9**）是**系统级动作**（扫热点、连 AP、切网），**这几步 P0 由人工在手机上完成，不能用 `curl` 代替**；写 **App** 的步骤（1/10/14）是纯 HTTP 调用，P0 可用服务器自带调试脚本或 `curl` 代替（验收脚本见 §13.5）。

| 步 | 谁 | 动作 | 接口 / 引脚 | 期望结果 | 异常处理 |
|---|---|---|---|---|---|
| 1 | App | 注册 / 登录，拿 JWT | §6.3 / §6.4 | `code=0` + `data.token` | `1102` 账号或密码错 |
| 2 | 用户 | **长按网关配对键 3 s** | 配对键（接线表 §2.5） | 串口 `[PROV] enter AP mode`（**r5：不做本地声光提示**） | 无反应 → 查按键通断（CAL-14） |

| 4 | 手机（系统 WLAN 设置） | 用设备贴纸/串口日志上的口令连上该 AP | 系统 API | 连上，DHCP 拿到驱动给的网段地址（占位 `192.168.4.1xx`） | 提示「已连接，无法访问互联网」是**正常现象**，不要被系统弹窗误导 |
| 5 | 手机浏览器 | 确认在配网窗口内 | `GET /api/provision/status` | `mode=ap`、`remain_s>0`、`hub_online=true` | `1600`/`1601` → 回到第 2 步重新长按 |
| 6 | 手机（系统 WLAN 设置） | 列出家庭 Wi-Fi（手动输入隐藏 SSID） | 系统 API | 拿到 `ssid` | 5 G 热点不要选（§12.6 约束） |
| 7 | 手机浏览器 | 提交家庭 Wi-Fi | `POST /api/provision/wifi` | `saved=true`、`precheck.ap_found=true`、`settle_s=90` | `1602` → 查 SSID/密码（`reason=not_found`/`auth`） |
| 8 | 网关 | 切 STA 连家庭 Wi-Fi，`settle_s` 后关 SoftAP | — | 串口 `[PROV] sta connected ip=192.168.1.23` | 30 s 内连不上 → 自动退回 AP，手机重试第 4 步 |
| 9 | 手机（系统 WLAN 设置） | 切回家用 Wi-Fi 或蜂窝网络（此后**本地 API 不可达**） | 系统 API | 能访问服务器 | 「无法访问互联网」若持续 >2 s → 手动切网 |
| 10 | App | **绑定账号**（必须联网，走服务器） | §6.6 `POST /api/devices/bind` | `code=0` | `1201` 绑定码错 / `1202` 已被绑定 / `1203` 已过期 |

### 13.3 两条合法顺序（**实现任选，契约都支持**）

任务卡里的顺序（提交 Wi-Fi → 绑定账号 → 触发节点扫描/绑定）对应下面的 **B2 顺序**，是默认路径：

| 顺序 | 步骤序列 | 优点 | 代价 |
|---|---|---|---|
| **B1（推荐现场用）** | 4 → 5 → 11 → 12 → 13 → 7 → 8 → 10 | 扫描/绑定全在 AP 内完成，**不依赖公网**；一次把现场做完 | App 要在提交 Wi-Fi 前多做三步 |
| **B2（任务卡默认）** | 4 → 5 → 7 → 8 → 10 → 11 → 12 → 13 | 与「先联网、再配节点」的直觉一致；可远程加节点 | 扫描/绑定必须走**云端命令**（§4.5），需要服务器加接口（P1，PM 裁决） |

> 为什么两条都能成立：§12 的 5 个本地接口在**窗口期内任意时刻**都可调用（没有顺序依赖），而 §4.5 的 `pair_scan`/`pair_bind` 在**联网后任意时刻**都可用——两条路最终都落到同一组 UART 命令（§3.4 `0x20`/`0x22`），汇聚侧只有一套逻辑。

### 13.4 蓝牙配网（**不做** —— r5 决议删除 BLE/蓝牙，本节仅留结论）

| 项 | 结论 |
|---|---|
| P0 范围 | **只做 Wi-Fi 配网**（本节流程） |
| 蓝牙 | **不做、不承诺**：安卓侧蓝牙配网需要设备暴露 GATT 服务 + 安卓 12+ 的 `BLUETOOTH_SCAN`/`CONNECT` 权限 + 厂商 ROM 差异，P0 时间不够 |
| 若将来做 | **不做**（r5 删除）：原方案是「BLE 只传 SSID/口令，不传业务数据」；节点/网关需新增 GATT 服务 → 若重启须 PM 立项，见 CAL-15 |

### 13.5 失败与恢复矩阵（现场排障用）

| 现象 | 最可能原因 | 动作 |
|---|---|---|
| 手机看不到 `ElderCare-XXXX` | 没进窗口（没长按满 3 s）/ 手机是 5 G-only 连接策略 | 重按 3 s 看串口是否打 `[PROV] enter AP mode`；CAL-14/CAL-12 |
| 连上 AP 但打不开页面 | 网关 HTTP 服务没起来（CAL-12）/ **地址不是占位那个**（实际地址由驱动决定，以串口首行为准）/ 手机把 AP 当无网自动切走 | 先看串口首行的 AP 地址，再显式输 `http://<实际地址>/api/provision/status`；关闭「自动切换网络」 |
| `1602 reason=not_found` | 选了 5 G 热点 / SSID 打错 / 家庭路由器隐藏 SSID 但没勾 `hidden` | 换 2.4 G SSID；隐藏网络勾 `hidden=true` |
| `1602 reason=auth` | 口令错 | 重新输入（口令不回显，注意大小写） |
| 提交成功后 App 一直连不上服务器 | 手机仍黏在已关闭的 AP / 网关切 STA 失败 | 等 90 s；手动切回家用 Wi-Fi；看网关串口 `[PROV]` 日志 |
| `1605` 汇聚离线 | `H1` 没上电 / 串口 TX-RX 反 / 没共地 | 按接线表 §2.1 三线检查（TX/RX/GND） |
| 扫描列表只有 `sn:"?"` | 节点固件未实现 §2.7 的 `0xFF` 广播结构 | 固件按 §2.7 改；临时办法：用 `mac` 手工 `add` 一次，白名单会记住映射 |
| 绑定成功但 App 一直显示离线 | 属性 60 s 周期还没到 / `nodes` 明细 300 s 未到 | 等一个周期；或用 `demo` 注入验证链路（§6.12） |
