## 0. 通用约定

### 0.1 命名与大小写

- **设备编号 `sn`**：大写字母 + 数字，见 §0.7。JSON 里字段名一律 `snake_case`（小写+下划线）；`type` 取值小写单词；MQTT topic 全小写（IoTDA 规定的 `$oc/` 前缀除外）。
- **服务器侧主键 `device_id`**：MySQL `BIGINT` 自增；**不要**和 IoTDA 的 `device_id`（字符串，平台生成）混用。前者命名 `device_id`，后者命名 `iotda_device_id`。
- 数值字段禁止用字符串传数字（`"320"` ✗，`320` ✓）。

### 0.2 时间

- 南向 JSON 与 REST API：时间戳字段统一命名 `ts`，类型 **int64**，单位 **Unix 毫秒（UTC）**。示例 `1760000000000` = 2026-10-09 18:13:20 UTC。
- MySQL：业务时间列为 `DATETIME(3)`（UTC，连接必须 `SET time_zone='+00:00'`），另有 `*_ms BIGINT` 冗余列供精确比对。
- 报表的「日/小时」一律按 **Asia/Shanghai（UTC+8）日历**切分（§7.6）。
- IoTDA 报文的 `event_time` 是唯一例外，用平台格式，见 §4.6。
- 时钟来源：节点/汇聚无 RTC，开机后以「首次上电 → 汇聚轮询应答」由网关下发一次基准时间（P1，见 §3.4 `0x13`）。**P0 允许 `ts` 为设备侧自开机毫秒数**,服务器按收到时刻纠正——此降级必须在 `/api/health` 的 `clock_source` 里暴露（见 §6.16）。

### 0.3 单位与精度

| 量 | 单位 | 类型 | 精度/范围 | 示例 |
|---|---|---|---|---|
| 气体（烟雾/可燃气/CO） | mV（**已折算回传感器 AO 侧**，0–5000） | int | 1 mV | `320` |
| 温度 | °C | double | 0.1，−40.0–125.0 | `24.5` |
| 湿度 | %RH | double | 0.1，0.0–100.0 | `56.2` |
| 时间戳 | Unix ms | int64 | ≥0 | `1760000000000` |
| 持续时长 / 周期 | 秒 | int | 1–86400 | `1800` |
| 距离 | m | double | 0.1–10.0 | `2.4` |
| 电平 | 0/1 或 bool | — | — | `true` |
| 序号 | — | int | 0–65535（uint16，回绕） | `65535` |

### 0.4 布尔与空值

- JSON 布尔用 `true` / `false`，**禁止** `0`/`1`。数据库存 `TINYINT(1)` 的 0/1。
- 「无值」：JSON 字段**缺省即无值**，不要写 `null` 占位（`payload` 内必填字段除外，见各 type 表）。数据库列允许 `NULL` 时语义见列说明。

### 0.5 编码与前向兼容

- 文本一律 **UTF-8 无 BOM**；JSON 不允许注释、尾随逗号、`NaN`/`Infinity`。
- **接收方必须忽略未知字段**（前向兼容）；**新增必填字段 = 破坏性变更**，必须走 PM。
- 枚举遇到未知值：设备侧按「最保守」处理（如未知 type 丢弃并计数）；服务器侧存原值 + 记 WARN，不拒绝整条报文。

### 0.6 协议版本

每个链路都有 `ver`/版本标识：SLE JSON 用信封可选字段 `fw`；UART 帧用第 3 字节 `VER=0x01`；REST 用 URL 前缀 `/api`（v2 时改 `/api/v2`）。**v1 序号即本文件名里的 v1**，变更记录见 §12。

| sn | 角色 | 房间 | 搭载传感器 | 优先级 | 状态 |
|---|---|---|---|---|---|

> ⚠️ **到货情况**：截至 2026-10-17 手上只有 **2 块 WS63 开发板**（够 1 汇聚 + 1 节点），第 3 块**待用户采购确认**。因此 P0 施工顺序是「先跑通 1 汇聚 + 1 节点 + 网关」的闭环，第三块到货后再插入星型网络（星型支持 8 路，加节点不需要改协议）。
> 网关自身的 IoTDA 侧编号：`node_id` = 网关 SN = `M0-` + WiFi/BLE MAC 后 3 字节大写十六进制（示例 `M0-3F1A2B`），控制台录入时填这个值。

## 1. 系统分层与地址模型

```
┌─────────────┐  SLE 星闪(0x060B/0x1122)   ┌──────────────┐   UART 115200 8N1   ┌──────────────┐
│ M1/M2/M4 等 │ ─────── JSON 上行 ───────▶ │  H1 汇聚节点 │ ──── 二进制帧(+) ──▶ │ M0 RK2206 网关│
│  WS63 节点  │ ◀────── 下行命令 ──────── │  WS63(Central)│ ◀─── 二进制帧(−) ── │  (唯一上云口) │
└─────────────┘                           └──────────────┘                     └──────┬───────┘
       ▲ 433MHz 门铃接收器（不经星闪，直进网关 GPIO 中断，唯一独立生命线）                │ MQTT 1883
       └──────────────────────────────────────────────────────────────────────────────┤
                                                                                       ▼
   ┌──────────────┐   HTTP webhook    ┌────────────────┐   规则引擎数据转发   ┌────────────────┐
   │ 鸿蒙 App     │ ◀── REST/轮询 ──▶ │ 自建服务器      │ ◀────────────────── │ 华为云 IoTDA   │
   │ (ArkTS)      │      Push Kit     │ Node.js+MySQL8 │                      │ 1 台设备=网关   │
   └──────────────┘                   └────────────────┘                      └────────────────┘
```

| 层 | 作者（ownership） | 契约章节 |
|---|---|---|
| 节点/汇聚固件 | `ws63-firmware/` | §2、§3、§8 |
| 网关固件 | `rk2206-gateway/` | §3、§4、§8 |
| 云端服务 | `server/` | §5、§6、§7、§9 |
| 手机应用 | `harmony-app/` | §6、§9 |

**数据流三条通路**（三者互不替代，实现时都要做）：

1. **周期通路**：节点每 3 s 被轮询应答一次 → 汇聚聚合 → 网关每 60 s 上报一次 IoTDA 属性（§4.3）。
2. **事件通路**：跌倒/燃气/SOS/门磁跳变/节点离线 → 不排队，逐级立即上报（目标：传感器检出 → App 可见 ≤3 s）。
3. **兜底通路**：星闪断 → 433 仍直进网关；公网断 → 网关本地声光 + 缓存补传（§4.7）。

## 2. 链路一：节点 → 汇聚（星闪 SLE）

### 2.1 传输层（沿用现有固件，不改）

| 角色 | 节点 = SLE 服务端（Peripheral）；汇聚 = 客户端（Central） | `ws63-firmware/src/sle_hub.h:18` |
| 服务 UUID | `0x060B` | `sle_hub.h:18` ✅ |
| 通知属性 UUID | `0x1122`（NOTIFY/INDICATE，节点→汇聚上行） | `sle_hub.h:21` ✅ |
| 上行 API | `sle_uuid_server_send_report_by_handle_id(uint8_t *data, uint16_t len, uint16_t connect_id)` | `sle_hub.c:149` ✅ |
| 下行 API | 汇聚对 `g_property_handle` 发 SSAP write request；节点侧回调 `ssaps_write_request_cbk` 已注册 | `sle_hub.c:122` ✅ |
| 单条长度 | **≤ 512 字节**（硬约束，超限由节点裁剪可选字段，不引入分片） | ⏳ CAL-05 |
| 字符集 | UTF-8 | 本契约 |
| 轮询周期 | 3 s/节点；节点须在 **200 ms** 内应答 | 实施计划 §5 |

| 组网形态 | **单主多从星型；不做中继/多跳**——星闪多跳无一手依据（官方「中继特性说明」讲的是 Wi-Fi 中继），**本契约不出现 mesh 组网方案** | 可行性核查 §3.2 |

| 组网排障 | 扫描不到设备时，先查「设备是否已在配对设备列表中 / 是否已与其他设备配对」，需先清除配对信息 | 《软件开发指南》`:2181` |

### 2.2 上行信封（所有 type 共用）

| 字段 | 类型 | 必填 | 单位 | 说明 | 示例 |
|---|---|---|---|---|---|
| `sn` | string | 是 | — | 节点编号，§0.7 | `"M1"` |
| `ts` | int64 | 是 | Unix ms | 采样时刻（§0.2） | `1760000000000` |
| `type` | string | 是 | — | §2.3 之一 | `"gas"` |
| `payload` | object | 是 | — | §2.4，随 type 变化 | `{"smoke":320}` |
| `seq` | int | 否 | — | 节点侧自增序号（0–65535 回绕），用于丢包统计 | `12` |
| `req_id` | int | 否 | — | 回显汇聚 poll 的 `id`；**应答 poll 时必填** | `7` |
| `fw` | string | 否 | — | 节点固件版本（`MAJOR.MINOR.PATCH`） | `"0.1.0"` |

**完整示例（单行，实际发送无换行）：**

```json
{"sn":"M1","ts":1760000000000,"type":"gas","payload":{"smoke":320,"lpg":180,"co":12,"temp":24.5,"humi":56.2},"seq":12,"req_id":7,"fw":"0.1.0"}
```

### 2.3 type 取值表

| `type` | 产生节点 | 触发方式 | 优先级 |
|---|---|---|---|
| `gas` | M1（MQ-2 烟雾 + AHT20） | 轮询应答 + 超阈值立即 | P0 |
| `fall` | M2（M3 P1） | 事件立即（不等轮询） | P0 |
| `door` | M4 | 状态跳变立即 + 轮询应答（ch0 玄关门、ch1 阳台门；ch2/ch3 窗磁 P1 预留） | P0 |
| `presence` | M4（M5 P1） | 轮询应答 + 由静到动立即 | P0 |
| `status` | 全部 | 轮询应答兜底（节点自检） | P0 |
| `env` | M1 | 温湿度越界（§8.3） | P1 |

> `sos` **不作为节点上行 type**：433 按钮进网关 GPIO，由网关直接产生（§4.4）；App 发起由服务器下发命令。实施计划 §10 里 `sos` 的出现位置是「网关 → 云」，本契约与之一致。

### 2.4 各 type 的 payload 字段

#### 2.4.1 `gas`（M1 厨房；**P0 只装 MQ-2**）

| 字段 | 类型 | 单位 | 范围 | 必填 | 说明 | 示例 |
|---|---|---|---|---|---|---|
| `smoke` | int | mV（**已折算回 AO 侧**） | 0–5000 | 是 | MQ-2 烟雾通道（ADC 读数 ×2）。datasheet 参考：2000 ppm C₃H₈ 下输出 `Vs = 2.5–4.0 V` | `320` |
| `temp` | double | °C | −40.0–125.0 | 是 | AHT20 | `24.5` |
| `humi` | double | %RH | 0.0–100.0 | 是 | AHT20 | `56.2` |
| `lpg` | int | mV（AO 侧） | 0–5000 | 否 | MQ-5 可燃气；**P0 未装 → 字段缺省**（P1 装后才有） | `180` |
| `co` | int | mV（AO 侧） | 0–5000 | 否 | MQ-7 CO；**本阶段不接**（P1） | `12` |
| `adc_mv` | int[] | mV（**分压后**） | 0–3300，长度 1（P1 扩到 3） | 否 | 调试用原始 ADC 读数；P0 = `[ch2]` = `[IO09]` | `[160]` |
| `warmup` | bool | — | — | 否 | MQ-2 处于预热/老化期 | `false` |

**MQ-2 的电气硬约束（一手 datasheet《MQ-2 Manual Ver1.4》）**：

| 项 | 值 | 契约要求 |
|---|---|---|
| 加热电压 `VH` | **5.0 V ± 0.1 V** | 🔴 **必须 5 V 供电**，datasheet 没有任何一款支持 3.3 V 加热 → 节点另配 5 V 轨 |
| 加热电阻 `RH` | 29 Ω ± 3 Ω | 5 V 下 ≈172 mA（`PH ≤ 950 mW`） |
| 输出 `Vs` | 2.5–4.0 V（2000 ppm C₃H₈） | 🔴 **超过 3.3 V ADC 量程，必须分压后再进 ADC** |
| 预热 | **>48 小时** | 老化期间不得长期断电 |
| 老化 | 存放 <1 个月 → ≥48 h；1–6 个月 → ≥72 h；>6 个月 → ≥168 h | 不可压缩的日历时间，**D1 就要通电** |
| 禁忌 | 有机硅蒸汽使灵敏度**永久不可恢复** | 装配与打胶时避开硅胶类物质 |

#### 2.4.2 `fall`（M2 卧室雷达）

| 字段 | 类型 | 单位 | 范围 | 必填 | 说明 | 示例 |
|---|---|---|---|---|---|---|
| `fall` | int | — | 0/1 | 是 | 1 = 跌倒（模块 0x0E02 DATA[0]=1 或 TX2 上升沿） | `1` |
| `presence` | int | — | 0/1 | 是 | 雷达有人/无人（人存判定，非跌倒） | `1` |
| `src` | string | — | `uart`/`tx2` | 否 | 触发通道；`tx2` = 硬件冗余通道 | `"uart"` |
| `dist` | double | m | 0.0–6.0 | 否 | 目标距离（模块参数回包可得时填，本版可缺省） | `1.8` |

> ⚠️ 模块内部要求**持续跌倒 15–20 s**（灵敏度 10，`LD6002C技术规格书V1.1`) 才上报，因此端到端延迟 ≈ 判定时间 + ≤100 ms。这是模块行为，不是链路问题。

#### 2.4.3 `door`（M4 门厅）

| 字段 | 类型 | 单位 | 范围 | 必填 | 说明 | 示例 |
|---|---|---|---|---|---|---|
| `door` | bool | — | — | 是 | **玄关门**（ch0 = `IO00`）：`true`=开、`false`=关 | `true` |
| `window` | bool | — | — | 是 | **阳台门/窗磁**（ch1 = `IO02`）：`true`=开；P1 扩到多路窗磁时取「任一开」 | `false` |
| `ch` | int | — | 0–7 | 否 | 本次跳变的通道（`0`=玄关门，`1`=阳台门，`2`/`3`=P1 窗磁预留），仅跳变上报时出现 | `0` |

> P0 只装 2 路干簧管（玄关门 + 阳台门）；`IO13`/`IO14` 为 P1 窗磁预留，见《引脚与接线表》§6。

#### 2.4.4 `presence`（M4 门厅 / M5 客厅）

| 字段 | 类型 | 单位 | 范围 | 必填 | 说明 | 示例 |
|---|---|---|---|---|---|---|
| `presence` | bool | — | — | 是 | 当前是否有人（PIR 触发后保持 `true`，见下） | `true` |
| `last_motion_ts` | int64 | Unix ms | ≥0 | 是 | 最近一次 PIR 触发时刻（**"无活动"判定的唯一依据**） | `1760000000000` |
| `count` | int | 次 | 0–65535 | 否 | 本节点自开机以来活动触发总次数 | `37` |
| `ch` | int | — | 0–7 | 否 | 触发通道，仅跳变上报时出现 | `0` |

`presence` 的保持语义：PIR 触发 → `presence=true`；**持续 60 s 无新触发 → `presence=false`**（与 30 分钟无活动判定口径不同，后者用 `last_motion_ts`）。阈值可由命令 `set`（§2.5）调整。

#### 2.4.5 `status`（所有节点，自检 + 兜底）

| 字段 | 类型 | 单位 | 范围 | 必填 | 说明 | 示例 |

### 2.6 汇聚侧行为（P0 必须实现）

1. 每 3 s 依次对 `M1/M2/M4` 发 `poll`，等 200 ms；收到应答即刷 `last_seen`。
2. 应答里的节点 JSON **原样**交给 §3（不解析业务字段，只做透传与聚合）——汇聚不做阈值判断，阈值判断在网关与服务器（避免三处逻辑不一致）。
3. 连续 3 次超时 → 生成 §3.4 `0x03`（节点离线事件）并在下一次`0x02`心跳里把 `online=false`。
4. 汇聚自己的心跳每 30 s 发一次 `0x02`（含所有节点在线表）。
5. 汇聚不缓存历史（只有最近一帧快照），断连期间的补传由网关的 Flash 环形缓冲负责（实施计划 §9.1 `config_task`）。

### 3.2 帧结构

```
 偏移  长度  字段        说明
  0     1     SOF1        0xAA
  1     1     SOF2        0x55
  2     1     VER         0x01（本契约版本）
  3     1     TYPE        §3.4，方向由 TYPE 决定
  4     2     SEQ         uint16 **小端**，发送方自增（0–65535 回绕）
  6     2     LEN         uint16 **小端** = PAYLOAD 字节数（0–1024）
  8     LEN   PAYLOAD     UTF-8 JSON（§3.5）
 8+LEN  2     CRC16       uint16 **小端**，CRC-16/MODBUS（§3.3），覆盖范围 = VER..PAYLOAD 末字节
```

- **整帧长度 = 10 + LEN**；`LEN > 1024` 的帧一律按非法帧丢弃（防伪造 SOF 导致的越界读）。
- 帧内多字节字段（SEQ/LEN/CRC）**统一小端**；只有 PAYLOAD 里的 JSON 是文本。**不要和雷达的 TinyFrame 混淆**（那套是帧头大端、数据小端，见 `radar_hub.c:24-29`）。

### 3.3 CRC-16/MODBUS

| 参数 | 值 |
|---|---|
| 多项式 | `0x8005`（反射实现 `0xA001`） |
| 初值 | `0xFFFF` |
| 输入/输出反射 | 是 / 是 |
| 结果异或 | `0x0000` |
| **自检向量** | `crc16("123456789") == 0x4B37` |
| 计算范围 | 帧内 `VER` 到 `PAYLOAD` 末字节（**不含** 2 字节 SOF，不含 CRC 本身） |

C 参考实现（网关与汇聚共用，放 `common/`）：

```c
uint16_t uart_frame_crc16(const uint8_t *d, uint16_t n)
{
    uint16_t crc = 0xFFFFu;
    for (uint16_t i = 0; i < n; i++) {
        crc ^= d[i];
        for (int b = 0; b < 8; b++) {
            crc = (crc & 1u) ? (uint16_t)((crc >> 1) ^ 0xA001u) : (uint16_t)(crc >> 1);
        }
    }
    return crc;
}
```

### 3.5 PAYLOAD 与 JSON

- PAYLOAD 就是一条完整 UTF-8 JSON 对象，**不允许数组或裸值作为顶层**。
- 节点 JSON 上行时由汇聚**原样透传**（§2.2），不改字段；汇聚自己产生的报文用 §3.4 定义的结构。
- JSON 内的 `ts` 等数值仍是 Unix 毫秒，与 §0.2 一致。

### 3.6 分帧与容错规则

| 情形 | 处理 |
|---|---|
| 粘包（一读多帧） | 按 LEN 循环切帧，直到剩余 < 10 字节 |
| 半包（帧不完整） | 保留残余字节，等下一批；残余 > 2058 字节（2×最大帧）未成帧 → 清空并计数 |
| 假 SOF | 逐字节滑动找 `0xAA 0x55`；LEN 越界或 CRC 错 → 丢弃首字节后重找，并回 `0x12 GW_NACK`（同一 SEQ 只回一次，防风暴） |
| CRC 错 | 丢帧 + `GW_NACK(reason=4)` + `err_cnt++` |
| 未知 TYPE | 丢帧 + `GW_NACK(reason=6)`，不崩溃 |
| 序号不连续 | 只记统计（`gw_rx_miss++`），**不要求重传**；下次 `0x01` 里带的 `seq` 自然揭示丢失 |
| 缓冲 | 收发各 ≥ 2048 字节环形缓冲（RK2206 侧沿用 `b6_uart0` 样例的环形缓冲） |

**重传策略（单向下行必答）**：`0x11 GW_CMD` 与 `0x13 GW_TIME` **必须**被 `0x10 GW_ACK` 确认；发送方等 500 ms 未收到对应 ACK → 重发，最多 3 次，仍失败则向上报 `result=1502`（下发失败）并记 ERROR。`0x01/0x02/0x03` **不需要**逐帧 ACK（周期通路天然自愈），网关可选择性回 ACK 用于方向自检。

| `set_report_interval` | `{"seconds":60}`（int，10–3600） | `{"result":"ok","seconds":60}` | 改属性上报周期 |
| `demo_trigger` | `{"event":"fall"}`（`fall`/`gas`/`sos`） | `{"result":"ok","event":"fall"}` | 演示注入，走**真实链路**，见 §11 D-07 |
| `mute_alarm` | `{"duration":300}`（秒，1–3600） | `{"result":"ok","duration":300}` | 静音本地声光（不改变告警状态） |

命令响应体（发往 `.../commands/response/request_id={request_id}`）：

```json
{"result_code":0,"response_name":"COMMAND_RESPONSE","paras":{"result":"ok","event":"fall"}}
```

`result_code`：`0` 成功；非 0 见 §9.3。

### 4.6 报文示例

**属性上报（每 60 s，QoS0）** — topic `$oc/devices/{device_id}/sys/properties/report`：

```json
{"services":[{"service_id":"gateway","event_time":"20261017T120000Z","properties":{"presence":true,"last_motion_ts":1760000000000,"door":false,"window":false,"temp":24.5,"humi":56.2,"smoke":320,"lpg":180,"co":12,"nodes_online":"{\"M1\":true,\"M2\":true,\"M4\":false}","battery":255,"alarm_state":0}}]}
```

**跌倒事件（立即，QoS1）** — topic `$oc/devices/{device_id}/sys/events/up`：

```json
{"services":[{"service_id":"gateway","event_type":"alert","event_time":"20261017T120002Z","paras":{"type":"fall","level":2,"node_sn":"M2","ts":1760000123000,"event_id":"M0-3F1A2B-fall-1760000123000","snapshot":{"fall":1,"presence":1}}}]}
```

**433 求助（立即，QoS1）**：

```json
{"services":[{"service_id":"gateway","event_type":"sos","event_time":"20261017T120500Z","paras":{"source":"button","ts":1760000305000,"event_id":"M0-3F1A2B-sos-1760000305000"}}]}
```

**节点明细（每 300 s 批量，QoS0）** — topic `$oc/devices/{device_id}/sys/messages/up`：

```json
{"name":"node_samples","id":"M0-3F1A2B-1760000300000","content":"[{\"sn\":\"M1\",\"ts\":1760000280000,\"type\":\"gas\",\"payload\":{\"smoke\":320,\"lpg\":180,\"co\":12,\"temp\":24.5,\"humi\":56.2}},{\"sn\":\"M4\",\"ts\":1760000281000,\"type\":\"presence\",\"payload\":{\"presence\":false,\"last_motion_ts\":1760000100000,\"count\":37}}]"}
```

> `event_time` 用 IoTDA 平台格式 `yyyyMMdd'T'HHmmss'Z'`（UTC）。格式与必填性联调首日确认（CAL-04）；**服务器不依赖该字段**（用 `paras.ts`）。

### 4.7 断网缓存与补传（P0 演示动作 6）

1. 网关检测到 MQTT 断开 → 立即本地声光（蜂鸣器 3 kHz，LED 闪烁）+ 进入缓存模式；`alarm_state` 保持。
2. 缓存写入板载 8 MB FLASH 环形缓冲（`b15_flash`/`b21_iot_flash` 样例），容量 **2000 条**（约 24 h 的 5 分钟明细 + 事件）。
3. 重连成功 → 先补**事件**（按 `event_id` 幂等），再把明细**按 5 分钟粒度聚合成 `node_samples`** 补传（**不逐条补**，避免超免费配额；见 §4.8）。
4. 补传完成告警全部消除；补传期间若再次断网，保留未发片段不重复写。
5. 补传进度写入 `device_online.last_heartbeat` 之外的一个属性 `sync_pending`（P1，不给 P0 增加负担）。

### 4.8 消息数预算（免费单元 10000 条/天）

| 用途 | topic | 频率 | 条/天 |
|---|---|---|---|
| 属性上报 | `properties/report` | 60 s | 1440 |
| 节点明细（M1/M2/M4） | `messages/up` | **每 300 s 发 1 条，`content` 里装全部 3 个节点的快照**（≈864 行/天入库） | 288 |
| 事件（报警/离线/恢复） | `events/up` | 按需，估 20 | 20 |
| 命令响应 | `commands/response/...` | 按需 | ≤10 |
| **合计** | | | **≈1758（17.6%）** |

结论：留出 5 倍余量。**红线**：任何新增周期上报都必须先算这张表并由 PM 批准（超过 5000 条/天即拒绝）。keepalive、订阅、命令下发不计入。

## 5. 链路四：IoTDA 规则引擎 → 自建服务器（webhook）

### 5.1 转发配置（控制台一次性配置，写进 server/README）

| 项 | 值 |
|---|---|
| 触发资源 | `device.property`（report）、`device.event`、`device.message` |
| 转发目标类型 | HTTP 推送 |
| 目标 URL | `https://{server_host}/api/iotda/webhook?token={WEBHOOK_TOKEN}` |
| 鉴权 | URL 查询串 `token` = 32 字节随机十六进制，存服务器环境变量；**不用自定义 Header**（推送头可配性不如 URL 可靠） |
| 失败行为 | 服务器返回非 200 → 平台按退避重试；服务器侧靠 `event_id` / 唯一键幂等 |
| SQL 过滤 | 首版**不加过滤**（全量转发），规则里保留 `WHERE` 注释行以备后续降噪 |

### 5.2 报文信封（服务器解析入口）

| 字段 | 类型 | 说明 |
|---|---|---|
| `resource` | string | `device.property` / `device.event` / `device.message`，用于分流 |
| `event` | string | 属性为 `report`；事件为 `event_type`（`alert`/`sos`/`recover`） |
| `event_time` | string | 平台时间，仅记日志 |
| `notify_data.header.device_id` | string | IoTDA 设备 ID → 反查 `devices.iotda_device_id` |
| `notify_data.header.node_id` | string | 网关 SN（P0 用不到，留作多网关扩展） |
| `notify_data.body.services[]` | array | **唯一业务数据源**（结构同 §4.6 的 `services[]`） |

**服务器实现约束**：只依赖 `resource` + `notify_data.header.device_id` + `notify_data.body.services[]`；**无法识别的 `resource` 一律返回 200 并记 WARN**（不阻断平台重试队列），缺 `device_id` 时用 SN 兼容匹配。这样即使平台信封字段有出入（CAL-04），业务也不受影响。

### 5.3 入库映射

| 来源 | 目标表 | 映射 |
|---|---|---|
| `device.property` → `properties` | `device_online` | `online=1`、`last_heartbeat=now`、`last_properties_json=properties` |
| `device.property` → `nodes_online` | `nodes` | 按 JSON 里的键更新 `nodes.online`/`last_seen` |
| `device.property` → `temp/humi/smoke/lpg/co` | `sensor_readings` | `node_sn="M0"`（网关快照）、`type="gateway"`、`payload_json=properties`、`ts=服务器接收时刻` |
| `device.event` → `paras` | `alerts` | `type/level/node_sn/ts`；`status='pending'`、`event_id` 唯一键去重 |
| `device.message` → `content` | `sensor_readings` | 展开数组，每条一行；`type` 取节点 JSON 的 `type` |
| 任意 | `activity_hourly`/`activity_daily` | 由 `sensor_readings` 里 `type=presence` 且 `payload.presence=true` 的记录定时归并（§7.6） |

## 6. REST API

### 6.1 通用约定

| 项 | 约定 |
|---|---|
| Base URL | `http://{host}:80/api`（Nginx 反代到 `127.0.0.1:3000`） |
| 编码 | `Content-Type: application/json; charset=utf-8` |
| 鉴权 | `Authorization: Bearer <JWT>`；除 `/api/auth/*` 与 `/api/health` 外全部必需 |
| JWT | HS256；载荷 `{sub:<user_id>, username, iat, exp}`；有效期 **7 天**；密钥来自环境变量，**不进仓库** |
| 统一响应体 | `{"code":0,"message":"ok","data":{...},"ts":1760000000000}` |
| 分页 | 查询参数 `limit`（默认 50，最大 200）、`offset`（默认 0）；响应带 `total` |
| 时间参数 | `from`/`to` 用 Unix 毫秒；服务器按 `[from, to]` 闭区间 |
| 幂等 | 写接口允许 `Idempotency-Key` 头；同一键 5 分钟内重复请求返回首次结果 |
| 错误 | HTTP 状态码表达类别，`code`/`message` 表达细节（§9） |
| CORS | 仅允许 `http://localhost`（鸿蒙 PC 预览与本地调试）；生产不放开通配 |

`code=0` 表示业务成功；HTTP 200 但 `code!=0` 的情况**不允许出现**（实现约束：错误必须同时体现在状态码上），保证 App 只判 HTTP 状态即可。

### 6.15 POST /api/alerts/{id}/disposition

请求：

| 字段 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| `action` | string | 是 | `contacted`（已联系）/`checked`（已上门）/`false_alarm`（误报）/`other` | `"checked"` |
| `note` | string | 否 | ≤200 字 | `"已让邻居上门查看，老人一切正常"` |

副作用（**闭环的关键**）：`status` → `resolved`；`next_push_at=NULL` 停推。若 `action=false_alarm`，同时把该告警写入误报统计（§6.18 用）。错误：`1301` 已处置（409）、`1302` 非法 action（400）。

### 7.1 通用约定

- 引擎 `InnoDB`，字符集 `utf8mb4` / `utf8mb4_0900_ai_ci`；主键 `id BIGINT UNSIGNED AUTO_INCREMENT`。

## 8. 阈值与状态机

### 8.1 级别定义（全系统统一）

| `level` | 名称 | 典型来源 | App/UI | 物模型 `alarm_state` |
|---|---|---|---|---|
| 0 | 正常 | — | 绿 | `0` |
| 1 | 预警 | 气体一级、无活动、节点/网关离线、门久开、温湿度越界 | 黄 | `1` |
| 2 | 报警 | 气体二级、跌倒、SOS | 红 | `2` |

`alarm_state` 取当前**未恢复**告警的最高 `level`（网关本地算，每 60 s 上报一次）。

### 8.2 燃气分级状态机（M1，网关 `algo_task` 执行）

```
         ┌──── 气体通道（P0 = MQ-2 `smoke`）≥ T1 连续 L1_HOLD(10 s) ────┐
         ▼                                                    │
    ┌─────────┐                                             ┌──────────┐
    │ 正常(0) │                                             │ 预警(1)  │
    └─────────┘ ◀── 全部 < T1−Δ(200 mV) 连续 15 次采样(30 s) ──└──────────┘
         ▲                                                        │
         │                气体 ≥ T2 连续 L2_HOLD(6 s)             │
         │                       或 预警态持续 60 s               │
         │              或（P1 多路时）≥2 路同时 ≥ T1            ▼
         │                                                   ┌──────────┐
         └──────────── 恢复条件同上（30 s 干净）──────────── │ 报警(2)  │
                                                            └──────────┘
```

| 参数 | 默认值 | 单位 | 可配 | 说明 |
|---|---|---|---|---|
| 采样周期 | 2 | 秒 | 否 | 沿用 `sensor_hub.c` `LOOP_INTERVAL_MS=2000` |
| `gas_t1_mv` | 1500 | mV（AO 侧） | 是 | 一级阈值；P0 只有 MQ-2 一路，P1 装 MQ-5/MQ-7 后默认多路共用（分路阈值 P1） |
| `gas_t2_mv` | 2500 | mV（AO 侧） | 是 | 二级阈值 |
| `gas_l1_hold_s` | 10 | 秒 | 是 | 一级需连续超限时长（=5 次采样） |
| `gas_l2_hold_s` | 6 | 秒 | 是 | 二级需连续超限时长（=3 次采样） |
| `gas_l1_to_l2_s` | 60 | 秒 | 是 | 一级滞留多久升二级 |
| `gas_recover_mv` | 200 | mV | 是 | 恢复回差（防抖） |
| `gas_recover_hold_s` | 30 | 秒 | 是 | 恢复需连续干净时长 |

动作：进入一级 → 本地声光（低频，1 Hz 灯 + 短鸣）+ 上报 `alert(level=1)` + App 推送；进入二级 → 声光连续 + 语音「燃气泄漏」+ 上报 `alert(level=2)`；恢复 → 停止声光 + 上报 `recover`。

> ⏳ 阈值 1500/2500 mV 是**结构默认值，不是标定值**。必须先做 CAL-02（洁净空气静置记基线 vs 打火机放气记峰值）再定稿，否则演示时可能不报或常报。
>
> 🔴 MQ-2 的 `Vs` 最高 4.0 V（2000 ppm C₃H₈），**必须分压后进 3.3 V ADC**；加热丝必须 **5.0 V ± 0.1 V**，且**预热 >48 h / 老化 48–168 h** 是不可压缩的日历时间（详见 §2.4.1）。

### 8.3 温湿度越界（M1，P1）

| 判据 | 默认值 | 级别 | 动作 |
|---|---|---|---|
| `temp` > `temp_high_c`(35.0 °C) 或 < `temp_low_c`(5.0 °C) 持续 `env_hold_min`(30 分钟) | 见左 | 1 | 上报 `alert(type=env)` |
| `humi` > `humi_high_pct`(85 %RH) 或 < `humi_low_pct`(20 %RH) 持续 30 分钟 | 见左 | 1 | 同上 |
| 恢复 | 回到区间内持续 10 分钟 | — | 上报 `recover` |

### 8.4 跌倒（M2/M3，P0，最高优先级）

跌倒判定是**三段串联**，契约只规定后两段，**不得把模块内部的 15–20 s 判定改写成「瞬时触发」**：

| 段 | 位置 | 行为 | 迟滞 / 时延 |
|---|---|---|---|
| ① 判定 | LD6002C 模块固件 | 点云离地高度持续低于阈值 | **默认灵敏度 10 下需持续跌倒 15–20 s** 才把跌倒位置 1（datasheet：Fall Sensitivity 3–30） |
| ② 上报 | 模块 → 节点 | `0x0E02` 的 `DATA[0]=1`（UART）或 TX2 电平拉高 | ≈0 ms |
| ③ 链路侧状态机 | 节点 → 汇聚 → 网关 | 见下 | **链路不额外加延时**，只做迟滞与抑制 |

链路侧状态机（迟滞型，不是「来一帧报警、下一帧恢复」）：

```
   收到 fall=1（DATA[0]=1 或 TX2 上升沿）
        │
        ▼
   ┌──────────┐                                   ┌───────────┐
   │ 正常 IDLE │                                   │ 报警 ALARM │
   └──────────┘ ◀── 连续 K 次 fall=0 且距最后一次触发 ≥ T_hold ──└───────────┘
```

| 参数 | 默认值 | 单位 | 说明 |
|---|---|---|---|
| 进入条件 | 任一通道出现 `fall=1` | — | **立即进入 ALARM，不额外延时** |
| `fall_suppress_s` | 30 | 秒 | ALARM 期内重复触发不产生新告警，不重置 `push_count` |
| 退出条件（迟滞，须**同时**满足） | `K=3` 次 `fall=0` **且** 距最后一次 `fall=1` ≥ `T_hold=30 s` | — | 两个条件缺一不可，防止「模块瞬时回落」导致告警闪断 |
| 恢复事件 | `recover` | — | 回到 IDLE 时写 `recovered_at`；**不自动改 `status`**，闭环仍由人工处置结束（§6.10） |

**端到端可见时延 = 模块判定 15–20 s + 链路 ≤100 ms。** 演示与答辩必须按这个时长讲解（人在雷达下快速倒一下不会触发，不要在现场误判成「没反应」）。
厂商标称：跌倒识别 **90%**、存在识别 95%、覆盖 3×3 m 单人小区域（datasheet `:66-68`）→ 因此 P0 保留 `demo_trigger` 注入路径（§4.5、§6.12），**注入必须走真实链路**（§11 D-07）。

### 8.5 无活动与外出模式（M4/M5，P0）

| 状态 | 进入条件 | 退出条件 | 行为 |
|---|---|---|---|
| `home`（在家） | 近 30 分钟内有活动（任一路 PIR 触发或 `door` 跳变） | 进入 `away` | 计时 `last_motion_ts`，超 `no_motion_min` 报警 |
| `away`（外出） | `door` 由关变开，且其后 `away_after_open_s`(600 秒) 内**无任何活动** | 检测到任意活动（PIR 或 door 再次跳变） | **抑制**无活动告警 |
| — | — | — | — |

| 参数 | 默认值 | 单位 | 范围 | 可配 |
|---|---|---|---|---|
| `no_motion_min` | 30 | 分钟 | 5–120 | 是（App 设置页） |
| `away_after_open_s` | 600 | 秒 | 60–3600 | 是 |
| `presence_hold_s` | 60 | 秒 | 10–600 | 是 |

触发时上报 `alert(type=no_motion, level=1, node_sn="M4")`，文案「30 分钟未检测到活动」（分钟数按实际配置替换）。

### 8.6 门久开（P1）

`door=true` 持续 `door_open_alarm_s`(180 秒) → `alert(type=door_left, level=1)`；关门 → `recover`。

### 8.7 离线判定（P0，两条独立规则）

| 对象 | 判定方 | 规则 | 参数 | 动作 |
|---|---|---|---|---|
| 节点 | 汇聚 | 连续 3 次轮询无应答 | 3 s × 3 = **9 s**（`node_offline_timeout_s`） | `0x03 HUB_EVENT` → 网关 → `alert(type=node_offline, level=1)`；`nodes.online=0` |
| 网关 | 服务器 | 连续 3 个上报周期无任何数据 | 60 s × 3 = **180 s**（`gateway_offline_timeout_s`） | `device_online.online=0` + `alert(type=device_offline, level=1)` |
| 恢复 | 各自 | 节点：1 次成功应答；网关：收到任意上报 | — | 上报 `recover`，`online=1` |

节点恢复时的 `recover` 事件由网关在 `0x03` 里带 `type=node_online` 触发。

### 8.8 报警抑制、去重与推送节奏（P0）

| 项 | 规则 |
|---|---|
| 去重键 | `(device_id, node_sn, type)`；`fall` 用 30 s 窗口，其余用 `alert_suppress_s`(60 s) |
| 窗口内重复 | **不新建告警**；只更新 `snapshot_json` 与 `recovered_at=NULL`；`push_count`/`next_push_at` 保持 |
| 推送节奏 | `[0, 60, 300]` 秒（`alert_repush_s`），即最多 3 次；Push 只是「叫醒」，通知里带 `alert_id` |
| 停推条件 | `status != 'pending'` **或** `recovered_at IS NOT NULL` **或** `push_count >= 3` |
| 升级 | 窗口内级别上升（1→2）→ 新建一条 `level=2` 告警，旧条置 `recovered_at=now` |
| 免打扰 | 跌倒 / SOS 不受免打扰限制；其余按用户设置（P1） |

### 9.1 HTTP 状态码用法
