# HLK-LD6002C 接线与验证步骤（E528H-WS63）

> **2026-10-16 16:35 更新：实物已接上并判通。** 抓 20 s + 120 s 实时日志：`rx_total` 单调增长
> （1,095,057 → 1,137,927）、`bad=0 drop=0`、`0x0E02` 以 ~24 帧/s（合计 ~28 帧/s）上报 `is_fall=0`，
> 且固件主动发的 `0x0E06` 收到 28 字节参数回包 → **收发两个方向都通**。
> ⚠️ **剩下卡住的不是接线，是安装姿势**：模块必须**吸顶装在 2.2~3.0 m**，
> 且默认灵敏度 10 下要**持续跌倒 15~20 s** 才会上报 —— 快速倒一下不会触发。
> 详见下面「五、为什么现在还不报跌倒」。

## 一、接线表（模块 8 脚排针 → 开发板）

| LD6002C 脚 | 名称 | 接到哪 | 说明 |
|---|---|---|---|
| 1 | 3V3 | 板 **3.3V** | ⚠️ **不是 5V**。模块只吃 3.1~3.5V |
| 2 | GND | 板 **GND** | 必须共地 |
| 3 | P19 / BOOT1 | 板 **GND** | 🔴 **必须接低**，否则模块不从内部 Flash 启动、一个字节都不发 |
| 4 | TX2 / GPIO20 | 板上丝印 **IO06** | **冗余**硬件跌倒电平：跌倒=高，无人跌倒=低。可选，但建议接 |
| 5 | AIO1 | 悬空 | |
| 6 | SCL0 | 悬空 | |
| 7 | **TX0** | 板上丝印 **IO07** | 模块发 → 板收（WS63 的 UART2_RXD） |
| 8 | **RX0** | 板上丝印 **IO08** | 板发 → 模块收（WS63 的 UART2_TXD） |

**只要 4 根线：3V3、GND、BOOT1→GND、TX0→IO07、RX0→IO08（5 根）。**

### ✅ 这 5 根线的判通证据（2026-10-16 16:35 实测，逐根）

| 线 | 状态 | 靠什么判定的（都来自实时日志，不是猜） |
|---|---|---|
| ① 3V3（脚1） | ✅ 通 | 模块在持续主动发帧 113 万+ 字节；没电不可能发 |
| ② GND（脚2） | ✅ 通 | 与①同理，且 `bad=0` —— 电平/地噪声干净，113,927 帧无一位校验错 |
| ③ BOOT1（脚3）→GND | ✅ 已拉低 | 模块从内部 Flash 启动并主动上报；规格书：BOOT1 不接低则**一个字节都不发** |
| ④ TX0（脚7）→IO07 | ✅ 通 | `rx_total=1,137,927`、`ok=113,927`、`bad=0 drop=0`（UART2 收） |
| ⑤ RX0（脚8）→IO08 | ✅ 通 | 固件发的 `TX type=0x0E06` 收到 `GET_PARAMS` 28 字节回包（UART2 发）|
| ⑥ TX2（脚4）→IO06 | ❓ 判不了 | `tx2=0 tx2_edges=0`。**正常态 TX2 本来就恒低** → 无法区分"没接这根线"和"接好了但没发生跌倒"。只有真跌倒（TX2 拉高）才能验证 |

→ **结论：UART 五根线全部判通，接线没有错。** 第 6 根（TX2）留到真跌倒那天才能验，但它不影响 UART 主通道。

### 关于第 4 脚 TX2：要不要接？

官方规格书原文（`LD6002C技术规格书V1.1.txt:125-126`）：

> LD6002C 模组**可直接使用 TX2 管脚输出检测到的目标信息（跌倒输出高电平，无人跌倒低电平）**，
> 同时 **UART0 按照规定协议输出检测结果，串口数据中包含目标跌倒信息**，用户根据具体应用场景灵活使用。

也就是说 —— **跌倒判定是模块内部算法做的，不依赖你怎么接线**。UART（第 7/8 脚）和 TX2（第 4 脚）
只是同一份结果的**两条播报通道**：

| 通道 | 内容 | 本项目 |
|---|---|---|
| UART（TX0/RX0） | 完整协议：跌倒状态 + 全部参数，还能反向配置高度/阈值/灵敏度 | **主通道**，固件已在解析 `0x0E02` |
| TX2（第 4 脚） | 一根线的电平：跌倒=高、正常=低 | **冗余通道**，固件在 `IO06` 上做双边沿中断 |

**结论：不接 TX2 完全不影响跌倒检测。** 接了的好处是：
① 不依赖协议解析，UART 万一丢帧也还有一路；
② 电平变化比解析一帧更快；
③ 演示时可以说"双通道冗余"。

固件里对应的日志：

```
[RADAR] TX2 pin IO06 init dir_ret=0 isr_ret=0 pull=down level=0
[RADAR] TX2 pin IO06 level=1  <= FALL via hardware pin! (edges=3)
[RADAR] alive ... tx2=1 tx2_edges=3
```

## 二、接线前必须知道的 4 件事

1. **别接 5V。** 模块标称 3.1/3.3/3.5 V。接到 5V 引脚会烧。
2. **BOOT1（第 3 脚）一定要接 GND。** 规格书写"模组内部上拉，模组启动前必须接低电平"。
   如果接 GND 后模块反而没数据，改成**上电瞬间短接一下再松开**再试。
3. **TX / RX 是交叉的**：模块 TX0 → 板 RX（IO07），模块 RX0 → 板 TX（IO08）。
   接反了收不到任何数据。
4. **供电可能不够。** 模块典型 120 mA、峰值 **600 mA**，规格书要求供电能力 >1 A、纹波 ≤50 mV。
   开发板 3.3V 由板载 LDO 出，若雷达一工作就重启 / 数据断断续续 →
   换**独立 3.3V 电源**（记得和开发板共地）。

## 三、丝印歧义（重要）

开发板资料里 IO07 / IO08 的**排针脚号有两种说法**：
- 《e528h-ws63 开发板规格书》写：18 = I/IO07、19 = IO08
- 《m528h-ws63 硬件设计参考手册》写：11 = IO07、12 = IO08

两份文档的**丝印名一致**，所以：**按板子上印的字找 "IO07" 和 "IO08"**，不要按手册上的脚号数。
接好没数据 → **把第 7、8 两根线对调**再试（这是最快的排查动作）。

## 四、上电后应该看到什么

按板上 **RST** 键，串口（COM14，115200）应出现：

```
[RADAR] uart2 init ret=0 (pin IO07=RX/IO08=TX mode=2, 115200 8N1)
[RADAR] rx callback register ret=0
[RADAR] TX type=0x0E06 len=0 cksum=0xF6          ← 固件主动问雷达参数，发得出去
[RADAR] RAW(9): 01 00 00 00 ...                  ← 收到模块回包（原始 HEX，前 24 块都会打）
[RADAR] FRAME#1 id=0x0000 type=0x0E06 len=28 data=...  <= GET_PARAMS (len=28)
[RADAR] alive rx_total=... ok=... bad=0 tx=1 fall_evt=0 state=0
```

**人在雷达前方走动 / 模拟跌倒时**应出现：

```
[RADAR] FRAME#n id=0x0000 type=0x0E02 len=1 data=01  <= FALL_STATUS is_fall=1 (FALL!)
```

`[RADAR] alive ...` 心跳每 10 秒一次，`rx_total` 持续增长 = 收数据正常。

## 五、为什么现在"能收包但还不报跌倒"——安装姿势（2026-10-16 新增）

接线判通后，实测 120 s 内 `fall_evt=0 state=0`，`0x0E02` 恒为 `is_fall=0`。这不是故障，
是两个**必须满足的前置条件**没满足：

### 1. 必须吸顶安装，挂高 2.2~3.0 m

官方规格书 §6.4 原文（`LD6002C技术规格书V1.1.txt:187-188`）：

> 顶装挂高 2.2-3.0m，最大感应范围 3*3m

判定原理是**"点云距离地面的高度"**（同文件 §3 原文：*目前是根据点云距离地面高度进行跌倒判定*），
而模块内部存的安装高度参数就是 **`high=2.400` m**（本次实测 `0x0E06` 回包读出）。

→ **模块现在如果是放在桌面/侧放，判定基准（2.4 m）与实际完全不符，永远判不出跌倒。**
→ 装到 **2.4 m 左右的吊顶**正好落在 2.2~3.0 m 区间内，**不需要改参数**；若装到别的高度，
  要用 `0x0E04` 把 `high` 改成实测高度（⚠️ **固件目前只会解析 `0x0E04` 回包，还没有下发它的代码**）。

### 2. 默认灵敏度下要"持续跌倒 15~20 s"

规格书原文（同文件 §3 参数配置）：

> 【Fall Sensitivity】：灵敏度设置，范围 3-30，默认 10。值越小跌倒上报越快，但误报率会提高。
> 默认 10，**持续跌倒 15~20s 上报跌倒状态**。

→ 站着快速倒一下、蹲一下就站起来，**不会**上报。演示与验证时要**真的躺在地上等 15~20 s**。
→ 想缩短时间：把灵敏度调小（`0x0E0A`），代价是误报变多。

### 3. 另一个合法做法：把跌倒阈值临时压低

`radar_hub.c` 里已有测试开关 `RADAR_THR_TEST_ENABLE`（默认 0）：打开后固件会发 `0x0E08`
把跌倒阈值从 0.6 m 压到 0.1 m，跑 75 s 自动写回 0.6 m，这样**普通起坐动作就能触发 is_fall=1**，
用来验证"UART 跌倒通路 + TX2 硬件通路"是否真的通（10-16 已用它验证过下发与恢复，见
[doc/9](../ws63-firmware/doc/9-跌倒阈值下发与恢复-2026-10-16.txt)）。用完记得改回 0。

### 4. 场景适用性（写进答辩材料）

规格书 §7 注意事项原文：*本产品只适用于浴室，卫生间小区域场景，单人情况* —— 与本项目
把 LD6002C 放在 **M3 卫生间** 的定位一致。

## 六、排查表

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `rx_total=0` 一直是 0 | ① TX/RX 接反 ② BOOT1 没拉低 ③ 供电不足 | 先对调 IO07/IO08 两根线；再确认第 3 脚接 GND；最后换独立电源 |
| `rx_total` 涨但全是 `BAD CKSUM` | 波特率/电平不对（模块可能不是 115200） | 看 `[RADAR] RAW(...)` 的原始字节规律；必要时用官方上位机把模块波特率改回 115200 |
| 只有 `rx_total` 涨，`ok=0 bad=0` | 帧不完整（SOF 一直没等到） | 正常，多等几秒；若长期如此说明字节流被截断，查地线 |
| 板子反复重启 | 3.3V 被雷达拉塌 | 换独立 3.3V/1A 电源，共地 |
| 完全没日志 | 看错串口 / 板子没上电 | 确认 COM14、波特率 115200 |
| `TX2 pin IO06 init ... isr_ret` 非 0 | GPIO 中断注册失败（极少见） | 忽略即可，UART 主通道不受影响 |
| `level` 一直是 1 但没人在跌倒位 | IO06 悬空拾到干扰 / 上拉被外部拉高 | 确认 IO06 只接模块第 4 脚，别接别的东西 |

## 七、"验证通过"的标准

同时满足下面三条，就可以记进 W0.11 传感器验证表：

1. `[RADAR] uart2 init ret=0` + `rx callback register ret=0`
2. `rx_total > 0` 且至少解出 1 个 `[RADAR] FRAME#...`
3. 人或手在雷达前移动时，`[RADAR] alive ... state=` 或 `FRAME# type=0x0E02` 有变化

## 八、协议速查（TinyFrame / TF）

```
SOF(1)=0x01 | ID(2,LE) | LEN(2,LE) | TYPE(2,LE) | HEAD_CKSUM(1) | DATA(LEN) | DATA_CKSUM(1)
总长 = 9 + LEN
校验 = ~(逐字节 XOR)；HEAD_CKSUM 覆盖前 7 字节；DATA_CKSUM 覆盖 DATA（LEN=0 时为 0xFF）
```

| TYPE | 含义 |
|---|---|
| `0x0E02` | 跌倒状态上报（DATA[0]：0=正常 1=跌倒），模块单向主动发 |
| `0x0E04` | 设置安装高度（回 0/1） |
| `0x0E06` | 读取雷达参数（回 LEN=0x1C，7 个 4 字节参数） |
| `0x0E08` | 设置跌倒阈值（默认 0.6 m） |
| `0x0E0A` | 设置灵敏度 |
| `0x0E0C` | 设置报警区域（4 个 float，范围 0.3~1.5） |

原始资料见同目录 `LD6002C技术规格书V1.1.pdf`、`LD6002C通信协议.pdf`（含文本提取 `.txt`）。
