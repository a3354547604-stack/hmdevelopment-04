## 3. 验收项②附：静默通过与假绿（含最小反例）

### 3.1 `harmony_build`：App 构建失败时整条链仍然 rc=0（**实测反例**）

- 代码事实：`harmony-app/tools/build-hap.sh:10` 是 `set -uo pipefail`（**没有 `-e`**）；两条 hvigor 流水线以 `tee -a "$LOG"` 收尾（`|| true`）；产物列举是 `ls -l entry/build/default/outputs/default/*.hap 2>/dev/null || echo "未找到 hap 产物"`；脚本最后再打几行 echo/tail ⇒ **脚本的退出码几乎恒为 0**。
- 最小反例（已实跑）：把 `hvigorw` 换成一个**永远失败**的桩（打印 `> hvigor ERROR: BUILD FAILED` 后 `exit 1`），用 `HOME=/tmp/t109-nohome` 隔离工具链，跑 `bash harmony-app/tools/build-hap.sh /tmp/t109-hap-stub.log` → **RC=0**，而日志两阶段都写着 `BUILD FAILED`；更要紧的是它列出的 HAP 是**上一轮的旧产物**（时间戳未变）⇒ 连「产物存在」都不能证明这次构建成功。
- 影响：一键脚本的 `harmony_build` 这一行**只能证明「脚本跑完了」**，不能证明 HAP 构建成功。冻结前若只在 App 侧改动过，`--full` 仍会给出「硬项全绿」的假象。
- 修法建议（不改工具，仅记录）：给 `build-hap.sh` 加 `set -e`（或显式 `exit ${PIPESTATUS[0]}`）、把「注入未定义常量必须 BUILD FAILED」的门自证从「打印」改成「断言」，并在缺失 HAP 时返回非 0。

### 3.2 「跳过」可以静默绿（**实测反例**）

`freeze_check.py` 的 hard_fail 只统计 `soft=False` 的失败项，skip 永不挡门（脚本第 3 行注释也这么写）。实测：`HM_FREEZE_OUT=/tmp/t109-skip bash tools/freeze-check.sh --quick --only gw_build` → **RC=0**，末行「所有硬项通过（跳过 1 项，逐条原因见上表）」，而实际什么都没跑。
- 这是**设计选择**（日常自检要能在容器没起时通过），但用在「冻结前放行」时是风险：环境门（容器没起、Docker 掉线、hvigorw 不在 PATH）会把整批项变成 skip，而输出的总结句仍是「所有硬项通过」。
- 修法建议：`--full` 模式把「soft=否 且 被 skip」也计入摘要并显式打印「N 项因环境未跑」，或在冻结模式加 `--strict-skips` 开关。

### 3.3 `pack_check_only`/`pack` 在我这一版上红（**归因：工具自指**，已被在飞修复）

- 失败原文（我的 `--full`）：`[FAIL] 解包后无身份/PII 命中 | … | 实测 tools/freeze_check.py:238 身份-院校/角色 «学校» ← k in ln for k in ("材料齐全", "提交格式", "学校/队名", "PPT", "docx")):`
- 链路：打包候选集 = `git ls-files` ∩ INCLUDE + 材料成品目录；`tools/freeze_check.py` 自 **`5fcb88a`（t101 自己的提交，`7aa4ac0` 的后代）** 起被跟踪 ⇒ 它进了提交包；而身份/PII 扫描的**自指豁免正则** `SCANNER_SELF_REF` 只覆盖 `^tools/test/review/(repo_health|check_[^/]+)\.py$`，**不含 `freeze_check.py`**；恰好该文件 238 行的关键字元组里写着「学校/队名」⇒ 工具把**自己**报成了泄漏。
- 快照实验（worktree `7aa4ac0`，755 文件，无 `tools/freeze_check.py`，打包器停在 t99 版）：`pack --allow-missing-materials` **rc=0**、`--check-only` **FAIL 0 / 共 10 条** ⇒ **t101 当年那张 rc=0 快照是真的**，只是它来自「工具还没进版本控制」的那棵树；报告写的「共 12 条」也是它当时那棵脏树的行数，不是 `7aa4ac0` 的行数（行数随包内容变动：我这次分别见到 13 条 / 12 条）。
- **在飞修复**：`tools/freeze_check.py` 在工作树里已被改成 `("材料齐全", "提交格式", "队名", "PPT", "docx")`（注释点名 t113），随后 `07ecc96` 入库。修复后我重打包一次：`PACK_RC=0`，`--check-only --allow-missing-materials` → **FAIL 0 / 共 12 条** rc=0；严格模式（不带 allow）→ **FAIL 1**（只剩「演示视频 mp4 缺件」，用户动作）。
- 结论：**「冻结前一键脚本在 HEAD 上必然红一项」这个坑真实存在过，且已被 t113 修掉**；t101 报告没预料到自己的工具一旦入库就会自伤，属可理解但需登记的盲点。修法建议（更彻底）：把 `tools/freeze_check.py`、`tools/freeze-check.sh`、`tools/README-一键验收.md` 也加进 `SCANNER_SELF_REF` 豁免（或把该关键字元组改成不出现真实身份词的拼接写法）。

### 3.4 `repo_health`（soft）：rc 恒 0，命中数没有基线

两次实跑命中 472 / 473（良性 5），其中身份-院校/角色 316、手机号 60、本机用户名 57、邮箱 23、口令赋值 16 —— 绝大多数是**文档里的占位符与规则引用句**。因为 rc 恒 0、且没有「基线快照」，这个 soft 项**无法区分「新增真泄漏」与「新增占位符」**。它作为「体检信息」合理，但**不能当作泄漏判据**；建议加基线 diff（相对上一版只报新增命中）。
