## 二、❌ 阻断级问题：南向架构在当前形态下不可实现

### 2.1 官方手册的硬事实

| 事实 | 依据 |
|---|---|
| XF_AT 全部指令 = 基础（HELP/RST/ECHO/SWINFO/IPR/**GPIO 数字读写**/DBGIO）+ SLE + BLE + WiFi（STA/SoftAP/TCP-IP）。**没有 ADC、没有 I2C、没有 PWM、没有 UART2 读取、没有 MQTT** | 《XF AT 指令使用指南 V2.1.x》指令一览表逐条核对；V2.0 WiFi 篇同样 |
| 透传是阻塞态：「**进入透传后，会暂停指令的解析**，直至退出透传状态」；循环透传只有单独发 `+++`（或 `AT+RST`、DBGIO 触发）才退出 | 同上，AT+SLESEND / AT+SLERECV / AT+SLETRAN 章节原文 |
| SLE 协议栈上限 **8 路**并发连接（conn_id 0~7），**仅星形、不支持 Mesh、多 Central 不能互连** | 海思官方文档 multi-connection 页；与计划 §5 一致 ✅ |
| **「1 个 Master 连 N 个 Slave」在 XF_AT 文档里完全没写**：唯一示例是两块板一对一透传；AT+SLEOBJ 一次只创建一个对象 | 计划 §5 的「1 汇聚 + 5 节点」**无官方依据**，是本案最大未知数 |

### 2.2 为什么计划 §9.2 的节点方案落空

计划 §9.2 写的是「按 RK2206 下发的轮询指令，`AT+GPIORD`/ADC 读 MQ-2/MQ-5/MQ-7」「LD6002C 走该板 IO07/IO08（UART2），结果 `AT+SLESEND` 回传」。这条路在「只用 XF_AT」下走不通：

- 节点板上**没有本地 MCU** → 没有任何东西会向它发 AT 指令；XF_AT 也不会开机自动读引脚并上报（配置保存只保存参数，透传是运行时指令）。
- 主机想远程驱动节点 → 只有透传模式能把无线侧数据送进节点串口，而**透传期间节点不解析 AT 指令** → `AT+GPIORD` 永远不会被执行；非透传时，无线侧收到的数据在节点上又没有出口。逻辑闭环死锁。
- 连带失效：M1 气体节点（ADC + I2C）、M2/M3/M5 雷达节点（UART2 取数）、以及所有「节点主动上报」设计。

计划自己已承认「星闪一断，网关只剩 433 按钮」；按当前路线不是「一断就瞎」，而是**从一开始就瞎**。

### 2.3 三条出路（按风险从低到高）

**A. 必做传感器收回主控板（推荐）**
红外 D203B + 干簧管接 GPIO、AHT20 接 E53 座 I2C0、模拟量接 E53 ADC 或板载 ADC——小凌派官方已有 `c5_人体检测`、`c7_智慧烟感`、`b1_adc`、`b11_i2c_scan` 等现成样例可抄。星闪退化为「2 块板做加分演示」。风险最低、与赛题原文和官方培训一致，省下的时间投到北向与材料。

**B. 每个节点加一颗小 MCU**（STM32/ESP32 类）读传感器 → 串口 → WS63 只做透传。
技术可行，但要 5 颗 MCU、5 份固件、5 套电源与外壳——等于把「多套硬件」这个赛题明确不要求的负担全扛上。

**C. 自研 WS63 C 固件**（`gitee.com/HiSpark/fbb_ws63`，Apache-2.0/MIT）
SLE 一主多从、ADC/I2C/PWM/UART 示例齐全，是彻底方案。**但它推翻了计划「如般微已停 SDK 支持 → 只烧 XF_AT」的核心决策**；社区可参考的一主多从代码「8 只是源码数组上限、未做多板压测」，官方示例还被指出重复初始化、数组下标误用等 bug。熟手 2~3 周紧凑可行，学生队伍风险高。若走 C，建议**砍掉 LD6002 雷达**（帧解析 + 5 连接稳定性的组合风险最高）。

### 2.4 买板前必做的两个 5 分钟实验（顺序不可颠倒）

1. 上电发 `AT+HELP` → 看**实际固件**支持哪些指令（不要只信 PDF）。
2. 连续 `AT+SLEOBJ=1,1` 建多个 Master 对象 + `AT+SLECONNSET` 连接，看是否返回 `ERR:MAX CNT`、能否 2 路以上并发收数。

**第 2 步失败 = 星形组网方案当场判死。** 别等买齐 6 块板、写完 5 份依赖它的代码才发现。
决策截止建议：**10/20**。

## 三、⚠️ 需逐条修正的技术细节

1. **华为云 SDK 选型写错**：小凌派仓库里**没有** huaweicloud_iotlink，**也没有 src/ 目录**（全树 3.98 万条路径检索 `iotlink`/`hwcloud`/`oh3.0` 命中 0）。计划 §6.5「解压 `oh3.0_hwcloud_iotlink-master.zip` 进 `src/third_party`」不存在，任务卡 C8 要重写。
   实际可用的是 `d2~d7` 样例自带的 `oc_mqtt`（`device_info_init` / `oc_mqtt_init` / `oc_mqtt_profile_propertyreport`）。

2. **「MQTT/TLS」名不副实**：oc_mqtt 样例是**明文 1883**（`oc_mqtt.h`：`OC_SERVER_PORT 1883`；`oc_mqtt.c` 直接 `NetworkConnect`，全文件无 tls/ssl/mbedtls 命中）。计划架构图与 §9.1 写的「MQTT/TLS 上行」「8883」需要自己接 mbedTLS 并预置华为云 CA（官方提供 CA 下载；MQTTS 必须预置 CA，1883 不需要）。
   → 老人居家数据明文上报，答辩大概率被追问；要么真做 TLS，要么在文档里主动写明取舍。

3. **`IoTMainTaskEntry` 那条坑不存在**：出自 BearPi-HM_Nano（Hi3861）文档，RK2206 例程里没有该函数 → 删掉，否则误导队友。

4. **「LiteOS-M 无 USB Host 栈」不准确**：仓库树里有 `drivers/adapter/khdf/liteos/model/usb/host`，只是没有 U 盘/读卡器样例、官方从未宣传 →「实践上做不了」的结论仍成立，但理由要改写。

5. **样例编号要核实**：`d8` 是「通鸿」平台样例、不是华为云；本地课件也只有 d1~d7、c1~c7。计划 §16.4 把它们与华为云样例并列，属过度归纳。

6. **Push Kit 的模拟器结论是错的**：官方《Push Kit 简介》明确**支持模拟器**（只不支持语音播报/实况窗/应用内通话三类），另「不支持云真机调试」。计划 §8.5「模拟器收不到 → 轮询是演示主通道」前提不成立。
   轮询仍值得做（不受权限/系统策略影响、可控），但**理由要改**，别把错误前提写进设计文档。

7. **Push 频控有官方数字**（计划写「具体阈值【待人工核实】」）：调测阶段每项目每自然日 ≤1000 条测试消息；**未申请自分类权益时，消息默认按资讯营销类管控——单设备单应用每天 2~5 条**；「服务与通讯」类无固定条数但受系统管控；自分类权益审核 3 个工作日、通过后 5 分钟生效、AGC 内提交消息示例即可。
   → 计划的「立即 → 60s → 5min 共 3 次」设计正确 ✅，但**必须去申请「服务与通讯」权益**，否则安全报警可能被当营销消息限流到每天 2~5 条。

8. **鸿蒙后台确实不能轮询**（官方：进程挂起后无定时器/网络等资源；退后台无长时任务会被强制断开 TCP/UDP，回前台需重建）。
   → 计划「前台轮询 + `onForeground` 必拉未确认 + Push Kit」方向正确 ✅，但设计文档里不能出现「后台轮询兜底」这类表述。

9. **华为云 IoTDA 额度 ✅ 基本正确，补充 4 点**：
   - S0 = 在线 1000 台 / 每日 1 万条 / 上下行 10 TPS / 应用侧 API 10 TPS；**HTTP 推送与 AMQP 基础版就有**，S0 属标准版 → 计划 §6.2 结论成立。
   - **心跳/协议层 ACK/订阅被官方列为免费计费项，不计入每日消息数** → 计划 §18.9 的【待实测】可以结案 ✅。
   - 超限即丢弃、公网转发 ≤1M/s、离线命令 48h（「设备异步命令老化时长」）✅。
   - 注意：官方措辞是「**免费试用**」单元，每区域每租户 1 个、不承诺 SLA，且**未公开有效期**——别把它写成长期可用假设。另：使用限制页写「标准版 API 100/s」与 S0 规格表「10 TPS」自相矛盾，答辩以产品规格表为准。

10. **北向版本策略 ✅ 成立**：API 23（6.1.0 Release）确于 2026-04-20 发布；`compile=23 / target=23 / compatible=12` 合法且推荐（官方约束 compatible ≤ target ≤ compile；compile 只能取 DevEco 自带 SDK 版本）。`compatibleSdkVersion` 写入包内 `minAPIVersion`，**低于该值的设备装不上**——API<12 的 HarmonyOS 4.x/API 9~10 装不了，所以「安卓备用端」这个判断有价值 ✅。

11. **60GHz 雷达有合规风险**（计划已标【推测】，现给结论）：微功率短距离设备目录 H 类只列 24–24.25GHz，未列 60GHz；《雷达无线电管理规定（试行）》2026-01-01 施行后不符规定不再受理型号核准。
    LD6002B/C 确实存在（60GHz FMCW，UART 115200，B 最多 3 人、侧装 0~6m / 顶装半径 1.5m@3m；C 单人、顶装 2.2~3.0m、0.6×0.6~3×3m；供电 **≥1A、纹波 ≤50mV**）；但「跌倒 90% / 存在 95%」是**厂商自述**（无测试方法与第三方认证）。
    → 演示风险低，但**不能写「合规」**；PPT 建议明确「演示样机，产品化切 24GHz 合规型号」。

12. **MQ-7 的「买成品（板载高低温循环电路）」要打问号**：多数廉价 MQ-7 模块加热丝常接 5V、**不带 1.5V 循环**；采购前必须看自家模块原理图。另：三路 MQ 按原厂加热功耗限值算是 **~530mA 峰值**（计划写 450mA）→ 5V/2A 设计正确 ✅；AO 高浓度趋近 5V，**接 3.3V ADC 必须分压**（计划已认账 ✅）。

13. **老化时间线与提交时间自相矛盾（会直接影响视频）**：计划 §12-7 / §18.7 写「元件必须 **11/10 前**上电老化」，但演示视频 **11/02~11/04 录制、11/06 提交**。MQ-2 官方要求 ≥48h 连续预热，且老化期间读数先高后缓降、不能用于判报警。
    → 倒推：**10/30 前必须上电**，否则视频里的气体报警要么拍不到、要么疯狂误报。

14. **串口分配冲突**：计划 §17.3 自己标注 `UART1_RXD/TXD_M1` 是**调试串口**（底板上是 CH340E），但 §9.1 又把「星闪汇聚节点」放在 **UART1** → 与调试/日志互相污染；**E53 座上的 `E53_UART0`** 是空闲的，更适合接汇聚，DFPlayer/雷达再另行排布。
    另：DIP-30 排针上的 **I2C1 只在 23/24 脚（U1TX/U1RX）**，计划 §16.1 写「AHT20 走 IO15/16 对应的 I2C1」——**该开发板排针上没有 IO15/IO16**，属引脚表内部矛盾，需实物核对。

15. **配网明文 HTTP**（❓建议自测）：计划让 App `POST http://192.168.4.1/config`。鸿蒙对明文 HTTP 有网络安全配置约束，可能被拦 → 要么配 network_config 允许明文，要么主推蓝牙配网、把 Wi-Fi 配网列为备选。

16. **433 门铃接收器做 GPIO 中断**（计划已认账一半）：继电器式/超再生接收模块会因邻频干扰输出毛刺，必须软硬件双重消抖 + 重触发窗口；建议同时保留 EV1527 解码方案，并做**10 分钟抗扰实压测**。老人场景半夜误报是硬伤。

17. **断网缓存写 8MB 板载 FLASH 偏乐观**：与固件同片、LiteOS-M 无文件系统（有 `b15_flash`/`a7_hal_file` 样例），环形缓冲 + 掉电保护要自己写。建议先内存队列 + 少量 KV 持久化，别当「地基」提前投入。

18. **局域网直连兜底（§18.10 提到 App 直连网关 <100ms）**：网关同时当 AP/STA/跑 HTTP 服务会抢资源，手机同网还需服务发现（mDNS/固定 IP）→ 明确列 P2，不要混进必做。
