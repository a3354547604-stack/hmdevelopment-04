### ⑤ 「发帧前预测 SEQ + `s_th_waiting`」竞态修法 —— ✅ **成立，而且是必须的**

- **机理**：`uart_task`（prio 24）比 `net_task`（prio 26）优先级高。`handle_set_threshold` 在 `net_task` 里同步等 ACK；原写法在**发帧之后**才登记 `s_th_seq`/清 `s_th_ack_done`，于是 uart_task 完全可能在 `gw_send_frame_expect_ack()` **返回之前**就处理掉这条 ACK —— 记下的 `s_th_seq` 还是**上一条**命令的 SEQ，本条命令的等待窗从没被打开，`s_th_ack_done` 停在 0 → 2500 ms 后误判「无 ACK」回 **12**。
- **修法**（`gw_main.c:1315-1318`，在 `:1319` 发送之前）：`s_th_seq = s_tx_seq; s_th_ack_done = 0; s_th_ack_result = -1; s_th_waiting = 1;` —— 先立等待窗再发帧，ACK 无论多早到都能匹配上。ACK 侧按 `s_th_waiting && ack_seq == s_th_seq` 记账（`:652-655`）。
- **预测 SEQ 是否安全**：`s_tx_seq` 全仓库**只有一个写者** —— `gw_send_frame_expect_ack()`（`:708 s_pending.seq = s_tx_seq++`），而它的**唯一调用点**就是 `handle_set_threshold`（`:1319`）；其余发帧点（`say_prov` :952、`pair_bind` :1027、nack :664/:897）各用各的 seq，不碰 `s_tx_seq`。⇒ 预测值与实发值必然相同。
- **不会留孤儿重发**：重发由 uart_task 的 `gw_pending_tick()`（`:906` 调用）做，满 `GW_ACK_MAX_RETRY=3` 次即 `s_pending.active = 0` 收手；新一轮命令直接覆盖 `s_pending`，旧 SEQ 的迟到 ACK 只走 `gw_pending_ack()`，不影响新命令（`s_th_ack_done` 只认 `== s_th_seq`）。

- **L-1（low，建议另开小卡）**：`result_code != 0` 时 `paras` 仍是成功回显。
  `gw_threshold_apply()` 在写生效值的同时把 `{"result":"ok","key":…,"value":…}` 填进 `resp_paras`；失败发生在**之后**（无 ACK `:1337`、汇聚拒绝 `:1344`）时这个回显没被清掉，于是响应体出现 `result_code=12`（或 1002/1003）而 `paras.result="ok"` 的语义打架。
  影响面很小：现行 App 侧**没有任何**消费者（`harmony-app/entry/src/main/ets` 里 grep `COMMAND_RESPONSE|result_code|paras` 无命中），云/IoTDA 只看 `result_code`。建议后续小卡：`rc != 0` 时清空 `paras` 或写 `{"result":"fail"}`（§4.5 未定义失败时的 `paras`，不构成契约违背）。
- **L-2（low，口径）**：卡面引用的 `259/0`、`ok=17` 是 **a538256 当天**的数字（我在快照里复现一致）；现行工作树是 `322/0`、`ok=19 err=0`（t34/t50 之后）。后续复核引用数字时务必带提交号，否则容易被误读成「数字对不上」。
- **L-3（说明性）**：D16 的 `3`（忙）在 `set_threshold` 上无实现路径（没有并发命令队列），`7` 只在拼帧/UART 写失败时可达（正常路径不可达）。口径本身落地无问题，只是「可达性」与契约并列列举的观感不同。
- **L-4（说明性，供后来者）**：主机探针必须照抄 `gw_main_entry()` 的启动顺序（三个规则 init → `gw_settings_init` → `gw_settings_sync`），否则全局 `s_settings` 停在 BSS 零值，会看到 `gas.t2_mv=0`、`dedup.*=0` 这种**假缺陷**。我第一次就踩了，已修并在 §2 用例 24 给出真值。

## 7. 结论

t33 的 §4.5 `set_threshold` **确实端到端接线**：21 键默认值与契约 §6.9 逐条一致（自己重算）、`0x11` 帧与 §3.7 SEQ=5 逐字节一致（66 B，含 CRC）、D16 返回码 `0/1/2/12` 与 `1002/1003` 透传实测符合、14 条负向全部落在契约码位；它顺带修的竞态**成立且必要**（变异复现：不带修法时 10/10 条带 ACK 的下发全部误判为 12，且生效状态不回写）。三条验收命令在**被复核提交**上独立复跑全过（259/0、ok=17 err=0、gateway 通过 2097152 B）。

**verdict：pass**（3 条 low 观察，建议 L-1 另开小卡）。
