## 1. 复核方法

只读复核：不改 `server/` 任何代码，只在 `docs/评审与验证/` 写本报告。全部证据为本机实跑，命令与输出摘要见 §2、§5。

关键做法（避免"假绿"）：

1. **干净卷**从零起栈（`down -v` → `up -d --build --wait`），不依赖任何残留数据；
2. **反向验证先行**：未灌演示数据时先跑一次 `demo-check.sh`，确认它确实会红（`rc=1`），再灌数看绿；
3. **独立读库**：不采信 `demo-check` 的自述，另用 `mysql` 直接查 `alerts` / `sensor_readings` / `activity_daily` 的分布与字段；

5. **状态比对**：自检前后对同一行数据做逐字比对（待处置燃气告警的 `status` 与 `next_push_at`）。

## 3. 发现（findings）

### F-01（low）：演示数据集只覆盖 8 类告警中的 7 类，而 README 写「覆盖全部类型」

- **现象**：`seed --demo` 灌的 10 条告警类型分布为 `gas×2`、`fall×2`、`sos×2`、`no_motion`、`door_left`、`device_offline`、`node_offline` —— **7 类**，缺 `env`（室内温湿度异常）。
- **依据**：
  - 契约 §7.7 `alerts.type` 枚举 **8 类**：`fall/gas/sos/no_motion/node_offline/device_offline/door_left/env`；
  - 契约 §6.13 文案表含 `env` / level 1 / 「室内温湿度异常」；§8.3 定义了 `env` 告警规则（`temp_high_c`/`temp_low_c` + `env_hold_min`）；
  - `server/app/settings_keys.py:87` 的 `ALERT_TYPES` 也含 `env`；
  - 而 `server/README.md:81` 写「**10 条覆盖全部类型的告警**（含已处置）」，t49 交付说明与 t61 卡面 acceptance 同样用了「覆盖 §6.13 全类型」的口径；
  - `server/app/demo_check.py` **没有任何类型覆盖断言**（`grep -nE "env|全类型" app/demo_check.py` 只命中报表 `env.temp_avg` 字段），所以这个缺口自检看不见。
- **影响**：不阻塞演示——P0 七动作（D1–D7）不含 `env` 告警，D7 报表的 `env` 统计有数据、`demo-check` 全绿；但"覆盖全部类型"是与事实不符的表述，与项目"不夸大"的红线相悖，且卡面 acceptance 第 3 条因此不成立。
- **建议修法（二选一，建议 ①）**：
  1. 把 `server/README.md:81` 改为「覆盖演示所需的 **7 类**告警（`env` 类 P0 网关不产生，见施工单诚实边界）」；施工单若无同类措辞则不动；
  2. 或在 `app/seed.py` 的告警清单里补一条 `env/1`（mock 注入），同步 README/施工单里所有条数描述（如「告警 10 → 11 条」）。
- **备注**：`env` 类告警在 P0 网关侧没有产生路径（`grep -rn "'env'" rk2206-gateway/src` 无命中），所以 ② 属纯 mock 注入；① 改动最小、不牵动已冻结的演示数字。

- **N-01｜卡面「未灌数据 `1/7 rc=1`」口径过期**：实测 5 种状态为 `0/7`（整库清空、账号在业务表空、只跑最小 `seed`）、`2/7`（只删读数与活动、只删告警），**没有 `1/7`**；`README.md:84-85` 已如实列出 `0/7 / 0/7 / 2/7` 并写「别把它当固定值」。反向验证的实质（未灌演示数据必红、退出码非 0）成立，建议卡面口径改为「非 0 退出即可，实测 0/7 与 2/7 两种」。
- **N-02｜复核期间环境被并发操作扰动**：复核中段 api 容器被并发 `docker` 操作重建（冻结钟环境变量 `T61_FAKE_NOW_MS`/`PYTHONPATH` 与容器内 `/tmp/sitecustomize.py` 消失、服务器回到真实钟），表现为间歇性连接拒绝与一次 `exit 137`（OOM；机器 7.5 GB，当时 `available≈3.9 GB`）。所有关键证据都在受控窗口内重跑取得；冻结钟那轮用 `GET /api/time` 自证（`utc_epoch_ms=1792339500000`）。建议：复核/演示期间避免并发 docker 与重构建。
- **N-03｜冻结钟复现步骤**（供后续复核复用，不写进仓库）：
  ```bash
  # 1) 插件：把 now_ms 钉在指定毫秒（仅在设置了 T61_FAKE_NOW_MS 时生效）
  cat > /tmp/t61-frozen/sitecustomize.py <<'PY'
  import os
  _f = os.environ.get("T61_FAKE_NOW_MS")
  if _f:
      import app.timeutil as _tu
      _v = int(_f)
      _tu.now_ms = lambda: _v
  PY
  # 2) override：给 api 服务加 PYTHONPATH 与冻结时刻
  cat > /tmp/t61-override.yml <<YML
  services:
    api:
      environment:
        PYTHONPATH: "/tmp:/srv"
        T61_FAKE_NOW_MS: "1792339500000"   # 2026-10-19 00:05 +08:00
  YML
  # 3) 重建容器 → 放进插件 → 启动（插件必须在进程启动前就位）
  docker compose -f docker-compose.yml -f /tmp/t61-override.yml create --force-recreate api
  docker compose cp /tmp/t61-frozen/sitecustomize.py api:/tmp/sitecustomize.py
  docker compose -f docker-compose.yml -f /tmp/t61-override.yml start api
  curl -s http://127.0.0.1:3000/api/time   # 自证：服务器进程也用冻结钟
  ```
