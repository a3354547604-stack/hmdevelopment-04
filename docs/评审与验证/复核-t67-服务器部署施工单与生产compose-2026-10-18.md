## 3. Findings（本轮新增；t48 的 F-01~F-06 处置见 §4）

### F-N1（low）两份 compose 共用 project 名与 `container_name`，dev 栈在跑时 prod `up -d` 会复用它——「db 不外露」可能假绿

- 现象（本次一手）：复核开始时机器上有另一名员工用**开发 compose**（`/tmp/t88rev-backend2/server/docker-compose.yml`）起的栈；我直接 `docker compose -f docker-compose.prod.yml up -d` 时 compose **复用了**那个已存在的 db 容器，于是：
  - `docker inspect hmprogram-server-db --format '{{json .HostConfig.PortBindings}}'` → `{"3306/tcp":[{"HostIp":"127.0.0.1","HostPort":"3306"}]}`
  - `… port db 3306` → `127.0.0.1:3306`、`ss -ltn | grep 3306` → 有监听
  - 容器 label 自证来源：`com.docker.compose.project.config_files:/tmp/t88rev-backend2/server/docker-compose.yml`
- 后果：按验收项 ② 的字面命令自检，会得到「db 暴露了 3306」的结论，**但它不是 prod 定义的行为**（prod 定义 `ports=None`，隔离栈实测 `:0`）。
- 缓解现状：`docker-compose.prod.yml` 头注释已写明「两者用同一套容器名与数据卷，切换时必须先 `down` 再起，不要把两份同时跑」；本次我用 `-p t68rev` + 仅改容器名的 override 规避。
- 建议（可选，不阻塞）：施工单 §3 的「起服务」前加一句——「若这台机器以前跑过开发 compose，先 `docker compose -f docker-compose.yml down`（**不要** `-v`）再起生产栈」。理由：施工单面向全新云服务器时风险低，但本机/复用机器上很容易踩到，且踩到时的现象（3306 暴露）恰好是最敏感的验收项。

### F-N2（low）`seed --password` 不校验长度，而登录接口要求 8–64 位：短口令会「seed 成功、登录 1001」

- 实测：`… exec api python -m app.seed --password 'abc'` → **成功**（`seed 完成…`）；而 `app/routers/auth.py:46` 对登录/注册强制 `8 <= len(password) <= 64`。
- 现状缓解：施工单 `:262` 已写 `--password '<8位以上口令>'`（提示正确），故不阻塞。
- 建议（可选）：seed 在 prod 分支加一句长度校验（`len(password) >= 8` 否则拒绝并提示），或在施工单该行补「短于 8 位会导致登录返回 1001」。

### F-N3（info）卡面 acceptance ①② 的字面写法与实现口径不同，判定按修正后的正确口径
