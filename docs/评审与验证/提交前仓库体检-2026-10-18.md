## 8. 附：t44 F-02（契约 §12.9 子原因措辞）的验收侧倾向

> captain 说这条恢复后处理，让我把倾向写在 t54 报告末尾，不另开卡。以下是验收视角的判断，不是裁决。

**事实**（t44 报告 §findings F-02）：本地配网 HTTP 对 `result=10`（网关连接数=1，`GW_PROV_RES_WL_FULL`）与 `result=11`（MAC 被占，`GW_PROV_RES_MAC_TAKEN`）都回 `409 / code=1605 / message="hub_offline"`（`rk2206-gateway/src/gw_prov.c:1073-1098`）；能区分子原因的地方只有串口日志与 `gw_prov_last_bind_result()`（`gw_prov.c:1118-1121`）。**云端命令路径是好的**：`gw_prov.c:1291-1305` 把两者分列（符合契约 v1.3 偏差 #9）。契约 §12.9 的措辞（「App 从 message 区分子原因」）与本地路径的实际行为不一致。

**倾向：改契约措辞，不改实现；把 `data.hub_result` 记为可选扩展。**

理由三条：

1. **P0 判分点不依赖这个区分**。本地配网失败的三种情形（离线/连接满/MAC 冲突）对用户的可行动作是同一句话——「网关侧配对失败，请重试或检查网关」；区分它属于体验优化，不是闭环缺口。云端路径已能区分，功能上没有丢失。
2. **改实现的代价跨三个模块**：网关错误体补字段（`gw_prov.c`）→ 契约 §12.5–§12.9 增字段 → H5/App 解析与文案（`rk2206-gateway/web/index.html`、App 配网页）。11/06 前改这条，回归面比收益大。
3. **契约必须能被执行**：一条「App 从 message 区分」的要求，在本地路径上没有任何可观测输出支撑（子原因没有出现在 HTTP 响应里），属不可验证条款——按验收口径应改成与实现一致的描述，或明确写「仅云端命令路径可区分」。

**具体建议措辞（供 PM/architect 直接采用或改写）**：把 §12.9 关于本地配网 `result=10/11` 的表述改为「本地 HTTP 配网路径下，`10`（连接数满）与 `11`（MAC 被占）一律回 §6.1 信封 `code=1605 / message="hub_offline"`（§9.2 1600 段错误码集合不变）；子原因仅串口日志与云端命令路径可见（`GW_PROV_RES_WL_FULL` / `GW_PROV_RES_MAC_TAKEN`）」，并在 §12 附注里加一行「可选扩展：网关本地错误体 `data.hub_result` 承载子原因（P0 不要求）」。

**若 PM 反过来选「改实现」**：最小改动是只在 `gw_prov.c` 的失败分支给 `data` 补 `"hub_result": <int>`（不改 code/message），App/H5 只做「有则展示、无则回退到 hub_offline」——这样不会破坏既有 §12.5–§12.9 字段域，也不会让 t44 F-01 那类「工具字段域过窄」的误报复发（必须同步把 `android-app/tools/check_local_api.py --js` 的字段域放开到 §9.2 1600 段值域，这条已登记随 t64 清理）。
