## 0. 结论摘要

t59 的三件事都是**真修**，主机侧可独立复现，板级“READY 可达 → 轮询起来”有上板日志：

1. CCCD 定位改成「属性句柄 `prop_handle`(0x11) + 描述符类型 `0x02`」——本 SDK 不吃 BLE 的「描述符 = 特征值 + 1」惯例；
2. 订阅成功判据不再看 write cfm（本 SDK 对**有效**的 CCCD 写 cfm 恒非 0，只有 `status=0x4` 是本机拒绝）；
3. 重试有上限，写满 `HUB_SUB_RETRY_MAX=3` 次仍未确认就**强制进 READY 并开始轮询**，堵住“CCCD 超时 → 回 PROP → 整轮重发现”的死循环。

主机自测在提交快照上 **PASS 192 / FAIL 0**，`hub_sub_decide()` 用例表 OK；三个反例（把错句柄改回去、把 cfm 当成功判据、去掉重试上限）**都能把门禁打红**，说明新断言有牙（本轮无静默绿灯）。

但有两处**必须写清的边界**，故本报告在 pass 之下带 4 条 findings：

- **F-01（medium）**：卡面验收③里“节点侧识别 CCCD 写”在**本卡的上板证据中不成立**——板 B 烧的是 t23 时编的镜像，日志里还是修复前行为；t59 文档 §10.5（第 359–361 行）**已如实披露**，不算失实自述，该证据后由 t70 的上板日志补齐（同一份 `sle_hub.c`，自 `ffdf63f` 未变）。
- **F-02（medium）**：「订阅成功以**收到首帧**为准」这条判据在实测路径上**不可达**：汇聚只对 READY 节点发 poll，而节点只在收到 poll（或本地事件）时才发帧 ⇒ 首帧到达时订阅状态机已经 DONE，`hub_sub_confirm_on_frame()` 早退。结果是正常路径**恒由 FORCE 兜底**，日志里永远没有 `sub-confirmed by first frame`。主机自测对这条只有**源码文本断言**（正则找函数名与日志串），没有按真实顺序的行为用例。

## 5. 专门裁定：强制 READY 会不会掩盖真故障？

**结论：不掩盖数据面故障，但会给“订阅未确认”发一张 READY 通行证。**

支持证据（我独立复算自 `out/t59-board-COM15-hub.txt` 的 `STAT` 行）：`rx=53 poll_ok=0 poll_miss=27`，同时节点侧每条 poll 都有应答 ⇒ 请求-应答链路是通的，只是**应答到达晚于 200 ms 判定窗口**。装配顺序与量化：主循环每 50 ms 一拍（`hub_cfg.h:65 HUB_TICK_MS 50`），且 `hub_pump_uplinks()`（收帧）在 `hub_agg_tick()`（结算 miss）**之前**（`hub_client.c:1617` vs `:1628`），所以窗口后的第一拍仍能结算；一旦应答晚于“deadline + 1 拍”（>200~250 ms）就永久丢结算。台架上 `interval = 0xa0`（≈200 ms 连接间隔）恰好落在这个量级，因此 27/27 全丢。后果链：`poll_miss` 累计 → 3 次判离线（`hub_agg.c:501-515`）→ 0x03 离线事件 → 节点在线状态每几秒抖一次（§8.7 误判）。这正是 t59 自己上报的缺陷②，我独立确认了根因链，判为 F-03。

所以对 captain 的专门问题，裁定如下：

1. **不能回到死循环**：强制 READY 是必要的兜底，方向正确（没有它，三节点在 App 上永远离线，比“订阅未确认但仍轮询”更糟）。
2. **但它必须有可观测的代价**：现在 FORCE 与 CONFIRMED 在状态机里都落到 `HUB_STAGE_DONE`（`hub_client.c:1234-1240` 与 `hub_cfg.h:136-140` 的返回值只在日志里区分），于是 ① `WARN: CCCD unconfirmed …` 在**正常**台架上就成了常态，告警信噪比归零；② `poll_miss` 无法区分“订阅其实没生效”与“超时窗口太紧”；③ 这两者在同一台架上同时成立时，运维只能靠人肉读日志。
3. **要求**（写进 findings，不阻断本卡）：
   - 把 FORCE 与 CONFIRMED 分成**两个可观测状态**（例如 `hub_agg` 的 `proc`/心跳里带子状态，或至少 `STAT` 行分别计数）；
   - 让首帧确认**真的可达**（见 F-02 的三种改法）；
   - 缺陷②修好后，台架应能看到 `poll_ok > 0`，此时再把 `poll_miss` 当故障信号使用。
4. **不构成静默绿灯**：真故障仍会在 poll 上浮现（本次 27 次 miss 全部可见），FORCE 没有把故障藏起来，只是把它与“订阅未确认”混在了同一个信号里。
