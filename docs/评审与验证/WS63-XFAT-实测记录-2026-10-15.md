# WS63（如般微 E528H-WS63）XF_AT 固件实测记录 — 2026-10-15

> 实测对象：手上这块如般微 E528H-WS63 开发板，USB 直连 PC。
> 结论一句话：**板子和 AT 通道都正常可用，但固件里确实没有 ADC / I2C / PWM / SPI 指令；同时「一主多从」在 AT 层实测可行（8 个 SLE 对象）。**

---

## 1. 实测环境

| 项 | 值 |
| --- | --- |
| 串口 | `COM14` — 设备名 `USB-SERIAL CH340 (COM14)`，实为 **CH330N**（`VID_1A86&PID_7523`） |
| 参数 | 115200 / 8 / N / 1 |
| 工具 | PowerShell + `System.IO.Ports.SerialPort`（脚本见 `ws63-firmware/scripts/at_send.ps1`、`ws63-firmware/scripts/at_probe2.ps1`） |
| 日志 | `ws63-firmware/scripts/at_probe_log.txt`（上电 + `AT+HELP` 全文）、`ws63-firmware/scripts/at_send_log.txt`（指令实测） |

### ⚠️ 坑 1：串口工具断言 RTS 会把模块按在复位里

原理图（`docs/如般微WS63/_txt/e528h-ws63-v01原理图.pdf.txt`）第 68 行：CH330N 的 `RTS#` 经 `R7/R8(10k)` + `Q1(CJ1012)` + `R9(100K)` 接到模块 **EN** 脚；规格书第 384 行「RST 按键内部连接模块 EN 管脚，低电平有效；**如果一直按下模块工作**」。

后果：第一次探测时我把 `DtrEnable/RtsEnable` 都设成 `$true`，板子**一个字节都不回**（表现为「端口能打开但完全静默」）。改成 **DTR=false、RTS=false** 后立刻正常。

⇒ 以后用 SSCOM / MobaXterm / PuTTY 连这块板，**务必确认 RTS 没有被勾选/拉低**，否则会误判成「板子坏了」。

### ⚠️ 坑 2：开机日志里有 Flash 初始化失败

上电后模块打印：

```
boot.
Flash Init Fail! ret = 0x80001341
verify_public_rootkey secure verify disable!
verify_params_key_area secure verify disable!
verify_params_area_info secure verify disable!
verify_image_key_area secure verify disable!
verify_image_code_info secure verify disable!
>> XF AT <<
```

固件仍能正常运行，但 **Flash Init Fail** 值得警惕：可能影响 `AT+CFGSAVE` 的非易失保存、以及后续 OTA / 烧录。**待验证**（下一步测 `AT+CFGSAVE=1` → `=0` 后重启看配置是否保留）。

## 4. 否定性实测：ADC / I2C 等确实不存在

直接下发这些指令，**全部返回 `ERROR`**：

| 下发指令 | 返回 |
| --- | --- |
| `AT+ADC` | `ERROR` |
| `AT+ADC=0` | `ERROR` |
| `AT+ADCGET` | `ERROR` |
| `AT+I2C` | `ERROR` |
| `AT+I2CSCAN` | `ERROR` |
| `AT+UART` | `ERROR` |
| `AT+UART2=115200` | `ERROR` |
| `AT+PWM=0` | `ERROR` |
| `AT+SPI` | `ERROR` |

配合 `AT+HELP` 的完整 55 条清单，可以下**板上实证的定论**：

> **芯片/模组有 ADC（最多 6 路）和 I2C（最多 2 路）——见 `m528h-ws63_硬件设计参考手册_v1.3`；但 XF_AT 固件没有把任何一个暴露成 AT 指令。**

与「基础指令表」逐条核对的结果一致（`docs/如般微WS63/_txt/xf_at_指令使用指南-v2.1.x.pdf.txt`），也与海思官方《WS63V100 AT命令 使用指南》目录一致（海思 AT 固件同样没有 ADC/I2C 指令）。

## 5. 意外收获：「一主多从」在 AT 层实测可行

评审报告（`docs/评审与验证/计划评审与可行性核查-2026-10-14.md` §2.4）把「用 AT 指令建多个 Master 对象」列为**能当场判死星形组网的实验 2**。实测下来是**通过的**：

```
AT+SLEENABLE=1        → OK
AT+SLEOBJ=1,1         → INFO:ID:0   OK
AT+SLEOBJ=1,1         → INFO:ID:1   OK
...                   → INFO:ID:2 3 4 5 6 7   OK
AT+SLEOBJ=1,1（第 9 个）→ ERR:MAX CNT:8   ERROR
AT+SLEOBJ=1,1（第 10~12 个）→ ERR:MAX CNT:8   ERROR
```

实测数字：**最多 8 个 SLE 对象，ID 0~7**（8 个成功，第 9 个起 `ERR:MAX CNT:8`）。与海思官方「WS63 协议栈最多 8 路 SLE 并发连接，conn_id 0~7」完全吻合。

**这意味着：**

- ✅ 汇聚节点「1 主连 5 从」在**对象预算**内，不会一开始就撞 `ERR:MAX CNT`；评审「实验 2 一失败星形组网当场判死」的预判**不成立**。
- ⚠️ **但这不等于 5 路并发连接真的能跑起来**。创建 8 个对象只证明对象池够用，没证明 8 条连接同时在线时的吞吐/稳定性/互不干扰。要证明这个，必须**真插 2~8 块从机板**做并发收数实测——这是下一步唯一有效的实验。
- ⚠️ 仍未解决的核心矛盾不变：**节点侧读不了模拟量/I2C 传感器**（本记录 §4），所以「所有传感器挂星闪节点」依然不成立。

---

## 6. 附带确认：GPIO 数字读写可用

```
AT+GPIOCFG=0,1   → OK      （配置 GPIO0）
AT+GPIORD=0      → INFO:0  OK   （读到低电平）
```

⇒ 星闪节点用 `AT+GPIORD` 读**开关量**（干簧管门窗磁、红外人体模块的数字输出、按键）在 AT 层是成立的；**但模拟量（MQ 气体）和 I2C（AHT20）读不了**。

## 7. 复现方式

```bash
# 上电日志 + 完整指令表（DTR/RTS 必须保持释放）
powershell -NoProfile -ExecutionPolicy Bypass \
  -File tools\at_probe2.ps1 -PortName COM14 -Baud 115200

# 任意指令序列（用 | 分隔）
powershell -NoProfile -ExecutionPolicy Bypass \
  -File tools\at_send.ps1 -PortName COM14 -Baud 115200 -WaitMs 900 \
  -Cmds "AT|AT+SLEENABLE=1|AT+SLEOBJ=1,1|AT+GPIORD=0"
```

> 注意：Windows 串口独占。跑脚本前请先关掉 MobaXterm 的 COM14 串口标签页（否则报「对端口 COM14 的访问被拒绝」）。

## 8. 对实施计划的影响（小结）

| 计划中的做法 | 实测判定 |
| --- | --- |
| 「WS63 不写 C 固件，只烧 XF_AT」 | ✅ 可行，固件是最新 V2.1.13-d，AT 通道正常 |
| 节点用 `AT+GPIORD` 读数字量（门窗磁/红外/按键） | ✅ 可行 |
| 节点用 ADC 读 MQ-2/5/7 气体 | ❌ **板上无此指令** |
| 节点用 I2C 读 AHT20 温湿度 | ❌ **板上无此指令** |
| 节点用 UART2 读 LD6002 雷达 | ❌ **无 UART 读取/转发指令** |
| 汇聚节点「1 主连 5 从」 | 🟡 对象上限 8（够用），**并发连接真伪待多板实测** |
| MQTT 直连云 | ❌ 无 MQTT 指令（只有裸 TCP/IP，需自己封 MQTT 报文） |
