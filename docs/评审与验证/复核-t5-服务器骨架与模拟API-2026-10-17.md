## 4. 不符项（findings）

### F-01（medium，契约/PM 裁决未落地）`gas_l1_to_l2_s` 出现在 §6.9 `items` 且可经 §6.10 下发

- 现象：`GET /api/devices/1/settings` 返回 **22 键**（§6.9 的 21 键 + `gas_l1_to_l2_s=60`）；`PUT /api/devices/1/settings {"items":{"gas_l1_to_l2_s":30}}` → **HTTP 200 code=0 且落库 30**。
- 契约：v1.2 §6.9 注（第 924 行）「`gas_l1_to_l2_s` 属 §8.2 的算法参数，**不在本节 `items` 示例里**」；§6.10（第 930 行）「`1003` 未知键（含 `gas_l1_to_l2_s`：它是 §8.2 算法参数，不可经本接口下发，见 §6.9）」。
- 代码：`server/app/settings_keys.py:41` `"gas_l1_to_l2_s": KeySpec("gas_l1_to_l2_s", "int", 60, 10, 600, "M1")`（文件头注释自述「契约 §6.9 字段表 21 项，加 §8.2 需要的 gas_l1_to_l2_s」——即实现明知超出契约而保留）。
- 建议修复（一处，二选一）：① 从 items 表移除该键，§8.2 算法继续用内部默认 60 s（推荐，零风险）；② 若确要开放运行时配置，走契约变更并同步 App。复核期间我把它写回 60，demo 数据已还原。

### F-02（low-medium，v1.2 新规则）§6.14 `dispositions[]` 元素的时间键是 `at`，契约写 `ts`

- 现象：`GET /api/alerts/{id}` 的 `dispositions[]` 元素键 `['action','at','id','note','user_id','username']`，缺契约 §6.14 示例（第 986 行）的 `ts`（示例：`{"id":3,"action":"checked","note":"…","user_id":1,"ts":1792243800000}`）。
- 影响：App 告警详情页按契约取 `ts` 会拿不到处置时间（`harmony-app` 的解析层对缺键会记 warning/报错，取决于该字段是否必填）。
- 代码：`server/app/services/alerts.py`（处置记录序列化处）。v1.1 只有 §6.15 响应示例用 `ts`，元素级示例是 v1.2 新增 —— 属落地缺口。

### F-03（low，v1.2 新规则）§6.13 `status` 未知取值返回 `1002`，契约明文 `1001`

- 现象：`GET /api/alerts?device_id=1&status=bogus` → HTTP 400，`code=1002`，`data={"field":"status","allowed":["pending","confirmed","resolved","all"]}`。
- 契约 §6.13（第 954 行）：「`status` 取值集合（v1.2 写死）… **未知取值 → `1001`**」。
- 代码：`server/app/routers/alerts.py` 的查询参数校验（走 §9.2 的 1002 越界分支）。
- 说明：`1002` 带 `field/allowed` 对调试更友好，但契约写死 `1001`；建议按契约改，或由 PM 改契约（**不要两边都不动**）。

### F-04（high，跨模块类型冲突；需 PM 裁决，非 t5 单方缺陷）§6.11 `accepted`/`rejected` 类型三处不一致

- 实测（HEAD 627257c，全新卷）：`POST /api/devices/1/config {"keys":["no_motion_min"]}` → `data={"command_id":"cmd-…","request_id":"3da1bf","accepted":1,"rejected":0,"dispatched_at":…,"timeout_s":10}`，**两个整型**。
- 契约 v1.2 §6.11 示例（第 939 行）与 §6.11 注（第 942 行 / PM D-05）：`"accepted":["no_motion_min","report_interval_s"],"rejected":[]`，明文「**字符串数组，元素为键名**」（位置 `data` 内，不在顶层 —— 这一点实现正确）。
- PM 裁决：t18 任务卡的背景口径写「accepted/rejected 为 data 内两个**整型**键，属实现正确性的一部分」→ 服务端**符合 PM 口径**。
- 但 **App 按契约实现**：`harmony-app/entry/src/main/ets/model/Types.ets:193-194` `accepted: string[]`，`:555-556` `accepted: strArray(o,'accepted','data.config')`，而 `harmony-app/entry/src/main/ets/common/JsonUtil.ets:138-150 strArray()` → `mustArray()` → `asArray()`，**值不是数组时抛错**（`JSON 字段错误：data.config.accepted 期望 array…`）。
- 影响：**P0 演示动作「阈值下发」「演示注入」在「鸿蒙 App + 真实服务器」组合下会解析失败**（Mock 传输层返回的是数组，所以自检/预览全绿、真机才炸）。
- 需要 PM 一次裁决（三处对齐）：契约文本改成整型（推荐，改动最小：契约 §6.11 示例 + D-05 注）、或在服务端改回数组并让 App 适配；同时 `harmony-app` 的 `CommandResult/DemoResult` 与 `MockData.ets:239` 要跟着改（t22 范围之外，需另开卡或扩 scope）。
