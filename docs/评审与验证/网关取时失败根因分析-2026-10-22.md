## 0. 结论（先看这一段，其余是可复核的证据）

**根因 B-1（第一顺位，静态可证）：固件从没给 lwip 安装「默认网卡」。**
STA 连上、`wlan0` 拿到 `192.168.137.171`，但全局 `netif_default` 始终是 `NULL`；lwip 的路由函数 `ip4_route()` 对**非本网段**的目的地址（`123.206.99.28`、`124.70.218.131`）先按「同网段前缀」遍历，全部不命中，最后要求 `netif_default` 可用，否则直接 `return NULL`。于是 `connect()` **立即**返回 `-1`（errno `EHOSTUNREACH`），HTTP 取时当场失败，NTP 兜底又是死代码（见 B-3），最终每次都打 `[gw] 取时失败：服务器与 NTP 都不可达，暂不连 IoTDA`，然后 `LOS_Msleep(5000)` 再来一遍。

> 一句话：**问题不在服务器、不在热点/NAT、不在 DNS、不在 5 s 超时、不在 KV 凭据，也不在射频**——是本机根本没有「默认路由」这个对象。

**根因 B-2（历史叠加项，20:07 后已消解）：服务器返回的字段名与固件白名单不匹配。**
固件只认 `"server_time" | "epoch" | "ts" | "unix"`（`gw_timesync.c:53`），而服务器原来只给 `utc_epoch` / `utc_epoch_ms` / `server_ts`。`"utc_epoch"` **不会**命中 `"epoch"`（前导字符是 `_` 不是 `"`），所以**在 20:07 加 `epoch` 别名之前，就算网络完全正常也必然取时失败**。这条解释了「为什么前面改服务器、重写凭据都白费」。

**根因 B-3（潜伏，必须一起修）：NTP 兜底是死代码。**
`gw_config.h:157` 的 `GW_NTP_HOST = "ntp.aliyun.com"` 被 `inet_addr()` 解析（`gw_timesync.c:157-160`，调用点 `gw_main.c:867-871`），域名输入必得 `INADDR_NONE`，函数立刻 `-1`，**永不发 DNS**，也不可能成功。它不耗时，但会让人误以为「还有一条兜底路」。

**根因 B-4（潜伏，修 B-1 之后才轮到它）：`link_up` 标志没人保证。**
`ip4_route()` 的默认网卡分支还要求 `netif_is_up() && netif_is_link_up()`。全镜像里 `netif_set_up` 只有 `libhardware.a:rk_wifi_set_mode()` 调（`wlan0` 会 up），但 **`netif_set_link_up` 在最终镜像里只有定义、没有任何调用者**（`liteos.map` 1 处，是定义）。驱动可能自己直接置位（预编译库，静态证不了），所以修订单里**把 set_up/link_up/default 三件一起做**，并把 `flags` 打印出来——`wifi net` 一条命令即可确认。

**修复代价：** 一次烧录 + 一条命令。**不需要**再复位、再写凭据、再改服务器、再试错。

## 2. 第 2 轮：对抗复核（假设第 1 轮结论是错的）

### 2.1 板子到底有没有互联网？
**不需要假设也能定案**：失败发生在 `connect()` 的**路由阶段**，`ip4_route()` 在发包前就返回 NULL——此时 ARP 都没发、SYN 都没出。也就是说，「有没有网」这个变量对本次现象**不构成影响**；但它会决定「修完 B-1 之后是否就能通」，所以仍要一条命令把两者分开（§3）。
**已有的正面证据**：同一台机器（WSL）对 `123.206.99.28:80` 直连成功（§7-A）；板子侧 `联网成功：IP=192.168.137.171`（`gw_main.c:1379`）说明 DHCP 已拿到地址。

### 2.2 SDK 厂商默认 STA（启动日志里的 `ip=192.168.2.10`）会不会让 `net_wifi_on()` 跳过必要初始化？
- `gw_net.c:44-55` 的 `s_wifi_on` 是**一次性门闩**：只挡「重复 EnableWifi」，不涉及 netif 安装。
- 厂商默认连接来自 SDK 的 `config_network.c`（`SetWifiModeOn` 读 Vendor 槽，t136 已定案），它与我们的 STA 连接**各自独立**，且它那条路径里恰好**显式调了 `SetLocalWifiGw()`**（`config_network.c:734`）——反过来说明「谁连的网谁负责装默认网卡」，而我们这条路没装。
- 结论：不是干扰项，反而是同一根因的对照组。

### 2.3 5 s 超时是否短于热点首包（ARP/DNS）延迟？
否。①失败点在任何报文发出之前；②本链路不需要 DNS（`time_host` 是 IP 字面量，`docs/执行/IoTDA建产品与设备指引.md:658` 也明确要求填 IP）；③同机实测 `/api/time` 往返 < 1 s（§7-A）。

### 2.4 `inet_addr()` 对 `124.70.218.131` 是否正常？（不凭记忆）
本机无编译器（`gcc/cc/clang` 均不存在），改用**板上真正运行的实现**：`third_party/lwip/src/core/ipv4/ip4_addr.c`

- `ipaddr_addr(cp)`：`if (ip4addr_aton(cp,&val)) return u32; else return IPADDR_NONE;`（`inet_addr` 就是它）。
- `ip4addr_aton` 对「首字符不是数字」的输入 `return 0`（`ip4_addr.c:214  /* initial nondigit */`）。
- 数值复核：`124.70.218.131` → 0x7C46DA83（网络序），LE 存储 0x8336DA7C，**不等于** `IPADDR_NONE(0xFFFFFFFF)` ⇒ HTTP 分支的 `inet_addr` 正常。
- `ntp.aliyun.com` → `ip4addr_aton` 返回 0 ⇒ `ipaddr_addr` 返回 `IPADDR_NONE` ⇒ `gw_timesync.c:37-40` 立刻 `-1`；`gw_main.c:862-871` 的 NTP 路径同理。**B-3 成立：NTP 兜底不可能成功，也不会卡 5 s。**

### 2.5 `netif_default` 到底有没有被设过？（这是本报告的核心证据链）
1. `netif_default` 是全局对象，`.bss`（`liteos.map:15258/15260`，0x3800b9e4），初值 0。
2. **唯一的写者**是 `netif_set_default()`（`third_party/lwip/src/core/netif.c:833`）；`netif_add()` 不设默认（`netif.c:280-300` 只在 `LWIP_SINGLE_NETIF` 下断言）。
3. 全镜像里引用 `netif_set_default` 的**只有一个目标文件**：`libs/libwifiservice.a(libwifiservice.wifi_device.o)`（`liteos.map:552`）；其余库扫过，无一引用（§7-B）。
4. 在该目标文件里，`netif_set_default` 的**唯一调用者**是 `SetLocalWifiGw()`（`objdump -dr` 的重定位：`<SetLocalWifiGw>: 98: R_ARM_ABS32 netif_set_default`）。
5. `SetLocalWifiGw` 在最终镜像里**没有任何调用者**（`liteos.map` 4 处全部是定义/`.rodata` 字串）。
6. 我们的源码 `rk2206-gateway/src/` 里 `SetLocalWifiGw|netif_set_default|netifapi_netif_set_default|RegisterWifiEvent` **零命中**（只有 `gw_net.c:567 IsWifiActive()`、`gw_net.c:727 netifapi_netif_find_by_name` 查 AP 口）。
7. 全镜像唯一还会设默认网卡的是 HDF 的 `drivers/adapter/khdf/liteos_m/network/src/net_device_adapter.c:448/492`，但 `DeviceManagerStart()` 在 `board/main.c` 里**被注释掉**。

⇒ **`netif_default == NULL` 是静态必然结果，不是猜测。**

### 2.6 现场「每 2 s」与代码「每 5 s」的冲突（陈旧固件判据）
`net_task` 失败分支是 `LOS_Msleep(5000); continue;`（`gw_main.c:1481-1483`）。若现场确为 **2 s 一刷**，说明板上跑的不是当前源码（旧版退避可能是 2 s）。
**但**：启动横幅 `gw_main.c:1937` 打的是 `GW_IMAGE_TAG`，而它是**常量** `ELDERCARE-GW-M0-v1.2`（`gw_config.h:136`），**不随提交变化** ⇒ 从日志无法判断板上是哪次构建。修订单 FIX-6b 把 `__DATE__ __TIME__` 打进横幅，从此一眼可辨。

### 2.7 服务器字段名（B-2）的真实形状
本机直连 `/api/time`（§7-A）返回：
```
HTTP/1.1 200 OK
Server: nginx
Content-Length: 194
Connection: close
cache-control: no-store

{"code":0,"message":"ok","data":{"utc_epoch":1792672341,"epoch":1792672341,"utc_epoch_ms":1792672341862,"iso8601":"...","tz":...}}
```
- 现在 `epoch` 已在（20:07 别名），`pick_epoch` 的 `strstr(body,"\"epoch\"")` 能命中（`"utc_epoch"` 里的 `epoch` 前导是 `_`，不会误命中）。
- **在此之前**，白名单四个键**一个都不在**响应里 ⇒ 即便 B-1 不存在，也必然取时失败。**两处必须同时正确**，这是前七八轮「改了看不到效果」的结构性原因。

### 2.8 仍未静态证明的一条（诚实标注）
`link_up` 位是否由预编译驱动直接置位，无法在源码层证明（驱动在 `libhardware.a` 里，闭源二进制）。因此：
- 报告不赌它：FIX-1 里把 `set_up / set_link_up / set_default` 三件一起做（幂等，无副作用）；
- `wifi net` 会把 `flags` 打出来，一次就能确认（§3）。

### 3.3 三种预期输出 → 三条处置分支（判据写死，不留「可能」）
| `wifi net` 的输出特征 | 含义 | 下一步 |
|---|---|---|
| `flags` 含 `up|link`、`is_default=YES`，两条 `probe … connect ok`，且串口随后出现 `[gw] 取时成功` / `IoTDA 已连接` | **B-1 已修复，链路通** | 完成，不需要任何后续动作 |

**但这只是旁证，不能替代 §3.2 的判据**（看不到 `is_default/flags`）。推荐直接烧 FIX 版，一次到位。

## 4. 第 4 轮：修订单（交给 gw-rk2206-op2 照做，逐条给文件行号）

> 原则：能一次烧录解决的，不拆成两次。FIX-1/2/3/4/5/6 打成一个镜像，用户只敲一条 `wifi net`。

### FIX-1（必须，修 B-1）：安装默认网卡
- 新增函数（建议放 `rk2206-gateway/src/gw_net.c`，紧跟 `gw_net_sta_ip()` 之后，约 `:840` 处）：
  ```c
  /* lwip 的 ip4_route 对"不同网段"的目的地址必须有 netif_default，
   * 否则 connect() 在发包前就返回 EHOSTUNREACH——RK2206 的 wifi 适配层
   * 不会替我们装（对照 vendor/.../b7_wifi_tcp/wifi_tcp_example.c:37、
   * config_network.c:734 都显式调了 SetLocalWifiGw）。 */
  int gw_net_install_default_iface(void)
  {
      struct netif *n = netifapi_netif_find_by_name("wlan0");
      if (n == NULL) return -1;
      (void)netifapi_netif_set_up(n);
      (void)netifapi_netif_set_link_up(n);
      (void)netifapi_netif_set_default(n);
      printf("[NET] 默认网卡=%c%c flags=0x%02x up=%d link=%d\n",
             n->name[0], n->name[1], n->flags,
             (int)netif_is_up(n), (int)netif_is_link_up(n));
      return 0;
  }
  ```

## 6. 复盘：为什么前面七八轮（烧录 4 次、写凭据 3 次、多次复位）都没修好

| 试过的方向 | 为什么不可能有效 |
|---|---|
| 改服务器（加 `epoch` 别名、查 200） | 服务器侧完全正常（§7-A），板子连 SYN 都没发出去（B-1） |
| 反复写凭据（CSV/串口 `wifi set`） | KV 已正确（`gw_main.c:174-176` 回显 `time=123.206.99.28:80`），问题在 IP 层之上 |
| 复位 / 关热点 / 重连 Wi-Fi | `wifi` 层面已达成功（打印了 IP），失败点在路由层，复位只会重复同一路径 |
| 怀疑 5 s 超时太短 | 失败发生在**发包前**，超时参数根本没被用到 |
| 怀疑热点没有 NAT | NAT 只影响 SYN 之后；B-1 让 SYN 都出不去，且它是**静态可证**的（§2.5） |
| 怀疑固件没烧进去 | 有可能，但启动横幅不含构建时间（FIX-6b），**所以以前无法判断**——这也是本报告必须补的诊断项 |

**根本教训：这条链路上有 13 个可失败点，代码只在最外层打一句「都不可达」。** 没有 errno、没有阶段、没有耗时，任何一次现场失败都只能猜。FIX-4/FIX-5/FIX-6 的价值就是把「猜」换成「读一行日志」。
