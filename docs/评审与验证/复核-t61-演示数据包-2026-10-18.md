## 2. 方法

1. **干净卷**：`docker compose down -v`（删卷）→ `up -d` → 先在**空库**跑自检（反向）→ `seed --demo` → 再跑自检（正向），全程用 `docker compose exec -T api …` 走真实 HTTP（`demo_check.py` 自己打 `127.0.0.1:3000`）。
2. **幂等**：`seed --demo` 连跑两次，stdout 落两个文件做 `diff`。
3. **时钟无关性**：宿主脚本 `/tmp/t61-clock-probe.py` 在容器内 patch `app.*` 全部模块的 `now_ms`（15 个模块）到 6 个钟点（0h / −22h / +4h / +13h / −11h / +28h），每个钟点重新 `seed --demo` 再跑 `demo_check`，比较形状（天数、告警类型集合、读数总数、网关跳变、D6 计数）。
4. **读码**：`app/demo_check.py`、`app/seed.py`、`tests/test_80_demo_seed.py`、`deploy/演示数据施工单.md` 逐行核对判据与文档措辞。
5. **回归**：`docker compose run --rm --no-deps -e DB_HOST=db api python -m pytest -q`（全量）。

## 5. findings

### F-01（medium）D4 读详情的副作用没写回，自检消耗「待处置 SOS」

- 现象：`demo_check` 跑完后，`sos`（source=app，id=7）由 `pending` 变 `confirmed`、`next_push_at` 被清空（§4.7 表）。
- 定位：`server/app/demo_check.py:188-198` 的 D4 对每条 SOS 直接 `api.get(f"/api/alerts/{item['id']}")`，没有像 D1 那样用 `_read_detail()`（`server/app/demo_check.py:114-126`）把 `status`/`next_push_at` 写回；服务端行为见 `server/app/routers/alerts.py:59-69`（打开详情 → `pending` 置 `confirmed`、`data.pop("next_push_at")`）与 `server/app/services/alerts.py:177-183`（`confirm_on_read` 只改这两列，所以 D1 的写回是完整的）。
- 影响：演示要演的「App 触发 SOS → 待处置」在自检后消失（待处置告警 4 → 3 条），与 `demo_check.py` 头注释声称的「自检不改变被检对象」自相矛盾；D1 保护的是燃气，卡面字面要求满足，但同类风险在 D4 复现。
- 最小修法：D4 也用 `_read_detail()`（或在 D4 前记录、后写回 `status`/`next_push_at`），并把「所有读详情处一律写回」写进 `demo_check.py` 头注释。

### F-02（medium）灌数 180 s 后自检必红；施工单对该边界的表述与代码不符

- 现象（独立复现）：`seed --demo` 后等 200 s 再跑 `demo_check` →
  ```
  [FAIL] D6 网关离线→恢复（跳变 + 补传 + 恢复告警）
         /status 显示网关仍离线
  == 有失败项（退出码 1）… ==        # rc=1，6/7
  ```
- 根因：`seed` 把 `device_online.last_heartbeat_ms` 写成真实 `now`，而 `server/app/config.py:76 gateway_offline_timeout_s=180`；`server/app/services/scheduler.py:46-70 tick_gateway_offline()` 在超时后置 `online=0` 并升起 `device_offline`（§8.7）。D6 的断言除了「至少一条带 `recovered_at`」还断言 `/status` 的 `online is True`（`server/app/demo_check.py:266`）。
- 与文档冲突：`server/deploy/演示数据施工单.md:88` 把「演示进行中多出一条待处置 device_offline」写成**预期行为**并称「D6 判据是「至少一条带 recovered_at」」——实际的 D6 判据还包含 `online=True`。
- 影响：**演示中途（>3 min）再点一次自检就红**；若演示持续 >3 min，服务器侧网关确实变离线（App 上会看到网关离线、多一条待处置告警），演示数字从 10 条告警漂到 11 条（实测 D7 证据行变成「告警 11 条」）。
- 最小修法（二选一，建议前者）：①`demo_check.py` 在 D6 前对演示设备补一次心跳（`PUT/POST` 现有心跳接口）或把 D6 的在线断言改成「`recovered_at` 存在」并在证据里如实打印当前 `online`；②`施工单` §3 改写为「180 s 后网关会被判离线、D6 会红，必须重跑第 2 步 `seed --demo`」，并把 D6 判据描述补齐为三条。

### F-03（high）D6 的「补传」判据与随附回归用例随钟点退化：13:00 CST 之后必红、证据标签失真

- 现象一（当晚实跑）：`demo_check` 的 D6 证据行在 13:00 CST 之后打印
  `窗口内补传 14 条（type=['gas','presence','status']，窗口内读数共 14 条）`，而设计与用例都要求 **11** 条；同日在 13:00 之前（探针 +28h 等钟点）打印的是 `窗口内补传 11 条（type=['status']）`。
- 现象二（提交自带用例变红）：
  ```
  FAILED tests/test_80_demo_seed.py::test_seed_demo_produces_reproducible_dataset
  E       assert 14 == 11
  tests/test_80_demo_seed.py:89: AssertionError
  PYTEST_RC=1        # 21:0x CST，全量 pytest 只有这 1 个 FAILED
  ```
- 根因：D6 用「`created_at` 晚于断网窗口结束（今日 13:00 CST）」来认补传（`server/app/demo_check.py:250-259`；用例同口径 `server/tests/test_80_demo_seed.py:88-89`）。而断网窗口内本来就有 3 条**实时**写入的行（燃气背景 12:00 + 活动点 12:12/12:48，`server/app/seed.py:354-430`），`seed` 的执行时刻只要晚于 13:00 CST，这 14 行**全部**满足 `created_at > 窗口结束`，判据就再也区分不出「补传」与「实时写入」。
- 影响：a) 演示若在傍晚/晚上做，自检证据行会写「补传 14 条」，与设计文档、契约 §4.7 演示动作 6 的口径不一致（读报告的人会以为多数了 3 条）；b) t49 提交自带的回归用例**在 13:00 CST 之后必然失败**，提交信息里的「pytest 112 passed」在晚上不可复现，`与运行时刻无关` 这句话对这条判据/这个用例不成立（数据集本身确实与时刻无关，见 §4.4）。
- 最小修法（建议）：把判据从「墙钟」改成「数据内自证」，例如断言「窗口内存在 `type='status'` 且 `created_at - ts > 0` 的行 ≥ 1 条」或给补传样本一个可核对的标识（`created_at = ts + 3 min` 已经在 `seed.py:402` 成立，直接断言这个差值即可），并同步改 `tests/test_80_demo_seed.py:88-89`，让全量 pytest 在任意钟点都绿。

### F-04（low）反向方向的条数与卡面/提交信息不符（0/7 vs 1/7）

- 现象：整库 TRUNCATE 后（演示账号一并被清）自检以「登录失败（HTTP 401，code=1102）」整体退出，计 **0/7**；卡面与 t49 自报写 **1/7**。
- 定位：`server/app/demo_check.py:354-374`（登录失败即整体失败，不逐条计），`server/deploy/演示数据施工单.md` 对两种反向做法都允许。
- 影响：纯文档口径；「未灌数据一定红 + rc=1」的目的达成。
- 最小修法：把卡面/自报里的「1/7」改成「0/7（整库清空时登录即失败）」或明确写「反向 = 未灌业务数据的库，账号仍在 → 1/7」。

### F-05（low）prod 守卫会被 config 占位符检查遮蔽

- 现象：直接 `-e APP_ENV=prod` 跑 → rc=1 的 `RuntimeError: APP_ENV=prod 但 JWT_SECRET/WEBHOOK_TOKEN 仍是占位符…`，看不到 `拒绝执行：APP_ENV=prod 下不允许 --reset/--demo`；注入非占位值后才走到 rc=2 的守卫。
- 影响：照施工单 §4 自测「prod 拒绝」的人会先撞到另一条错误，容易误判为缺陷。
- 最小修法：在 `施工单` §4 该行补一句「prod 自测需同时注入非占位 `JWT_SECRET`/`WEBHOOK_TOKEN`（见 §5 配置清单）」。

### F-06（low）断网窗口内存在 3 条实时写入的读数（F-03 的根）

- 现象：窗口 [今日 12:00, 13:00) 内共 14 条读数 = 11 条补传 + 燃气背景 1 条（12:00）+ 活动点 2 条（12:12/12:48）。
- 定位：`server/app/seed.py:354-430`（燃气每 2 h 一条在 `:07`、活动点按 `16+(i*7)%11` 落点）。
- 影响：本身不违反契约（断网是网关侧动作，节点读数照常入库），但让「窗口内读数=补传」的简化假设不成立（F-03 由此而来）。
- 最小修法：与 F-03 一起改判据即可；若要演示「断网期间一条都没有」，把燃气/活动点的落点移出 12:00–13:00。
