# 术语速查（答辩 / 给队友讲）

> 从《赛题四-实施计划》§18 拆出。答辩前复习用。

## 18. 术语速查（答辩/给队友讲）

### 18.1 MQTT broker 是什么

MQTT 是「发布/订阅」协议，**broker 就是转发消息的中心服务器**。

```
设备 --发布 topic: hm/dev01/property--> [broker] --推给订阅者--> 后端/App
App  --发布 topic: hm/dev01/cmd-------> [broker] --推给设备----> 设备
```

- 职责：维护上万设备的长连接、按 **topic** 路由、离线消息暂存、鉴权。
- **本项目谁当 broker**：**华为云 IoTDA 内部就是一个 MQTT broker**。设备连上它 = 完成"接入"。
- **自建服务器不用自己跑 broker**：它走 IoTDA 的**应用侧**接口取数（HTTP 推送 / AMQP 订阅）再转 App。
- → **全系统只有 1 个 broker（IoTDA）**，没有第二个 MQTT 服务器。

### 18.2 为什么要有心跳（keepalive）

MQTT 走 **TCP 长连接**。TCP 只保证链路通，**不保证对端还活着**：路由器 NAT 超时、运营商掐链、设备断电，双方可能几十分钟都发现不了，连接变成"僵尸连接"。

心跳 = 设备每 N 秒发 `PINGREQ`，broker 回 `PINGRESP`：
- broker：**超过 1.5×keepalive 未收到即判离线**，触发离线事件
- 设备：收不到回应就重连

**「数据不是实时传的吗」**——数据是**事件驱动**的（变化才报），两次上报之间可能几分钟什么都没有。**没有心跳，就分不清"没数据"是"一切正常"还是"设备掉线了"。** 而赛题第 3 项明确要求 App 显示「**设备在线状态**」——这就是心跳存在的理由。

IoTDA 官方口径：keepalive **30~1200 秒，推荐 120**。

### 18.3 QoS 是什么（不是负载均衡）

QoS = **消息投递保证等级**，MQTT 只有 3 档：

| QoS | 含义 | 代价 | 本项目用在哪 |
|---|---|---|---|
| **0** | 最多一次，**可能丢** | 最省 | 温湿度/人体等周期性常规数据 |
| **1** | 至少一次，没确认就重发，**可能重复** | 中 | **报警事件、求助按钮**（宁可重复不能丢） |
| **2** | 恰好一次，四次握手，**最慢** | 最大 | 不用（实时性差） |

（负载均衡是**服务器集群**概念，与 QoS 无关。）

### 18.4 华为云 IoTDA 与自建服务器各干什么

| 维度 | 华为云 IoTDA（**必须真跑**） | 自建服务器（增强） |
|---|---|---|
| 定位 | **设备接入与管理平台** | **业务后端** |
| 管什么 | 设备注册鉴权、TLS 证书、**MQTT broker**、物模型、**设备在线状态（心跳）**、**离线命令缓存（设备影子 48h）**、OTA | 用户账号/JWT、活动与预警业务数据、处置记录、**周/月报 SQL 聚合**、**报警未确认队列 + Push Kit 推送**、REST API |
| 不管什么 | 不存业务数据、不做复杂查询、不给手机推送 | 不管设备连接、不管设备鉴权 |
| 赛题对应 | 「**基于物联网云平台进行设备管理**」原文要求 | 赛题第 3/4/5 项的报表与处置闭环 |

**核心原则：设备只认 IoTDA 一个云端——服务器不知道设备 IP，设备不知道服务器存在。**

### 18.5 数据流示意（逐跳）

```
 [传感器：红外 / 门窗磁 / AHT20 / 雷达 / MQ-x]
      │ GPIO / I2C / ADC / UART
      ▼
 [WS63 星闪节点] --SLE 星闪--> [WS63 汇聚] --UART AT--> [RK2206 网关]
                                                          │
                              本地闭环：阈值判断 → 声光 + 语音（**不依赖网络**）
                                                          │
                                              WiFi 2.4G / MQTT（样例明文 1883，TLS 待接）/ QoS1
                                                          ▼
                                       ┌──── 华为云 IoTDA（broker）────┐
                                       │ 在线状态 / 物模型属性 / 命令下发 │
                                       └──────────────┬───────────────┘
                                         规则引擎 → HTTP 推送 / AMQP 订阅
                                                       ▼
                                        自建服务器（MySQL + 业务逻辑）
                                                       │ HTTPS(历史·报表) │ 报警：Push Kit 推送
                                                       ▼
                                             鸿蒙 App（+ uni-app 备用）
```

**五段链路**：传感 → 星闪 → 网关 → 云 → 手机。**本地声光报警在网关就闭环，前四段任一可用都能响**。

### 18.6 数据库分工

| 端 | 数据库 | 存什么 | 为什么 |
|---|---|---|---|
| 服务器 | **MySQL 8**（2G 够用，`innodb_buffer_pool_size=128M`） | 用户、设备、**活动记录**、**预警与处置日志**（赛题第 4 项）、物化报表 | 多用户、SQL 聚合、周/月报 |
| 手机 | **SQLite**（鸿蒙 `@ohos.data.relationalStore`） | **最近若干天的数据副本**、离线可看报表 | 弱网/断网 App 仍可用；省流量；列表不卡 |

> 手机 SQLite 不是第二份数据库，是**服务器数据的本地缓存副本，以服务器为准**。

### 18.7 MQ 系列为什么要"上电老化"，要一直插电吗

**MQ-2/5/7 是半导体气敏传感器**，内含一根加热丝（5V、约 150mA）。**新出厂的元件表面有制造残留、气敏材料未稳定**，需连续通电让加热丝烧掉残留、材料结构稳定 —— 这就是 **burn-in / 上电老化 / 预热**。

- 【数据手册】MQ-2 要求 **24~48 小时连续预热**；**长期存放（1 个月以上）后再用，同样需 24~48 小时**（[SunFounder](https://docs.sunfounder.com/projects/umsk/en/latest/01_components_basic/04-component_gas.html)、[iotwithesp](https://www.iotwithesp.com/sensors/air-quality/mq2/)）
- 老化期间读数**先高后缓降**，不能用于判报警（会疯狂误报）
- 老化结束后，**每次重新上电仅需 2~5 分钟**即可正常读数

**要一直插电吗**——分两段：
1. **老化期（首次 48h）**：**连续通电不断电**，效果最好
2. **比赛期（v2.1 更正）**：**10/30 前上电老化 → 之后尽量别断电，一直插电到 11/13 路演**；万一中途断电，现场至少提前 2 小时上电（保险起见前一晚通电）。原写"11/10"与 11/02~11/04 录制、11/06 提交冲突。

→ 这就是 BOM 里「**10/20 前到货、10/30 前上电**」的来由，留出老化 + 误报实测窗口。

### 18.8 星闪节点是不是开发板？网关还要不要直插传感器？

**节点就是开发板。** 每个"星闪节点" = **一块 WS63 板**：
- 如般微 **E528H-WS63 开发板 ¥26.07**（插 Type-C 就能用，推荐）
- 或 **M528H-WS63 模组 ¥13.24**（便宜，需自制底板）

节点 = 传感器 + 一块 WS63；**5 个节点 + 1 汇聚 = 6 块 WS63**。

**网关为什么不直插传感器**（本方案定版）：网关只接三路 —— ① 声光报警 + DFPlayer 语音（输出）② 433 接收模块（**GPIO 中断**）③ WS63 汇聚节点（UART1）。好处：接线最简、网关任务最少、传感器想放哪个房间就放哪个房间。

**⚠️"GPIO/I2C 采集"这句已作废（v2.1 修订）**：原文误引 —— 那句出自**赛题三**；赛题四原文只有「**开发板实时采集各传感器数据**」。且按 §9.2，星闪节点在 XF_AT 下**读不了 ADC / I2C / UART2**：
- ~~M1 气体节点：MQ-2/5/7 走 ADC、AHT20 走 I2C~~ → **不可行**
- ~~M5 客厅存在节点：LD6002B 走 UART2~~ → **不可行**
- M4 门窗磁节点：干簧管走 GPIO → 数字电平原理上可取，**但仍需节点侧有主机给它发 AT 指令**（无人发即死锁）

→ 结论：**走 §1 的路线 A（传感器接 RK2206 主控）**，这才是与赛题原文、官方培训一致的写法。

**代价（认账，写进文档）**：星闪链接一断，网关只剩 **433 求助按钮**还能报警 —— 它是唯一不经星闪的输入。因此：
- **433 按钮绝不下移到星闪节点**
- 网关必须上报"**节点离线**"事件（3 次轮询超时 = **9 秒**）
- 文档里写"**单链路设计取舍 + 节点离线监测**"，不要写"可退化"

### 18.9 报警会不会被"限频"拖慢？（关键澄清）

**不会。** 免费额度那两道限制跟报警实时性无关：

| 限制 | 口径 | 对报警的影响 |
|---|---|---|
| **每日消息数 10,000 条** | **一天总量**上限，超了丢弃 | 只有 **1 台设备**（网关）上报：60 秒一报 = **1,440 条/天 = 14.4%**，余量 8,560 条 |
| **上下行 10 TPS** | **每秒**最多 10 条 | 报警是突发几条，远不到 10 条/秒 |

**关键设计（必须写进固件）**：
- **周期性属性上报**（温湿度、人体存在等）：**60 秒一次** —— 目的是**省每日额度**
- **报警事件上报**：**立即发，不受 60 秒约束**，走独立 `event` 通道 + QoS 1
- 二者是**两条独立逻辑**，不是一个 60 秒定时器包打天下

→ 老人跌倒 / 按求助按钮 → **网关本地 0 秒响铃** → 同时立即上报云端 → **手机 1~2 秒内收到推送**。

**关于心跳（v2.1 已核实，原【待实测】可结案）**：华为云 IoTDA **计费项**官方表格明确把 **心跳 / 登出 / 协议层 Ack / 订阅 / 取消订阅列为"免费"**，**不计入每日消息数与 TPS** → 心跳随便打，keepalive 用官方推荐 **120 秒**。

### 18.10 为什么设备不直连自建服务器

| 若设备直连自建服务器 | 后果 |
|---|---|
| 要开**公网 MQTT 端口** | 暴露面大易被扫；校园/家庭网络常封 1883/8883 |
| 自己做**设备鉴权 + TLS 证书体系** | 每台设备签证书、做吊销，工作量翻倍 |
| 自己做**离线命令缓存** | IoTDA 免费送 48h 设备影子，自己写要几百行 |
| 自己做**心跳/重连/QoS 重传** | broker 的活，不建议学生项目自己维护 |
| **赛题原文不达标** | 「**基于物联网云平台进行设备管理**」——全走自建服务器等于没用云平台 |
| **延迟并不会更低** | 设备→公网走的是同一条网，瓶颈在公网不在 IoTDA |

**"想更快"的正确做法**：自建服务器用 **AMQP 长连接订阅** IoTDA（比 HTTP 回调快，通常百毫秒级），再用 **Push Kit** 推给 App（App 前台则直接轮询拉取）→ **端到端 1~3 秒**。
**"再加局域网直连兜底"（⚠️ v2.1 降级为 P2）**：手机与网关同一 WiFi 时 App 可直连网关 HTTP（**<100 ms**），但网关同时当 AP/STA 又要跑 HTTP 服务会抢资源，手机侧还需服务发现（mDNS / 固定 IP）→ **列为 P2，不进必做**。

### 18.11 TLS 证书是干什么的

TLS = 给 MQTT 连接**加密 + 证明身份**。没有它，同 WiFi 下的人抓包就能看到老人家里的一切，甚至伪造设备往服务器灌假数据。

IoTDA 支持两种设备认证：
1. **密钥认证**（简单，先跑通用这个）：每台设备一个 `device_id` + **预共享密钥**，MQTT CONNECT 时带上，链路仍 TLS 加密
2. **X.509 证书认证**（更严）：平台签发设备证书 + 私钥，设备侧验证服务器证书真伪 → **防中间人**

**不用自己发证书的那一半**：设备连 `xxx.iotda-device.cn-north-4.myhuaweicloud.com:8883`，**服务器证书是华为云的**，设备端用 SDK 内置 CA 校验即可。要自己生成的只有"设备身份"这一半。

⚠️ **v2.1 提醒**：小凌派 `oc_mqtt` 样例走的是**明文 1883**、代码里没有 TLS 栈 → **要用 8883 得自己接 mbedTLS 并预置上面的 CA 证书**（§6.5、§12-14）。

### 18.12 物模型是什么

**物模型 = 给设备写的一份"接口说明书"**（华为叫 TSL）。把设备能力结构化成三类：

| 类别 | 含义 | 本项目例子 |
|---|---|---|
| **属性 Property** | 设备状态，可读（可写） | `temp`(double)、`presence`(bool)、`last_motion_ts`(long)、`battery`(int) |
| **事件 Event** | 设备主动上报"发生了什么" | `fall_alarm`（跌倒）、`gas_alarm`（气体超限）、`sos`（求助按钮） |
| **命令 Command** | 云端下发让设备干活 | `set_report_interval`、`silence_alarm`、`demo_trigger` |

**作用**：平台按它校验上报格式，App/服务器按它生成界面与接口，控制台可视化展示。
**没有物模型**：设备上报一串裸 JSON，平台和 App 都不知道字段含义。

### 18.13 QoS 到底选哪个（结论）

| 场景 | 选择 | 理由 |
|---|---|---|
| 周期性属性上报 | **QoS 0** | 丢一条无所谓，60 秒后还有下一条 |
| **报警事件 / 求助按钮** | **QoS 1 + 应用层 `event_id` 去重** | QoS1 保证"不丢"，重复靠 event_id 在服务器侧去重 |
| 命令下发 | QoS 1 | 命令不能丢 |

**关于 QoS 2（你说的四次握手）**：你的时间估算没错 —— QoS2 = 2 个往返（PUBLISH→PUBREC→PUBREL→PUBCOMP），广域网上通常 **0.2~1 秒**，2 秒内能完成，不算慢。

**不选它的理由是"性价比"**：
- QoS1 唯一缺点是"可能重复"，而**重复用 `event_id` 一行去重就解决**
- QoS2 在**弱网下重传代价翻倍**（超时要重走四次握手）、**设备侧内存占用翻倍**（要存消息直到 PUBCOMP）
- 报警场景"晚 0.5 秒"比"卡住不动"更糟；QoS1 重传路径更短、恢复更快

→ **结论：QoS 1 + event_id 去重**。若评委追问"为什么不用 QoS2 保证不丢"，答：*"两端都保证不丢，但 QoS2 的四次握手会在弱网下放大重传；用 QoS1 加幂等键去重，等价且更稳。"*（若坚持演示 QoS2，改一个常量即可，不影响架构。）

### 18.14 OTA 是什么

**OTA = Over-The-Air，空中升级固件**。IoTDA 可把编译好的固件上传平台，**批量推送**给指定设备，设备下载、校验、重启到新版本。

- 对本项目：**比赛不是必须做**，但答辩时是很好的"工程化"加分点 —— 说明系统**可运维**：不用拆设备插 USB，云端点一下就能升级
- 演示方式：造个 v1.1 固件（如上报间隔 60 秒→30 秒），从 IoTDA 控制台推下去，肉眼看到设备重启后行为变化
- ⚠️ RK2206 是 LiteOS-M 小型系统，**IoTDA 的 OTA 要设备侧自己实现"下载 + 写 Flash + 校验 + 跳转"**，小凌派样例里不一定有 → **列为 P2 可选加分项，时间不够就砍**

### 18.15 全链路心跳对照表（哪一段需要保活）

| 链路 | 介质 | 需要专门心跳吗 | 怎么做 |
|---|---|---|---|
| **星闪节点 ↔ 汇聚节点** | SLE 无线、单跳、私有 | **不需要专门心跳** | **周期轮询本身就是心跳**：汇聚每 **3 秒**轮询 5 个节点，**连续 3 次超时应答（9 秒）即判该节点离线** |
| **汇聚 ↔ 网关 RK2206** | UART 串口（**用 `E53_UART0`，别占 UART1 调试口**）、板间直连 | **不需要** | 物理直连不会"悄悄断"；用**帧序号 + 超时重发**保证不丢 |
| **网关 ↔ 华为云 IoTDA** | 公网 MQTT | **需要** | IoTDA 的 keepalive（官方推荐 **120 秒**）——**免费、不计入每日消息数** |
| **自建服务器 ↔ 手机 App** | 公网 HTTP（短连接） | **不需要（v3 改）** | **v3 已砍掉 WebSocket 长连接与应用层心跳**。改为：App 前台**轮询**（首页 10s / 报警页 5s）+ **进前台必拉未确认**；后台靠 **Push Kit**（见 18.16）。HTTP 短连接每次请求自带"我还活着"的语义，**无需独立心跳**。 |

**为什么星闪段不用专门心跳**：云那段是**事件驱动**（没事就不发），所以必须靠心跳区分"正常"与"掉线"；星闪段是**周期轮询**（每 **3 秒**一定有往来），**每轮问答天然就是一次心跳**，再加一层 PING 纯属浪费射频时隙（SLE 8 路共享射频，每路约 20 ms）。

**节点侧协议建议**：**轮询为主**（心跳 + 常规数据）+ **事件主动上报**（用 `AT+SLESEND`，跌倒/求助不等轮询，把延迟从 **3 秒**压到 **<100 ms**）。

### 18.16 为什么砍掉长连接、改用「轮询 + Push Kit」

**v3 结论**：**不做 WebSocket 长连接、不做应用层心跳**。理由不是"长连接没用"，而是**在本项目的演示条件下，长连接的收益换不来它的复杂度，而 Push Kit + 轮询已能覆盖全部场景**。

**长连接原本要解决的问题**：TCP 是"哑管道"，它不会告诉你对面还在不在。手机上四种情况会让连接悄悄死掉 —— WiFi↔4G 切换/进电梯、NAT 超时（5~30 分钟）、锁屏冻结后台、App 被杀。**最坏的失败模式**：老人摔倒 → 服务器推了报警 → 但那条连接早死了 → App 没收到，**而服务器以为推成功了**。安全类应用最不能接受"静默失败"。

**v3 的替代设计：把"不静默失败"的责任从连接层移到数据层**

| 原方案（长连接 + 心跳） | v3 方案 | 为什么更好 |
|---|---|---|
| WebSocket 保活 30 秒，断了要重连 | **HTTP 短连接轮询**（前台 10s / 报警页 5s） | 每次请求都是独立的全新连接，**根本不存在"僵尸连接"**；没有重连逻辑、没有心跳、没有连接状态机 |
| 服务器维护"活跃连接清单" | **服务器只维护"未确认报警"**（`alerts.status=pending`） | 状态落在**数据库**而不是**内存里的连接对象**；服务器重启、App 重启都不丢 |
| 靠推送成功与否判断送达 | **靠 App 拉到了没有判断送达**（拉到 → 用户点确认 → 停推） | "推成功"不等于"人看到"；"用户确认了"才是真送达 |
| 后台靠长连接（但后台会被冻结，本来就不行） | 后台靠 **Push Kit 系统推送**（锁屏也能弹，**这才是真正叫得醒的手段**） | 后台场景长连接本来就不可靠，早期方案也只是"兜底"，现在把它做成主手段之一 |

**四条关键设计（缺一条就会退化成"低保真"）**：

1. **App 启动 / `onForeground` 时无条件拉一次 `GET /api/alerts?status=pending`** —— 这条**比推送频率重要得多**，是"一条都不漏"的真正保证。
2. **Push **不是用来"传输内容"的，只是"叫醒"**：通知里带 alert_id，用户点了 → App 去 `GET /api/alerts/{id}` 取全量数据。所以 push 丢了也不丢数据。
3. **未确认分级重推**（立即 → 60 秒 → 5 分钟 → 停），而不是每 15 秒一条，理由见 §8.5。
4. **确认即停推**：`POST /api/alerts/{id}/disposition` 触发服务器 `UPDATE alerts SET status='confirmed'` —— 这就是**赛题必做第 4 项**。

**代价（认账）**：
- 前台数据不再"自动跳数字"，最快 5 秒刷新一次 —— 对独居老人监测**完全够用**（人活动是以分钟计的）
- 但**不需要写**：WebSocket 服务端、心跳定时器、断线重连、连接状态机、App 侧连接生命周期管理 —— **省下约 300 行和一堆难调的竞态 bug**，省下的时间投到南向硬件与文档

**一句话**：**v3 不靠"保持一根管子活着"，而靠"服务器永远记得有哪些报警没人管"。**
