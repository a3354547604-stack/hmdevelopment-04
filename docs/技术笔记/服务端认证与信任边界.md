# 服务端认证与信任边界

> 目的：说清「谁在跟服务器说话、各自怎么证明身份、哪些地方是故意的取舍」。
> 依据：`server/app/{deps,security,config}.py`、`server/app/routers/{webhook,vendor}.py`、`server/deploy/nginx.prod.conf`、`docs/技术/接口契约.md` §5/§6/§7。
> 建立于 2026-11-01（用户问「JWT 是不是只给 App 用、会不会被伪造」时整理）。

## 1 四条链路，四种认证

| 链路 | 谁发起 | 认证方式 | 代码位置 |
|---|---|---|---|
| App → 服务器 | 家庭成员手机 | **JWT**（HS256，7 天） | `security.py:41` `create_token`、`deps.py:19` `current_user` |
| 设备 → 华为云 IoTDA | 网关 RK2206 | **设备密钥 HMAC**（一机一密，clientId 四段） | 固件 `rk2206-gateway/src/gw_iotda.c` |
| 华为云 → 服务器 | IoTDA 规则引擎 | **URL `?token=` 共享密钥**（常量时间比较） | `routers/webhook.py:26` |
| 厂商 → 服务器 | 出厂工具/脚本 | **`X-Product-Key`** | `routers/vendor.py:56` |
| （例外）服务器 → 任何人 | 探针/网关 | **无认证**：`/api/health`、`/api/time` 只读 | `routers/push.py:62`、`:94` |

关键点：**JWT 只负责「人」**。设备没有 JWT，它靠 IoTDA 的设备密钥；IoTDA 到服务器靠共享 token；厂商靠 Product-Key。

## 2 JWT 细节

- 载荷：`{sub: "<user_id>", username, iat, exp}`，`sub` 按 JWT 规范写成字符串（读回 `int()` 还原）。
- 签名：HS256，密钥 `JWT_SECRET`（`config.py:69`）；有效期 `JWT_EXPIRE_DAYS=7`。
- 校验：`deps.py:19` 取 `Authorization: Bearer <token>` → `decode_token` → 过期/签名错 → `1101`；没带 → `1100`；用户行不存在 → `1101`。
- 生产校验：`APP_ENV=prod` 时拒绝用占位密钥启动（`config.py` 启动校验）。

## 3 `user_devices` 为什么不能被伪造（三道防线）

**比喻：酒店房卡。**

| 防线 | 说的是 | 代码证据 |
|---|---|---|
| ① 身份不可自报 | 租客只能报「房间号 + 验证码」，不能报「我是 3 号房的张三」——「你是谁」由前台根据房卡决定 | `routers/devices.py:88` `bind_device(payload, user: CurrentUser)`：`user` 来自 token，**请求体只有 `sn` + `bind_code`，没有 `user_id`** |
| ② 房卡不可涂改 | 卡上有防伪签名；把「你是谁」改成别人，签名立刻对不上，闸机拒 | HS256 签名；改 `sub` → `decode_token` 抛 `PyJWTError` → `1101`；密钥只在服务端进程里 |
| ③ 房间另有锁 | 就算卡是真的，还要查「这张卡是否登记过这间房」 | `deps.py:38` `device_context()`：查 `user_devices`（`deleted_at IS NULL`），非成员 `1104`；改设置/演示要求 `role='owner'` |

补充：所有数据查询都以 **token 解出的 `user_id`** 为条件（如告警只查已绑定设备），SQL 里没有「客户端传来的 user_id」这个变量，所以不存在「改一个参数换个人看」。

## 4 残余风险（已知、可接受但必须写下来）

| 编号 | 风险 | 现状与影响 | 加固建议 | 优先级 |
|---|---|---|---|---|
| R1 | **无 token 吊销/黑名单** | 签发后 7 天内一直有效；token 泄露即冒用，无法主动失效 | 加 `token_version`（用户表一列，改密/登出时 +1，校验时比对） | 中 |
| R2 | **软删不即时失效** | 解绑/停用走 `deleted_at`，token 仍能通过 `current_user`（只在用户被真删时 `1101`） | 校验时同时查 `users.deleted_at IS NULL` | 低 |
| R3 | **webhook token 在 URL 里** | nginx `access_log /dev/stdout`（`deploy/nginx.prod.conf:23`）默认格式会记录完整 URI，**token 落盘** | 自定义 `log_format` 去掉 `$args`；或改放 Header（需规则引擎支持）；定期轮换 | **高** |
| R4 | **IoTDA 不签名** | 只能证明「知道 token 的人发的」，无法证明「确实来自华为云」 | 出口 IP 白名单（IoTDA 侧地址段）+ token 轮换 | **高** |
| R5 | **webhook 无限流** | 拿到 token 可高频灌数据（写入受唯一键幂等保护，但可放大写入量） | nginx `limit_req` 或应用层令牌桶 | 中 |
| R6 | **dev 默认密钥** | compose 默认 `JWT_SECRET=dev-only-change-me`、`WEBHOOK_TOKEN=dev-webhook-token-change-me`；若公网误用即为公开口令 | `APP_ENV=prod` 已拒绝占位密钥启动；部署施工单要求生成随机值（`openssl rand -hex 24`） | 中（已有兜底） |
| R7 | `/api/health`、`/api/time` 未鉴权 | 可被探测版本/时间/DB 状态 | 信息量低，保留；若担心可用 nginx 限制来源 | 低 |
| R8 | 设备侧数据可被平台侧伪造 | 若有人同时掌握 IoTDA 控制台权限与 device_id，即可伪造读数 | 属云账号治理（子账号 + 最小权限），非本项目代码可解 | 低（演示环境） |

## 5 结论（答辩口径）

- 人能看到的每一份数据，都经过「JWT 身份 + `user_devices` 归属」两道判；
- 设备链路不共享用户凭证，设备密钥只存在网关 Flash 与 IoTDA；
- 已知的弱点是「共享密钥 + 无签名 + 无吊销」，属于**原型阶段的取舍**，加固路径已在 §4 列明（R3/R4 优先）。
