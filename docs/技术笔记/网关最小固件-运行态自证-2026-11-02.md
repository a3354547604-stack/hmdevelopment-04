# 网关最小固件：运行态自证与「等 PUBACK 不卡死」（t193，2026-11-02）

> 对象：`rk2206-gateway/min/`（t192 从零写的最小网关固件）
> 现象：2026-11-01 23:26:38 之后服务器一条 webhook 都没有，但 `ping 192.168.137.6` 通、
> `/api/time` 只在 23:08 那次启动时被命中 3 次（说明没有重启）。
> 结论：**「不再上报」至少要分三种原因**，光看「没上报」分不出来；本次只加观测 + 堵住
> 「等 PUBACK 可能永久阻塞」这一个具体死路，**不动协议 / QoS / 联网 / 取时 / 接入**四段。

## 1. 判读表（现场第一件事）

| 日志现象 | 结论 | 下一步 |
|---|---|---|
| `[min] alive` / `uart rx` / `pub` **三条全不动** | 主任务死了（异常 / 栈溢出 / 被 SDK 卡住） | 看 `[min] !! fatal`；没有则看 `stk 峰值` |
| `alive` 在涨、`uart rx=` 不涨 | 串口侧没数据（汇聚没发 / 线松 / 波特率不对） | 查汇聚 COM17 与 RX 线 |
| `uart rx` 在涨、`frames=` 不涨 | 帧头 / CRC 对不上（噪声或错帧） | 抓一次 `uart rx` 的增量 |
| `frames` 在涨、`pub` 不涨或 `err` 在涨 | 报文拼装或 MQTT 发布这条路 | 看 `⚠` 那几行（超长 / PUBACK 超时 / rc） |

## 2. 日志格式（每行都以字面 `[min]` 开头，便于 `strings | grep`）

```
[min] alive n=<圈数> up=<开机秒> uart=<累计收到字节> pub=<发布成功次数> err=<失败次数>   ← 5 s 一行
[min] stk 已用 <B> / 峰值 <B> / 栈 <B>                                              ← 跟心跳同频
[min] uart rx=<B> frames=<解析出的完整帧数>                                          ← 8 s 一行
[min] pub seq=<帧序号> len=<payload> rc=<上一次 publish 的返回码>                      ← 每次发布前
[min] 已上报 node seq=<帧序号> len=<报文长度>（PUBACK）rc=0                             ← 成功
[min] ⚠ 上报失败 rc=<码>（seq=… len=…）                                              ← 失败
[min] ⚠ PUBACK 超时（5s 预算内没等到）→ 重连 seq=… len=…                               ← 平台不回 PUBACK
[min] ⚠ MQTT 断开重连 n=<第几次> rc=<上次返回码>
[min] !! fatal <原因>（stage=… n=… uart=… pub=… err=…）                              ← 崩溃 / 卡死
```

`min_mqtt_publish` 返回码：`0` 成功（拿到 PUBACK）、`-1` socket 错、`-2` **等 PUBACK 超预算**。
`-2` 不是致命错：打一行超时日志 → 关 socket → 走原有退避（30/60/120/300 s）重连，
**主循环继续转、心跳照打**，绝不 `break` 出主循环、也不原地重发。

## 3. 「等 PUBACK」为什么可能卡死，以及怎么堵

- 旧实现：`mqtt_recv()` 直接 `recv(fd, …)`；最多看 4 个包，每个都可能一直等。
  一旦平台不回 PUBACK，主循环就停在 `recv` 里：不读 UART、不打日志、也不再发。
  Wi-Fi / lwIP 后台仍在跑，所以 `ping` 还通、也不触发复位——四个现象同时成立。
- 事实核对（避免照错结论改代码）：MQTT 的 fd 来自 `min_net_tcp_open()`，那里**本来就有**
  `SO_RCVTIMEO = 5 s`（`rk2206-gateway/min/min_net.c:144-147`），且本 SDK 的
  `device/rockchip/rk2206/third_party/lwip/lwipopts.h:123` 是 `LWIP_SO_RCVTIMEO 1`。
  所以「socket 从没设过超时」不成立；真正的风险是**依赖 socket 超时语义**——万一 lwIP 那层
  不生效或被改配置，就是死等。
- 现在的两层闸：
  1. **select 预算闸（主）**：`mqtt_wait_readable()` 用 `select` 切片等 1 s，
     总预算 `MIN_MQTT_PUB_BUDGET_MS = 5000 ms`，到点无条件返回 `-2`。
     ⇒ 即使平台一条 PUBACK 都不回，主循环最多停 5 s。
  2. **socket 兜底（辅）**：`min_mqtt_connect()` 建立前把该 fd 的 `SO_RCVTIMEO` 固定成
     `MIN_MQTT_RECV_TIMEOUT_S = 3 s`（取时那条 HTTP socket 仍是 5 s，互不影响）；
     设不上会打印出来，不静默。
- 顺带把「丢这一帧」和「链路坏了」分开：报文超长 / 转义溢出返回 `1`，只丢该帧、不重连；
  只有 socket 错或 PUBACK 超时才返回 `-1` 触发重连。

## 4. 「PUBACK 不返回」怎么验证

**A. 主机侧（不需要板子，每次 `--check` 都跑）**

`test_puback_timeout()`（`rk2206-gateway/min/test/test_min.c`）用 `socketpair` 造
「对端一个字节都不发」的场景，断言三件事：`min_mqtt_publish` 返回 `-2`、
耗时在 5 s 预算内、`packet id` 不前进（超时不算成功）。

```bash
bash tools/gw-build-min.sh --check      # 通过 58 / 失败 0
```

变异验证（证明这几条断言真的会咬）：
- 把 `MIN_MQTT_PUB_BUDGET_MS` 改 300 → `57/1`（红在「总预算应约 300 ms，实际 301 ms」）；
- 把超时分支改成 `m->next_id++; return 0;` → `56/2`（红在 rc 与 packet id 两条）。

**B. 板上人为制造（哪天现场要复现）**

- 最简单：在 PC 上**关掉热点共享的「网络」**（热点本身留着）→ 板子 Wi-Fi 还连着，
  broker 的应答回不来；
- 或者在本机防火墙加一条**出站 TCP 1883 阻断**规则；
- 期望：`[min] ⚠ PUBACK 超时（5s 预算内没等到）→ 重连` 之后仍有 `[min] alive …` 每 5 s
  一行、`uart rx` 继续涨（说明 UART 采集没停），而不是整机静默。

## 5. 故障钩子与守卫任务（「崩溃前至少留一行」）

- `HardFault_Handler` / `BusFault_Handler`：elf 里原本是**弱符号**（`nm liteos.elf` 显示 `W`，
  默认实现是 `b .` 死循环），这里给强定义 → 异常时先打一行 `[min] !! fatal` 再停。
  异常上下文里 printf 依赖的 UART 驱动可能已不可用，所以这是「尽力而为」。
- `minGuard` 任务（栈 2048 B / 最低优先级）：主任务 `g_loops` 20 s 不涨就喊
  `[min] !! fatal 主任务 20 s 没有前进（stage/seq/n/uart/frames/pub/err）` + 栈用量。
  专治「卡在 SDK 死循环里、既不复位也不打日志」——t190 的 `resident set timeout` 就是那样。
- 栈：主任务 8192 → **12288 B**，同时把最大的两块缓冲从栈上挪到静态区
  （`min_msg_node_samples()` 的 `inner[]` 2 KB、`s_ctx.body` 2.3 KB）。
  真实峰值看 `[min] stk 峰值`；内核判栈写穿时 `bOvf=1` 会另外喊一条 `!! fatal`。

## 6. 顺带修掉的两个小坑

- `min_parser_pull()`：不喂新字节、只从缓冲里再解一帧 —— 一次 `LzUartRead` 带回多帧时不再吞帧。
- 读 0 字节不忙等：主循环每圈 `LOS_Msleep(MIN_IDLE_MS=20 ms)`，且 `report()` 在任何分支之后，
  退避窗口内也照样打心跳。
