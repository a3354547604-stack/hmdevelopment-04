# 润和 WS63 开发板：烧录成功但无法启动 —— 排查记录（2026-11-01）

> 用途：交接给另一个会话/另一位工程师继续定位。本文只记事实、证据与可复现命令，不含推测性结论以外的内容。

## 1. 目标

把门磁节点固件 `NODE_M4MOD.fwpkg`（单路干簧管 + 模块模式）烧进润和板，使其作为「门厅门磁节点」上线（`sn=M4`）。

| 项 | 值 |

| 供电/下载口 | **Type-C 单口**；板载 CH340K，**COM20**（VID_1A86 & PID_7522） |

## 3. 正确的 ws63 命令（关键，之前一直用错）

```bat
:: 擦除整片（-l 传 fwpkg，不是 loader.bin）
BurnToolCmd.exe --erase -n ws63 -m serial COM20 --baudRate 115200 -l C:\path\xxx.fwpkg

:: 烧写
BurnToolCmd.exe --burn  -n ws63 -m serial COM20 --baudRate 115200 -f C:\path\xxx.fwpkg

:: 回读（-a 地址 -r 长度）
BurnToolCmd.exe --read  -n ws63 -m serial COM20 --baudRate 115200 -a 0x0 -r 0x400 -l C:\path\xxx.fwpkg -f read.bin
```

**错误写法**（曾用，导致误导性报错）：把 `COM20 115200 0 0` 当位置参数 → 工具退回默认 `loader.bin` → 报
`flag(121634927) is not equal to 0xefbeaddf! File: BurnToolCmd\loader\loader.bin format error!`

## 4. 现象时间线

1. 用错误语法擦除 → 失败（上面那条报错）；把 SDK `loaderboot.bin` 换进 `loader/loader.bin` 也报同样错（格式要求另一套 magic）。
2. 换成 **正确语法** `-l <fwpkg>` 擦除 → `Erase all flash successfully.`
3. 正确语法烧写 → 7 个分区全部 `downloaded ... successfully` → `Burned successfully.`
4. **复位后串口只回 4 个字符**：`boot.`，之后永久静默（多次 RST、多次拔插 USB 均同）。
5. 换烧 **原厂/已知可用镜像** `ws63-tools\fw\ws63-liteos-app_all.fwpkg`（md5 `ee6064d2a96a92c2d2cbf6549e7fd4fe`）→ 同样 `Burned successfully` → 同样只回 `boot.`。

## 5. 决定性证据：回读 flash

`--read -a 0x0 -r 0x400` 读回（hexdump）：

```
00000000  FF FF FF FF FF FF FF FF  ...（0x00–0x7F 全为 FF，擦除态）
00000080  1E A5 87 4B 00 00 01 00 00 01 00 00 40 00 00 00  ...
```

解读：
- **镜像确实写进去了**（0x80 处有结构化的镜像头，magic `0x4B87A51E` 小端）。
- **但 0x0 处是空的（全 FF）**。
- ROM 上电从 0x0 取引导镜像 → 取不到 → 停在 ROM 下载模式（所以只打 `boot.` 后等待，且此时 BurnToolCmd 无需复位即可握手）。

## 6. 已排除

| 怀疑项 | 排除依据 |
|---|---|
| 固件代码问题 | 同一 fwpkg 在另一块板（如般微 E528W 系）可跑；且原厂 stock 镜像同样不启动 |
| 波特率/串口 | 115200 双向正常（`boot.` 能收到；`AT` 时代能回 `OK`） |
| 烧录流程/分区顺序 | 7 分区顺序与地址三次完全一致，全部 successfully |
| 镜像文件损坏 | 回读可见镜像头；md5 与源文件一致 |
| 擦除不干净 | 已 `Erase all flash successfully` 后重烧，0x0 仍为 FF |

## 7. 待验证假设（按优先级）

- **H1（最可能）**：这块板的 ROM 要求引导镜像从 **0x0** 起；而 BurnToolCmd 按 fwpkg 内分区表写到了 **0x80**（可能少了 128 B preloader/padding，或 fwpkg 分区表与这块板 flash 布局差 0x80）。
- **H2**：ws63 烧写需要额外的 **programmer** 参数（`-p`），当前未传，工具用了默认流程。
- **H3**：需要工具自带 GUI 版（`hispark\tools\cfbb\BurnTool\BurnTool.exe`）完成一次「带校验的完整擦写」，命令行版缺少某一步。
- **H4**：这块板的 flash 容量/型号与 fwpkg 假设不同（如 2 MB vs 4 MB），导致尾部越界回绕覆盖头部。

## 8. 建议的下一步实验

1. **对照实验（最有信息量）**：对一块**能正常启动**的同系列板（如 COM17 汇聚板）执行同样的 `--read -a 0x0 -r 0x400`，看它的引导头在 0x0 还是 0x80。
   - 若在 0x0 → 证实 H1，需要修 fwpkg 分区表偏移或换烧写方式。
   - 若也在 0x80 → H1 不成立，转 H2/H3。
2. 查 `hispark\tools\BurnToolCmd\config\` 下 ws63 的配置文件（`burn.config` / `config_chip_type_ws63.ini`），确认分区偏移与 flash 大小假定。
3. 用 **GUI 版 cfbb BurnTool** 的「Erase all + Send file」走一遍（它的 ws63 流程可能与命令行不同）。
4. 装 **HiSpark Studio**（`https://hispark-obs.obs.cn-east-3.myhuaweicloud.com/HiSparkStudio.exe` 曾 403；可试 developers.hisilicon.com 注册下载），用「工程配置 → 程序加载」。
5. 若仍不行：考虑 **JTAG**（toolchain 内有 `hw_openocd` 与 `WS63-jtag.cfg`）直接写 flash。
