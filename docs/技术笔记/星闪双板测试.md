## 二、两套固件长什么样

同一份源码用编译宏分角色（`-def=SPIKE_ROLE=2` 出从端）：

| 文件 | 作用 |
|---|---|
| `ws63-firmware/spike/spike_common.h` | 两块板共用的契约常量（UUID 0x060B/0x1122、双方 MAC、广播名、负载格式）+ 纯函数（温度模拟、`seq` 解析、MAC 比较、广播里找标记） |
| `ws63-firmware/spike/spike_server.c` | 主节点：注册 SSAP server → 建服务/属性 → 广播 → **常驻线程每秒 notify 一帧** `SPIKE seq=N t=25.0C` |
| `ws63-firmware/spike/spike_server_adv.c` | 主节点广播/扫描响应数据（名字 `SPIKE_SRV_NODE_1`） |
| `ws63-firmware/spike/spike_client.c` | 从节点：扫描 → 锁定主节点 → 连接 → 配对 → 交换 MTU → 服务发现 → 属性发现 → 写 CCCD 订阅 → 打印每一帧并统计丢包 |

两块板上的身份（不需要区分物理板子，烧对了就行）：

- 主节点 `11:22:33:44:55:66`，广播名 `SPIKE_SRV_NODE_1`
- 从节点 `13:67:5c:07:00:51`
- 服务 `0x060B` / 属性 `0x1122` —— **和现有生产代码 `ws63-firmware/src/sle_hub.h` 一致**，
  所以这次实测的结论可以直接搬到 t3，不用重新验证 UUID 层面的连通性。

从节点认主节点的方式是「MAC 匹配 **或** 广播/扫描响应原始字节里含 ASCII
`SPIKE_SRV_NODE_1`」——两条路任一条命中就算找到。万一主节点本地地址没设上，
整个测试不会因此全废。

## 三、踩到的三个坑（都会复发，写下来省下一次）

### 坑 1：从节点的服务发现回调定义了却没注册 → 编译直接失败

```text
/sdk/src/application/samples/custom/spike_client.c:462:13: error:
    'spike_cli_find_structure_cmp_cbk' defined but not used [-Werror=unused-function]
```

SDK 的 `ssapc_register_callbacks` 结构体里字段叫 **`find_structure_cmp_cb`**
（`src/include/middleware/services/bts/sle/sle_ssap_client.h:446-466`）。少注册一个
回调，SDK 不会报“缺回调”，而是让函数变成“定义未使用”被 `-Werror` 拦下。
**教训：`-Werror=unused-function` 在 SDK 里就是“回调漏注册”的报警器。**

这个坑还顺带说明了一件事：**`-fsyntax-only` 查不出它**（它属中端优化阶段的警告），
所以主机侧自检必须真的产出 `.o`。

### 坑 2：`grep "[SPIKE-SRV]"` 数镜像里的字符串，结论是假的

方括号在基本正则里是字符集：`grep -c "[SPIKE-SRV]"` 实际在数「出现了 S/P/I/K/E/R/V
里任意一个字母的行数」，主包数出 5414 这种荒唐值；换成 `[SPIKE-CLI]` 更会因
`E-C` 是逆序区间直接报 `grep: Invalid range end`。**数镜像字符串一律 `grep -aF`，
或直接数原始字节**（本次核对用 python `bytes.count()` 复核，38/44/1/0 对得上）。

### 坑 3：Docker 编出来的 fwpkg 属主是 root，宿主机删不掉

在容器里以 root 跑 `build.py`，产物 `…/src/output/ws63/fwpkg/ws63-liteos-app/ws63-liteos-app_all.fwpkg`
属主是 root。宿主机 `rm` 报 `Permission denied`；更阴的是某些路径下**删除失败不影响
构建成功**，于是出现「编译成功但产物还是上一轮的旧包」。构建脚本现在的做法是：
在容器内删旧包 + 构建前后比 sha256，不一致才算真的产出了新包。

> 顺带：`build.py` 对同一 workspace 是共享 `output/` 的，**本次冒烟构建会覆盖 SDK
> 输出目录里的生产包**。生产包请用仓库里的 `ws63-firmware/output/ws63-liteos-app_all.fwpkg`，
> 别拿 SDK 目录里那个去烧节点。

### 5.3 根因（两处，都在本次 inScope 内）

**根因 1 —— 主端一帧未发：把 `conn_id == 0` 当成「没连上」**

`ws63-firmware/spike/spike_server.c:111`

```c
if (g_conn_hdl == 0 || g_property_handle == 0) { continue; }   /* ← 恒真 */
```

本 SDK 给第一条连接分配的 `conn_id` 就是 `0x0`（两端日志都打了 `conn state changed: conn_id=0x0 state=0x1`），
所以这个守卫每次都 `continue`：90 s 里 17 行 `alive … tx=0 err=0`，`tx seq` 0 次。
`err=0` 说明连 `ssaps_notify_indicate()` 都没调用过——**不是发失败，是根本没发**。

**修法**：把「连没连上」和「句柄等于几」分开——用连接状态回调置位一个 `bool g_connected`
（断开回调清掉），守卫改成 `if (!g_connected) continue;`；发送时用回调里存下的 `g_conn_hdl`（允许为 0）。

**根因 2 —— 从端 ≈12 Hz 死循环、永远走不到订阅成功**

`ws63-firmware/spike/spike_client.c:450-464`：`spike_cli_find_structure_cmp_cbk` 没有按
`structure_result->type` 分支。服务发现分两轮（先 service 再 property），两轮都回调同一个函数；
属性轮（`type=3`）的回调里又发起一次 `ssapc_find_structure(…, SSAP_FIND_TYPE_PROPERTY)`，于是自我重入：
90 s 里 1096 次 `structure discovery DONE type=3`、1094 次 `TARGET property 0x1122 at handle 0x11`。
附带现象：往 handle `0x12` 写 CCCD 返回 `status=0x4`（`write cfm: client=0 handle=0x0 status=0x4`）。

**修法**：`type == SSAP_FIND_TYPE_SERVICE` 时才进入「找属性」那一轮；拿到属性的那一轮**停止再发起发现**并
写 CCCD。即使订阅失败也不该卡死——主端连上就发，CCCD 只是可选路径（施工单第五节已列为「允许」）。

> 两处都是 t8 时期照官方样例改出来的。官方 `sle_speed_client` 没暴露这个死循环——它只在
> 「未配对」那条路径上走一次发现，走不到第二次；但代价是已配对的板子重连后什么都不做
> （见第六节第 1 条）。写 t3 生产代码时这两条都要覆盖。

## 六、对 t3（1 主 3 从汇聚）的影响 —— 现在就确定的部分

上板实测印证了下面两条，并且暴露出第三条（**同样会要 t3 的命**）：
**官方 `sle_speed_client` 样例的流程不能照抄进 t3。**

1. **官方从端样例第二次连接会卡死。** 它只在 `pair_state == SLE_PAIR_NONE` 时才发起
   配对，配对完成的回调里才去 `exchange_info`。已经配对过的板子重连时，那两个分支
   都不进，结果就是「连接成功，然后什么都不做」。生产端必须把
   「连接 → 交换信息 → 服务发现 → 订阅」做成每次连接都走一遍的流程。
2. **官方主端样例靠对端发 READ 请求来触发发包**（在 `read_request_cbk` 里销毁/重建
   发包线程）。这意味着从端如果不先读一次，主端一帧都不会发。本次主节点改成
   **常驻线程每秒看一次连接句柄、连上就发**，去掉了「必须先有人来读」这个前置条件，
   同时避开运行中反复 destroy/create 线程的竞态。

3. **「连接句柄 == 0」不能当「没连上」用。**（实测踩中，见 5.3）本 SDK 第一条连接的
   `conn_id` 就是 `0x0`。t8 主端用 `if (g_conn_hdl == 0) continue;` 做前置守卫，结果连上以后
   一帧都不发，而且日志看起来一切正常（`conn state changed`、`PEER CONNECTED` 都在打）。
   t3 的汇聚必须用连接状态回调维护的布尔量判断「连没连上」，句柄只当参数，**允许它是 0**。
4. **服务发现的完成回调必须按 `type` 分支**，否则「找服务」和「找属性」两轮会互相触发，
   从端以 ≈12 Hz 空转、永远订阅不上（见 5.3 根因 2）。t3 从端要一次连接只走一轮发现。

这四条是这次冒烟包在“写生产代码之前”就已经拿到的收益。

## 七、遗留风险

- **t8 的两处代码缺陷未修**（`spike_server.c:111`、`spike_client.c:450-464`）：本任务只负责验证、不改实现，
  两个固件也不会留在板子上。要拿到「notify 每秒到达、`lost=0`」这条结论，必须修完再重跑第五节。
- **间隔/吞吐没有测到**：一帧未收，`STAT(… interval=..)` 一次都没打出来。修好后要顺带记录
  1 s 周期的实际抖动与长跑（≥10 min）表现。
- **1 主 3 从没测**：见下。
- 1 主 3 从与 1 主 1 从的差别（三个从端争用同一主端、连接数上限、并发 notify 的
  带宽与调度）**不在本次范围**，需要单独验证。
- 从节点写 CCCD 定为「尽力而为」：写失败不算测试失败，因为主端连上就发、不看订阅状态。
  **实测正好落在施工单第五节说的另一半**：`CCCD write failed` 与 `rx` 0 帧同时出现，
  所以这条订阅路径必须跟着根因 2 一起修、一起重测，不能按「尽力而为」放过。
- **出厂 MAC 认不出是哪块板**：两块板的开机自检行**逐字节相同** ——
  `APP|sle_mac:0x 0,0x 1,0x 9,0x40,0x**,0x**` 与 `APP|mac_addr:0x34,0x1f,0xc4,0x 7,0x**,0x**`
  （后两字节是固件自己打的 `0x**`，看不到；可见的前 4 字节两板一致）。
  所以 t3 组网不能拿「出厂 MAC」当板子身份或唯一键——按契约 §2.7 用 SN 派生地址与白名单。
- COM14 那块板是**原厂固件**、COM15 那块是**自研固件+雷达**；本次为了烧冒烟包，
  两块板都被覆盖过一次，收工时已分别恢复成「仓库生产固件」和「厂家 XF_AT 救砖包」（见 5.4）。
