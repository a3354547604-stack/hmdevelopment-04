# 怎么看串口输出（WS63 + LD6002C 现场判读手册）

> 2026-10-16 写。给**人**看的：怎么打开串口、每一行日志是什么意思、跌倒验证怎么做、什么算通过。
> 所有解释都来自实测日志，不是猜的。原始证据见 [10-LD6002C实物接线判通-2026-10-16.txt](../../ws63-firmware/doc/10-LD6002C实物接线判通-2026-10-16.txt)。

## 一、三个办法，挑一个

| 办法 | 命令 / 操作 | 适合 |
|---|---|---|
| **A. watch.ps1（推荐）** | 见下 | **已解码、带颜色、结束给结论** —— 你要的就是这个 |
| B. MobaXterm | Session → Serial，`COM14` / `115200` / 8-N-1 / Flow control = `None` | 想用现成图形界面（便携版中文 v24.3 已在你机器上） |
| C. ser.ps1 | `ser.ps1 -Action listen -Seconds 20` | 原始输出，我（AI）用的就是这个 |

### 办法 A：一条命令

在 Windows 上开 PowerShell（不是 WSL），跑：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\Administrator\ws63-tools\watch.ps1" -Seconds 40 -HideAdc
```

（仓库里的副本在 [ws63-firmware/scripts/watch.ps1](../../ws63-firmware/scripts/watch.ps1)，两份一样。）

参数：

| 参数 | 作用 |
|---|---|
| `-Seconds 40` | 抓 40 秒后自动停并给结论；**不加就是一直抓到按 Ctrl-C** |
| `-HideAdc` | 隐藏每轮 4 行 ADC 噪声（推荐，不然刷屏） |
| `-Port COM14` | 换串口（默认 COM14） |
| `-Raw` | 不解码、不染色，原样吐出 |

结束时它会自己算并打印结论，长这样（这是刚才实测的真实输出）：

```
================ VERDICT ================
rx_total delta in this window = 5490 bytes
window ~24 s  ->  229 B/s,  ~23 frames/s
UART2 RX ....... OK, radar is streaming (wiring + baud fine)
checksum errors  0  -> clean signal, ground OK
FALL .......... none in this window (fall_evt=0)
   reminder: ceiling mount 2.2-3.0 m, lie down 15-20 s (default sensitivity 10)
TX2 pin IO06 .. 0 edges (normal while nobody falls)
```

⚠️ **至少抓 30 秒**。因为 `[RADAR] alive` 那行**每 10 秒才打一次**，抓 12 秒只会看到 1 行，
脚本会告诉你「INCONCLUSIVE」—— 那不是雷达坏了，是窗口太短。

## 二、开口之前必须知道的三个坑

这三个都是这项目真踩过的，不知道会白折腾半小时。

### 坑 1（最容易误判）：RTS = 复位，且**断电前一直生效**

复位电路是 `CH330N 的 RTS# → Q1 → 模组 EN（低有效）`（[doc/1](../../ws63-firmware/doc/1-通宵进展与烧录方法.md) §三F）。
**哪 个程序在打开串口时把 RTS 拉高，板子就被按在复位里 —— 一个字节都不会输出**，你会以为固件烧坏了。

更坑的是：**RTS 状态跨 `Close()` 保持**。程序关了，RTS 还是高的，板子继续装死。

→ **自救：跑一次 `watch.ps1`**。它在 `Open()` 之前强制 `RtsEnable = $false`，
   一打开就把复位释放掉，板子立刻活。**"板子没反应"第一个动作就是跑它。**
→ MobaXterm 里如果一片空白：也是这个原因（Flow control 别选硬件流控；必要时改用 watch.ps1）。

### 坑 2：串口是独占的，同一时刻只能一个程序占用

`MobaXterm 开着` → `watch.ps1` 报 `OPEN-FAIL: 拒绝访问`，反之亦然。
**抓串口前先把 MobaXterm / BurnTool / 烧录脚本全关掉。**

### 坑 3：`.ps1` 脚本必须**纯 ASCII**（你去改脚本时必看）

PowerShell 5.1 按 ANSI 读 `.ps1`，**脚本里出现一个中文字符，整份脚本解析失败**（报一堆莫名其妙的语法错）。
所以 `watch.ps1` 里全是英文注释。你要改它，就继续用英文；中文写在 `.md` 文档里（UTF-8，没问题）。

## 三、日志逐行字典

### 启动那一段（按板上 RST 键后出现）

```
############################################
#  WS63 SELF-BUILT FIRMWARE  (sensor_hub)  #
############################################
[BOOT] firmware is alive. build=Oct 16 2026 13:55:16   ← 看这行确认烧的是哪版固件
[RADAR] uart2 init ret=0 (pin IO07=RX/IO08=TX mode=2, 115200 8N1)   ← ret=0 才正常
[RADAR] rx callback register ret=0                    ← ret=0 才正常
[RADAR] TX2 pin IO06 init dir_ret=0 isr_ret=0 pull=down level=0
```

⚠️ 注意：**没按 RST 就不会有这一段**，但 `---- round N ----` 会继续涨 —— 那是板子一直在跑，正常。
反过来说：**判断"板子有没有重启"要看 `round 1` 或 banner，不要看有没有新日志。**

### 循环段（每轮都刷，属于噪声，可以 `-HideAdc` 屏蔽）

```
---- round 2727 ----
  ADC ch2 =    1 mV          ← ch2~ch5 = GPIO_09~12，MQ 气体传感器的模拟量
```
现在这 4 路都接的是空脚，所以恒为 0~40 mV 的漂移，**属正常，不用管**。
真接了 MQ-2/5/7 后，读数会明显抬高（几百 mV 以上）。

### 雷达段（**你真正要看的东西**）

```
[RADAR] TX type=0x0E06 len=0 cksum=0xF6
```
固件开机主动"问雷达参数"（`0x0E06` = 读参数）。**只发 1 次。**

```
[RADAR] RAW(470): 01 35 A2 00 01 0F 09 6E 01 FE ...
```
原始收到的字节（前 24 帧打全，之后只在特殊情况下打）。**调试用，平时不用看。**

```
[RADAR] FRAME#2 id=0x35A3 type=0x0E02 len=1 data=00  <= FALL_STATUS is_fall=0 (normal)
```
解出来的一帧。**只有①跌倒状态发生变化、②非 0E02 的帧（比如参数回包）才会打** —— 
所以平时看不到 FRAME 行是正常的，别慌，看下面的 alive 行。

```
[RADAR] types 0E02=107298 0E01=0 0E04=0 0E06=1 0E08=0 0E0A=0 0E0C=0 0E0E=0 other=17883
```
累计收到各类型帧的数量。
- `0E02` = 跌倒状态上报，模块**一直**以 ~24 帧/s 刷（所以这个数巨大是正常的）
- `0E06` = 读参数回包（开机那 1 次）
- `other` = `0F09`，官方协议文档里**没有**、但模块周期性在发，值恒为 `01`，只计数
  （固件里已注明，不影响任何判断）

```
[RADAR] alive rx_total=1251857 drop=0 ok=125182 bad=0 tx=1 fall_evt=0 state=0 tx2=0 tx2_edges=0
```
### 🔴 这是全场最重要的一行，逐字段：

| 字段 | 含义 | 正常值 |
|---|---|---|
| `rx_total` | UART2 收到的**原始字节总数**（只增不减） | **必须一直涨**。不涨 = 模块没在发（接反/没电/BOOT1 没拉低） |
| `drop` | 驱动层丢掉的字节 | `0` |
| `ok` | 成功解出的帧数 | 与 rx_total 同步涨 |
| `bad` | **校验错**的帧数 | `0`。非 0 = 波特率不对或地线脏 |
| `tx` | 固件主动发出的帧数 | 开机后 `1`（就是那条 0x0E06） |
| `fall_evt` | **跌倒状态翻转次数**（0→1、1→0 都算） | 平时 `0`；**做完跌倒演示应 ≥ 1** |
| `state` | **当前跌倒状态** | `0` = 正常，`1` = **正在跌倒** |
| `tx2` | IO06（模块第 4 脚 TX2）当前电平 | 平时 `0` |
| `tx2_edges` | IO06 电平跳变次数 | 平时 `0`；跌倒时应该涨 |

**一句话判读法：**
- `rx_total` 在涨 + `bad=0` → **接线和串口完全没问题**（本次实测就是这样）
- `fall_evt` 从 0 变 1 → **跌倒检测通了！**
- `rx_total` 一直 0 → 去查接线（见下）

### 别的模块

```
[SLE-HUB] alive. conn_hdl=0x0 server_id=0x1     ← 星闪服务端活着；conn_hdl=0x0 = 暂无对端（只有一块板，正常）
[WIFI] ========== found 3 AP ==========          ← WiFi 扫描结果
APP|[SYS INFO] mem: used:137236, free:219072; log: drop/all[0/0]  ← 内存/日志统计
```

## 四、跌倒验证 SOP（**先看这条，否则一定失败**）

### ⚠️ 前提：**模块放在桌面上，永远不可能报跌倒**

规格书 §6.4 / §3 原文：

> 顶装挂高 2.2-3.0m，最大感应范围 3*3m …（跌倒判定）**根据点云距离地面高度**进行跌倒判定
> 【Fall Sensitivity】范围 3-30，默认 **10**，…**持续跌倒 15~20s 上报跌倒状态**

而模块内部存的安装高度参数实测是 **`high=2.400` m**（`0x0E06` 读出来的）。
**桌面高度约 0.3 m，判定基准差了 2 米多 → 算法不可能判出跌倒。** 详情见
[接线与验证步骤.md §五](../雷达LD6002C/接线与验证步骤.md)。

### 正确步骤

1. 把模块**吸顶装到 2.2~3.0 m**（装 2.4 m 左右最省事，不用改参数）。
2. 确认共地、供电稳（模块峰值 600 mA，规格书要求 >1 A、纹波 ≤50 mV）。
3. 按板上 RST，确认看到 `[RADAR] uart2 init ret=0` + `rx callback register ret=0`。
4. 开抓：`watch.ps1 -Seconds 90 -HideAdc`
5. **人在雷达下方，真的躺在地上，保持 15~20 秒不要动。** ← 站着倒一下、蹲一下就起来，**不会触发**。
6. 看两个地方：
   - 屏幕上一行**红底**的 `FRAME#… type=0x0E02 … is_fall=1 (FALL!)`
   - 结束时的 `VERDICT` 里 `FALL .......... DETECTED`

### 通过标准（三条同时满足）

| # | 判据 |
|---|---|
| 1 | `[RADAR] uart2 init ret=0` + `rx callback register ret=0` |
| 2 | `rx_total` 持续增长，`bad=0` |
| 3 | 躺着 15~20 s 后 `fall_evt` 或 `state` 发生变化（出现 `is_fall=1`） |

### 如果装不到吊顶，还有一个合法的偷懒办法

`radar_hub.c` 里有测试开关 `RADAR_THR_TEST_ENABLE`（[radar_hub.c:62](../../ws63-firmware/src/radar_hub.c#L62)，默认 `0`）：
打开后固件会发 `0x0E08` 把跌倒阈值从 `0.6 m` 压到 `0.1 m`，跑 75 秒自动写回 `0.6 m`。
阈值一压，**普通起坐动作就能触发 `is_fall=1`**，用来验证"UART 跌倒通路 + TX2 硬件通路"是否真的通。
代价：要重新编译 + 烧录（约 12 秒编译 + 2.5 分钟烧录），且**用完记得改回 `0`**。
（10-16 已用它验证过下发与自动恢复，见 [doc/9](../../ws63-firmware/doc/9-跌倒阈值下发与恢复-2026-10-16.txt)。）

## 五、现场排错表

| 现象 | 最可能的原因 | 怎么办 |
|---|---|---|
| **完全没有输出**（连 round 都不涨） | RTS 被别的程序拉高，板子被按在复位 | 关掉 MobaXterm/BurnTool，**跑一次 `watch.ps1`**（它会释放 RTS）|
| 脚本报 `OPEN-FAIL: 拒绝访问` | 端口被占用（串口独占） | 关掉 MobaXterm / BurnTool，再跑 |
| `rx_total=0` 一直不涨 | ① TX/RX 接反 ② BOOT1 没拉低 ③ 模块没供电 | 先**对调 IO07/IO08 两根线**；再确认第 3 脚接 GND；最后量 3.3V |
| `rx_total` 涨但 `bad` 一直涨 | 波特率/电平不对 | 看 `RAW(...)` 字节规律；模块波特率应回 115200 |
| `rx_total` 涨、`ok=0 bad=0` | 帧头 `01` 一直没等到（字节流被截断） | 查地线；多等几秒 |
| 板子反复重启 | 3.3V 被雷达拉塌（峰值 600 mA） | 换**独立 3.3V/1A 电源**，共地 |
| 躺着不动也**不报**跌倒 | ① 没吸顶装（最常见）② 躺的时间不够 15~20 s | 先解决安装高度，再躺够时间 |
| `tx2_edges=0` 但 `fall_evt` 涨了 | TX2（第 4 脚）那根线**没接** | 接上模块第 4 脚 → 板上丝印 `IO06`（可选，不影响 UART 主通道）|

## 六、看串口到底能看出什么（写答辩素材用）

- **`rx_total` / `bad` 是"接线正确性"的客观证据**：113,927 帧、`bad=0`，等于把 UART 五根线逐根判通。
- **`fall_evt` 是"功能正确性"的客观证据**：它跳变一次，才算跌倒检测真的通过。
- 这两个数都是**设备自己报的计数器**，不是我们打印的"测试通过" —— 这是它的说服力所在。
