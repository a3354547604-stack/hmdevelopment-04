# 服务器部署施工单（t41 · 面向不熟 Linux/Docker 的人）

目标：从零到 `curl /api/health` 通 + IoTDA 能回调进来。
每段最多 3 条命令；每条都写「成功标志」与「失败怎么办」。
**本卡只做准备，真实部署要等用户确认（Q8）后再照本单执行。**

---

## 0. 三步摘要（只需要记这三句）

1. **装 Docker**（一条命令装好 docker + compose，然后把用户拉进 docker 组）。
2. **放代码 + 填 `.env`**（把 `server/` 放到 `/opt/hmprogram/server`，复制 `.env.example` 为 `.env` 并填 5 个必填值）。
3. **起服务 + 验活**（`docker compose -f docker-compose.prod.yml up -d --build`，然后 `curl 127.0.0.1:3000/api/health` 看到 `"db":"ok"`）。

后面 §4 装开机自启、§5 备份演练、§6 接 IoTDA，都是「可选但建议做一次」。

## 1. 开工前要有的东西（缺一样就先别开始）

| 项 | 从哪来 | 没有会怎样 |
|---|---|---|
| 公网 IP（或域名） | 云服务器控制台 | IoTDA 回调不到，P0 演示链路断 |
| SSH 账号 + 口令/密钥 + 端口 | 用户（问题清单 **Q8**） | 上不了机器 |
| 云安全组放开 `<PUBLIC_HTTP_PORT>`（默认 80） | 云控制台「安全组/防火墙」 | 外网能 ping 通但 webhook 404/超时 |
| 部署机 root 或 sudo | 用户 | 装不了 docker |
| ≥ 2 GB 内存、≥ 10 GB 空闲磁盘 | `free -m`、`df -h` | MySQL 起不来（本机 WSL 只有 7.4 GB，所以 compose 里写了内存上限） |

> 硬约束（全程有效）：**只操作本项目（compose 项目名 `hmprogram`）的容器**。
> 不要 `docker system prune`、不要 `docker rm -f` 别的容器、不要改系统自带 nginx/apache、不要用 host 网络。

## 2. 装 Docker（3 步）

```bash
# ① 一条命令装 docker + compose 插件（官方脚本）
curl -fsSL https://get.docker.com | sudo sh
# ② 让当前用户免 sudo 用 docker（重新登录后生效）
sudo usermod -aG docker "$USER"
# ③ 验证（应打印 Docker version / Compose version 两段）
docker version && docker compose version
```

- **成功标志**：`docker version` 有 `Server: Docker Engine` 一段；`docker compose version` 打印 `v2.x`。
- **失败对策**：
  - `curl` 不通 → 机器没有外网出口，让用户在控制台放通出网，或用官方离线包；
  - 提示 permission denied → 第 ② 步后**要重新登录 SSH**（或 `newgrp docker`）才生效；
  - 装完 `docker compose` 找不到 → 系统源里的老 compose 是 `docker-compose`（带横杠），本单要求 compose v2，重跑第 ① 步。

## 3. 放代码、填配置、起服务（3 步）

> **前提（t67/F-05 实测）**：本节、以及本单所有 `docker compose -f docker-compose.prod.yml …` 命令，
> 都必须在 `server/` 目录下执行，且 `.env` 已按第 ② 步填好。否则**任何** compose 子命令
> （`ps`、`port`、`logs` 也一样）会先报 `required variable … is missing a value`（缺哪个变量就补哪个，
> 不是 docker 装坏了）。

```bash
# ① 放代码（用仓库/压缩包都行；下面假定已在 /opt/hmprogram）
sudo mkdir -p /opt/hmprogram && sudo chown "$USER" /opt/hmprogram
# 把本仓库的 server/ 整个拷进去，最终长这样：/opt/hmprogram/server/docker-compose.prod.yml
cd /opt/hmprogram/server

# ② 填配置：复制样例，改 5 个必填值（随机值用 openssl rand -hex 32 生成）
cp .env.example .env
sed -i "s/^APP_ENV=.*/APP_ENV=prod/" .env
nano .env      # 改 MYSQL_ROOT_PASSWORD / DB_PASSWORD / JWT_SECRET / WEBHOOK_TOKEN / PUBLIC_HTTP_PORT

# ③ 起服务（首次会构建镜像，约 2~5 分钟）
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps
curl -s http://127.0.0.1:3000/api/health
```

- **成功标志**：`ps` 里 `hmprogram-server-db`/`api` 是 `healthy`、`proxy` 是 `Up`；
  `curl` 回 `{"code":0,...,"data":{"db":"ok",...}}`。
- **失败对策**（按报错关键字找）：
  - `生产必须设置 JWT_SECRET/WEBHOOK_TOKEN/DB_PASSWORD` → `.env` 没填全，`compose` 会直接拒绝；
  - `APP_ENV=prod 但 JWT_SECRET/WEBHOOK_TOKEN 仍是占位符` → 用了样例里的 `dev-only-change-me`，换成随机值；
  - `api` 一直 `starting` / `/api/health` 里 `db:"down"` → 先看 db 是否 healthy：`docker compose -f docker-compose.prod.yml ps db`；
    ⚠ 本 compose 的 db 健康检查是**带鉴权**的（root 与 `DB_USER` 两个账号都要能 `SELECT 1`），所以
    `db` 显示 `unhealthy` 基本就等于「口令不对」（不是「MySQL 没起来」），直接按下面第 4 条处理；
    只有 db `healthy` 而 api 仍起不来，才去看 `docker compose -f docker-compose.prod.yml logs --tail 50 api`。
  - `Access denied for user 'eldercare'@...`（或 db 一直 `unhealthy`）且**这台机器以前跑过开发 compose** → MySQL 只在**数据卷首次初始化**时按 `.env` 建账号，之后改 `DB_PASSWORD` 不会改库里的口令。二选一：把 `.env` 改回旧的 `DB_PASSWORD`，或在 db 里执行
    `ALTER USER 'eldercare'@'%' IDENTIFIED BY '<新口令>';`（`docker exec -it hmprogram-server-db mysql -uroot -p`）。
    改完再 `docker compose -f docker-compose.prod.yml up -d`（db 健康检查转 healthy 后 api 才会被启动）。
    ⚠ 不要用 `down -v` 图省事，那会删掉数据卷和全部数据。
  - 端口被占（`bind: address already in use`）→ 把 `.env` 的 `PUBLIC_HTTP_PORT` 改成 8080，并在云安全组放通 8080；
    （若报 `Ports are not available ... forbidden by its access permissions`，那是 Windows/Docker Desktop 的「保留端口段」问题，换一个端口即可；Linux 服务器上不会出现。）
  - 内存不足（MySQL 被 OOM kill）→ `docker compose -f docker-compose.prod.yml down`，确认机器 ≥2 GB 内存再起。
- **验证「MySQL 没有暴露到公网」**（本卡验收项，自行确认一次）：
  ```bash
  docker compose -f docker-compose.prod.yml port db 3306   # 期望输出 :0（= 没有宿主机映射）
  docker compose -f docker-compose.prod.yml ps db          # PORTS 只有 "3306/tcp"，没有 0.0.0.0:/127.0.0.1: 前缀
  ss -ltn | grep 3306                                      # 无输出（公网侧没有 3306 监听）
  ```
  （`port` 必须带端口参数：只写 `port db` 会报 `requires at least 2 arg(s), only received 1`；
  输出 `:0` 表示「容器端口没有映射到宿主机」，这就是我们要的结果。）

## 4. 开机自启 / 掉线自愈（二选一，推荐 A）

**A. systemd（推荐：开机自启 + 一条命令看状态）**

```bash
# ① 装 unit（路径不是 /opt/hmprogram 就先把 unit 里的两处路径改掉）
sudo cp /opt/hmprogram/server/deploy/hmprogram-server.service /etc/systemd/system/
# ② 启用并立刻启动
sudo systemctl daemon-reload && sudo systemctl enable --now hmprogram-server
# ③ 验证
systemctl status hmprogram-server --no-pager && curl -s http://127.0.0.1:3000/api/health
```

- **成功标志**：`systemctl status` 里 `Active: active (exited)`；`curl` 仍回 `db:ok`。
- **失败对策**：`Unit docker.service not found` → docker 没装好（回 §2）；`status=203/EXEC` → unit 里的
  `/usr/bin/docker` 路径不对（`which docker` 看真实路径）；改了目录忘了改 unit → 编辑
  `/etc/systemd/system/hmprogram-server.service` 后 `daemon-reload` 再来一次。

**B. 只用 compose 的重启策略（本卡已在 `docker-compose.prod.yml` 里写好 `restart: unless-stopped`）**

```bash
sudo systemctl enable --now docker        # ① 让 docker 开机自启，容器才会被带起来
docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' hmprogram-server-api   # ② 应输出 unless-stopped
```

- **成功标志**：② 输出 `unless-stopped`；`sudo reboot` 后 `docker compose -f ... ps` 仍是 healthy。
- **失败对策**：重启后容器没起来 → docker 服务没 enable（回 ①）；或有人手动 `docker compose stop` 过（stop 不会自愈，用 `up -d` 恢复）。

## 5. 备份 / 恢复演练（建议部署当天就做一次）

**5.1 先备份（3 步）**

```bash
cd /opt/hmprogram/server
# ① 立即备份（在 db 容器里 mysqldump，不需要宿主机装 mysql 客户端）
bash tools/db-backup.sh
# ② 看一眼这份备份的行数清单，记住「合计行数」
bash tools/db-rows.sh
# ③ 记下备份文件名（下一步要用；默认保留最近 14 份）
ls -1t backups/db-*.sql.gz | head -3
```

**5.2 恢复演练（3 步；清库不可逆，生产上请先确认当前数据可以不保）**

```bash
cd /opt/hmprogram/server
# ① 先停 api：SCHEDULER 与 webhook 会往库里写，演练期间有写入会让行数比对误判成「不一致」
docker compose -f docker-compose.prod.yml stop api
# ② 清库恢复（会要求输入 yes）
bash tools/db-restore.sh backups/db-eldercare-<时间戳>.sql.gz
# ③ 把 api 起回来并确认服务恢复
docker compose -f docker-compose.prod.yml up -d api && curl -s http://127.0.0.1:3000/api/health
```

- **成功标志**：② 最后打印 `✓ 一致：全部表行数与清单相同`，退出码 0；③ 的 `curl` 回 `db:ok`。
- 脚本用 `bash` 显式调用（仓库里的模式位是 644，克隆/拷贝后没有执行权限）；要用 `./tools/xxx.sh` 就先 `chmod +x tools/*.sh`。
- **⚠ 别只看 `/api/health`**：清库后（表全没了）它**照样**回 `db:"ok"`（健康检查只验证「连得上 MySQL」，
  不验证表是否存在）。所以恢复是否成功，以 `db-restore.sh` 的行数比对为准。
- **⚠ 演练期间不要停 api 太久**：`stop api` 后网关上报会积压（云端会重试），演练一般 1 分钟内做完；做完务必执行 ③ 把它起回来。
- **失败对策**：`✗ gzip 校验失败` → 备份文件坏了，换上一份；`✗ 有 N 处不一致` → **不要对外提供服务**，
  先保留现场（别再写库），把 `server/backups/` 下的清单发回来排查；
  `Access denied` → `.env` 里的 `DB_USER/DB_PASSWORD` 与实际库不一致。
- **日常建议**：`crontab -e` 加一行 `15 3 * * * bash /opt/hmprogram/server/tools/db-backup.sh >/var/log/hmprogram-backup.log 2>&1`
  （每天 03:15 备份，默认保留最近 14 份；磁盘占用 ≈ 每份几十 KB~几 MB）。

## 6. 接 IoTDA 规则引擎（详见 `IoTDA回调前置清单.md`）

```bash
# ① 从外网确认回调入口通（把 IP 换成公网 IP；这一步在**别的机器/手机热点**上做）
curl -s -o /dev/null -w '%{http_code}\n' "http://<公网IP>:${PUBLIC_HTTP_PORT}/api/health"   # 期望 200
# ② 拿 webhook token（就是 .env 里的 WEBHOOK_TOKEN，别发到群里）
grep '^WEBHOOK_TOKEN=' /opt/hmprogram/server/.env
# ③ 在 IoTDA 控制台加一条「数据转发 → 规则」，动作填（详见前置清单 §3）
#    https://或http://<公网IP>:<端口>/api/iotda/webhook?token=<WEBHOOK_TOKEN>
```

- **成功标志**：① 返回 200；规则动作里「测试/重试」后服务器日志出现
  `app.webhook | ...` 行且 `curl -s http://127.0.0.1:3000/api/health` 的 `webhook_last_at` 不再是空。
- **失败对策**：① 超时 → 云安全组没放通端口，或 `PUBLIC_HTTP_PORT` 与实际监听不一致
  （`docker compose -f ... ps` 看 proxy 的端口）；① 返回 404 → 只暴露了 `/api/`，路径写错；
  平台侧收到 401/`1502` → token 不匹配（改 `.env` 后要 `docker compose -f docker-compose.prod.yml up -d api` 重启 api，并同步改规则里的 URL）。

## 7. 回滚（升级/改配置出问题时用）

**回滚代码（回到上一个能用的版本）**

```bash
cd /opt/hmprogram
git log --oneline -5                      # ① 找到上一个能用的 commit
git checkout <上一个commit>               # ② 切回去（或 git revert <坏commit> 生成反向提交）
cd server && docker compose -f docker-compose.prod.yml up -d --build api   # ③ 重建并只重启 api
```

- **成功标志**：`curl -s http://127.0.0.1:3000/api/health` 回 `db:ok`，且 `/api/time`/`/api/alerts` 按预期返回。
- **失败对策**：重建失败 → `docker compose -f docker-compose.prod.yml logs --tail 80 api`；
  镜像层损坏 → `docker compose -f docker-compose.prod.yml build --no-cache api`。

**回滚数据（配错了/误删了数据）**

```bash
cd /opt/hmprogram/server
# ① 先停 api，再选一份「出问题之前」的备份（避免恢复期间还有写入，干扰行数比对）
docker compose -f docker-compose.prod.yml stop api
ls -1t backups/db-*.sql.gz | head -3
# ② 清库恢复（会要求输入 yes）
bash tools/db-restore.sh backups/db-eldercare-<时间戳>.sql.gz
# ③ 把 api 起回来并确认
docker compose -f docker-compose.prod.yml up -d api && curl -s http://127.0.0.1:3000/api/health
```

- **成功标志**：恢复脚本打印 `✓ 一致：全部表行数与清单相同`；③ 的 `curl` 回 `db:ok`。
- **失败对策**：备份太旧导致 App 看到旧数据 → 这是预期取舍（数据以备份为准）；恢复中报 `Access denied` → 口令不对，先修 `.env`；
  恢复中途放弃也要执行 ③（别让 api 一直停着）。

**只回滚配置（`.env` 改坏了）**

```bash
cd /opt/hmprogram/server
cp .env .env.bad.$(date +%s)               # ① 留个现场，别直接删
cp .env.ok .env                            # ② 用最近一次验证通过时留的副本覆盖（每次改成功都 cp .env .env.ok）
docker compose -f docker-compose.prod.yml up -d api    # ③ 只重启 api 让新配置生效
```

- **成功标志**：`curl -s http://127.0.0.1:3000/api/health` 回 `db:ok`。
- **失败对策**：没有 `.env.ok` 副本 → 按 `.env.example` 的「部署机必填 5 项」重新填一遍（`.env` 不在 git 里，这一点无法自动回滚，所以养成留副本的习惯）。

## 9. 日志与磁盘占用（部署机磁盘有限，照这个口径控）

| 东西 | 占用 | 怎么控 |
|---|---|---|
| 容器日志 | 每个服务 `json-file` 轮转：api/db 各 `10m × 3`、proxy `5m × 2` ≈ 最多 70 MB | 已写在 `docker-compose.prod.yml`；看日志用 `docker compose -f docker-compose.prod.yml logs --tail 100 api`（不要 `-f` 挂太久） |
| 数据库数据卷 | 演示规模几十 KB~几十 MB，随读数增长 | `docker system df` 看总占用；`docker volume inspect hmprogram-server-db-data` 看挂载点 |
| 备份 | 每份 ≈ 几十 KB~几 MB，默认保留 14 份 | `.env` 的 `BACKUP_KEEP`；旧备份由 `db-backup.sh` 自动删 |
| 镜像 | api 镜像 ≈ 300 MB（python:3.12-slim + 依赖层） | 升级后删旧镜像：`docker rmi <旧镜像ID>`；**不要** `docker system prune`（会影响别的项目） |

- 排查命令（都只碰本项目）：`docker compose -f docker-compose.prod.yml ps` / `logs --tail 100 <服务>` / `docker stats --no-stream`
- 磁盘告警（`df -h` 剩余 <1 GB）时：先 `docker compose -f docker-compose.prod.yml down` 停服务，删旧备份与旧镜像，再起。
- 内存：三容器上限 768m + 512m + 64m，本机实测稳态 ≈ **63 MiB(api) + 412 MiB(db) + 24 MiB(proxy) < 0.5 GB**；
  WSL 只有 7.4 GB、云服务器也可能只有 2 GB，所以别把上限改大。
- 演示数据（P0 演示前跑一次）：`docker compose -f docker-compose.prod.yml exec api python -m app.seed --password '<8位以上口令>'`
  —— `APP_ENV=prod` 下 seed **必须**显式给 `--password`（防止在公网机上误清库），这是刻意的保护，不是故障。
