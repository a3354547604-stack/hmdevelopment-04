# 演示数据施工单（t49）

现场演示前把库重置成「D1–D7 都能演」的确定状态：**一条命令灌数据 + 一条命令自检**。
所有命令都在 `server/` 目录下执行（Windows 上用 WSL，或把 `bash` 换成 Git Bash）。

---

## 0. 三步摘要（现场只做这三步）

1. `cd server && docker compose up -d` —— 等 `docker compose ps` 里 api 变 `healthy`
2. `docker compose exec api python -m app.seed --demo` —— 输出 `today=18, yesterday=24, alerts=10`
3. `bash tools/demo-check.sh` —— 末行出现 `演示数据自检：7/7 通过`

任何一步失败，看对应小节里的「失败对策」；最省事的兜底永远是**重跑第 2 步**。

---

## 1. 前置条件

| # | 条件 | 检查 |
|---|---|---|
| 1 | docker compose 可用，3000/3306 没被别的项目占 | `docker compose ps` |
| 2 | 演示栈是 dev compose，`server/.env` 里 `APP_ENV=dev` | `grep APP_ENV server/.env` |
| 3 | App/手机与服务器互通（开发者设置里填服务器 IP） | App 首页能出数据 |

**成功标志**：`curl -s http://127.0.0.1:3000/api/health` 返回 `"db":"ok"`。

> ⚠️ 环境陷阱：`.env` 里若残留 `APP_ENV=prod`（部署准备时留下的临时值），第 2 步会被**刻意拒绝**
> （防手滑清库）。仓库只保留 `.env.example`，`.env` 不入库。

## 2. 灌入演示数据

```bash
docker compose exec api python -m app.seed --demo
```

**成功标志**（末行）：

```
演示数据完成：user_id=1, device_id=1, unbound_device_id=2, activity_days=60, today=18, yesterday=24,
readings={'gateway': 284, 'gas': 15, 'fall': 4, 'door': 5, 'backfill': 11}, alerts=10
下一步：bash tools/demo-check.sh 逐条核对 D1–D7
```

- `--demo` **隐含清空**（TRUNCATE 业务表），可反复执行，结果逐次相同。
- 只想要「最小幂等种子」（不清库）时用 `python -m app.seed`（3 天读数 + 3 条告警）。
- 灌完可**再跑一次**验证幂等：末行数字必须与第一次逐字相同（条数不翻倍）。

**失败对策**

| 现象 | 原因 | 处理 |
|---|---|---|
| `拒绝执行：APP_ENV=prod 下不允许 --reset/--demo` | `.env` 是 prod | 改回 `APP_ENV=dev`；生产库上**不要**跑 `--demo` |
| `Table 'eldercare.xxx' doesn't exist` | 表还没建 | 先 `docker compose up -d`，让 api 启动时建表（`DB_AUTO_MIGRATE`） |
| `Can't connect to MySQL server` | db 没起来 | `docker compose ps`，必要时 `docker compose up -d db` |
| 端口被占 | 其它项目容器 | 改 `server/.env` 的 `API_PORT`，别停别人的容器 |

## 3. 自检（逐条核对 D1–D7）

```bash
bash tools/demo-check.sh          # 生产栈用：bash tools/demo-check.sh --prod
```

> ⚠️ 用 `--prod` 自测前先给 `.env` 注入**非占位**的 `JWT_SECRET` 与 `WEBHOOK_TOKEN`（`openssl rand -hex 32`）：
> 否则 `app/config.py` 的占位符守卫会先报 `RuntimeError: APP_ENV=prod 但 JWT_SECRET/WEBHOOK_TOKEN 仍是占位符`，
> 看不到真正的 prod 行为，容易误判成缺陷（t61 F-05）。

输出形如（每项一行 PASS + 一行证据）：

```
[PASS] D1 燃气二级报警（列表字段 + 详情读数越阈值）
       gas 2 条，头牌 id=1 level=2 status=pending summary=厨房燃气泄漏报警；snapshot.adc_mv=2680 ≥ 2500 mV（§8.2 gas_t2_mv）
...
演示数据自检：7/7 通过
```

**反向验证（可选，30 秒）**：没灌数据时自检必须**红**（否则自检没有意义）。条数取决于「库里还剩什么」，
**不要把它当成固定值**（t61 F-04 的 0/7 与 1/7 之争就源于此）——实测三种：

| 反向做法 | 实测 | 为什么 |
|---|---|---|
| 整库清空（连演示账号都没了） | `0/7`，rc=1 | 登录就失败，整体退出（不逐条计） |
| 只清业务数据、账号与设备仍在 | `0/7`，rc=1 | 逐条跑，7 项全红 |
| 只删读数与活动、告警还在 | `2/7`，rc=1 | D1/D4 只看告警，不需要读数 |

三种都是退出码 1（红）；**只要不是 7/7 就算通过反向验证**。

**失败对策**

| 现象 | 原因 | 处理 |
|---|---|---|
| 登录失败 / 账号下没有设备 | 没灌数据或灌到别的库 | 重跑第 2 步 |
| D6「补传样本条数 / 入库时刻」 | 库里是旧数据（被别的脚本写过，或用了旧版 seed） | 重跑第 2 步 |
| D6「窗口内出现了非补传读数」 | 窗口里混进了实时写入的行 | 重跑第 2 步；若仍红说明 seed 被改坏，见 §6 |
| D7「今日活动应为设计值 18」 | 库被改过，或跨了 CST 零点 | 重跑第 2 步；零点前后重跑即可 |
| 列表里出现「今天稍晚」的时刻 | 冻结时钟设计（见 §6） | 预期，不用处理 |
| 灌数 3 分钟后 App 显示网关离线、告警 10 → 11 条 | 调度器 180 s 没收到真实心跳（§8.7） | **预期行为，自检仍绿**（D6 判据只认 `recovered_at`，不看在线瞬时值）；要回到「网关在线 + 10 条」就重跑第 2 步 |
| api 容器没在跑 | 栈没起 | `docker compose up -d` |

## 6. 数据设计说明与诚实边界

- **冻结时钟**：所有时刻锚定到 CST 日历日的固定钟点（08:00–19:00 活动、10:00 燃气、15:00 跌倒、
  12:00–13:00 断网），等价于「把现在冻结在今天 20:00」。因此 00:05 与 23:55 各跑一次，
  报表数字与告警列表完全相同（验收要能复算）。**若在当天该钟点之前运行，列表里会出现「今天稍晚」
  的时刻**——这是刻意的，不是时间错误。唯一例外是 `device_online.last_heartbeat` 用真实时间，
  否则调度器会在 180 s 后立刻把网关判离线（这条边界见下面「灌数 3 分钟后」）。
- **报表口径差异（既有，不在本卡范围）**：活动归并的实现按 §7.9 代码统计 `type=presence` 且
  `presence=true`；契约 §14 ⑭ 写的 P0 口径是 `door` 跳变。演示数据两者都给：`presence` 供报表数字、
  `door` 供 D3/D5 与门磁展示。已登记待 PM 裁决。
- **离家状态**：契约 §4.3 的 14 个属性里没有独立的 `away` 字段（§8.5 是网关本地状态机），
  所以 D5 验的是「判定输入（门磁跳变）+ 参数（`away_after_open_s=600`）」，不是一个不存在的字段。
- **断网补传（D6）**：窗口 12:00–13:00 内**不写任何实时读数**（网关快照断档制造 75 分钟时间戳跳变，
  燃气背景值与活动点也挪出窗口），窗口里只剩 11 条补传样本；这 11 条在 payload 里带
  `origin=backfill` 标记，且 `created_at` **显式写成恢复后 3 分钟**。判据因此有两条互相独立的证据：
  ①按标记认「窗口内只有补传样本」；②样本自证「入库时刻晚于采集时刻」。
  为什么不用「入库时刻晚于窗口结束」当判据：那样 13:00 CST 之后实时写入的行也会满足条件，
  同一份数据在上午数出 11 条、晚上数出 14 条——判据一旦依赖运行钟点就不可复算了（t61 F-03）。
- **灌数 3 分钟后（预期行为）**：`device_online.last_heartbeat` 写的是**真实时间**（否则调度器会在
  灌数瞬间就把网关判离线），所以 180 s 后调度器按 §8.7 合法地把网关置离线并升起一条待处置
  `device_offline`：App 上网关显示离线、告警 10 → 11 条。这**不影响自检**——D6 的在线判据是
  「`device_offline` 至少一条带 `recovered_at`」，证据行只是如实打印当前 `online` 值。
  演示中途想回到「网关在线 + 10 条告警」，重跑第 2 步即可（t61 F-02）。
- **读数页的窗口**：`GET /api/devices/{id}/readings` 不传 `from/to` 时默认取「近 24 h（到此刻为止）」，
  而演示数据的钟点锚在日历日上，所以**当天该钟点之前**跑演示时，读数页默认窗口里看不到今天稍晚的那批
  （补传样本、12:00 之后的快照）。要现场展示这批数据就显式给窗口，例如
  `readings?type=status&from=<今天12:00的ms>&to=<今天13:00的ms>`（已实测 total=11）。
- **重推**：待处置告警会被调度器按 §7.7 的 0/60/300 s 推满 3 次；seed 把首次重推放在 5 分钟后，
  演示开场不会被刷屏。
- **阈值**：`adc_mv=2680` 越过 §8.2 的二级阈值 2500 mV，但 1500/2500 mV 本身仍是**结构默认值**，
  CAL-02 标定后才定稿——演示数据的意义是「链路与文案对」，不是「阈值已标定」。
