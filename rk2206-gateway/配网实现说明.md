## 2. 分层：为什么状态机不碰 SDK

```
gw_prov_route.c  (URL → 接口)      gw_main.c (板级 ops 注入 + 任务编排)
        │                                   │
        └────────► gw_prov.c ◄──────────────┘
                 (窗口/扫描/绑定/白名单/指示)
                        │  gw_prov_ops_t（函数指针）
        ┌───────────────┴────────────────┐
   gw_net.c + gw_store.c            test/gw_prov_sim.c
   (wifi_lite / Flash)              (假 Wi-Fi / 假汇聚 / 假时钟)
```

理由：配网逻辑是**流程与约束**（窗口 600 s、"先扫后绑 300 s"、8 条上限、`1600`–`1606` 判定），
放在状态机里才能在主机上被穷举测试；Wi-Fi/Flash 是**平台差异**，经 `gw_prov_ops_t` 注入后，
主机上换一套假实现就能把 §12 的每条规则跑一遍（`test/run-prov-sim.sh` 129 用例）。
`gw_prov_ops_t` 必须放在**文件作用域**：`gw_prov_t` 只存指针，指向栈上的 ops 会在函数返回后悬空
（主机模拟器第一版就是这么崩的：ASAN 报 `gw_prov_resync_step` 里 ops 偏移 `0x68` 处 SEGV）。

## 3. 关键实现决定

1. **STA 连接拆成 `sta_start` + `sta_poll`**：一次 30 s 的阻塞连接会把 tick 任务钉住，
   LED 不闪、配对键读不到——配网窗口里这两件事恰恰是用户在等的反馈。
2. **`gw_prov_enter()` 在 `ap_start` 失败时不开窗口**并返回 -1：宁可"长按没反应"，
   也不要开一个打不开的入口（用户会以为手机坏了）。
3. **扫描受理的记账顺序**：`hub_online` 不通过 → 409/1605（不"受理了没人干活"）；
   `scan_id` 先自增 → `scan_state=SCANNING` → **先置 `busy=scan` 再发帧** → 发帧失败回 409/1605 + 清 busy。
   顺序反了会出现"汇聚秒回 0x21 → on_scan_rsp 置 DONE → 又被盖回 SCANNING"（模拟器抓到的真 bug）。
4. **绑定先落盘再发 `0x22`**：契约 §12.9 明确"等 `0x23` 超时也要保留白名单"，
   所以持久化必须在汇聚应答之前。**但汇聚"明确拒绝"（`0x23 result=10/11`）时回滚**——
   留一条汇聚不会接受的记录，只会在每次重建时被再拒一次。
5. **汇聚重建不放在收帧任务里**：`gw_prov_on_hub_frame()` 在"离线→在线"时只置 `resync_wanted=1`，
   真正的 `0x22 op=list` + 逐条 `add` 由 tick 任务分步做（`GW_PROV_RESYNC_WAIT_MS=300 ms` 短等待）。
   在 uart 收帧任务里等 `0x23` 会把收帧任务自己堵死。
6. **`nodes[].bind` 以网关白名单重算**，不信汇聚的 `bind` 字段：汇聚不落盘，它那边的状态可能过期。
7. **`nodes[].role` 按整数存**（§12.8 明确 `1`=节点 `2`=汇聚），不是字符串。
8. **时间戳一律 64 位**：unix 毫秒（`1792243200000`）早超 `uint32` 范围，`scanned_at`/`last_seen`/`ts` 全用 `uint64_t`；
   未校时时 `gw_time_ms()` 返回 0，配网接口就报 0 —— 不编假时间。
9. **口令处理**：STA 口令只在 `gw_prov_t.pend_psk` 存活到连接结束，之后立刻清零；不进日志、不回显；
   落盘前用设备标识派生密钥做 XOR 混淆（`gw_store.c` 注释写明**这只是混淆不是加密**，真正的边界是
   "口令不进日志、不回显、不落仓库"）。AP 口令按 §12.2 允许在串口首行给出（现场要看得到）。
10. **HTTP 一律 `Connection: close` + `Cache-Control: no-store`**，`SO_RCVTIMEO/SNDTIMEO = 5 s`：
    单任务串行处理请求，一个慢客户端不能把配网服务占死。
11. **H5 页面直发常量体**：页面 9219 字节 > 8 KB 响应缓冲，与其把缓冲加到 12 KB（多吃 RAM），
    不如给请求结构加 `literal/literal_len` 直接发常量。
12. **配网期间 LED 让位**：`gw_alarm_tick()` 之后由 `gw_prov_led_level()` 覆盖 LED；
    配网进入/进行中不发声，仅"配网成功"短鸣 ≤300 ms，且尊重 `mute_alarm`（§12.2 可静音）。

## 4. H5 页面（§12.11）

- 真源 `rk2206-gateway/web/index.html`（单文件，CSS/JS 内联，**0 外部 URL**），
  生成 `src/gw_h5.h`：`python3 rk2206-gateway/web/gen-h5-header.py`（`--check` 校验一致性，改完不重跑会被 CI 拦住）。
- 页面只调 §12 五个接口，全部**相对路径**（不写死 AP 地址，见 CAL-12）；
  每请求 3 s 超时（`AbortController`），错误码 `1600`–`1606` 有中文文案表；
  提交口令后立即清空输入框、不落 `localStorage`；DOM 一律 `createElement`/`textContent` 构建。
- 页面**不受窗口限制**（窗口关了也能打开，页面自己显示"不在配网模式"），否则用户看到空白页只会以为坏了。

## 8. t33 竞态留痕：阈值命令的 ACK 为什么不会被误判

- 风险：`on_cmd()` 跑在 net_task（优先级 26），UART 收帧跑在 uart_task（优先级 **24，更高**）。
  于是 `gw_send_frame_expect_ack()` 还没返回，节点回的 `0x10` ACK 就可能已经被 uart_task 处理掉了。
- 如果"在等 ACK"这个标志是发帧**之后**才置的，这个**早到的 ACK 会被漏掉** ——
  节点明明回了 ACK，网关却按"三次重发无 ACK"回 `result_code=12`（现场表现为 App 说超时、节点其实收到了）。
- 做法（`src/gw_main.c`）：发帧**之前**先预测 SEQ（`s_th_seq = s_tx_seq`，与
  `gw_send_frame_expect_ack()` 内部 `s_pending.seq = s_tx_seq++` 同值）并置 `s_th_waiting = 1`；
  `handle_frame()` 的 `GW_T_GW_ACK` 分支在 `gw_pending_ack()` 之后比对 `ack_seq == s_th_seq` 记结果；
  轮询窗口 `GW_ACK_TIMEOUT_MS × (GW_ACK_MAX_RETRY + 2)` = 500 ms × 5 = **2500 ms**（3 次重发 + 余量），每 20 ms 查一次标志。

## 9. t34 凭证 KV：边界、负向与一个被自测抓出来的真 bug

- 落盘布局见 `src/gw_kvcfg.h` 顶部注释（256 B 定长块 + FNV-1a CRC，写在同一 4 KB 扇区，擦除粒度 4096）。
- **为什么"回落编译期默认值"只写在 `gw_kvcfg_load()` 一处**：调用方（`gw_main.c` 的 `creds_init()`）
  拿到的一定是**完整凭证**或**完整默认值**，绝不会是半截 —— 三条负向（缺凭证/写失败/读回不符）都走这条路。
- **自测抓到的真 bug**（值得记一笔）：`put_str()` 原先的注释写着"目标已清零：尾巴天然是 NUL"——
  这在 `encode()`（先 `memset` 整块）里成立，但 `gwkv set device=…` 这种**部分更新**是拿
  "当前生效的配置"当基线改字段的，字段里还留着旧值 ⇒ 只拷 n 字节会读出 `DEV-00024e5f`、
  时间服务器 `192.168.1.500`（旧默认值 `6a1b2c3d4e5f` / `192.168.1.100` 的尾巴）。

  `strstr(out, "DEV-0002")` 是**抓不到**这个 bug 的（这正是它第一轮漏过的原因）。
- 三条负向用**注入式 flash ops** 造（`test/gw_selftest.c` 的 `kvf_ops`：写失败返回 -1 / 写入前改一个字节），
  真 Flash 上没法稳定复现这两个故障。
- `tools/gw-host-test.sh` 的 `OBJS` 由本卡加了一项 `gw_kvcfg.c`（`tools/` 归 t16，已在完成报告里报备）；
  `gw_kvcfg_shell.c`（`osCmdReg` 那层）是板级，主机刻意不编 —— 与 `gw_plat.c`/`gw_main.c` 同理。

## 10. t137 增量：首次上电自动配网 + 页面上一次填完云端凭据

> 背景：现场那台网关是**全新的**（Flash 里没有家庭 Wi-Fi），而且 `EX_GPIO_A3` 的配对键常常没人接。
> t136 给了串口 `wifi set` 这条免按键通路，但"用户要自己去串口敲命令"仍然不是产品形态；
> t137 把入口补成了"**上电自己开窗 → 手机连热点 → 一个表单填完 Wi-Fi 与华为云三件套**"。

### 10.1 自动开窗：只在"从没配过"时开一次

- 入口 `gw_prov_auto_boot(p, now_ms, wifi_configured)`（`src/gw_prov.c:353`），由 `gw_prov_tick()` 每拍调用；
  **不能放在 `gw_main_entry` 里直接开**——SoftAP 要 wifi 服务先就绪，开机早期调 wifi 接口会拿到"设备忙"。
- 判定状态机只有两态（`gw_prov_t.auto_state`）：`IDLE`（还没判定）→ `DONE`（已了结）。
  一旦置 `DONE` 就永不再自动开，**不会每拍都问一遍**。
- 三种了结方式：①已有凭据 → 只打印一行"不自动开窗"；②已经有人在配（`window_open`，手动入口）→ 直接 `DONE`；
  ③开窗成功 → `DONE`；开窗失败按 `GW_PROV_AUTO_RETRY_MS`(5 s) 重试，`GW_PROV_AUTO_MAX_TRIES`(3 次) 用尽后
  打进日志并 `DONE`。
- **为什么"只判定一次"而不是一直盯着**：射频只有一套，配网窗口期间 STA 要停。若每拍都问"还没配，要不要开窗"，
  那么"不想配 Wi-Fi、只用串口 `gwkv` 走别的联网方式"的机器会被反复打断，连路由都连不上。
- 凭据探测走 `ops->cred_probe()`（板上 = `gw_kvcfg` 之外的 `gw_store_cred_load()` 是否成功）。
  **为 NULL 时按"没有凭据"处理**：宁可多开一次窗（用户随手关掉），也不能让全新网关因为探不到而永远开不出配网入口。

### 10.2 云端三件套：扩展 `POST /api/provision/wifi`，不新增路由

- **没有新开 `/api/cloud` 端点**，理由两条：①手机在 AP 口上只能提交一次表单——Wi-Fi 一提交，STA 就起来、
  AP 准备退场，分两次提交会多出一个"只配了一半"且谁也连不上的中间态；②§12.4 的路由表是契约的一部分，
  加一条路由要走契变。
- 字段（全部可缺省，出现任意一个就要求三件套齐全）：`host`（接入地址，可带 `:端口`）、`port`（可选，与 host 里的端口
  不能打架）、`device_id`（也收 `device` 这种写法）、`secret`。
- **三件套也可以单独提交**（不给 `ssid`、且 Flash 里已有 Wi-Fi 凭据）：响应
  `{"saved":true,"connecting":false,"iotda":{…},"note":"只更新了云凭据（家庭 Wi-Fi 未改动）"}`，
  用于现场只换云端设备/密钥。没有任何 Wi-Fi 凭据又缺 `ssid` → `400 bad_ssid`（那种机器配完也没网，必须整段一起填）。
- 失败原因细化到"页面能看懂"：`bad_host` / `bad_host_len` / `bad_host_char` / `bad_port` / `bad_device` /
  `bad_device_len` / `bad_device_char` / `bad_secret` / `bad_secret_len` / `bad_secret_char` /
  `cloud_failed`（带 `detail`，例如"模拟写 Flash 失败"）。
- **落盘在 Wi-Fi 预检之后**：预检不过（`not_found`）时一个字段都不写，语义最干净。
- 写的是**同一份 KV**：`ops->cloud_save` → `src/gw_main.c` 的 `prov_op_cloud_save()` → `gw_kvcfg_cmd("set host=… port=…
  device=… secret=…")`，与串口 `gwkv set` 完全同一条路（省掉两套存储互相覆盖的风险）。
  写完置 `s_creds_dirty`，由 `net_task` 在自己那侧重装凭据并重连 `gw_cloud`（避免跨任务撕裂 `s_cloud`）。
- **密钥边界**：落盘后 `cloud_load` 只回 `has_secret` 布尔值——**连长度、指纹都不给**，
  因为站在 AP 口上的任何人都能拿指纹做离线对拍。串口日志同样只打长度。

## 11. t138 增量：板载按键（`USER_KEY_ADC`）做配网入口 + `keys` 诊断命令

### 11.1 三层分工：判定逻辑不碰 SDK

| 层 | 文件 | 职责 | 主机自测 |
|---|---|---|---|
| 纯逻辑 | `src/gw_key.c` / `src/gw_key.h` | 基线（中位数 + 慢漂移跟踪）、去抖、长按、事件队列、电压分档命名 | **参与**（在 `tools/gw-host-test.sh` 的 `OBJS` 里） |
| 板级 ADC | `src/gw_hw_adc.c` / `src/gw_hw_adc.h` | `LzSaradcInit`、通道→引脚复用（`GPIOn_PCx` → `SRADCn`）、raw→mV、通道扫描 | 不参与 |
| 板级聚合 | `src/gw_hw.c` / `src/gw_hw.h` | 采一次 ADC 喂给 `gw_key.c`、`keys` 诊断文本、`gw_hw_key_tick/pressed` | 不参与 |
| shell 挂载 | `src/gw_kvcfg_shell.c` | `osCmdReg("keys", …)`（板上只有这个文件 include `shell.h`） | 不参与 |

为什么拆这么细：判定规则（阈值滞回、去抖窗口、长按计时）是最容易出错、
也最容易在改动中悄悄回归的部分；把它放在不依赖 SDK 的纯 C 文件里，
主机上就能把"抖动 30 ms 不触发""按 2.9 s 不触发、3.0 s 触发""基线缓慢漂移不误触"全跑一遍，
不用等烧板。

### 11.2 判定口径（都用相对基线，不用绝对电压）

- **基线**：开机静默 `GW_KEY_BASELINE_MS`=2 s（tick 100 ms → 实际约 20 个采样点，数组上限 `GW_KEY_BASELINE_MAX`=33），取**中位数**并记峰峰值。
  取中位数而不是均值：单个毛刺（比如有人碰了一下）不会把基线拉偏。
  峰峰值 > `GW_KEY_BASELINE_SPREAD_WARN_MV`(200 mV) 会提示「开机采基线期间有人在按键」。
  基线 < 100 mV 或 > 3000 mV 直接判「通道没接/悬空」并禁用板载键（只告警，不影响外接键与串口）。
- **按下**：`mV + GW_KEY_PRESS_DELTA_MV(300) <= 基线` 且**连续保持** `GW_KEY_DEBOUNCE_MS`(50 ms)，
  才产生 `DOWN` 事件。50 ms 在 100 ms 的 tick 下等价于"至少两个采样点都低"，
  压掉按键机械抖动与 ADC 偶发跳点。
- **松开**：回升到「基线 − `GW_KEY_RELEASE_DELTA_MV`(120)」以上才算，形成 180 mV 的**滞回带**，
  避免在阈值附近抖动出连击。
- **长按**：从按下时刻到松手 ≥ `GW_KEY_LONG_MS`（直接复用 `GW_PAIRKEY_LONG_MS`=3000，与外接键同一个值）
  → `LONG` 事件 + 记 `press_ms`；不足 3 s 是短按（只有 `PRESS`，不触发配网）。
- **漂移跟踪**：未按下时按 `GW_KEY_DRIFT_Q8`(8/256 ≈ 3%/采样) 把基线往当前值拉。
  1 mV/采样的慢漂移稳态只落后约 32 mV，远小于 300 mV 阈值；而按下是阶跃，跟踪追不上。
  这样电池/温度导致的分压缓慢变化不会在几小时后变成"没按也进配网"。
- **分档命名**：`GW_KEY_BAND_*` 只用于日志和 `keys` 里说"这是 K2"，**不参与**按下判定——
  绝对电压随板子/电池变，拿它当判据就是给自己埋雷。

### 11.3 与外接键的关系：一条状态机、两个入口

`gw_main.c` 的 `tick_task` 里，板载键与 `EX_GPIO_A3` 各自维护一个 `gw_pairkey_t`（上一次电平 + 按下时刻），
但**都调用同一个 `pair_key_step()`**，并且只在那一处调 `gw_prov_toggle()`。
理由：两套边沿检测同时跑，迟早出现"板载键开了窗、外接键又给关了"这种现场无法解释的抖动。

两个开关都在 `gw_config.h`：`GW_KEY_ENABLE_BOARD` / `GW_KEY_ENABLE_EXTERNAL`，默认都开。

**为什么 ch0/ch1 不扫描**：调试串口是 `UART1_M1`（SDK `board/uart.c` `UART_DEBUG_PORT 1`）。
这两个脚如果被复用成 `SRADC0/1`，切过去就会丢控制台——现场等于失明。
所以 `keys` 的通道扫描固定只扫 ch2–ch7。

### 11.4 `keys` 命令

```
keys        # 打印当前状态 + ch2..ch7 通道扫描
keys 4      # 对指定通道（0..7）做一次采样，标定时逐个试通道用
```

输出三段：**当前状态**（通道、基线、峰峰值、raw/mV、按下判据、是否按下、最近一次短按/长按的时长）、
**判定依据**（阈值与去抖窗口，便于现场核对是否被改过）、**通道扫描**（每个通道 raw/mV，并标 `<= 当前通道`）。
电平接近 0 或接近满量程的通道会标 `⚠ 短接GND / ⚠ 悬空`，方便判断"按键到底挂在哪一路"。

`keys <ch>` 是这条命令的可选参数：原理图与实物不一致（按键其实挂在别的通道）时，
现场能直接逐个通道试，不必改 `GW_KEY_ADC_CHANNEL` 重编固件——这是"标定"这件事在
没有示波器、没有源码改动窗口时唯一可用的手段。

**参数口径（t139 修正）**：LiteOS-M 的 `osCmdReg(..., XARGS, ...)` 会把**命令名**放进 `argv[0]`
（SDK 证据：`sdk_liteos/shell/src/shell_hwinfo.c:70` 的 `if (argc == 1)` 就表示「没有参数」，
`argv[1]` 才是第一个实参；实机证据：2026-10-20 COM14 上裸 `keys` 的 argc 为 1 且 `argv[0]=="keys"`）。
因此判断"有没有参数"必须看 **`argc < 2`**：**裸 `keys` = 完整报告，`keys <n>` = 单通道采样**。

t138 这里写成 `if (argc >= 1u)`，实机表现是裸 `keys` 永远进参数分支、第一个 token 是 `keys`
必判非法 → **完整报告永远打不出来**（只有 `keys 5` 这种也不会被正确解析）。t139 把参数分派抽成
纯函数 `gw_keys_cmd()`（`src/gw_hw.c`，ops 注入 `report`/`probe`），主机测直接覆盖
「无参 → 完整报告 / 合法数字 → 单通道采样 / 非法 → 用法 + 失败码」三条路径——
这类"只有真机敲才撞得到"的口径错误，从此能在主机侧拦住。

同一口径核对（三条命令）：
| 命令 | 现在怎么处理 argv[0] | 结论 |
|---|---|---|
| `keys` | `gw_keys_cmd()` 自己跳过 `argv[0]=="keys"`（也容忍不带命令名） | 本次修好 |
| `gwkv` | handler 把 argv 拼成一行（含着命令名）交给 `gw_kvcfg_cmd()`，后者 `base = (argv[0]=="gwkv") ? 1 : 0` | 行为正确（靠容忍命令名），但源码注释「shell 传进来的 argv 不含命令名」是**错的**，且该文件不在本卡范围，未改，待 PM 派单 |
| `wifi` | 同 `gwkv`（`gw_wifi_cmd()` 里 `base = (argv[0]=="wifi") ? 1 : 0`） | 同上 |

## 12. t140 增量：板载 ADC 链路完全不工作的根因与修法

t138 烧到板上之后 `keys` 只打印到「分档」就结束、开机也没有「板载键基线」那一行。
t140 拿现场日志把根因定死，并把「SDK 已经做过一遍」这件事写进代码结构里。

### 12.1 现场证据

```
OHOS # keys
[GPIO:E]LzGpioInit: id 18, channel has already been initialized
[DEV:E]DevIoInit: CTRL1 pin  init failed
... id 19 / 20 / 21 / 22 / 23 各一条，全部 init failed ...
[key] 板载按键（USER_KEY_ADC）诊断
  通道     : ch5（gw_config.h 的 GW_KEY_ADC_CHANNEL）
  采样口径 : SARADC 10 位，AVDD 基准，mV = raw * 3300 / 1024
  分档     : 空闲 ≥2000；K1 <300；K2 <780；K3 <1330；K4 <1950（单位 mV
OHOS #
```

开机日志里只有 `[SARADC:D]LzSaradcInit: saradc is initialized successfully`，
没有 `[gw] 板载键基线：ch5 中位 …mV`。

### 12.2 根因（两条，都是「SDK 已经替我们做过」）

1. **引脚已经被 HDF ADC 驱动初始化过。**
   `vendor/lockzhiner/rk2206/hdf_config/adc_config.hcs:20-26` 的
   `device_adc0 { gpio = 21; channelId = 5; }`（21 = `GPIO0_PC5`）⇒ 开机时
   `hdf_drivers/adc/adc_driver.c:215` 的 `HdfAdcDriverParseInit → HdfAdcDriverInitSRADC`
   已经 `DevIoInit(GPIO0_PC5)`。而 `DevIoInit` 内部先 `LzGpioInit`，它对本进程
   已 init 过的引脚一律返回 `channel has already been initialized`
   （反汇编 `libhardware.gpio.o` 的 `LzGpioInit` 可确认：每引脚一个 inited 标志，
   命中即打印上面那句并返回 1）。t138 每读/扫一个通道就 `DevIoInit` 一次，
   于是**开机第一次 mux 就失败**，之后每次都失败。
2. **`LzSaradcInit()` 对「已初始化」也返回非 0。**
   反汇编 `libhardware.saradc.o` 的 `LzSaradcInit`：开头读一个 inited 标志，
   非 0 就短路返回 1（不重复 RequestIrq/ToyMutexInit）。而 HDF 驱动的
   `HdfAdcDriverStart()`（`adc_driver.c:68`）开机已经调过一次 ⇒ 我们调它必然拿到 1，
   t138 把「rc != LZ_HARDWARE_SUCCESS」判成失败 → 整条链路判死。

顺带定位第三个现象：**`keys` 报告在约 256 字节处被截断**。
报告是拼进一个大缓冲再一次 `printf("%s", out)`，LiteOS-M 的 printf 单次输出有
上限（现场正好停在「（单位 mV」处，与 256 字节边界吻合），后面的「当前/判定/扫描」
全丢。与 ADC 无关，但同样会让现场「看不到读数」。

### 12.3 修法（三条原则）

1. **复用只写 IOMUX**：`PinctrlSet(GPIO0_PC0+ch, MUX_FUNC1, PULL_NONE, DRIVE_KEEP)`。
   它是幂等寄存器写，不依赖 `LzGpioInit` 的「一次」语义，开机后再写也安全。
   `gw_hw_adc.c` 里已不再出现 `DevIoInit`。
2. **init 的返回值不是判据，试读才是**：`gw_hw_adc_init()` 采完 IOMUX、调
   `LzSaradcInit()`（非 0 只打一行说明）、写 AVDD 基准，然后**试读一次**：
   读到数才算可用（返回 0），读不到才返回 -1 并打印「试读失败」。
3. **失败必须留痕，输出必须分片**：读失败计入 `gw_hw_adc_read_fails()` 并写进
   `keys` 报告；`keys` 的输出改成**逐行打印**（每行一次 printf），不再受单次
   输出上限影响。

### 12.4 与 SDK 依赖的关系：ops 注入

`gw_hw_adc.h` 现在把四个板级动作（`pinctrl_set / saradc_init / saradc_read /
select_avdd`）抽成 `gw_hw_adc_ops_t`，策略层（mux/init/read/scan/计数）永远参与
编译，板级实现放在 `#ifndef GW_HW_HOST` 段里懒注册。这样「SDK 说已初始化」「读失败」
「IOMUX 写不进」这三条分支可以在主机的假实现上跑一遍（`test_hw_adc()`），
不需要再靠烧板子猜。

### 12.5 主机自测新增（`test/gw_selftest.c` 的 `test_hw_adc()`，13 条断言）

| 断言 | 防的是什么 |
|---|---|
| 没有板级实现时 init 返回失败 | 不许把「没实现」静默当成「读到 0」 |
| `saradc_init` 返回 1 时 init 仍成功 | 就是 t138 判死的那个分支 |
| init 只写一次 IOMUX / AVDD 只做一次 / 末尾试读一次 | 复用不该重复 |
| init 之后读通道不再写 IOMUX | t138「每读一次都 DevIoInit」的回归 |
| `raw=512 → mV=1650` | 10 位 AVDD 换算口径 |
| 扫描对每个通道各写一次 IOMUX；输出含 `ch5: raw=`、`← 配置通道`、`ch0/ch1 未扫描` 说明 | 标定读数要能看懂 |
| 读失败 → init 失败 + 计数 + 扫描里写「读失败」 | 失败不许静默 |
| IOMUX 写不进但读得到 → init 仍成功，扫描里写明 | HDF 已复用好的板子不该被判死 |

用例总数：**411 → 447**（基线 411，卡面要求 ≥431）。

### 12.6 仍未实测

板上的真实读数仍然要靠 `keys` 回传（§11.5 的「本板实测」列还是待回填）。
t140 只是把「为什么读不到」和「读不到时该怎么看见」修好；四个键的实际 mV

## 14. t142：SoftAP 配网卡死的根因与异步化

### 14.1 一句话根因

`EnableHotspot()` 内部那条等固件回复的路径用的是 **永久等待**（没有超时），
而它原先是从 `tick_task` 里同步调用的 —— 固件不回事件，整个 tick 循环
（按键采样、心跳、声光指示）就一起停在那儿，现场看到的就是「卡死」。

### 14.2 证据链（反汇编 `libhardware.a`，不是猜）

调用链：`EnableHotspot()` → `WifiStartAP` → `rk_wifi_start_ap`
→ `wifi_start_ap_internal` → `wifi_send_cmd`。

| 层 | 位置 | 关键事实 |
|---|---|---|
| `WifiStartAP` | `libhardware.wifi.o` | 只把 `rk_wifi_start_ap()` 的返回值翻成 0/1 |
| `rk_wifi_start_ap` | `libhardware.rk_wifi_api.o` | 先 `wifi_start_ap_internal(ifname, ssid, len)`，成功后再 `dhcpd_start(ip)` |
| `wifi_start_ap_internal` | `libhardware.wifi_api_internal.o` | 组一个 0x70 字节的命令结构，交给 `wifi_send_cmd` |
| **`wifi_send_cmd`** | 同上 | 反汇编 `0x2c`–`0x34`：`mvn r1,#1`（= `0xFFFFFFFF`）→ `LOS_MuxPend/LOS_SemPend`；`0x72`–`0x82` 是 `do { pend(0xFFFFFFFF); … } while (flag != 17)` —— **等固件事件，无超时** |

结论：只要固件不回这个事件（AP 与 STA 抢射频、AP 模式不被接受、wifi 服务未就绪），
调用者就**永远不返回**。这不是「慢」，是「不回来」。

SDK 自己的正确顺序也印证了单射频冲突：`config_network.c` 的
`TaskConfigApModeEntry()` 是 **先 `SetWifiModeOff()` 再 `SetApModeOn()`**。
我们原来的 `gw_net_ap_start()` 反着来：先 `EnableWifi()`（开 STA）再起 AP。

### 14.3 改法（三件事）

1. **AP 起停搬到专用任务**：新增 `gwAp` 任务（`GW_AP_TASK_STACK` 4096 /
   `GW_AP_TASK_PRIO` 29，比 UART24/tick25/net26/配网 HTTP28 都低）。
   `gw_net_ap_start()` 只登记请求（微秒级返回），真正的阻塞调用在任务里跑。
   → 即使固件仍然不回事件，UART、上云、心跳、按键都不受影响；日志停在
   `[NET] AP: EnableHotspot 开始…` 这一行本身就是可判读证据。
2. **起 AP 前先关 STA**：`net_sta_off_for_ap()` 里 `IsWifiActive()==WIFI_STATE_AVALIABLE`
   就 `DisableWifi()` + 等 300 ms。与 SDK 官方顺序一致。
3. **状态可问**：`gw_net_ap_state()` / `gw_net_ap_state_text()`
   （0 未启动 / 1 正在启动 / 2 已启动 / 3 失败 / 4 已关闭），
   串口新命令 `prov on|off|status` 直接打印窗口剩余、AP 状态、页面地址、STA 连接。

`GW_PROV_AP_ENABLE` 已从 0 恢复为 **1**（原注释里写的「留到演示后再修」到此关闭）。

### 14.4 为什么不是别的方案

| 方案 | 结论 |
|---|---|
| 继续同步调用，只加超时 | 做不到：`wifi_send_cmd` 在预编译库里，没有超时参数 |
| 只在串口配（`wifi set` / `gwkv set`） | 可用但不满足「手机浏览器打开页面」的要求；保留为**故障时的退路** |
| 改成 STA 模式跑 HTTP，手机同 LAN 打开 | 首配时**没有家庭 Wi-Fi 凭据**，鸡生蛋问题；只在「Wi-Fi 已配好、只改云凭据」时成立 |

### 14.5 已知限制（必须让用户知道）

- **SoftAP 开着时扫不了 Wi-Fi**：单射频，驱动会拒绝 `Scan()`（`gw_net_scan_list()`
  已有这条提示）。所以页面里的 SSID 一律**手输**，不做扫描下拉。若一定要列热点，
  只能在开窗**之前**扫一次缓存起来（本期未做）。
- **AP 口地址由驱动决定**（CAL-12）：官方 b14 样例是 `192.168.2.1`，用户预期
  `192.168.4.1`。代码不硬写，一律以日志
  `[NET] SoftAP 已启动 ssid=… 地址 http://…/` 那一行为准。
- 配网 HTTP 服务仍然可能在 AP 地址就绪前先绑 `0.0.0.0`（30 s 超时后退化）。
  这不影响手机访问 AP 地址，只是日志里多一行 ⚠。

### 14.7 t143：SSID 下拉（开窗前扫一次，缓存给 `/api/scan`）

**为什么必须"开窗前"扫**：单射频，SoftAP 一开驱动就拒绝 `Scan()`；而配网页面
恰恰只有 AP 开着时才可达。所以列表只能是**开窗那一刻**（还在 STA 模式）扫出来的
快照，之后缓存着给页面用。

**顺序**（都在 `gwAp` 任务里，tick 不参与）：

```
prov on / 长按 3 s
  → gw_net_ap_start() 登记请求
  → gwAp 任务：net_scan_cache_refresh()   ← STA 模式扫一次（失败只打日志，不阻塞）
  → net_sta_off_for_ap()                  ← DisableWifi + 300 ms
  → SetHotspotConfig → EnableHotspot      ← 仍然可能永久阻塞，但只堵这个任务
```

**缓存口径**（`gw_net.c` 的 `s_scan_cache`）：

| 规则 | 值 | 理由 |
|---|---|---|
| 频段 | 只留 2.4 G（`net_freq_to_ch() != 0`） | 5 G 连不上，列出来只会误导 |
| 去重 | 同名取最强 RSSI，信道跟着最强那条 | 一个家常有 2–3 个同名 AP |
| 上限 | 20 条 | 页面下拉不该无限长；响应体也要可控 |
| 隐藏 SSID | 不列 | 用户勾「隐藏网络」手输 |
| 时间戳 | `scanned_at` = 扫描时刻（开机毫秒，与 `gw_now_ms()` 同一算式） | 页面显示"扫描于开机后 N 秒" |

**`GET /api/scan`**（`gw_prov.c:gw_prov_api_wifi_scan_cache`）：

```json
{"code":200,"message":"ok","data":{
  "cached":true,"scanned_at":123456,"age_ms":2345,"count":2,"limit":20,
  "list":[{"ssid":"HOME-2.4G","rssi":-41,"ch":6},{"ssid":"CMCC\"quote","rssi":-67,"ch":11}]},"ts":0}
```

- 缓存为空 → 仍 **200**，`cached:false`、`count:0`、`list:[]`（页面退回手输，不卡人）；
- **不受配网窗口限制**（只读缓存）：窗口外打开页面也能渲染出上次扫到的东西，不会 1600；
- SSID 里的 `"` 与 `\` 一律转义（中文/符号 SSID 很常见，转义漏了整份响应变非法 JSON，页面静默白屏）；
- 方法不对 → 405。

**页面**（`web/index.html`，生成物 `src/gw_h5.h`）：第一步卡片里新增

```
[下拉：选一个，或在下面手输]
若列表里没有你的 Wi-Fi，请在下方手动输入（列表是网关开窗前扫到的那一批 2.4G 热点：扫描于开机后 N 秒）。
[输入框：Wi-Fi 名称（可在上方列表选，也可手输）]
```

选中下拉项 → 自动填进输入框（用户仍可改）。**下拉与手输并列**，缓存为空时下拉只有
一行提示，手输照常可用。

**这是硬件限制，不是缺陷**：手机连着热点时再扫一次是不可能的（单射频）；缓存反映的是
**开窗那一刻**的信号环境，若列表里没有你的 Wi-Fi（比如路由器刚开），手输即可。
