## 2. 分层：为什么状态机不碰 SDK

```
gw_prov_route.c  (URL → 接口)      gw_main.c (板级 ops 注入 + 任务编排)
        │                                   │
        └────────► gw_prov.c ◄──────────────┘
                 (窗口/扫描/绑定/白名单/指示)
                        │  gw_prov_ops_t（函数指针）
        ┌───────────────┴────────────────┐
   gw_net.c + gw_store.c            test/gw_prov_sim.c
   (wifi_lite / Flash)              (假 Wi-Fi / 假汇聚 / 假时钟)
```

理由：配网逻辑是**流程与约束**（窗口 600 s、"先扫后绑 300 s"、8 条上限、`1600`–`1606` 判定），
放在状态机里才能在主机上被穷举测试；Wi-Fi/Flash 是**平台差异**，经 `gw_prov_ops_t` 注入后，
主机上换一套假实现就能把 §12 的每条规则跑一遍（`test/run-prov-sim.sh` 100 用例）。
`gw_prov_ops_t` 必须放在**文件作用域**：`gw_prov_t` 只存指针，指向栈上的 ops 会在函数返回后悬空
（主机模拟器第一版就是这么崩的：ASAN 报 `gw_prov_resync_step` 里 ops 偏移 `0x68` 处 SEGV）。

## 3. 关键实现决定

1. **STA 连接拆成 `sta_start` + `sta_poll`**：一次 30 s 的阻塞连接会把 tick 任务钉住，
   LED 不闪、配对键读不到——配网窗口里这两件事恰恰是用户在等的反馈。
2. **`gw_prov_enter()` 在 `ap_start` 失败时不开窗口**并返回 -1：宁可"长按没反应"，
   也不要开一个打不开的入口（用户会以为手机坏了）。
3. **扫描受理的记账顺序**：`hub_online` 不通过 → 409/1605（不"受理了没人干活"）；
   `scan_id` 先自增 → `scan_state=SCANNING` → **先置 `busy=scan` 再发帧** → 发帧失败回 409/1605 + 清 busy。
   顺序反了会出现"汇聚秒回 0x21 → on_scan_rsp 置 DONE → 又被盖回 SCANNING"（模拟器抓到的真 bug）。
4. **绑定先落盘再发 `0x22`**：契约 §12.9 明确"等 `0x23` 超时也要保留白名单"，
   所以持久化必须在汇聚应答之前。**但汇聚"明确拒绝"（`0x23 result=10/11`）时回滚**——
   留一条汇聚不会接受的记录，只会在每次重建时被再拒一次。
5. **汇聚重建不放在收帧任务里**：`gw_prov_on_hub_frame()` 在"离线→在线"时只置 `resync_wanted=1`，
   真正的 `0x22 op=list` + 逐条 `add` 由 tick 任务分步做（`GW_PROV_RESYNC_WAIT_MS=300 ms` 短等待）。
   在 uart 收帧任务里等 `0x23` 会把收帧任务自己堵死。
6. **`nodes[].bind` 以网关白名单重算**，不信汇聚的 `bind` 字段：汇聚不落盘，它那边的状态可能过期。
7. **`nodes[].role` 按整数存**（§12.8 明确 `1`=节点 `2`=汇聚），不是字符串。
8. **时间戳一律 64 位**：unix 毫秒（`1792243200000`）早超 `uint32` 范围，`scanned_at`/`last_seen`/`ts` 全用 `uint64_t`；
   未校时时 `gw_time_ms()` 返回 0，配网接口就报 0 —— 不编假时间。
9. **口令处理**：STA 口令只在 `gw_prov_t.pend_psk` 存活到连接结束，之后立刻清零；不进日志、不回显；
   落盘前用设备标识派生密钥做 XOR 混淆（`gw_store.c` 注释写明**这只是混淆不是加密**，真正的边界是
   "口令不进日志、不回显、不落仓库"）。AP 口令按 §12.2 允许在串口首行给出（现场要看得到）。
10. **HTTP 一律 `Connection: close` + `Cache-Control: no-store`**，`SO_RCVTIMEO/SNDTIMEO = 5 s`：
    单任务串行处理请求，一个慢客户端不能把配网服务占死。
11. **H5 页面直发常量体**：页面 9219 字节 > 8 KB 响应缓冲，与其把缓冲加到 12 KB（多吃 RAM），
    不如给请求结构加 `literal/literal_len` 直接发常量。
12. **配网期间 LED 让位**：`gw_alarm_tick()` 之后由 `gw_prov_led_level()` 覆盖 LED；
    配网进入/进行中不发声，仅"配网成功"短鸣 ≤300 ms，且尊重 `mute_alarm`（§12.2 可静音）。

## 4. H5 页面（§12.11）

- 真源 `rk2206-gateway/web/index.html`（单文件，CSS/JS 内联，**0 外部 URL**），
  生成 `src/gw_h5.h`：`python3 rk2206-gateway/web/gen-h5-header.py`（`--check` 校验一致性，改完不重跑会被 CI 拦住）。
- 页面只调 §12 五个接口，全部**相对路径**（不写死 AP 地址，见 CAL-12）；
  每请求 3 s 超时（`AbortController`），错误码 `1600`–`1606` 有中文文案表；
  提交口令后立即清空输入框、不落 `localStorage`；DOM 一律 `createElement`/`textContent` 构建。
- 页面**不受窗口限制**（窗口关了也能打开，页面自己显示"不在配网模式"），否则用户看到空白页只会以为坏了。

### 4.1 §12.11 六条约束逐条对照（复核按这张表核）

| # | §12.11 约束 | 落在哪里 | 怎么核（不依赖硬件） |
|---|---|---|---|
| 1 | 单文件 HTML，CSS/JS 内联，不引外部字体/图标 | `web/index.html` 只有一个文件；样式在 `<style>`、脚本在 `<script>`；无 `<link>`/`<img>`/`@import` | `grep -c '<link\|@import\|<img' rk2206-gateway/web/index.html` → 0；`wc -c` → 9219 字节 |
| 2 | 全离线、无 CDN、不引外部资源 | 页面里没有任何 `http://`/`https://` 资源引用（只有一个注释提示"入口是 HTTP 不是 HTTPS"） | `grep -n "src='http\|src=\"http\|href='http\|fetch('http" rk2206-gateway/web/index.html` → 无命中；模拟器 `t_window_and_page`（`test/gw_prov_sim.c:359`）按同一判据断言（"正文里出现 `http://` 字样"不算违规，只有真的去取才算） |
| 3 | 只调 §12 的五个本地接口，不得调 §6 云端 REST | 页面里出现的 URL 只有 `/api/provision/status`、`/api/provision/wifi`、`/api/pair/scan`、`/api/pair/nodes`、`/api/pair/bind` 五个相对路径 | `grep -o '/api/[a-z/]*' rk2206-gateway/web/index.html \| sort -u` → 恰好这 5 条 |
| 4 | 不做账号绑定、不回显/不存口令 | 提交后立即 `input.value=''`；无 `localStorage`/`sessionStorage`/cookie；状态卡只显示 `sta_ssid`（SSID），从不显示口令 | `grep -c 'localStorage\|sessionStorage\|document.cookie' rk2206-gateway/web/index.html` → 0；`curl` 打 `status` 看不到任何口令字段 |
| 5 | 每个请求 3 s 超时 + `1600`–`1606` 中文文案表 | `api()` 里 `AbortController` + `setTimeout(3000)`；`ERR` 表逐条列 `1600 不在配网模式`…`1606 白名单已满` | `grep -o '16[0-6][0-9]' rk2206-gateway/web/index.html \| sort -u` → `1600 1601 1602 1603 1604 1605 1606` 全在；错误码路径由模拟器断言（409/1600、400/1602、409/1603、400/1604、409/1605、409/1606）；JS 语法 `node --check` |
| 6 | 入口是 `http://<AP地址>/`（HTTP 非 HTTPS，同源） | 路由 `GET /` 与 `/index.html` 直接发常量体（`gw_prov_route.c`），HTTP 81/80 端口明文 | 模拟器 `t_http_socket` 真 TCP 回环断言 `HTTP/1.1 200` + `Content-Type: text/html`；页面里所有 API 都是相对路径（同源） |

生成与一致性：页面真源改动后必须 `python3 rk2206-gateway/web/gen-h5-header.py` 重新生成 `src/gw_h5.h`；
`--check` 模式在"真源与头文件不一致"时 exit 1（`tools/gw-build.sh` 的断言里也挂了这个检查），
所以**手工同步头文件这条路被堵住了**。

## 6. 与契约/现实的偏差（需要 PM 与验收知道）

| # | 偏差 | 原因与处置 |
|---|---|---|
| CAL-12 | **AP 地址做不到 §12.3 的 `192.168.4.1/24`（DHCP `100–199`）** | RK2206 的 SoftAP 由预编译库 `libhardware.a` 实现：`WifiConfigAP(ssid, psk, channel)` 只接受这三个参数，地址/DHCP 池由驱动决定（官方 b14 样例实测是 `192.168.2.1`，客户端 `192.168.2.10`）。处置：HTTP 绑"实际 AP 口地址"（取不到时退化绑 `0.0.0.0` 并打警告），H5 用相对路径，串口打印真实地址，**施工单以现场实际地址为准**。建议契约 §12.3 的地址改为"由驱动决定，以串口输出为准"。**地址口径：待上板实测确认——地址由板级驱动决定，占位 `192.168.4.1`**（候选值 `192.168.237.1`/`192.168.2.1`/`192.168.5.1`，详见 `doc/契约偏差清单.md` 第一行）。 |
| CAL-12b | §12.3"最多 1 客户端"**无法硬性限制** | `wifi_lite` 的 `GetStationList()`/`DisassociateSta()` 在本 SDK 里是空壳（返回成功但不填数据/不动作）。处置：HTTP 服务单请求串行，等效于"同时只有 1 个请求在跑"；文档与施工单写明。 |
| CAL-16 | AP 口令是占位值 `echub8888` | 契约要求口令值待用户确认、仓库不写死。处置：`gw_config.h` 的 `GW_PROV_AP_PSK` 可改（施工单一句话说明），SSID 由 SN 后 4 位十六进制派生（`M0-3F1A2B` → `ElderCare-1A2B`）。 |
| §4.3.1 | **`nodes` 明细的 `mac`/`rssi` 未上报** | 明细记录是在采样事件时预渲染成文本的（`gw_main.c` 的 `s_sample_slots`），要加这两个字段得改明细通路的记录格式。处置：本次不上报，白名单以属性 `bound_nodes`（SN 数组）回流云端；缺口已在本表登记。 |
| §4.3 | `bound_nodes`/`pair_state` **只在 60 s 属性报文里带**，没有"状态变化时立即" | `gw_report_props()` 目前是 60 s 节拍。处置：白名单/配网状态的变化最迟 60 s 内可见；若要"立即"，需要在 net_task 里加一个"立刻补报"标志位（本次未做）。 |
| §12.5 | status **没有失败原因字段** | 契约 §12.5 的字段表里没有 `reason`（逐字核过），按 AGENTS.md「契约没覆盖的字段先提问、不自行发明」不加 JSON 字段；失败原因只在串口日志与主机自测里可见（`gw_prov_last_reason()`）。**建议契约加 `last_error`**。 |
| 存储 | 白名单与口令存 **Vendor Flash 明文/混淆** | 用 SDK 原生 vendor 槽（`VENDOR_ID_CUSTOM+0..21`），不与 `0x6FF000`（设备凭证 KV）和 `0x700000`（事件缓存）冲突；代价是不满足 §12.6"写 Flash 前用设备密钥加密"的字面要求——SDK 自身的 `SetWifiModeOn()` 读的也是原始口令，加密会与它不兼容。 |
| §4.5 | `pair_scan` 响应 `paras` 是 `{"result":"accepted","id":…}` | 契约 §4.5 表格里给的是同步结果形状（含 `nodes`），但同节的注解又明确要求异步受理（避免 IoTDA 命令超时）。按注解实现：先回受理，结果随后经 `bound_nodes` 属性回流。 |
| §4.5 | 汇聚明确拒绝时错误码用 `result_code=10/11` | §9.3 的 `8–11` 与 §3.4 `0x23` 的 `result` 数值一致，直接透传；HTTP 侧仍用 `409/1605`（契约只在 §12.9 给了这一个码）。 |

## 7. 遗留

- `set_threshold`（§4.5）**已接入 `on_cmd()`**（t33）：21 键逐条校验 → 落生效值 → 发 `0x11` 等 `0x10` ACK；未知键回 `1`、越界回 `2`、三次重发无 ACK 回 `12`、汇聚拒绝的码原样透传；断言见 `test/gw_selftest.c` 的 `test_set_threshold()`（含与 §3.7 SEQ=5 实测帧逐字节一致的 payload 比对）。
- 凭证写 Flash KV 的命令行工具（省一次重编）属 t34。
- WiFi 账密不在固件里：P0 假设"编译期写死 + 板子已联网"（走 SDK `config_network.h`）；
  §12 的配网接口把 2.4 G SSID/口令写进 Vendor Flash，但**启动时是否改由它联网由 t34/后续任务决定**（当前 `net_task` 仍调 SDK 的 `SetWifiModeOn()`）。
